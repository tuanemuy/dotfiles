# Phase 1: 計画ガイド

spec.md を起点に `/speckit.plan` → 計画レビュー → `/speckit.tasks` → `/speckit.analyze` → tasks レビュー の順で進める。

すべての成果物は `{FEATURE_DIR}` 配下、レビュー履歴は `{FEATURE_DIR}/review/` 配下に保存する。

## Step 1: `/speckit.plan` の実行

spec-kit のスラッシュコマンドを呼んで計画を生成する。

```
/speckit.plan
```

このコマンドは以下を生成・更新する:

- `{FEATURE_DIR}/plan.md` — 技術計画（Technical Context, Constitution Check, Project Structure, Complexity Tracking）
- `{FEATURE_DIR}/research.md` — 技術選定の根拠
- `{FEATURE_DIR}/data-model.md` — エンティティ・リレーション・制約
- `{FEATURE_DIR}/contracts/` — API/イベント契約

### 結果の検収

`/speckit.plan` が完了したら以下を確認する:

1. 生成された各ファイルを実際に読み、内容が空でないことを確認する
2. `plan.md` の **Constitution Check**（Phase 0 / Phase 1 の両方）が PASS かを確認する
3. **FAIL** がある場合は、`plan.md` の Complexity Tracking セクションに正当化が記載されているかを確認する
4. 記載がない FAIL があれば、再実行か手動修正が必要になる旨をユーザーに報告し、判断を仰ぐ
5. `contracts/` が空で、かつ spec.md の機能要件に API/イベントが含まれている場合は plan の品質に問題がある可能性が高い。レビューループで指摘するか、再生成する

`/speckit.plan` が失敗・タイムアウトした場合は、ユーザーに通知してから手動再実行を試みる。3 回連続失敗すれば本スキルを中断する（spec-kit 環境の問題の可能性）。

## Step 2: 計画レビューループ（最大3周）

`plan.md` が完成したら、**2 つのサブエージェントを並列に起動してレビュー → 反映** を最大 3 周繰り返す（委譲方式は `../../_shared/references/subagent-policy.md` に従う）。

レビュー観点は「要件カバレッジ」と「アーキテクチャ整合性・リスク」の 2 つに絞る。Phase 3 の PR レビューでレイヤー別の多角レビューが入る前提で、計画段階は要件と実現可能性の確認に振り切る。

### 終了条件

以下のいずれか先に到達したら終了:

- **両レビュアーが「問題点ゼロ」を報告** — 計画が両視点で問題なしと判断された
- **3 周完了** — 残課題があれば `plan.md` 末尾の「未解決事項」セクションに明記して終了する

### 各周の流れ

1. 2 エージェント並列でレビュー実施
2. 両方の結果を統合（同じ問題を指摘していたら 1 件にまとめる）
3. 問題点（要修正）を `plan.md` に反映、改善提案はスコープ内で妥当なもののみ取り込む
4. 重要な設計判断が生じたら `{FEATURE_DIR}/adr.md` に追記する
5. レビューファイルを `{FEATURE_DIR}/review/plan-review-{NNN}.md` として新規作成する（NNN は 001 から開始）
6. `plan.md` 末尾の「レビュー履歴」セクションに反映内容を追記する
7. 両レビュアーとも問題点ゼロなら終了、未解決の問題が残れば次の周に進む

いずれかのレビュアーが失敗・タイムアウトした場合は、成功した結果だけで進める。両方失敗した周はスキップして次の周に進む（連続 2 周失敗ならレビューループを打ち切り、未解決事項として記録）。

### 共通テンプレート

各エージェントには以下のテンプレートを渡す（**視点**の部分だけ差し替える）:

```
あなたは spec-kit で生成された実装計画をレビューするエンジニアです。
あなたの視点: **{視点}**

## レビュー対象
- フィーチャー: {FEATURE_DIR}
- spec.md: {FEATURE_DIR}/spec.md
- plan.md: {FEATURE_DIR}/plan.md
- 関連: {FEATURE_DIR}/research.md, data-model.md, contracts/, .specify/memory/constitution.md
- 既存設計判断: {FEATURE_DIR}/adr.md（存在する場合）

## やること
1. まずプロジェクトルートの CLAUDE.md を読む
2. {FEATURE_DIR}/spec.md を読み、機能要件（FR-xxx）・成功基準（SC-xxx）・ユーザーストーリー・前提条件を把握する
3. {FEATURE_DIR}/plan.md を読む。Technical Context・Constitution Check・Project Structure・Complexity Tracking すべてに目を通す
4. research.md, data-model.md, contracts/ も読み、plan.md が一貫しているか確認する
5. .specify/memory/constitution.md を読み、原則との整合性を確認する
6. 既存コードのうち計画と関連する箇所を調査する
7. 上記の視点で計画を厳しくレビューする

## 重要な原則
- **spec.md の要件を満たすかどうかが最重要** — スコープ外の提案はしない
- spec.md のユーザーストーリー・FR・SC をすべて検証する。1 つでもカバーされていなければ Blocker
- 具体的で実行可能なフィードバックを出す。「もっと丁寧に」のような曖昧な指摘は禁止
- 良い点も明確に伝える
- 問題点が見当たらない場合は「問題点ゼロ」と明示する（無理に粗探しをしない）

## 出力フォーマット

#### 問題点（要修正）
- **[P-001]** {問題の説明}
  - 関連: {spec.md の FR-xxx / SC-xxx / ユーザーストーリー、または plan.md の該当セクション}
  - 理由: {なぜ問題か}
  - 提案: {どう修正すべきか}

（問題点がなければ「問題点ゼロ」と明記）

#### 改善提案（検討推奨）
- **[S-001]** {提案の説明}
  - 理由: {なぜ改善になるか}

#### 良い点
- {計画の優れている点}
```

### 視点 1: 要件カバレッジ・スコープ整合性

```
**spec.md の要件カバレッジ・スコープ整合性** を重視してレビューしてください。
spec.md のユーザーストーリー（P1/P2…）、機能要件（FR-xxx）、成功基準（SC-xxx）、
エッジケース、前提条件のそれぞれが plan.md / data-model.md / contracts/ のいずれかで
扱われているかを 1 件ずつ突き合わせて確認してください。
スコープ外の作業が紛れ込んでいないか、`[NEEDS CLARIFICATION]` の残存有無、
ユーザーストーリーの独立テスト可能性が plan に反映されているかを徹底的に確認してください。
```

### 視点 2: アーキテクチャ整合性・Constitution・リスク

```
**Constitution との整合性・実現可能性・リスク** を重視してレビューしてください。
.specify/memory/constitution.md を読み、原則に対する違反がないか、
plan.md の Constitution Check が形式的でなく実質的に PASS しているかを確認してください。
Complexity Tracking に書かれた正当化が妥当か、よりシンプルな代替がないかも検証してください。
加えて、Technical Context（言語・依存・ストレージ・性能目標）が現実的か、
data-model.md と contracts/ の整合性、見落とされた依存関係・副作用・エッジケース、
設計判断のトレードオフが適切かを徹底的に確認してください。
既存コードに合わせるだけで Constitution から外れていないか、
逆に spec の範囲を超えて理想形を追求しすぎていないかを両方向で見てください。
```

`{FEATURE_DIR}/review/plan-review-{NNN}.md`:

```markdown
# Plan Review #{NNN}

**Feature:** {NNN-feature-name}
**Date:** {日付}
**Round:** {N}周目

---

## Summary

- 視点1（要件カバレッジ）: 問題点 {数} / 改善提案 {数}
- 視点2（アーキ・リスク）: 問題点 {数} / 改善提案 {数}
- Verdict: **BLOCKED** / **APPROVED**

---

## 視点1: 要件カバレッジ・スコープ整合性

{視点1の結果}

## 視点2: アーキテクチャ整合性・Constitution・リスク

{視点2の結果}

---

## 反映方針

- 取り込む: {P-xxx, S-xxx の一覧と取り込み方}
- 見送る: {S-xxx と見送り理由}
```

### plan.md への反映

問題点と取り込む改善提案を `plan.md` の該当セクションに反映する。直接編集してよい（spec-kit のテンプレートは Markdown なので安全）。

末尾の「レビュー履歴」セクションを追記:

```markdown
## レビュー履歴

### 1周目（{日付}）
**修正した点**:
- {P-001 への対応: 何をどう修正したか}

**取り込んだ改善提案**:
- {S-001: 何を取り込んだか}

**見送った提案とその理由**:
- {S-002: スコープ外、等}

### 2周目（実施した場合）
...
```

レビュアーが「問題点ゼロ」を返した周も「{N}周目: 両視点とも問題点ゼロで終了」と記録する。

### 未解決事項セクション（3周完了しても残った場合のみ）

```markdown
## 未解決事項

- **[P-XXX]** {未解決の問題}
  - 経緯: {なぜ3周で解消できなかったか}
  - 引き継ぎ: {実装フェーズでどう扱うべきか}
```

## Step 3: `/speckit.tasks` の実行

`plan.md` のレビューが完了したら、タスクを生成する。

```
/speckit.tasks
```

このコマンドは `{FEATURE_DIR}/tasks.md` を生成する（5 フェーズ構成: Setup → Foundational → User Stories → Polish → Dependencies、`[P]` 並列マーカーと `[USx]` ストーリー紐付け付き）。

### 結果の検収

1. `tasks.md` が生成され、空でないことを確認する
2. spec.md のユーザーストーリー（P1, P2, ...）の各 ID が `[USx]` でタスクに紐付いていることを確認する
3. テスト系タスク（契約テスト・統合テスト・E2E）が実装タスクより前に置かれているかを確認する（TDD 順序）
4. `depends on Txxx` 形式の依存表現が破綻していないかを目視確認する

## Step 4: `/speckit.analyze` の実行

spec ↔ plan ↔ tasks の一貫性を検証する。

```
/speckit.analyze
```

### 結果の取り扱い

- analyze が **PASS** なら次のステップへ
- **指摘あり**の場合:
  - 軽微な整合性ズレ → plan.md / tasks.md を直接修正する
  - 根本的な齟齬（spec と plan の食い違い等） → `plan.md` を修正し、必要なら `/speckit.tasks` を再実行する
  - 修正後、analyze を再実行して PASS を確認する
- 3 回再実行しても PASS しない場合は、未解決事項として記録し、ユーザーに判断を仰ぐ

## Step 5: タスクレビュー（1周）

`tasks.md` に対し、サブエージェント 1 つで以下の観点をまとめてレビューする。計画レビューほど厳しくは回さない（既に analyze で機械的整合性は検証済みのため、人間視点の合理性チェックに絞る）。

### レビュー観点

- **依存関係の妥当性** — `depends on Txxx` が現実的に成立する順序か
- **並列性** — `[P]` マーカーが付いているタスクが本当に並列実行可能か（同じファイルを編集していないか）
- **テスト先行性** — 契約テスト/統合テスト/E2E が対応する実装タスクより前にあるか
- **ストーリー独立性** — 各ユーザーストーリー（US1, US2, ...）が独立にデリバリ可能になっているか
- **欠落** — spec.md のユーザーストーリー・FR・受け入れ基準がいずれかのタスクでカバーされているか

### サブエージェントに渡すプロンプト

```
あなたは spec-kit の tasks.md をレビューするエンジニアです。

## レビュー対象
- フィーチャー: {FEATURE_DIR}
- spec.md: {FEATURE_DIR}/spec.md
- plan.md: {FEATURE_DIR}/plan.md
- tasks.md: {FEATURE_DIR}/tasks.md

## やること
1. プロジェクトルートの CLAUDE.md を読む
2. spec.md のユーザーストーリー・FR・SC、plan.md の Technical Context・Project Structure、tasks.md の全タスクを読む
3. 上記レビュー観点で tasks.md をレビューする

## レビュー観点
- 依存関係の妥当性（depends on Txxx が成立するか）
- 並列性（[P] が付いているタスクは本当に独立か。同じファイルを触っていないか）
- テスト先行性（契約/統合/E2E テストが実装より前か）
- ストーリー独立性（US1, US2... が独立にデリバリ可能か）
- 欠落（spec.md の FR-xxx/SC-xxx/エッジケースのいずれかがカバーされていないタスクはあるか）

## 出力フォーマット

#### Blockers
- **[B-001]** {問題}
  - 場所: tasks.md の {タスク ID または行}
  - 理由: {なぜ問題か}
  - 提案: {どう直すか}

#### Warnings
- **[W-001]** {問題}
  - 場所: {タスク ID}
  - 理由: {なぜ気になるか}
  - 提案: {改善案}

#### Notes
- **[N-001]** {良い点や参考情報}

Blocker がなければ Blockers セクションに「なし」と書く。
```

### 修正の反映

- Blocker は全件修正する（`tasks.md` を直接編集 or `/speckit.tasks` 再実行 + 必要なら `/speckit.analyze` 再実行）
- Warning も原則修正する。修正コストが極端に大きい場合のみ「未解決事項」に回す
- 修正後、`{FEATURE_DIR}/review/tasks-review-001.md` としてレビューファイルを保存する

タスクレビューは原則 1 周で完了する（Phase 3 の PR レビューで実装後にもう一度多角的に見るため）。

## Step 6: Phase 1 完了報告

Phase 1 が完了したら、Phase 2 に進む前に以下をユーザーに報告する（自動で Phase 2 に進んでよい）:

```
Phase 1（計画）が完了しました。

- 計画レビュー: {N}周（終了理由: {問題点ゼロ / 最大ラウンド到達}）
- analyze: {PASS / 再実行N回後 PASS / 未解決}
- タスク数: {数}（うち並列可能 [P]: {数}）
- ユーザーストーリー: {US1, US2, ...}
- 未解決事項: {数}件
```

未解決事項が Blocker 級の場合はユーザー判断を仰ぐ。それ以外は Phase 2 に進む。

## 重要な注意点

- 委譲方式・並列実行・失敗時の扱いは `../../_shared/references/subagent-policy.md` に従う
- spec-kit のスラッシュコマンドが利用できない環境では本スキルは保留する。自前で plan.md を書き起こさない（spec-kit のテンプレート整合性が崩れるため）
- レビューでは spec.md を一次資料として参照する。plan.md だけ見て判断しない
- ADR は本当に重要な設計判断のみ。些細な実装詳細は ADR にしない
