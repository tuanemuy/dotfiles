Markdownドキュメントを、読み手が構造を把握しやすい状態に整える。

重要なのは構造であり、装飾は意味を持たない。記法ごとに、構造を表しているか、見た目を飾っているだけかを問い、飾りなら削る。

## ルール

### 見出し

- h1（`#`）は文書のタイトルにだけ使い、1ドキュメントに1つだけ置く
- タイトルを本文の外に持つ文書（Issue・PR、frontmatter付きの記事など）にはh1を置かず、`##`から始める
- レベルを飛ばさない
- 強調（`**太字**`）を見出しの代わりに使わない

### 強調・装飾

- 区切り線（`---`や`***`）を入れない。セクションの区切りは見出しが担う
- 絵文字や記号を装飾に使わない
- 鍵括弧は文言の引用にだけ使う
- 強調（`**太字**`・`*斜体*`）は際立たせたい語にだけ使う

### 空行とマーカーの統一

- 見出し・リスト・コードブロック・テーブルの前後には空行を入れる
- 箇条書きのマーカーは`-`に統一する
- 行末に余分な空白を残さない
- 番号付きリストは順序に意味があるとき（手順など）だけ使う

### 改行と段落

- 段落やリスト項目の中で改行しない
- 明示的な改行が必要な場合は、行末の半角スペースではなくリストやテーブルで構造化する

### コードとリンク

- コードブロックには言語を指定する（` ```bash `, ` ```ts `など）
- コマンド・ファイル名・識別子など、本文に登場するコード片はインラインコード（`` `getUser()` ``）で囲む
- リンクテキストはリンク先の内容を表す

### 文章

- 見出しを読めば分かる前置きやまとめ（「以下では〜について説明します」「以上が〜でした」）を書かない
- 文の単位では[明快な文](../_shared/references/clear-writing.md)に従う
- 日本語と英単語の間の空白は既存の文書に合わせ、新規なら入れない
- リスト項目の末尾の句点は既存の文書に合わせ、新規なら付けない。項目の中の文の区切りには付ける

## 整形の進め方

次の順で、各節のルールに照らして見る。

1. 対象を決める。引数`target`があればそれ、なければgit diffの変更分や会話中で扱っているMarkdownを対象にする
2. 見出しの構造を確かめる
3. 装飾を削る
4. 空行・マーカー・コード・リンクの記法を整える
5. 段落内の改行をつなげる
6. 文章を削る

意味を変えない。内容の追加や書き換えが要るなら、ユーザーに確認する。
