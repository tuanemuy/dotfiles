# Issue Triage

追加の業務判断なしに、変更と検証を終えてレビュー可能な PR を出せるかを判定する。Ready は実装への着手可能を意味し、変更の完成や同時実行可能を意味しない。

## 対象と根拠

指定がなければ全オープン Issue が対象。番号やラベルで範囲を指定できる。bug に限定せず、改善・テスト・文書・リファクタリングも含める。ページネーションして全件を取得し、取得上限で対象を切らない。

本文・最新コメント・関連 PR の状態と、判断に必要な spec・コードを読む。古い報告より新しい合意と現行の根拠を優先するが、単なる提案を合意に読み替えない。本文に Ready とあるだけでは認定しない。未取得のコメントや PR の状態は未確認として残す。

原因を突き止めるための再現実験や広範なコード追跡が必要なら、問いと必要な証拠を定めて調査へ渡す。トリアージ中に実装・調査のループへ入らない。

## 判定

Ready は以下をすべて満たすもの。

- 期待する振る舞いと、検証可能な完了条件が分かる。
- 業務ルール・権限・利用者の操作を左右する未決定事項がない。既存規約の範囲での実装方法、部品選択、余白などはエージェントが決められる。
- 1 本のレビュー可能な PR として目的がまとまっている。ファイル数やバグ以外の種別を理由に除外しない。
- 完了を確かめる方法と必要な環境を利用できる。環境の利用可否が未確認なら、その確認を調査へ渡す。
- 他者の回答や未完了の先行変更を待たずに PR を完成できる。

原因未特定だけでは除外しない。期待結果・観測手段が明確で、通常の修正作業内で調査できるなら Ready。不具合が実在するか、どの経路で起きるか自体が不明なら調査必要とする。

スキーマやマイグレーションも、変更案と必要な検証を PR で完結できれば対象。本番適用・データ補正は別工程として扱う。ただし、未決定の移行方針や利用できない環境がコードの正しさを左右するなら切り離したことにしない。

| 判定 | ラベル | Issue に残す内容 |
| --- | --- | --- |
| Ready | `ready` | 方針、範囲、完了条件、検証方法 |
| 一部 Ready | `triage:partial` | 独立して完了できる作業と残りの依存。子 Issue に分け、子だけを Ready にする |
| 調査必要 | `triage:investigate` | 調べる問い、必要な証拠、調査の終了条件 |
| 確認待ち | `triage:blocked` | 未決定事項、回答者または依存先、再開条件 |
| 管理用 | `triage:tracking` | ダッシュボード・親 Issue などの追跡先。実装キューには入れない |
| 対応済み・不要 | Close | 完了の根拠、不要の理由、重複なら統合先 |

一部 Ready の分割は既存の子 Issue を探してから行い、同じ子を重ねて作らない。修正 PR がオープンなだけでは対応済みとして Close しない。再現しなかっただけでも Close しない。

## 反映

トリアージの実行依頼では、対象 Issue の本文・ラベルの整理、必要な子 Issue の作成、根拠のある Close まで行う。相談・評価だけの依頼では判定を返し、GitHub を更新しない。

本文の古い事実や方針を訂正し、根拠リンク・未確認事項・完了条件を残す。ユーザーの報告や必要な証跡を失わない。ラベルは上表の判定ラベルを排他的に管理し、他のラベルや担当者を維持する。必要なラベルだけ作成する。変更前に最新の本文・コメント・状態を再取得し、途中の更新を上書きしない。変更のない再実行では同じコメントを追加しない。

担当者、実行中ラベル、オープン PR がある Issue は進行中として扱う。既存作業を取り消したり二重着手したりしない。`ship:needs-human` は停止理由を確認し、再開条件の充足または明示的な再試行指示がない限り維持する。

## 実行キュー

キュー作成を指定された場合だけ、Ready のうち今回実行できる Issue に `ship:auto` を付ける。判定だけの実行では新たにキューへ入れない。ただし Ready でなくなった Issue の古い `ship:auto` は外す。

- キュー作成時は対象範囲外も含め、既存キュー、実行中の Issue、オープン PR を確認する。担当者・実行中・未解消の `ship:needs-human`・オープン PR がある Issue を新たにキューへ入れない。
- ファイルの重複は Ready を取り消す理由にしない。編集箇所や契約が競合する組だけ順番を付け、今のキューと両立するものを追加する。大きなファイルを共有するだけで一律に競合としない。
- 実行待ちには競合先と再開条件を本文に残す。先行 PR の取り込みが必要なら「エージェント終了」ではなく「PR のマージ」が再開条件。
- 既存キューも再点検し、競合が見つかった未着手分は Ready のまま待機させる。担当者や実行中ラベルを外してキューに戻さない。

件数上限は設けない。優先度・依存・競合に基づく今回のキューと、着手可能な全体を区別して報告する。

## 完了報告

対象件数と各判定の件数、変更・Close した Issue、キューに追加した Issue、Ready だが待機する Issue とその理由を示す。未確認を「迷うため」とまとめず、解消すべき問いとして残す。取得や更新が失敗した Issue は未処理として明記する。
