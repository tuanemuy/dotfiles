# 進捗管理と委譲

## 作業ファイルと所有者

Manager は `.goal-implement/` 直下と各実行ディレクトリの `brief.md`・`plan.md` を読み、元の依頼の参照先、対象範囲、完成条件を今回の指示と照合する。同じ依頼の継続・修正なら、そのディレクトリを再利用する。記録がなければ `.goal-implement/`、別依頼の記録だけがあれば未使用の `.goal-implement/{run-id}/` を使う。別依頼の記録は保持する。

確定した場所を `{run-directory}` とし、元の依頼の参照先とともに `plan.md` に記録する。以下の作業ファイルはすべてその配下に置く。委譲文、goal、最終報告には確定したパスを渡す。Manager が全体の管理ファイルを更新し、Implementer はフェーズごとの報告を更新する。

| ファイル | 内容 | 更新者 |
| --- | --- | --- |
| `brief.md` | 元の要求、対象範囲、制約、仮定、未決事項 | Manager |
| `design.md` | 現在採用する全体設計と共有契約 | Manager |
| `plan.md` | 全体目標、フェーズ、項目の状態と受け入れ根拠、依存関係、現在地、停滞の目安、再開条件 | Manager |
| `phases/{id}.md` | 現在の作業、実装結果、検証結果、障害、引き継ぎ | 担当 Implementer |

既存の設計資料があれば参照し、同じ本文を複製しない。設計の詳細が増えたら `design.md` から必要なファイルへリンクする。要件の原文は参照できる状態に保つ。

## 完了台帳

`plan.md` を計画・項目状態・受け入れの正本にする。初回委譲前に、各項目を短い表かリストで記録する。

- 固定 ID、対応する要件 ID と原文の参照先。基盤作業も支える要件に結び付ける。
- 担当フェーズ、依存する項目 ID、観測できる完了条件、検証方法と期待値。
- 現在の状態、フェーズ報告の根拠へのリンク、障害と解消条件。

Manager だけが項目状態を更新する。通常の遷移は `pending → in_progress → review → done` とする。Implementer の完了候補を受け取ったら `review`、Manager が受け入れたら `done` にする。差し戻しは `in_progress`、前提が崩れた項目は `pending` に戻す。`blocked` からは障害の解消後に再開する。項目の `blocked` は goal API の状態とは別に管理する。

受け入れ・差し戻し・再オープン・範囲変更には、実時刻、対象 ID、理由を短く残す。元の検証根拠は保持する。ユーザーが範囲を変更した場合は、変更元と対象外になった ID を記録する。未完了項目を進捗率のために削除しない。

進捗は `plan.md` に現在のフェーズ、`done` 数 / 対象数、`review` 数、障害、次の一手、更新日時を短く記す。受け入れ前の項目は完了数に含めない。進捗専用の JSON・HTML・グラフは生成しない。

## 検証根拠

Implementer はフェーズ報告に、項目 ID、変更ファイル、検証コマンドや操作、期待値と結果、実行日時を記録する。成功・失敗・未実行を区別する。日時はタイムゾーン付き ISO 8601 形式にする。

根拠には検証対象のコミット ID を付ける。未コミット変更がある場合は、追跡外を含む対象ファイルのハッシュ一覧など、検証時の内容を識別できる記録も残す。Git や初回コミットがない場合は対象ファイルのハッシュなどで識別する。同じ状態の検証は一つの記録を参照し、長いログは必要な箇所へのリンクで示す。

Manager は検証対象と受け入れ対象のコード・設定・実行環境を照合する。根拠が現在の状態に適用できない項目は、依存関係を通じた影響も確認して再オープンし、再検証する。

## フェーズの定義

各フェーズに目的、対象 ID、依存フェーズ、変更範囲、完了条件を付ける。委譲時には現在のフェーズで必要な設計と検証環境を確定する。後続フェーズの詳細な処理手順は、依存先が完成してから決める。

最後に統合検証を置く。全要件に対応する作業項目があり、主要シナリオが端から端まで検証されることを確認する。実装項目の完了だけで統合検証を省略しない。

## 委譲文

```text
Complete phase {id} completely, extremely well.

全体の目的: {利用者が達成する結果}
作業場所: {ディレクトリ・ブランチ・共有範囲}
全体計画: {run-directory}/plan.md
入力と設計: {brief.md、design.md の該当箇所と必要なコード}
対象項目: {ID と完了条件}
変更範囲: {担当する機能・ファイル、他担当との境界}
実行上の制約: {SKILL.md のスキル呼び出し制約と、現在のフェーズに適用する制約}
検証環境: {起動方法、利用可能なサービス、検証コマンド}
報告先: {run-directory}/phases/{id}.md
goal: {独立したフェーズ goal を設定する指示、または委譲文で目標を管理する旨}

現在のフェーズを詳細化し、実装・接続・検証まで完了してください。
完了候補は項目 ID ごとに変更内容と検証根拠を報告してください。
検証根拠には実行日時と、コミット ID・未コミット変更を含む検証対象の識別情報を付けてください。
共有契約に変更が必要な場合は、影響と提案を Manager に報告してください。
停滞時は試した方法、得た根拠、障害、次の一手を報告してください。
全体の管理ファイルは Manager が更新します。次フェーズの開始は Manager に返してください。
```

全体計画は参照可能にし、現在のフェーズに不要な過去の議論や実行ログを委譲文へ詰め込まない。実行環境が分かれる場合は、成果をブランチやパッチで受け渡し、統合後に検証する。

## 受け入れと再開

Manager は報告の各項目を元の要求、対象コード、検証結果と照合する。証拠が不足する項目だけを再検証し、受け入れ済みで変更のない検証を繰り返さない。差し戻しには項目 ID、満たしていない条件、観測結果を付ける。

再開時は goal の状態、`plan.md`、最後のフェーズ報告を読み、コードの変更を確認する。記録された検証が現在のコードに適用できるかを判断し、影響を受ける項目を再オープンする。進捗記録だけで完成を判断しない。

外部依存で停止する場合は、残項目、試した代替策、再開に必要な入力・権限・環境、次に行う操作を `plan.md` に残す。完了と停止のどちらでも作業ファイルを保持する。

既存の `checklist.json` がある場合は、Manager が受け入れ結果と検証根拠を照合し、固定 ID と必要な履歴を `plan.md` に取り込む。受け入れが確認できない完了候補は `review` とする。元の記録は保持し、以後の状態更新は `plan.md` に集約する。
