# 進捗管理と委譲

## 作業ファイルと所有者

Manager は `.goal-implement/` 直下と各実行ディレクトリの `brief.md`・`plan.md` を読み、元の依頼の参照先、対象範囲、完成条件を今回の指示と照合する。同じ依頼の継続・修正なら、そのディレクトリを再利用する。記録がなければ `.goal-implement/`、別依頼の記録だけがあれば未使用の `.goal-implement/{run-id}/` を使う。別依頼の記録は保持する。

確定した場所を `{run-directory}` とし、元の依頼の参照先とともに `plan.md` に記録する。以下の作業ファイルはすべてその配下に置く。委譲文、goal、最終報告には確定したパスを渡す。Manager が全体の管理ファイルを更新し、Implementer と Verifier は担当の報告を更新する。

| ファイル | 内容 | 更新者 |
| --- | --- | --- |
| `brief.md` | 元の要求、対象範囲、制約、外部依存と検証段階、仮定、未決事項 | Manager |
| `design.md` | 現在採用する全体設計と共有契約 | Manager |
| `plan.md` | 全体目標、フェーズ、項目の状態と受け入れ根拠、依存関係、現在地、停滞の目安、再開条件 | Manager |
| `status.json` | `plan.md` の項目状態の機械可読な写し | Manager |
| `phases/{id}.md` | 現在の作業、実装結果、検証結果、障害、引き継ぎ | 担当 Implementer |
| `reviews/{id}.md` | 項目ごとの合否、検証対象、根拠、未検証事項、追加観察、再検証結果 | 担当 Verifier |

既存の設計資料があれば参照し、同じ本文を複製しない。設計の詳細が増えたら `design.md` から必要なファイルへリンクする。要件の原文は参照できる状態に保つ。

## 完了台帳

`plan.md` を計画・項目状態・受け入れの正本にする。初回委譲前に、各項目を短い表かリストで記録する。

- 固定 ID、対応する要件 ID と原文の参照先。基盤作業も支える要件に結び付ける。
- 担当フェーズ、依存する項目 ID、観測できる完了条件、検証方法と期待値。
- 現在の状態、フェーズ報告の根拠へのリンク、障害と解消条件。

Manager だけが項目状態を更新する。通常の遷移は `pending → in_progress → review → done` とする。Implementer の完了候補を受け取ったら `review`、Verifier の合格報告と根拠に基づき Manager が受け入れたら `done` にする。差し戻しは `in_progress`、前提が崩れた項目は `pending` に戻す。`blocked` からは障害の解消後に再開する。項目の `blocked` は goal API の状態とは別に管理する。

受け入れ・差し戻し・再オープン・範囲変更には、実時刻、対象 ID、理由を短く残す。元の検証根拠は保持する。ユーザーが範囲を変更した場合は、変更元と対象外になった ID を記録する。未完了項目を進捗率のために削除しない。停滞で次の項目へ進むときも、満たしていない条件は項目に残したまま状態を変えない。

進捗は `plan.md` に現在のフェーズ、`done` 数 / 対象数、`review` 数、障害、次の一手、更新日時を短く記す。受け入れ前の項目は完了数に含めない。進捗管理用の別形式の成果物は作らない。

### status.json

`plan.md` の項目状態を更新するたびに、同じ内容を `status.json` に書く。外側のループや終了時の hook はこのファイルだけを読む。

```json
{
  "updatedAt": "2026-01-01T00:00:00+09:00",
  "items": { "R01": "done", "R02": "review", "R03": "pending" },
  "done": 1,
  "total": 3,
  "lastDoneAt": "2026-01-01T00:00:00+09:00",
  "terminal": null
}
```

`terminal` は `null`、`"done"`、`"done-pending-external"`、`"blocked"` のいずれかとする。`null` はループ継続中を表す。`"done"` は全項目の受け入れ、`"done-pending-external"` は完了 (実接続待ち)、`"blocked"` は代替手段のない停止を表す。`lastDoneAt` は最後に `done` が増えた実時刻で、停滞の判断に使う。

## 検証根拠

Implementer と Verifier は各自の報告に、項目 ID、対象ファイル、検証コマンドや操作、期待値と結果、実行日時を記録する。成功・失敗・未実行を区別する。日時はタイムゾーン付き ISO 8601 形式にする。

完了候補ごとにコミットし、根拠には検証対象のコミット ID を付ける。Git を使えない場合は対象ファイルのハッシュで識別する。同じ状態の検証は一つの記録を参照し、長いログは必要な箇所へのリンクで示す。

Verifier は検証対象と受け入れ対象のコード・設定・実行環境を照合する。根拠が現在の状態に適用できない項目と、依存関係を通じた影響を報告する。Manager は完了条件に影響する項目だけを再オープンし、Verifier に再検証を依頼する。

各報告の先頭に対象項目の結果、根拠の参照先、Manager の判断が必要な事項をまとめる。Manager への通知もこの要約に絞り、詳細な証跡は参照先に残す。

Verifier は項目 ID ごとの合格・不合格・未検証を明記する。Implementer の検証結果を利用した範囲と、自らレビュー・操作・再実行した範囲を区別する。完了条件に含まれない発見は追加観察として分けて記録する。

## フェーズの定義

各フェーズに目的、対象 ID、依存フェーズ、変更範囲、完了条件を付ける。委譲時には現在のフェーズで必要な設計と検証環境を確定する。後続フェーズの詳細は、依存先が完成してから決める。

最後に統合検証を置く。全要件に対応する作業項目があり、主要シナリオが端から端まで検証されることを確認する。実装項目の完了だけで統合検証を省略しない。

## 委譲文

### 実装

```text
Complete phase {id} completely, extremely well.

全体の目的: {利用者が達成する結果}
作業場所: {ディレクトリ・ブランチ・共有範囲}
全体計画: {run-directory}/plan.md
入力と設計: {brief.md、design.md の該当箇所と必要なコード}
対象項目: {ID と完了条件}
検証段階: {外部依存ごとの実接続 / 契約検証 / 対象外}
変更範囲: {担当する機能・ファイル、他担当との境界}
実行上の制約: {SKILL.md のスキル呼び出し制約と、現在のフェーズに適用する制約}
検証環境: {利用方法と検証手順}
報告先: {run-directory}/phases/{id}.md
goal: {独立したフェーズ goal を設定する指示、または委譲文で目標を管理する旨}

現在のフェーズを詳細化し、実装・接続・検証まで完了してください。
完了候補は項目 ID ごとに変更内容と検証根拠を報告してください。
完了候補ごとにコミットし、検証根拠には実行日時とコミット ID を付けてください。
完了条件に含まれない観察は追加観察として分けて報告してください。
共有契約、レイヤー境界、ポートの形に触れる変更は、実装前に影響と提案を Manager に報告してください。
{停滞の目安}を超えて完了項目が増えなければ、試した方法、得た根拠、障害、次の一手を報告し、次の項目へ進んでください。
完了候補・障害・判断依頼は報告ファイルに記録し、Manager に通知してください。
検証への引き継ぎ時は、補助エージェントを含めて対象コードの変更を止めてください。
全体の管理ファイルは Manager が更新します。次フェーズの開始は Manager に返してください。
```

全体計画は参照可能にし、現在のフェーズに不要な過去の議論や実行ログを委譲文へ詰め込まない。実行環境が分かれる場合は、成果をブランチやパッチで受け渡し、統合後に検証する。

### 検証

```text
フェーズ {id} のコードレビューと動作検証を担当してください。

作業場所: {ディレクトリ・ブランチ・共有範囲}
元の要件と設計: {brief.md、design.md と原文の参照先}
対象項目: {plan.md の ID と完了条件}
規約: {プロジェクトのアーキテクチャ・設計規約の参照先}
実装報告: {run-directory}/phases/{id}.md
検証対象: {コミット ID}
検証環境: {利用方法、検証手順、引き継ぎ状態}
実行上の制約: {SKILL.md のスキル呼び出し制約と、現在のフェーズに適用する制約}
報告先: {run-directory}/reviews/{id}.md

元の要件、完了条件、規約を基準にコードと動作を確認してください。
主要シナリオを実際の実行環境で検証してください。Web アプリではブラウザを使ってください。
既存の検証根拠が現在の対象に適用できるか確認し、不足する検証を実行してください。
受け入れ条件は対象項目に記載のものに限ります。条件外の発見は追加観察として分け、条件への追加が必要なら対応する要件を添えて提案してください。
受け入れ済み項目への影響は、その完了条件に影響するかどうかを根拠付きで報告してください。
実装コードと全体の管理ファイルは変更せず、不具合は項目 ID、再現手順、期待値と実際の結果を報告してください。
合格・不合格・未検証と根拠の参照先を項目 ID ごとにまとめてください。
完了・障害・判断依頼を Manager に通知し、検証環境の引き継ぎ状態を伝えてください。
```

## 受け入れと再開

Manager は Verifier の報告に全対象項目の合否と根拠があり、元の要求と完了条件を満たすか判断する。不合格項目は Implementer に差し戻し、根拠が不足する項目は Verifier に追加確認を依頼する。差し戻しには項目 ID、満たしていない条件、観測結果を付ける。修正後は Verifier が変更と依存先への影響を確認し、必要な範囲を再検証する。受け入れ済みで変更のない検証は繰り返さない。

再開時は Manager が goal の状態、`plan.md`、最後の実装・検証報告を読む。Verifier がコードの変更と検証根拠の適用範囲を確認し、Manager は完了条件に影響する項目だけを再オープンする。進捗記録だけで完成を判断しない。

新しい Manager スレッドで再開するときは、以前の担当を操作できるか確認する。操作できなければ、以前の担当による書き込みの停止を確認し、引き継ぎ記録から新しい担当を起動する。

外部依存で停止する場合は、残項目、試した代替策、再開に必要な入力・権限・環境、次に行う操作を `plan.md` に残す。完了と停止のどちらでも作業ファイルを保持する。

既存の進捗記録が別形式で残っている場合は、Manager が受け入れ結果と検証根拠を照合し、固定 ID と必要な履歴を `plan.md` に取り込む。受け入れが確認できない完了候補は `review` とする。元の記録は保持し、以後の状態更新は `plan.md` に集約する。
