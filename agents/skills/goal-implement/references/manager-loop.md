# 進捗管理と委譲

## 作業ファイルと所有者

作業ファイルをプロジェクトの `.goal-implement/` に置く。Manager が全体の管理ファイルを更新し、Implementer はフェーズごとの報告を更新する。

| ファイル | 内容 | 更新者 |
| --- | --- | --- |
| `brief.md` | 元の要求、対象範囲、制約、仮定、未決事項 | Manager |
| `design.md` | 現在採用する全体設計と共有契約 | Manager |
| `plan.md` | 全体目標、フェーズ、依存関係、現在地、停滞の目安、再開条件 | Manager |
| `checklist.json` | 要件と作業項目、状態、受け入れ根拠、進捗の履歴 | Manager |
| `progress.html` | 全フェーズの状態、件数、時系列グラフ | Manager |
| `phases/{id}.md` | 現在の作業、実装結果、検証結果、障害、引き継ぎ | 担当 Implementer |

既存の設計資料があれば参照し、同じ本文を複製しない。設計の詳細が増えたら `design.md` から必要なファイルへリンクする。要件の原文は参照できる状態に保つ。

## 完了台帳

`checklist.json` を項目状態と集計の正本にする。各項目は次の情報を持つ。

| フィールド | 内容 |
| --- | --- |
| `id` | 再計画でも保持する固定 ID |
| `requirement_ids` | 対応する要件 ID。基盤作業も支える要件に結び付ける |
| `source` | 元の指示、要件ファイルの参照先 |
| `phase` | 担当するフェーズ ID |
| `outcome` | 観測できる完了条件 |
| `verification` | 結果を確かめるコマンド、操作、期待値 |
| `depends_on` | 前提となる項目 ID |
| `status` | `pending`、`in_progress`、`review`、`done`、`blocked` |
| `evidence` | 対象コード、実行コマンドや操作、結果、検証したリビジョンまたは作業状態、実時刻 |
| `blocker` | 障害と解消条件。障害がなければ空 |
| `updated_at` | 最終更新日時 |

通常の遷移は `pending → in_progress → review → done` とする。`review` は Implementer の完了候補、`done` は Manager の受け入れを表す。差し戻しは `in_progress`、前提が崩れた項目は `pending` に戻す。`blocked` からは障害の解消後に再開する。項目の `blocked` は goal API の状態とは別に管理する。

状態変更時に、同じ JSON 内の履歴へ実時刻、項目 ID、変更前後の状態、理由を追記する。項目の追加と再オープンも記録し、現在の対象件数と完了件数を再計算する。進捗率を保つために未完了項目を削除しない。ユーザーが範囲を変更した場合は、変更元と対象外になった ID を記録して集計対象を変える。

`progress.html` は JSON の内容を埋め込み、ローカルで開ける単独ファイルにする。全体とフェーズごとの完了数・対象数、各項目の状態・根拠・障害、更新日時、時系列の完了件数と対象件数を表示する。再オープンによる完了数の減少も表示する。

初回委譲前に台帳と HTML を作り、Manager が状態変更後に HTML を再生成する。JSON を直接編集できる画面や外部サービスとの連携は追加しない。

## フェーズの定義

各フェーズに目的、対象 ID、依存フェーズ、変更範囲、完了条件を付ける。委譲時には現在のフェーズで必要な設計と検証環境を確定する。後続フェーズの詳細な処理手順は、依存先が完成してから決める。

最後に統合検証を置く。全要件に対応する作業項目があり、主要シナリオが端から端まで検証されることを確認する。実装項目の完了だけで統合検証を省略しない。

## 委譲文

```text
Complete phase {id} completely, extremely well.

全体の目的: {利用者が達成する結果}
作業場所: {ディレクトリ・ブランチ・共有範囲}
全体計画: .goal-implement/plan.md
入力と設計: {brief.md、design.md の該当箇所と必要なコード}
対象項目: {ID と完了条件}
変更範囲: {担当する機能・ファイル、他担当との境界}
実行上の制約: {SKILL.md のスキル呼び出し制約と、現在のフェーズに適用する制約}
検証環境: {起動方法、利用可能なサービス、検証コマンド}
報告先: .goal-implement/phases/{id}.md
goal: {独立したフェーズ goal を設定する指示、または委譲文で目標を管理する旨}

現在のフェーズを詳細化し、実装・接続・検証まで完了してください。
完了候補は項目 ID ごとに変更内容と検証根拠を報告してください。
共有契約に変更が必要な場合は、影響と提案を Manager に報告してください。
停滞時は試した方法、得た根拠、障害、次の一手を報告してください。
全体の管理ファイルは Manager が更新します。次フェーズの開始は Manager に返してください。
```

全体計画は参照可能にし、現在のフェーズに不要な過去の議論や実行ログを委譲文へ詰め込まない。実行環境が分かれる場合は、成果をブランチやパッチで受け渡し、統合後に検証する。

## 受け入れと再開

Manager は報告の各項目を元の要求、対象コード、検証結果と照合する。証拠が不足する項目だけを再検証し、受け入れ済みで変更のない検証を繰り返さない。差し戻しには項目 ID、満たしていない条件、観測結果を付ける。

再開時は goal の状態、`plan.md`、台帳、最後のフェーズ報告を読み、コードの変更を確認する。記録された検証が現在のコードに適用できるかを判断し、影響を受ける項目を再オープンする。進捗記録だけで完成を判断しない。

外部依存で停止する場合は、残項目、試した代替策、再開に必要な入力・権限・環境、次に行う操作を `plan.md` に残す。完了と停止のどちらでも作業ファイルを保持する。
