# Goal Implement

要件を観測できる完成条件に変換し、設計・実装・検証を一つのループで進める。入力は会話、要件ファイル、プロジェクトテンプレート、既存コードから受け取る。`spec/` や特定の設計書形式に依存しない。

本ワークフローでは `spec`・`spec-implement` を呼び出さず、この制約をすべてのサブエージェントへの委譲に引き継ぐ。

## 役割と目標

| 担当 | 責務 |
| --- | --- |
| Manager | 要件の整理、全体設計、完成条件とフェーズの管理、進捗監視、成果の受け入れ |
| Implementer | 現在のフェーズの詳細設計、コードの実装、検証、完了候補と停滞の報告 |

Manager はメインエージェント、Implementer は別エージェントとする。Manager は実装コードを変更せず、要件と差分と動作を照合する。Implementer に成果と完了条件を伝え、実装方法と検証手順の具体化を任せる。

品質目標は `extremely well` とする。要求を満たす振る舞いと検証根拠で受け入れ、受け入れ済みの成果を好みで磨き続けない。

開始時に goal 管理、エージェントの起動・継続・メッセージ送信、利用可能な検証手段を確認する。

- ユーザーが goal の利用を明示し、対応機能があれば、既存の goal を確認する。全体の完成条件を整理してから、Manager に依頼範囲全体の goal を設定する。Implementer の goal は現在のフェーズの完成とする。
- goal の作成・状態変更は提供された API の条件に従う。無関係な未完了 goal を上書きしない。親子で goal を分離できない場合は、全体 goal を Manager だけが管理し、フェーズ目標を委譲文で渡す。
- 予算はユーザーが指定した場合だけ設定する。全体予算を各エージェントへ重複設定しない。予算切れを達成として記録しない。
- goal の利用指定がない場合や機能がない場合は、ファイルと継続依頼で同じループを動かす。goal 機能がない場合はその制約を報告する。プロンプト中の `/goal` を機能の実行と扱わない。
- 別エージェントを使えない場合は制約を報告し、同一エージェントで計画・実装・受け入れを順に行う。

goal の実行指示の例:

```text
$goal-implement requirements.md とこのテンプレートを使い、goal を設定して設計から実装・動作検証まで完了させてください。
```

## 1. 入力と作業場所を把握する

プロジェクトの `AGENTS.md`、`CLAUDE.md`、`README.md`、依存関係、既存コードを読む。起動・ビルド・テストの方法と現在の動作を確認する。テンプレートが渡された場合は、認証、永続化、UI 部品、外部連携、検証基盤の実装済み範囲を調べる。

指定されたテンプレートと既存の規約を設計の前提にする。要件との不一致は具体的に示し、必要な箇所を調整する。テンプレートのサンプル機能をプロダクト要件に取り込まない。

既存の `.goal-implement/` があれば、要件、進捗、コード、検証根拠を照合して再開する。ユーザーの変更を保持し、完了済みの作業は関連する変更や失敗がない限り繰り返さない。

## 2. 要件と完成条件を固定する

Manager が `.goal-implement/brief.md` に依頼範囲をまとめる。

- プロダクトの目的、利用者、主要な操作と期待する結果
- 必須機能、対象外、優先度、譲れない業務ルール
- 技術・運用・見た目の制約、完成を確かめる実行環境
- 元の指示の参照先、採用する仮定、未決事項

ユーザーの要求とエージェントが補った仮定を区別する。可逆的な UI・実装判断は、テンプレートと目的に合わせて決め、仮定を共有して進める。プロダクトの対象、権限、課金ルールなど、結果を大きく変える判断が入力から決まらない場合だけ質問する。回答待ちの間は、その判断に依存しない作業を進める。

Manager は [進捗管理と委譲](references/manager-loop.md) を読み、要件 ID と完了条件を台帳にする。完了条件は利用者から観測できる結果で書く。たとえば、保存機能なら入力後に一覧へ反映され、再読み込み後も保持されることを確かめる。

要件に存在しない機能を完成条件に追加しない。実装上必要な基盤作業は、それが支える要件に結び付ける。

全体 goal には利用者が達成する結果、対象範囲、統合検証まで含む完成条件と `brief.md` の場所を含める。「設計書を作る」「計画を立てる」だけを全体 goal にしない。

## 3. 全体を設計し、直近のフェーズを具体化する

Manager が `.goal-implement/design.md` に複数の機能に影響する決定を記録する。実際の要件に必要な範囲で、次を決める。

- 主要な画面、画面遷移、入力・空・読込中・失敗時の振る舞い
- データの所有者、権限、業務ルール、状態遷移
- コンポーネントの境界、共有するデータや API の契約、永続化と外部連携
- テンプレートから再利用するものと、追加・変更するもの
- 見た目の方針と主要画面の構成

設計の量はアプリの複雑さに合わせる。特定のアーキテクチャや永続化の抽象化を一律に導入しない。詳細なフィールド、処理手順、局所的な構造は Implementer が現在のコードに合わせて具体化する。

`.goal-implement/plan.md` に全体のフェーズと依存関係を置き、直近フェーズだけを実装・検証できる粒度にする。初期のフェーズで主要シナリオを画面から保存・再表示まで開通させる。成立が不明な外部連携や技術的な難所は、それに依存する実装より先に検証する。

見た目や操作感の不確実性が高い場合は、代表画面の試作を先に置く。全画面の詳細設計を先に完成させることは求めない。試作やモックで確認した範囲を記録し、本接続が必要な要件の完成とは区別する。

計画と主な仮定を簡潔に共有し、実装を開始する。既に任された範囲でフェーズごとの承認を挟まない。

## 4. Manager Loop を回す

1. Manager が依存条件を満たすフェーズを選び、Implementer に対象の要件 ID、設計、変更範囲、完了条件を渡す。
2. Implementer が詳細設計・実装・接続・検証を行い、根拠を添えて完了候補を報告する。独立した作業は、利用可能な枠と統合負担を見てサブエージェントへ委譲する。書き込み先を分け、全体の進捗ファイルは変更させない。
3. Manager が進捗と未解決事項を確認する。長時間の作業中も、ユーザーに完成した機能と次に確かめる点を伝える。
4. Manager が差分、実行結果、元の要件との対応を確認する。要求を満たさない振る舞い、再現する不具合、必要な検証の不足を項目 ID とともに差し戻す。
5. 受け入れた項目を完了にし、依存する次フェーズを継続依頼する。全フェーズの受け入れまで続ける。

エージェントの終了や「完了」という自己申告だけでは受け入れない。途中終了なら残項目から継続させる。同じ Implementer を継続利用し、文脈の混乱や停滞が続く場合は、書き込みの停止を確認して交代する。

実装で設計の不整合が判明した場合は、Manager が元の要件と照合して設計・契約・依存計画を更新する。影響を受ける受け入れ済み項目は再度未完了に戻す。ユーザーの完成条件を達成しやすい条件に書き換えない。

### 停滞と外部依存

完了項目が増えない時間の目安を計画に記録する。指定がなければ15分を出発点にし、既知の長時間処理は予定所要時間を記録する。経過時間は実時刻で判断する。

閾値を超えたら、Implementer は試した方法、得た根拠、障害、次の一手を報告する。Manager は処理の進行状況を確認し、作業の分割、別の実装方法、独立項目への切り替えで計画を組み直す。同じ試行を根拠なく繰り返さない。

資格情報、利用者の判断、外部環境の変更が必要になったら、依存しない実装と検証を完了させる。代替手段がなくなった時点で障害、未完了項目、再開条件を報告する。goal の `blocked` などの状態変更は API の条件を満たした時点で行う。

自走の指示は公開・本番デプロイ・外部への送信の許可を増やさない。必要な権限が不足する場合は、具体的に実行できる状態まで準備してから判断を求める。

## 5. 統合検証して完了する

最終フェーズで、統合後のアプリを元の要件から再確認する。

- 対象範囲の全要件に実装と検証の根拠があり、Manager が受け入れている。
- プロジェクトが要求する build・typecheck・lint・test の該当コマンドが成功している。
- 主要シナリオが実際の実行環境で端から端まで動く。Web アプリではブラウザで操作、表示、保存結果を確認する。
- 要件に応じた異常系、権限制御、状態遷移を確認している。テストは振る舞いとリスクに合わせて選ぶ。
- 必須機能に仮実装、ダミーデータへの置換、未接続の操作が残っていない。
- 起動方法、必要な環境変数、データ初期化など、利用と再実行に必要な手順をプロジェクトに残している。

未検証・ブロック中の必須項目があれば全体完了にしない。ブラウザや実サービスに接続できない場合は、代替検証で分かった範囲と未検証部分を記録する。既存の無関係な失敗は今回の変更と区別して報告し、全体検証の成功と扱わない。

全体の完成条件を満たしたら Manager が goal を完了にする。予算付き goal の完了報告に使用量が返る場合は、ユーザーへその値を伝える。

最終報告には、完成した機能、主な設計判断、検証結果、起動方法、残課題、進捗ファイルの場所を記載する。未完了なら再開条件を含める。
