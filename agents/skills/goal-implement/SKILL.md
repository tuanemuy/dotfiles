# Goal Implement

要件を観測できる完成条件に変換し、設計・実装・検証を一つのループで進める。入力は会話、要件ファイル、プロジェクトテンプレート、既存コードから受け取る。`spec/` や特定の設計書形式に依存しない。

本ワークフローでは `spec`・`spec-implement` を呼び出さず、この制約をすべてのサブエージェントへの委譲に引き継ぐ。

完成条件を先に固定し、やり方は担当に任せる。手順を細かく指示するより、完了とは何かを明確にする。

## 役割と目標

| 担当 | 責務 |
| --- | --- |
| Manager | 要件と完成条件の管理、設計判断、フェーズの委譲、進捗管理、報告に基づく受け入れ判断 |
| Implementer | 既存実装の調査、設計提案、現在のフェーズの詳細設計・実装・テスト、修正 |
| Verifier | 実装から独立した読みと動作の観測、完了の定義への反例の報告 |

Manager はメインエージェント、Implementer と Verifier は別エージェントとする。Manager は要件・計画・設計判断と報告の要約を扱い、調査・詳細設計・実装・検証は担当エージェントへ委譲する。根拠の不足や報告の矛盾は、担当へ追加確認を依頼する。

Verifier は担当フェーズの実装に参加していないエージェントを使い、Manager が直接委譲する。検証中は Implementer と補助エージェントによる対象コードの変更を止める。実装の並列数は検証用の枠を確保して決め、共有する検証環境の操作担当を一人に定める。Verifier は不具合を報告し、修正は Implementer が行う。Verifier に渡すのはコミットした完了候補だけで、計画・設計案・実行前の手順のレビューは依頼しない。設計案を読ませるのは、別の読み手による設計の読み 1 回だけとする。計画は Manager が決め、成立が不明な前提は小さな実装で確かめる。

受け入れの基準は「完了の定義」とする。独立した読み手が完了の定義への反例ゼロを返した項目は次へ進める。完了の定義の外の指摘で受け入れ済みの成果を磨き続けない。

開始時に、実行環境が提供する goal 管理、エージェントの起動・継続・メッセージ送信、通知待機、検証手段を確認する。機能の名称と API は実行環境ごとに異なる。Claude Code で実行する場合は [Claude Code での実行](references/claude-code.md) に従い、対応表の読み替えと Stop hook の確認を行う。

- ユーザーが goal の利用を明示し、対応機能があれば、既存の goal を確認する。全体の完成条件を整理してから、Manager に依頼範囲全体の goal を設定する。Implementer の goal は現在のフェーズの完成とする。
- goal の作成・状態変更は提供された API の条件に従う。無関係な未完了 goal を上書きしない。親子で goal を分離できない場合は、全体 goal を Manager だけが管理し、フェーズ目標を委譲文で渡す。
- 予算はユーザーが指定した場合だけ設定する。全体予算を各エージェントへ重複設定しない。予算切れを達成として記録しない。
- goal の利用指定がない場合や機能がない場合は、`plan.md` の台帳と継続依頼で同じループを動かす。実行環境がセッション終了時の hook や外側のループを提供する場合は、`status.json` の終端状態を終了判定に使う。goal 機能がない場合はその制約を報告する。プロンプト中の `/goal` を機能の実行と扱わない。
- 別エージェントを使えない場合は制約を報告し、同一エージェントで計画・実装・検証を順に行う。この場合は独立検証なしと記録する。

goal の実行指示の例:

```text
$goal-implement requirements.md とこのテンプレートを使い、goal を設定して設計から実装・動作検証まで完了させてください。
```

## 完了の定義

項目と全体は、次の 3 つが成り立ち、それぞれを根拠で示せるときに受け入れる。フェーズでは対象項目と変更が届く範囲に、統合検証では依頼範囲全体に問う。

- 成果が `../_shared/references/quality.md` の性質を満たしている
- 外部依存を `brief.md` で決めた検証段階で検証している
- 利用者に見える振る舞いを実際の実行環境で観測し、期待どおりである

### 反例

成り立つとは反例が無いこと。反例は、条件を破る箇所の引用と、その箇所で条件を破る具体的な入力・状態の組で示す。2 つの箇所の食い違いでは、もう一方の箇所の引用が具体的な状態にあたる。構造と UI では、拡張できたはずの既存のものや同種の既存画面の引用がそれにあたる。

実装には良くする方向の指摘がいくらでも出せる。形を取らない指摘（一般的な強化策、裏づけのない規模の想定）まで数えると、反例ゼロは磨き尽くした状態でしか成り立たない。形を取らない指摘は、完了の定義の外の指摘として扱う。

問うのは変更と項目の完了条件。変更の前から同じ入力で起きていた破れは、完了条件を破るときだけ反例になる。それ以外は最終報告で今回の変更と区別して報告する。

反例はどれも同じ硬さで扱う。構造と UI の反例は、いま何も壊していなくても見送る理由にならない。

### 読み替え

`quality.md` の言葉は、このスキルでは次のものにあたる。

- 要求は元の要件とユーザーの回答（`brief.md`）、要件は項目の完了条件（`plan.md`）。各完了条件は観測方法（ブラウザ / 自動テスト / コマンド出力）を持つ
- プロジェクトのアーキテクチャには、`design.md` が定めたレイヤーとポートを含む

### 観測

- 対象は、主要シナリオの端から端までと、実装した振る舞いのうち結果が利用者に見えるもの（エラー表示・バリデーション・空状態・権限なし・二重送信・再読み込み後の状態）
- Web アプリではブラウザを使い、対象の画面幅で観測する
- 期待結果は要件と設計から決まり、観測した画面からは決まらない
- 期待とおおよそ一致するだけの観測は不一致とする
- テストが通ることは、画面に出ることの根拠にならない
- 観測できないものは未観測として残し、推測で埋めない

### 根拠

- 項目ごとの、満たすコードと観測結果
- 実装した振る舞いとテストの対応、変異（条件反転・境界±1・ガード削除）で赤くなった記録
- 変更が届く箇所ごとの確かめ方。届く箇所は、変更した箇所が返す値・投げる失敗・書く状態を受け取る箇所、変えた・消した型・名前・スタイルを使う箇所、受け入れ済み項目の完了条件。受け取ったものを別の失敗や値に変えて渡す箇所では、渡した先までたどる。既存テストが守る箇所はそのテストの通過で、守っていない箇所はテストを足すか実測して確かめる
- 自動検証の実行結果。フェーズでは、テストなど時間のかかる検証を対象項目と届く箇所を守る部分に絞る
- 非自明な判断の理由を書いた `design.md`
- 対象の画面幅ごとの観測と、比べた画面
- 観測ごとの期待と実際、スクリーンショット

## 独立した読み

完了の定義は自分の枠の中でしか確かめられない。枠そのものの誤りは、別の目が狭い目的で読んで初めて出る。読み手は新しいコンテキストのエージェントで、読む対象の作成に参加していないものを使う。Manager が直接委譲し、Manager と Implementer の自己評価・完了報告は渡さない。

読みは次の 3 つ。

- 設計の読み: 最初のフェーズの実装の前に 1 回行う。要件の原文、`brief.md`、`design.md`、完了の定義の「反例」（転記）、`quality.md` の絶対パスを渡し、`brief.md` が要件の意図を取りこぼしている点・条件の片側しか書いていない点・要件と `brief.md` が前提にしている事実や指定のうちコードと規約で成り立たない点と、`design.md` への `quality.md` の構造と UI の反例を挙げさせる。Manager は返った指摘を反映して実装を始め、読み直しは行わない
- フェーズの読み: Verifier が完了候補ごとに行う（「4. Manager Loop を回す」）
- 統合の読み: Verifier が統合後の成果に行う（「5. 統合検証して完了する」）

フェーズの読みと統合の読みでは、次を守る。

- 読み手の目的は完了の定義への反例を探すこと。成立の認定はさせず、反例の一覧だけを返させる
- 反例には効く項目 ID と、破る条件（`quality.md` なら性質）を添えて返させる。形を取らない指摘は、完了の定義の外として理由を添えて分けて返させる
- `quality.md` の絶対パスを渡す

最初の依頼に、上で決めたもの以外で足してよいのは、環境の事実と出力の形だけ。どこを疑ってほしいか（不安な箇所・見てほしい点・例・観点の言い換え）は書かない。疑ってほしい箇所は、反例が返ってきた後で同じ読み手に追加で聞く。先に渡すと、読み手はその箇所を中心に読み、自分の盲点を読まなくなる。

### 反例の扱い

完了の定義への反例は、どの条件のものも Manager が見送らない。見送ってよいのは完了の定義の外の指摘だけ。反例ゼロと言うのは読み手で、Manager でも Implementer でもない。完了の定義の外の指摘は、受け入れ条件にも差し戻し理由にもならない。

読み手が完了の定義の外に置いた指摘も「反例」の節に照らし、あたるものは反例として扱う。形を取るか迷う指摘は、同じ読み手に返して判定させる。

構造と UI の反例は、書いた後に見つかると作り直しになる。設計の読みのほかに、いつ何を読ませれば安く済むかは Manager が決める。

構造と UI の反例を受けて設計を変えたら、`design.md` の該当する決定に、変える前の案と変えた理由を添える。読み手は過去の判断を知らないので、記録した判断と逆を向く反例も返す。その反例には、該当する決定を同じ読み手に追加で渡し、判断の前提がいまも成り立つかを読み手に判定させる。前提が成り立てば読み手は反例を取り下げ、崩れていれば直す。同じ判断を 2 度覆すことになるときは、直す前にユーザーに聞く。

## 1. 入力と作業場所を把握する

Manager はプロジェクトの指示・設計資料と要件を確認する。既存実装と実行・検証方法の調査は Implementer に委譲し、要件に対して再利用できる範囲と不足を報告させる。

指定されたテンプレートを設計の前提にする。要件との不一致は具体的に示し、必要な箇所を調整する。テンプレートのサンプル機能をプロダクト要件に取り込まない。

Manager は [進捗管理と委譲](references/manager-loop.md) を読み、今回の依頼に対応する作業ディレクトリを確定する。同じ依頼の記録があれば要件と進捗を確認し、コードと検証根拠の照合を Verifier に委譲して再開する。別依頼の記録は分離する。以降、`{run-directory}` は確定した作業ディレクトリを表す。

ユーザーの変更を保持し、完了済みの作業は関連する変更や失敗がない限り繰り返さない。

## 2. 要件と完成条件を固定する

Manager が `{run-directory}/brief.md` に依頼範囲をまとめる。

- プロダクトの目的、利用者、主要な操作と期待する結果
- 必須機能、対象外、優先度、譲れない業務ルール
- プロジェクトの制約、完成を確かめる実行環境
- 対象の画面幅。プロジェクトが定めていなければ、ここで決める
- 外部依存と、それぞれの検証段階
- 元の指示の参照先、採用する仮定、未決事項

ユーザーの要求とエージェントが補った仮定を区別する。可逆的な設計・実装判断は、プロジェクトの方針と目的に合わせて決め、仮定を共有して進める。結果を大きく変える判断が入力から決まらない場合と、元の要件から外れる判断が要る場合だけ質問する。回答待ちの間は、その判断に依存しない作業を進める。回答がなく作業を止められない判断は、可逆で安全な側を採用し、仮定として `brief.md` に記録する。

### 外部依存

資格情報・アカウント・外部環境がないと実接続できない依存 (認証プロバイダ、メール送信、LLM、外部ストレージなど) を `brief.md` に列挙する。依存ごとに検証段階を決め、完了条件に書く。

- 実接続: 実際のサービスで検証する。
- 契約検証: ポートに対する代替アダプターでシナリオを通す。実アダプターには、資格情報があるときだけ実行する契約テストを置く。
- 対象外: 依存する要件ごと対象外にする。

段階の決定に利用者の入力が要る依存は、この時点で一度にまとめて質問する。回答がない依存は契約検証で進める。契約検証で受け入れた項目は、実接続の検証手順と必要な設定を `plan.md` に残す。

### 完成条件

Manager は `plan.md` に要件 ID と完了条件を記録する。機能の完了条件は利用者から観測できる結果で書く。

完了条件の出どころは次の二つに限る。

- 要件・シナリオの ID
- `brief.md` / `design.md` に記録したリスク

`quality.md` と観測は、完了の定義が全項目に問う。項目の完了条件に書き写さない。

要件に存在しない機能を完成条件に追加しない。実装上必要な基盤作業は、それが支える要件に結び付ける。

全体 goal には利用者が達成する結果、対象範囲、統合検証まで含む完成条件と `brief.md` の場所を含める。「設計書を作る」「計画を立てる」だけを全体 goal にしない。

## 3. 全体を設計し、直近のフェーズを具体化する

Implementer が調査結果に基づく全体設計案と判断が必要な事項を報告する。Manager は要件との整合性を判断し、採用する設計と理由を `{run-directory}/design.md` に記録する。複数のフェーズに影響する設計判断と共有契約を確定し、既存実装からの変更範囲を明らかにする。要件がどのレイヤー・どのポートで実現されるかを記録し、フェーズごとに構造を発明させない。

プロジェクトのアーキテクチャと設計規約に従う。方針が未指定の範囲は、要件と既存構造に合わせて決める。設計の量は対象の複雑さに合わせ、詳細設計は Implementer が行う。

`{run-directory}/plan.md` に全体のフェーズと依存関係を置き、直近フェーズだけを実装・検証できる粒度にする。初期のフェーズで主要シナリオを端から端まで動かす。成立が不明な前提は、それに依存する実装より先に検証する。

最初のフェーズを委譲する前に、設計の読み（「独立した読み」）を行う。計画と主な仮定を簡潔に共有し、実装を開始する。既に任された範囲でフェーズごとの承認を挟まない。

## 4. Manager Loop を回す

1. Manager が依存条件を満たすフェーズを選び、Implementer に対象の要件 ID、設計、変更範囲、完了条件、「完了の定義」の節の全文（転記）、`quality.md` の絶対パスを渡す。受け入れ条件はこの委譲時に確定する。
2. Implementer が詳細設計・実装・接続・検証を行い、検証対象を識別できる根拠を添えて完了候補を報告する。独立した作業は、利用可能な枠と統合負担を見てサブエージェントへ委譲する。書き込み先を分け、全体の進捗ファイルは変更させない。
3. Manager が Implementer の報告から進捗と未解決事項を確認する。ユーザーには完成した機能と次に確かめる点を伝える。
4. Manager が完了候補を `review` にし、元の要件と `brief.md`、完了条件、「完了の定義」の節の全文（転記）、`quality.md` の絶対パス、検証対象を Verifier に渡す。Implementer の実装報告からは検証対象と実行方法だけを渡す。Verifier は動作を観測してフェーズの読みを行い、項目 ID ごとに反例・未観測事項・観測記録を報告する。
5. Manager は報告に全対象項目の反例と観測があるかを確かめる。反例のある項目は Implementer に差し戻し、観測の不足は Verifier に追加確認を依頼する。受け入れ条件の追加は Verifier が対応する要件を添えて提案し、Manager が採否を決める。修正後に、同じ Verifier に増分を読ませるか、新しい Verifier に全量を読ませるかは Manager が決める。
6. Manager は反例ゼロで未観測事項の無い項目を受け入れて `done` にし、依存する次フェーズを継続依頼する。全フェーズの受け入れまで続ける。

待機中の担当に次フェーズ・修正・追加検証を依頼するときは、実行を開始する継続依頼を使う。通知だけで再開したと扱わない。

エージェントの終了や「完了」という自己申告だけでは受け入れない。途中終了なら残項目から継続させる。現在の Manager から操作できる間は同じ Implementer を継続利用する。文脈の混乱や停滞が続く場合は、書き込みの停止を確認して交代する。

共有契約、レイヤー境界、ポートの形に触れる修正は、Implementer が Manager に報告してから行う。実装で設計の不整合が判明した場合は、Manager が元の要件と照合して設計・契約・依存計画を更新する。受け入れ済み項目は、その完了条件に影響する変更があった場合だけ未完了に戻す。隣接する変更の影響は Verifier が根拠付きで報告する。ユーザーの完成条件を達成しやすい条件に書き換えない。

### 待機と進捗確認

Manager は独立して進める管理・判断がなければ、通知待機ツールで担当エージェントの報告を待つ。待機時間は、実行環境の上限、ユーザーへの報告間隔、停滞確認の期限に収まる範囲で長く取る。通知待機ツールがない場合は、同じ間隔で sleep と状態確認を行う。

Manager は完了・障害・判断依頼の通知、または停滞確認の期限で報告と進捗ファイルを読む。待機のタイムアウトだけでは読み直さない。新しい通知も期限の到来もなければ再び待機する。定期的なユーザー報告のために状態照会やレビューを追加しない。

### 停滞と外部依存

完了項目が増えない時間の目安を計画に記録する。指定がなければ15分を出発点にし、既知の長時間処理は予定所要時間を記録する。経過時間は実時刻で判断する。

閾値を超えたら、担当エージェントは試した方法、得た根拠、障害、次の一手を報告する。Manager は次の項目へ進めることを既定にし、満たしていない条件は項目に残す。同じ項目に留まるのは、後続の依存先で代替がない場合に限る。同じ試行を根拠なく繰り返さない。

資格情報、利用者の判断、外部環境の変更が必要になったら、依存しない実装と検証を完了させる。代替手段がなくなった時点で障害、未完了項目、再開条件を報告する。goal の `blocked` などの状態変更は API の条件を満たした時点で行う。

自走の指示は公開・本番デプロイ・外部への送信の許可を増やさない。必要な権限が不足する場合は、具体的に実行できる状態まで準備してから判断を求める。

### ループの上限

goal の予算とは別に、ループに次の上限を置く。

- 同じ項目の差し戻し → 修正 → 読み直しは 3 周まで（同じ読み手への追加の問いは数えない）。超えたら項目を `blocked` にし、残る反例と試したことを残して次の項目へ進む
- 統合の読みは 2 回まで（「5. 統合検証して完了する」）
- フェーズの数が計画の 2 倍を超えたら、残りの項目と見通しをユーザーに報告し、続けるか聞く

## 5. 統合検証して完了する

最終フェーズで、Manager は統合後の成果に対する統合の読みを、新しい Verifier に委譲する。範囲は依頼範囲全体で、完了の定義をそのまま問う。Verifier は統合後のコードでプロジェクトの検証手順と主要シナリオの観測を実行し、反例を効く項目 ID 付きで返す。

成果が大きいと、新しい読み手は読むたびに、それまでの読み手が見落とした小さな反例を一定の数だけ拾う。全体の読みを重ねても反例の数は減らない。一方、1 つの項目に残る反例は数件で、範囲を絞った読みなら反例ゼロまで閉じられる。そのため反例は項目ごとに閉じる。

- 統合の読みは 2 回まで行い、反例ゼロが返ればそこで終える
- 反例のある項目は差し戻す。修正後は、その項目と変更が届く範囲に絞ったフェーズの読みで反例ゼロにしてから、次の統合の読みへ進む
- 2 回目の統合の読みの反例は、項目ごとに閉じた時点で終える
- 最後に、最終のコードでプロジェクトの検証手順と主要シナリオの観測を実行し、すべて通ることを確かめる。失敗したら該当項目を差し戻す

未観測・ブロック中の必須項目があれば全体完了にしない。必要な検証環境を利用できない場合は、代替検証で分かった範囲と未検証部分を記録する。既存の無関係な失敗は今回の変更と区別して報告し、全体検証の成功と扱わない。

残る未検証項目が実接続待ちだけの状態を「完了 (実接続待ち)」とし、ループの終端にする。再検証に必要な設定と手順を `plan.md` に残し、goal は完了にせず API の条件に従って `blocked` などへ更新する。

Manager は統合検証報告と全体の完成条件を照合し、全項目を受け入れたら goal を完了にする。予算付き goal の完了報告に使用量が返る場合は、ユーザーへその値を伝える。

最終報告には、完成した機能、主な設計判断、検証結果、独立した読み（統合の読みの回数と回ごとの反例の数、項目ごとに閉じた反例の数、完了の定義の外で見送った指摘）、利用手順、残課題、進捗ファイルの場所を記載する。契約検証で受け入れた項目と実接続待ちの項目は別枠で示す。未完了なら再開条件を含める。
