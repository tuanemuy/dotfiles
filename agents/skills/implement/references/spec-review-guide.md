# Phase 1: Spec レビューガイド

設計ドキュメントの品質を実装前に確認する。レイヤーごとに並列でサブエージェント（**審査区分**。`../../_shared/references/subagent-policy.md`）を起動し、独立してレビューさせる。

## レビュー対象と観点

### シナリオ（spec/scenario/）

レビュー出力先: `spec/scenario/review/{連番}.md`

観点:

- 利用シナリオが要件を網羅しているか
- 利用者の視点で具体的なフローが分かるように記載されているか
- フローに不自然な迂回や無駄なステップがないか

### ページ設計（spec/pages/）

レビュー出力先: `spec/pages/review/{連番}.md`

観点:

- 要件を実現するために適切なページ構成になっているか
- レイアウトやコンポーネントの粒度が適切か
- UXが考慮されているか（ページ遷移、タブ、モーダル等の使い分け）

### ドメイン設計（spec/domains/）

レビュー出力先: `spec/domains/review/{連番}.md`

観点:

- エンティティや値オブジェクトが適切に定義され、型安全であるか
- 集約ルートが適切に定義され、整合性が保たれているか
- ビジネスロジックがドメインモデルに適切に配置されているか
- 外部依存は適切なポートとして定義されているか
- ポートに振る舞いの契約（一意性・整合性の担保、クエリ要件、並行性、可視性）が定義されているか
- ポートが特定の永続化技術に依存する語彙・型を露出していないか（アダプターの差し替え可能性）

### ユースケース設計（spec/usecases/）

レビュー出力先: `spec/usecases/review/{連番}.md`

観点:

- ユースケースが要件を満たしているか
- ユースケースが適切に分割され、単一責任の原則に従っているか
- フロントエンドで行うべき処理がユースケースに含まれていないか
- 複数集約に書き込むユースケースに UnitOfWork の要否が記載されているか

### テストケース定義（spec/testcases/）

レビュー出力先: `spec/testcases/review/{連番}.md`

観点:

- ユースケースのエラーケースがテストケースでカバーされているか
- `spec/testcases/ports/` にポート適合テストがあり、全ポートメソッドと契約項目をカバーしているか
- 適合テストのケースが特定バックエンドを前提にしていないか

## サブエージェントへの指示テンプレート

```text
あなたは「{対象レイヤー}」の設計品質をレビューする専門家です。

## レビュー対象
- 設計ファイル: {spec/対象パス}

## やること
1. 設計ファイルを読む
2. 上記の観点でレビューする
3. 対応が必要な問題点のみ記載する（良い点の列挙は不要）

## 出力フォーマット
問題がある場合:
- **[P-001]** 問題の説明
  - 場所: 該当箇所
  - 理由: なぜ問題か
  - 提案: どう修正すべきか

問題がない場合: 「問題なし」とだけ書く。
```

## レビュー → 修正ループ

指摘の仕分けは `../../_shared/references/review-loop.md` の指摘台帳方式に従う。台帳は対象ディレクトリの `review/triage.md` に置き、Key が一致する既出指摘は判定を継承して再審議しない。

問題があれば `fix` と仕分けた指摘をサブエージェントで修正させ、再レビューする。**`fix` が0件のラウンドで完了**（台帳に記録済みの指摘は件数に含めない。最大3ラウンド）。収束しない場合は残った指摘をまとめてユーザーに報告し、判断を委ねる。
