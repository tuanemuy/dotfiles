# Implement — 設計ドキュメントからの段階的実装オーケストレーター

`spec/` の設計ドキュメントに基づき、レイヤーごとに実装を進める。各レイヤーの実装とレビューはサブスキルに委譲し、本スキルは全体の進行管理と統合品質ゲートに集中する。

**メインエージェントの役割はオーケストレーションのみ。** コードの読み書きはすべてサブエージェントに委譲し、自身は実装の指揮・進捗管理・次フェーズの判断に集中する。

## いつ使うか — spec-to-issues との使い分け

spec が大きいほど 1 回の実行スコープが肥大し、実装もその検証もコンテキストが薄まって漏れが生まれやすくなる。Phase 0 で規模を見て進め方を判断する:

- **小規模**（目安: シナリオが 1〜2 本、台帳 `spec/inventory/` の総行数 50 行以下）— 本スキルで一括実装する
- **それ以上** — spec-to-issues で縦スライス Issue 化し、issue-implement で 1 Issue ずつ実装する進め方を推奨としてユーザーに提案する。ユーザーが一括実装を選んだ場合のみ本スキルで続行する

特定レイヤーの再実装や、implement-audit の指摘対応のような絞られたスコープの再実行は、規模によらず本スキル（または個別 implement-*）で行う。

## なぜこの順序か

ドメインモデル → アダプター → ユースケース → テスト → フロントエンドの順で実装する。内側から外側へ向かうことで各レイヤーが安定した依存先の上に載り、テストはユースケース実装後に書くことで仕様に忠実になり、フロントエンドは API が固まってから組める。

各レイヤーは実装直後に**完全性ゲート → レビューサイクル**を回す。完全性ゲートは、typecheck + lint では拾えない省略（スタブ・ダミーデータ・部分実装・未実装）をレイヤー単位で早期に潰し、最終段の監査（Phase 8）まで持ち越さない仕組み（`../_shared/references/completeness-gate.md`）。

## Workflow Overview

```text
Phase 0: 準備
  spec/ の存在確認 → プロジェクトコンテキスト把握 → 進捗ファイル確認 → 途中再開 or 新規開始

Phase 1: Spec レビュー（省略可）
  設計ドキュメントの品質を並列レビュー → 問題があれば修正

Phase 2: ドメイン実装＋完全性ゲート＋レビュー
  implement-domain の手順に従う → 実装 → 完全性ゲート（省略検出）→ レビュー完了まで

Phase 3: アダプター実装＋完全性ゲート＋レビュー
  implement-adapter の手順に従う → 実装 → 完全性ゲート → レビュー完了まで

Phase 4: ユースケース実装＋完全性ゲート＋レビュー
  implement-usecase の手順に従う → 実装 → 完全性ゲート → レビュー完了まで

Phase 5: テスト実装＋完全性ゲート＋レビュー
  implement-test の手順に従う → 実装 → 完全性ゲート → レビュー完了まで

Phase 6: フロントエンド実装＋完全性ゲート＋レビュー
  implement-frontend の手順に従う → 実装 → 完全性ゲート → レビュー完了まで

Phase 7: 統合品質ゲート
  全体 typecheck + lint + test run

Phase 7.5: ブラウザ検証（条件付き）
  Web UI プロジェクト + spec/manual-tests/ がある場合のみ
  → manual-test スキルに委譲

Phase 8: 実装監査＋再実装ループ
  implement-audit で全体スキャン → Critical/Warning があれば Phase 2〜7 を再実行 → 再監査

Phase 9: 完了報告
```

途中のフェーズから再開する場合は、進捗ファイルを確認して該当フェーズから開始する。

## Phase 0: 準備

### spec/ の確認

以下の設計ドキュメントが存在するか確認する:

- `spec/index.md` — 設計インデックス
- `spec/scenario/` — 利用シナリオ
- `spec/domains/` — ドメイン設計
- `spec/usecases/` — ユースケース設計
- `spec/pages/` — ページ設計（フロントエンドがある場合）
- `spec/testcases/` — テストケース定義（`spec/testcases/ports/` のポート適合テストを含む）
- `spec/design/` — UIデザイン成果物（design-flow スキルの出力。フロントエンドがある場合）

存在しない場合はユーザーに確認する。spec スキルで設計を先に作成する必要があるかもしれない。

### プロジェクトコンテキストの把握

CLAUDE.md と README.md を読み、以下を確認する:

- 使用言語・フレームワーク
- ディレクトリ構成（ドメイン・アダプター・ユースケース・フロントエンドの配置先）
- typecheck・lint・test の実行コマンド
- コーディング規約

これらの情報はサブエージェントへの指示に含める。プロジェクトごとに言語もディレクトリ構成も異なるため、spec とプロジェクトコンテキストの両方に従って実装する。

既存コードの下調べ（各レイヤーの実装状況、参照できる既存実装の収集）が必要な場合は、サブエージェント（**探索区分**。`../_shared/references/subagent-policy.md`）に委譲する。

### 進捗管理

`spec/progress.md` で実装進捗を管理する。なければ新規作成する。

```markdown
# 実装進捗

## ドメイン
- [ ] {domain名}
- [ ] {domain名}

## アダプター
- [ ] {adapter名}

## ユースケース
- [ ] {domain名}
- [ ] {domain名}

## テスト
- [ ] {domain名}

## フロントエンド
- [ ] {page名}
```

各フェーズの開始時に `[ ]` → `[-]`（進行中）、完了時に `[x]` に更新する。備考があれば行末に追記する。

### 実装例の確認

`docs/backend_implementation_example.md` や `docs/frontend_implementation_example.md` が存在するか確認する。存在する場合はサブエージェントに参照先として渡す。

### 共通

- Phase 0 の確認が完了したら、以降は最後まで自走する（フェーズ間でユーザー承認を挟まない）
- ただし設計に問題がある場合や判断に迷う場合はユーザーに確認する

## Phase 1: Spec レビュー（省略可）

`references/spec-review-guide.md` を読み、その手順に従って設計ドキュメントをレビューする。

`spec/index.md` に各フェーズのレビュー完了が記録されていれば、spec / spec-domain スキルでレビュー済みなのでスキップする。**レビューファイルの有無では判定しない** — 両スキルは収束時に `review/` を削除する運用なので、残っている `spec/*/review/` はむしろ未収束のサイン。その対象はレビューを実施する。

成果物:

- `spec/{対象}/review/{連番}.md` — レビュー記録

指摘の仕分けはガイドの指摘台帳方式に従う。**`fix` と仕分けた指摘が0件のラウンドでレビュー完了**（最大3ラウンド）。

レビューが完了したら、対象ディレクトリの `review/` を削除する（`../_shared/references/review-loop.md` の「後片付け」参照。最大ラウンドに達して収束しなかった対象は削除せず残し、完了報告に明記する）。片付けが済んだら Phase 2 へ。

## Phase 2: ドメイン実装＋レビュー

`../implement-domain/SKILL.md` を読み、その Phase 2（実装）・Phase 2.5（完全性ゲート）・Phase 3（レビューサイクル）の手順に従う。Phase 1（準備）は Phase 0 で完了済みのため省略する。

レビューサイクルが完了したら Phase 3 へ。

## Phase 3: アダプター実装＋レビュー

`../implement-adapter/SKILL.md` を読み、その Phase 2（実装）・Phase 2.5（完全性ゲート）・Phase 3（レビューサイクル）の手順に従う。

レビューサイクルが完了したら Phase 4 へ。

## Phase 4: ユースケース実装＋レビュー

`../implement-usecase/SKILL.md` を読み、その Phase 2（実装）・Phase 2.5（完全性ゲート）・Phase 3（レビューサイクル）の手順に従う。

レビューサイクルが完了したら Phase 5 へ。

## Phase 5: テスト実装＋レビュー

`../implement-test/SKILL.md` を読み、その Phase 2（実装）・Phase 2.5（完全性ゲート）・Phase 3（レビューサイクル）の手順に従う。

テスト実装では `../_shared/references/e2e-test-methodology.md` のE2Eテスト方法論に基づき、spec/testcases/ の定義を網羅しつつ、実装コードの分析から見えた追加観点（境界値・異常系・状態遷移等）もカバーする。

レビューサイクルが完了したら Phase 6 へ。

## Phase 6: フロントエンド実装＋レビュー

`../implement-frontend/SKILL.md` を読み、その Phase 2（実装）・Phase 2.5（完全性ゲート）・Phase 3（レビューサイクル）の手順に従う。

フロントエンドがないプロジェクトではスキップする。レビューサイクルが完了したら Phase 7 へ。

## Phase 7: 統合品質ゲート

全レイヤーの実装とレビューが完了したら、プロジェクト全体で品質チェックを実行する。

```text
1. typecheck（CLAUDE.md のコマンドに従う）
2. lint（CLAUDE.md のコマンドに従う）
3. test run（CLAUDE.md のコマンドに従う）— Phase 5 で作成したテストを含む全テストを実行
```

テスト失敗がある場合は、失敗内容を分析する:

- Phase 5 で作成したテストの失敗 → テストまたは実装の修正が必要
- 既存テストの失敗 → 実装が既存機能を壊している可能性がある（リグレッション）

エラーがある場合はサブエージェント（**判断区分**）を起動して修正させる。サブエージェントにはエラー内容と関連ファイルを渡す。

すべてパスするまで繰り返す（最大3回）。3回で収束しない場合はユーザーに報告して判断を仰ぐ。

## Phase 7.5: ブラウザ検証（条件付き）

Web UI を持つプロジェクトで、かつ `spec/manual-tests/` が存在する場合、`../manual-test/SKILL.md` を読み、その手順に従ってブラウザ検証を実行する。

manual-test に渡す情報:

- テストソース: `spec/manual-tests/`
- 成果物ディレクトリ: `.manual-test/`

`spec/manual-tests/` が存在しない場合は、spec-manual-test スキルで先に生成することを検討する。ただし、以下の場合はこの Phase をスキップする:

- Web UI を持たないプロジェクト（CLI ツール、ライブラリ等）
- spec/pages/ が存在しない（フロントエンドがない）
- agent-browser が利用できない

ブラウザ検証で失敗がある場合は、manual-test が原因分析を行い GitHub Issue を起票する。起票された Issue は Phase 9 の完了報告に記載する。

## Phase 8: 実装監査＋再実装ループ

`../implement-audit/SKILL.md` を読み、その手順に従って実装の完全性を監査する。

統合品質ゲート（Phase 7）はコンパイルエラーやテスト失敗を検出するが、TODO・仮実装・省略箇所・spec との乖離は拾えない。implement-audit が三段構え（パターンマッチング＋コード意味分析＋spec 照合）でプロジェクト全体をスキャンし、未完成箇所を構造化レポート（`.audit/completeness/`）として検出・出力する。

### 監査結果に Critical・Warning がある場合

監査レポートの内容をサブエージェントへのコンテキストとして渡し、Phase 2〜7 を再実行する。再実装時は、各サブエージェントに監査レポートの該当箇所を明示的に渡して、検出された問題を確実に修正させる。

再実装→品質ゲート→再監査のサイクルを回す。**2回連続で Critical 0件 かつ Warning 0件** になったら監査完了。最大3ラウンド。3ラウンドで収束しない場合は残っている指摘をまとめてユーザーに報告し、判断を委ねる。

監査が収束したら `.audit/completeness/` を削除する — 検出はすべて修正済みで、レポートは役目を終えている。収束しなかった場合は削除しない（ユーザーが残指摘を確認するために残す）。

## Phase 9: 後片付け・完了報告

すべてのフェーズが完了したら、レビューの中間成果物を片付けてからサマリーを出す。

- Phase 8 が収束していれば、各レイヤーのレビュー記録 `.review/` を削除する — 指摘はすべて修正済みか台帳の判定として決着している（`../_shared/references/review-loop.md` の「後片付け」参照）
- レビューが収束しなかったレイヤーがある場合、そのレイヤーの `.review/{layer}/` は残す（ユーザーが残指摘を確認するため）
- Phase 1 の spec レビュー記録 `spec/*/review/` が残っていないか最終確認する。収束済みなのに残っていれば、ここで削除する
- `spec/progress.md`・ADR は成果物なので残す

```text
実装が完了しました！

## 進捗
- spec/progress.md を参照

## 実装レイヤー
- ドメイン: {数} ドメイン
- アダプター: {数} 個
- ユースケース: {数} 個
- テスト: {数} ファイル
- フロントエンド: {数} ページ

## 品質
- typecheck: PASS
- lint: PASS
- test: PASS ({数} tests)

## ブラウザ検証（実行した場合）
- テストケース: {数}件（PASS: {数} / FAIL: {数}）
- 修正ラウンド: {数}回
- レポート: .manual-test/report.md を参照

## 実装監査
- ラウンド数: {数}回
- 初回検出: Critical {数}件 / Warning {数}件 / Info {数}件
- 最終結果: Critical 0件 / Warning 0件 / Info {数}件
- レポート: {収束のため削除済み / 未収束のため .audit/completeness/ を参照}

## レビュー
- spec レビュー: {削除済み / spec 側でレビュー済みのためスキップ / 未収束の対象のみ spec/{対象}/review/ を参照}
- 実装レビュー: {削除済み / 未収束のレイヤーのみ .review/{layer}/ を参照}
```

## 原則

共通原則は `../_shared/references/implement-principles.md` に従う（省略を残さない・完全性は構文チェックで担保できない・spec 同期・ADR 記録など）。オーケストレーター固有:

- 各フェーズは前フェーズの成果に基づいて進める — 飛ばさない（部分実行の場合を除く）
- **並列実行時はドメイン間の依存関係を尊重する** — 依存先を先に実装してから依存元を起動する
- **フェーズ完了ごとに git commit する** — 途中で中断しても成果が失われないようにする
- `spec/progress.md` はフェーズ完了ごとに更新し、進捗を反映する
