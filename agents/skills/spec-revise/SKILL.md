# Spec Revise

プロンプトまたはファイルで与えられた修正指示をもとに、既存の `spec/` の設計を改訂する。指示の字面に最小差分で応えるのではなく、「新しい要件が最初からあったならどう設計したか」を問い直し、その設計に既存の成果物を揃える。更新は上流（シナリオ）から下流（テストケース・マニュアルテスト）へ一貫して伝播させ、レビューループで品質を担保する。

## 設計思想

### 場当たり的に直さない

修正指示に対して既存の設計へ最小のパッチを当てると、設計は改訂のたびに劣化する。本スキルでは、指示が触れる範囲について「新要件を含めた前提での最適な設計」をゼロベースで再検討し、既存設計と一致するならそのまま、一致しないなら既存側を作り直す。既存の構造は「変更コストが低いから維持する」理由にはなるが、「最適だから維持する」根拠にはならない — どちらの理由で維持するのかを常に区別する。

### 波及を追い切る

設計は連鎖している。シナリオの変更はページに、ページの変更はドメインに、ドメインの変更はユースケース・DB・テストケースに波及する。指示が直接言及していない成果物でも、整合性が崩れるなら更新対象に含める。逆に、指示から必然的に導かれない部分には手を出さない（スコープクリープの禁止）。

### 決定は spec に現在形で表す

改訂で下した判断の唯一の記録は spec/ 本体。新しい設計を現在形で書き、経緯・代替案・旧仕様の痕跡は spec に残さない（旧仕様は git 履歴が持つ）。検討した代替案とトレードオフはコミットメッセージと完了サマリーで報告する（`../_shared/references/adr-guide.md`）。

## Phase 0: 指示の受領と解釈

1. 修正指示を特定する
   - プロンプトで与えられた場合: 内容をそのまま入力とする
   - ファイルで与えられた場合: 指定されたファイルを読む
   - どちらも不明瞭な場合: ユーザーに指示の所在を確認する
2. `spec/index.md` と既存の成果物を読み、現行設計の全体像を把握する
3. 指示を要求項目に分解し、番号付きの一覧（指示台帳）としてまとめる
   - 各項目に「何を・なぜ変えたいのか」を一行で記載する
   - 解釈が分かれる項目・矛盾する項目・現行設計の前提を壊す項目があれば、質問をすべてまとめて一度にユーザーへ確認する
4. 確認が完了したら指示台帳を `spec/review/revise/instructions.md` に保存し、以降は最後まで自走する（フェーズ間でユーザー承認を挟まない）

## Workflow Overview

```text
Phase 0: 指示の受領と解釈
  修正指示の特定 → 現行 spec/ の把握 → 指示台帳の作成
  → 不明点をまとめてユーザーに一括確認 → 以降は自走

Phase 1: 影響分析
  指示台帳 × 現行設計 → 影響マップ（成果物ごとの変更要否と理由）

Phase 1.5: 規模判定（ルート分岐）
  影響マップから改訂の規模を判定 → 軽量ルート / 標準ルート を決定
  → 以降の Phase 2・Phase 4 の重さがルートで変わる

Phase 2: 設計再検討
  影響範囲についてゼロベースで最適設計を再導出
  → 代替案の比較 → 採用案の決定
  （軽量ルートは代替案の比較文書化を省く）

Phase 3: spec/ 更新
  シナリオ → ページ → ドメイン → ユースケース → DB → テストケース → マニュアルテスト
  の順に、影響のある成果物だけを更新 → spec/index.md 更新

Phase 4: レビューループ
  標準ルート: 指示対応性 × 設計妥当性 の2視点で並列レビュー
    → 修正 → 再レビュー（`fix` 0件になるまで、最大5ラウンド）
  軽量ルート: 1体が2視点をまとめて1ラウンド
    → `fix` が1件でも出たら標準ルートへ昇格
```

途中のフェーズから再開する場合は、`spec/review/revise/` 配下の既存成果物を確認して該当フェーズから開始する。

## Phase 1: 影響分析

指示台帳の各項目について、現行の成果物のどこに影響するかを洗い出し、影響マップを作成する。

対象とする成果物のチェーン:

- `spec/scenario/` — ユーザー体験・シナリオ
- `spec/pages/` — 画面構成
- `spec/domains/` — ドメインモデル・ポート契約
- `spec/usecases/` — ユースケース
- `spec/testcases/` — テストケース（ユースケーステスト・ポート適合テスト）
- `spec/manual-tests/` — マニュアルテスト

影響マップには成果物ごとに以下を記録する:

- **変更の要否**: 変更する / 変更しない
- **理由**: どの指示項目からどう波及するか。「変更しない」にも理由を書く（指示と無関係、または現行のままで整合する等）
- **変更の方向性**: 何をどう変えるかの概要（詳細は Phase 2 で決める）

指示が直接言及していなくても、整合性が崩れる成果物は「変更する」に含める。出力先: `spec/review/revise/impact-map.md`

## Phase 1.5: 規模判定（ルート分岐）

影響マップをもとにルートを決め、以降のフェーズの重さを揃える。

**軽量ルート** — 次の両方が成り立つとき:

- 「変更する」とした成果物より下流がすべて「変更しない」
- 既存の構造・命名・契約にそのまま乗り、ゼロベースで考え直しても既存設計と同じ答えになる

**標準ルート** — 次のいずれかに当たるとき:

- ドメインモデル・集約境界・ポート契約に触れる
- 既存 spec の設計前提が変わる
- 複数の成果物にまたがり、どこに責務を置くかを決め直す必要がある

グレーな改訂は**標準側に倒す**。設計の劣化は実装まで波及してから発覚するため、軽くして得られる時間より失うものが大きい。

| フェーズ | 軽量ルート | 標準ルート |
| --- | --- | --- |
| Phase 2 | ゼロベース再検討のみ（代替案の比較文書化を省く） | 代替案の比較 → 採用案の決定（比較は完了サマリーで報告） |
| Phase 4 | 1体が2視点をまとめて1ラウンド | 2視点を並列レビュー → 修正ループ（最大5ラウンド） |

Phase 0・1・3 はルートによらず同じ。省くのは検討の記録と検証の厚みだけで、**判定・波及の追跡・更新そのものは削らない**。

判定結果は理由とともに影響マップ（`spec/review/revise/impact-map.md`）の冒頭に一行で記録する（例: 「`spec/pages/` の表示項目の追加のみ・下流波及なし → 軽量ルート」）。

### 標準ルートへの昇格

軽量ルートで進めている途中に次のいずれかが起きたら、その時点で標準ルートへ切り替える（逆方向の格下げはしない）:

- Phase 2 で代替案の比較を要する非自明な判断が出た
- Phase 3 で影響マップにない成果物を触る必要が生じた
- Phase 4 のレビューで `fix` と仕分けた指摘が1件でも出た

昇格したら影響マップの記録を更新し、該当フェーズを標準ルートの手順でやり直す。

## Phase 2: 設計再検討

影響マップで「変更する」とした範囲について、設計を再導出する。

1. **ゼロベースで考える**: 「新要件が最初から存在していたら、この範囲をどう設計するか」を既存設計を見ずに構想する
2. **代替案を比較する**: 少なくとも「既存設計への最小変更案」と「ゼロベース案」を比較する。両者が一致すればそのまま採用。乖離する場合は、設計品質・変更コスト・将来の拡張性を比較して採用案を決める
3. **既存 spec と突き合わせる**: 採用案が既存 spec の設計と矛盾する場合、その設計の前提が新要件で変化したのかを確認する。変化したなら Phase 3 で spec を新しい現在形に書き換え、していないなら採用案を再考する
4. **判断の経緯を報告する**: 採用案・不採用の代替案・トレードオフは完了サマリーとコミットメッセージで報告する（spec には結果だけを書く）

軽量ルートでは 2 の比較の文書化を省き、1 と 3 だけを行う。比較を要する非自明な判断が出た時点で標準ルートへ昇格する（Phase 1.5）。

設計再検討の粒度は spec / spec-domain スキルと同じ基準に従う: Issue をまたぐ決定（ドメイン境界・用語・ビジネスルール・ポート契約）は型とシグネチャまで詰め、Issue 内で閉じる詳細（入出力の全フィールド・エラー分岐の網羅・境界値・処理手順）は書かず実装フェーズに委ねる。

## Phase 3: spec/ 更新

採用した設計に沿って、影響のある成果物を上流から下流の順に更新する:

1. シナリオ (`spec/scenario/`)
2. ページ (`spec/pages/`)
3. ドメイン (`spec/domains/`)
4. ユースケース (`spec/usecases/`)
5. テストケース (`spec/testcases/`)
6. マニュアルテスト (`spec/manual-tests/`)

各成果物のフォーマット・記載粒度は、既存ドキュメントの形式に合わせる。判断に迷う場合は spec スキル（`../spec/references/`）・spec-domain スキル（`../spec-domain/references/`）の各ガイドを参照する。

更新時の原則:

- 変更箇所だけを差し替えるのではなく、更新後のドキュメントが単体で一貫して読めるかを確認する（旧要件の記述の残骸を残さない）
- 影響マップで「変更しない」とした成果物には手を付けない
- 完了後、`spec/index.md` を更新する

## Phase 4: レビューループ

`references/review-guide.md` を読み、その手順に従ってレビューを行う。共通構造は `_shared/references/review-loop.md` と `_shared/references/spec-review.md` に従う。**指摘の受理基準**（上流・指示台帳の記述を引用できない指摘は受理せず実装フェーズに委ねる）は委譲プロンプトで必ず伝える。

レビューの視点は2つ。ルートによらず両方を見る:

1. **指示対応性レビュー**: 指示台帳のすべての項目が過不足なく設計に反映されているか
2. **設計妥当性レビュー**: 改訂後の設計が、改訂の経緯を知らない読者にとって一貫した最適な設計になっているか

回し方は Phase 1.5 で決めたルートに従う:

- **標準ルート** — 2視点を独立したレビューとして並列に実施する。問題があれば該当フェーズ（多くは Phase 2〜3）に戻って修正し、再レビューする。**`fix` と仕分けた指摘が0件のラウンドで完了**（台帳に記録済みの指摘は件数に含めない）。最大5ラウンドで収束しない場合は、残った指摘をまとめてユーザーに報告し判断を委ねる
- **軽量ルート** — 1体のレビュアーが2視点をまとめて1ラウンドだけ実施する。`fix` と仕分けた指摘が0件ならそのまま完了。**1件でもあれば標準ルートへ昇格**し、修正後は2視点の並列レビューでラウンドを続ける（連番は続きから、上限は同じく5ラウンド）

出力先: `spec/review/revise/${連番}.md`（2視点を1ファイルにまとめる）。指摘の仕分けは `spec/review/revise/triage.md` に記録する。

## 完了報告

レビューが完了したら `spec/review/revise/` を削除する。指示台帳・影響マップ・レビュー記録は改訂実行中の作業ファイルで、結果は spec/ 本体に反映済みのため残す必要はない（残すと後続セッションの検索に紛れ込んでコンテキストを浪費する）。**最大ラウンドに達して収束しなかった場合は削除せず**、残った指摘とともにユーザーに報告する。

そのうえで、改訂のサマリーを出す。

```text
設計の改訂が完了しました！

## 対応した指示
- {指示項目の要約} (x{数} 件)

## ルート
- {軽量 / 標準}（判定理由: {一行}）{／Phase {N} で標準へ昇格: {理由}}

## 更新した成果物
- spec/scenario/... (変更内容の一行要約)
- spec/domains/...
- ...

## 変更しなかった成果物と理由
- spec/testcases/ports/{port}.md — {理由}

## 主要な設計判断
- {採用案と不採用の代替案・トレードオフの一行要約}

## レビュー
- {数}ラウンドで収束（spec/review/revise/ は削除済み。未収束の場合のみ参照）
```

## 原則

- 指示の字面ではなく意図に応える — ただし意図の解釈に幅があるときは Phase 0 で確認し、勝手に補完しない
- グレーな改訂は標準ルートに倒す — 軽量で想定外の重さが出たら昇格し、格下げはしない
- 要件に対応しない記述を足さない — 実装時に決まる詳細は issue-planner に委ねる
- 波及は追い切り、スコープ外には手を出さない — 判断の根拠は影響マップに残す
