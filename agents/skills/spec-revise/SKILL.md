# Spec Revise

修正指示を受け、既存の `spec/` を Implementation Ready な状態へ改訂する。完了の定義・層・独立した読み・不変条件・予算は `../_shared/references/spec-ready.md` に従う。このスキルが定めるのは契約・範囲・条件の読み替え。

改訂は、指示の字面への最小のパッチではない。指示が届く範囲について、新しい要求が最初からあった場合の設計を導き、既存の成果物をその設計に揃える。最小のパッチを重ねた設計は、改訂のたびに例外と曖昧な分岐が増える。

## 契約

出典は修正指示（プロンプト、または指定されたファイル）。指示の所在が分からなければユーザーに聞く。`spec/review/contract.md` に次の 2 つを置く。

### 指示台帳

指示を要求項目に分解した番号付きの一覧。各項目は「何を・なぜ変えたいのか」の一行を持つ。

### 影響マップ

層の成果物ごとに、次の 3 つを持つ。

- 変更の要否: 変更する / 変更しない
- 理由: どの指示項目からどう波及するか。「変更しない」にも理由を書く
- 変更の方向性: 何をどう変えるかの概要

指示が直接言及していない成果物でも、整合が崩れるなら「変更する」にする。

## 範囲

影響マップで「変更する」とした成果物。「変更しない」とした成果物は範囲の外にある。設計の途中で影響マップにない成果物を変える必要が出たら、影響マップを先に更新する。

## 条件の読み替え

完了の定義の 7 条件を、改訂では次のように読む。

### 1. 要求を取りこぼしていない

- 上流は指示台帳と、改訂後の上流の層
- 指示台帳のすべての項目が、字面ではなく意図のとおりに反映されている
- 指示の影響が最下流の層まで伝播している

反例の形: 指示台帳の項目の引用と、未反映・意図と食い違う反映・旧仕様のままの下流の場所

### 2. 足しすぎていない

- 指示から導かれない変更がない
- 影響マップで「変更しない」とした成果物が変わっていない

反例の形: 変更箇所の引用と、指示台帳に引用元がないこと

### 4. 矛盾がなく、現在形で単体で読める

- 旧要求に基づく記述・図・テストケースが残っていない
- 更新したファイルが、改訂の経緯を知らない読者に単体で一貫して読める
- 改訂した部分と既存の部分で、命名と粒度が揃っている

### 7. 次の改訂が前より高くつかない設計である

- 改訂後の設計が、新しい要求が最初からあった場合の設計と一致している
- 一致しない箇所は、変更コストを理由に既存の構造を残している。既存の構造を「最適だから残す」のか「変更コストが低いから残す」のかを述べられる

反例の形: 既存の構造を残したために生じた曖昧な分岐や例外と、それが消える代案

根拠: 最小変更案とゼロベース案の比較

## 独立した読み

spec の読みには、改訂で変えたファイルの一覧を足す。旧仕様の本文と、自分が設計を再検討した経緯は渡さない。読み手は改訂後の spec を、経緯を知らない読者として読む。

## ユーザーに聞く場面

`spec-ready.md` の場面に加え、指示の解釈が分かれる・指示どうしが矛盾する・指示が現行設計の前提を壊すときに聞く。読み手の指摘が指示台帳の読み方に関わるときも、直さずに聞く。

## 派生物

- `spec/manual-tests/` は、範囲の成果物に対応するシナリオを `../spec-manual-test/SKILL.md` で更新する
- `spec/inventory/` は、存在するときだけ、変えた spec ファイルに対応する行を追加・修正・削除する

## 成果物の形式

既存のドキュメントの形式と粒度に合わせる。
