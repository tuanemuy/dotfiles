# Spec Revise レビューガイド

改訂後の spec/ を「指示対応性」と「設計妥当性」の2視点でレビューする。共通構造は `_shared/references/review-loop.md`（出力フォーマット・指摘台帳・修正ループ・サブエージェント運用）と `_shared/references/spec-review.md`（**指摘の受理基準**・完了条件）に従う。本ガイドは spec-revise 固有のレビュー観点を定義する。

## レビューの進め方

- 各レビュアーには「指示台帳（instructions.md）」「影響マップ（impact-map.md）」「改訂後の spec/」を渡す。前ラウンドのレビューファイルは渡さない（ゼロベースの独立レビュー）
- 結果は `spec/review/revise/${連番}.md` に2視点をまとめて記録する
- 指摘の仕分けは `spec/review/revise/triage.md` で管理する

体制は `../SKILL.md` Phase 1.5 で決めたルートに従う:

- **標準ルート** — 2視点をそれぞれ独立したサブエージェント（**審査区分**）で並列にレビューする
- **軽量ルート** — 1体（**審査区分**）が2視点を続けて担当し、1ファイルにまとめて出す

## 軽量ルートのレビュー

軽量ルートでも**チェック項目は落とさない**。視点1・視点2の項目をすべて通し、1ラウンドで判定する。

- `fix` と仕分けた指摘が0件 → 完了
- `fix` が1件でもある → **標準ルートへ昇格**。修正後は2視点の並列レビューに切り替えてラウンドを続ける（連番は続きから、上限5ラウンド）

`fix` が出た時点で軽量と判断した根拠は崩れている。同じ体制で追いかけず、体制を戻してから修正する。

## 視点1: 指示対応性

指示台帳を基準に、指示への対応が過不足ないかを確認する。

### チェック項目

- **網羅性**: 指示台帳のすべての項目が設計に反映されているか。部分的にしか対応していない項目はないか
- **正確性**: 反映の内容が指示の意図と一致しているか。字面だけ満たして意図を外していないか
- **波及の完全性**: 指示の影響が下流の成果物（ユースケース・DB・テストケース・マニュアルテスト）まで伝播しているか。上流だけ直して下流が旧仕様のままになっていないか
- **スコープ遵守**: 指示から導かれない変更が紛れ込んでいないか。影響マップで「変更しない」とした成果物が変更されていないか
- **残骸の除去**: 旧要件に基づく記述・図・テストケースが残っていないか

### Blocker 基準（視点1固有）

- 指示台帳の項目に未対応・誤対応がある
- 指示の波及が下流成果物に伝播していない
- 旧要件の記述が残り、新旧が混在して矛盾している

## 視点2: 設計妥当性

改訂の経緯を知らない読者として、改訂後の spec/ が一貫した設計として読めるかを確認する。

### チェック項目

- **アーキテクチャ適合性**: spec-domain スキルのアーキテクチャ制約（ドメインの独立性・ビジネスロジックの配置・集約境界・ポートによる抽象化・ドメイン間の非循環）に違反していないか
- **トレーサビリティ**: シナリオ → ページ → ドメイン → ユースケース → テストケースのチェーンが改訂後も切れていないか
- **設計の一貫性**: 改訂部分と既存部分で命名・粒度が揃っているか。「継ぎ足した」跡が読み取れる箇所はないか
- **場当たり検出**: 新要件に対して既存構造を無理に温存した歪み（責務の曖昧な分岐、例外だらけのルール）がないか
- **履歴の混入検出**: 改訂後の spec に経緯・旧仕様の痕跡（「以前は」「〜から変更」等）が残っていないか。spec は現在形で単体一貫して読めること

### Blocker 基準（視点2固有）

- トレーサビリティのチェーンが切れている
- アーキテクチャ制約への違反
- Issue をまたぐ決定（ドメイン境界・用語・ビジネスルール・ポート契約）が未定義のまま残っている
- 旧仕様の記述が新しい設計と矛盾したまま残っている

**記述を増やす方向の指摘は出さない。** 改訂後の spec に「エラーケースが足りない」「境界値が未定義」と感じても、指示台帳と上流の成果物に対応する記述を引用できないなら指摘にしない（`../../_shared/references/spec-review.md` の受理基準）。粒度の不足は指摘の対象だが、それは**同じ成果物の既存要素と比べて明らかに粗い**ときに限る。

## 修正と再レビュー

- Blocker・Warning の修正は `_shared/references/review-loop.md` の修正ループに従う
- 指示の解釈そのものに関わる指摘（指示台帳の読み方が分かれる等）は、修正せずユーザーに確認する
- 設計の再検討が必要な指摘は Phase 2 に、反映漏れは Phase 3 に戻って対応する
- 最大5ラウンドで収束しない場合は、残った指摘をまとめてユーザーに報告する
