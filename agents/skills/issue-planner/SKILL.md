# Issue Planner

GitHub Issue に対する実装計画を、1 人のプランナーが作り、方針レビュー 1 周で確かめるスキル。計画が決めるのは方針（受け入れ基準・スコープ・設計の置き場所・型と契約の形）で、コードの書き方は実装フェーズが決める。

## Workflow Overview

```
Issue取得 → spec-slice判定 → 規模判定（小規模 / 通常）
  → [spec-slice] ファストパス: spec とチェックリストから転記ベースで plan.md / steps.md 作成
    → レビューなし → 完了
  → [小規模] プランナー1体（判断区分）で plan.md / steps.md 作成 → レビューなし → 完了
  → [通常] プランナー1体（審査区分）で plan.md / steps.md 作成
    → 設計判断があれば adr.md に記録
    → 方針レビュー1周: レビュアー1体 → 取り込む問題点を反映 → 再レビューなし
    → 足場（plan-review/）を削除して完了
```

計画の成果物はライフサイクルで分ける（詳細は `references/plan-template.md`）:

| ファイル | 役割 | 寿命 |
| --- | --- | --- |
| `plan.md` | 契約 — 目的 / 受け入れ基準 / スコープ / リスク / テスト方針 | 全フェーズが読む |
| `steps.md` | 設計と手順の意図 | 実装フェーズまで |
| `plan-review/` | 足場 — レビューファイル・台帳 | 凍結時に削除 |
| `adr.md` | 設計判断の唯一の記録先 | 恒久 |

## Step 1: Issue の取得と分析

Issue番号またはURLを受け取ったら、まず内容を把握する。

```bash
git fetch origin
gh issue view <Issue番号> --json title,body,labels,assignees,milestone,comments
```

調査対象のコードが古いままだと、既に解決済みの問題を前提に計画してしまう。`git fetch origin` でリモートを取り込んだうえで、ローカルの作業ツリーがベースブランチ（通常 `origin/main`）から大きく遅れていないかを `git status -sb` で確認する。遅れている場合はユーザーに取り込みを確認してから進める。

Issueが取得できない場合（番号違い、権限不足、リポジトリ違いなど）はユーザーに確認して正しい情報を得る。推測で進めない。

Issueの内容を読み、以下を整理する:
- **目的**: このIssueは何を達成したいのか
- **要件**: 具体的に何が求められているか
- **制約**: 明示的・暗黙的な制約はあるか
- **スコープ**: Issueの範囲に含まれるもの・含まれないもの
- **コメントの要点**: コメント欄での議論・方針変更・合意事項があれば要約する（コメントには最新の合意や却下されたアプローチなど重要な情報が含まれることが多い）

### 既存計画の確認

`.thread/{Issue番号}/plan.md` が既に存在するかチェックする。存在する場合はユーザーに以下を確認する:
- 既存の計画を上書きして新しく作り直すか
- 既存の計画をベースに更新するか

ユーザーの指示に従って進める。

### spec-slice Issue のファストパス

Issue 本文の先頭に `<!-- spec-slice -->` マーカーがある場合（spec-to-issues が起票した縦スライス Issue）、フルの計画フローを通さない。spec は Issue をまたぐ決定（用語・境界・ビジネスルール・ポート契約）がレビュー済みで、Issue 本文にはチェックリスト（`spec/inventory/` 由来）・依存・検証方法が自己完結で書かれている — 計画はこの2つからの**転記**であって再導出ではない。spec が持たない実装詳細（DTO のフィールド・エラー分岐・境界値）は steps.md で先取りせず、実装フェーズがコードを読んで決める。

サブエージェント1体（**審査区分**）に plan.md / steps.md を作らせる:

- **plan.md** — 目的は Issue 本文の「目的」から。受け入れ基準の表にはチェックリスト全行を転記せず、「実装チェックリスト全行の実装（Issue #{番号} 本文参照。スタブ・仮実装不可）」を1行の基準とし、対象シナリオが end-to-end で動くことをシナリオレベルの基準として添える。スコープは対象シナリオと依存 Issue から、テスト方針はチェックリストの TC 行から書く。**規模メタデータは「通常」と記録する**（ファストパスで省略するのは計画レビューだけで、Phase 3 の実装レビューはフルで行う）
- **steps.md** — 「設計」セクションは新規設計せず、チェックリスト行の定義場所（`spec/domains/` 等）への参照で埋める。「実装ステップ」はチェックリスト行をレイヤーの依存順（domain → adapter → usecase → frontend → test）に並べ替えて束ねたもの。各ステップに対応する台帳 ID と spec の参照先を書く

Step 3（ADR）は転記中に設計判断が生じた場合のみ。**Step 4（方針レビュー）はスキップする** — 計画の妥当性は spec のレビューループで担保済みで、転記に再レビューを重ねない。転記元の spec と Issue 本文が矛盾している場合だけは機械的に進めず、ユーザーに確認する。

受け入れ基準の観測方法は Issue 本文の「検証」から書く。Step 5 の完了報告には方針レビューの行の代わりに「spec-slice ファストパス（計画レビュー省略）」と記す。

### 規模の判定

判定するのは「方針レビューを回すか」と「プランナーの区分」。**2択。** issue-implement から呼ばれた場合は Phase 0 の判定（小規模 / フル → 通常）をそのまま使い、判定し直さない。

- **小規模** — 影響が 10 ファイル程度以内に収まり、トレードオフのある設計判断が無い（直し方が Issue 本文と現場確認で決まる）。プランナー1体（**判断区分**）に plan.md / steps.md を書かせる。Step 3（ADR）は不要、Step 4（方針レビュー）はスキップし、Step 5（凍結・完了報告）へ進む
- **通常** — 小規模と言い切れないもの。Step 2 でプランナー（**審査区分**）が初稿を作り、Step 4 の方針レビューを 1 周回す

plan.md には `**規模:** 小規模` / `**規模:** 通常` のどちらかを記録する。実装レビューの担当数は実際の差分から決まり、この判定は効かない。

## Step 2: 実装計画の作成

サブエージェントを1つ起動して初稿を作成する（区分は規模判定に従う。委譲方式とモデル選択は `../_shared/references/subagent-policy.md` に従う）。

プランナーは各ファイルを**直接書き込み**、メインには短いサマリーだけを返す。計画全文をメインのコンテキストに往復させない。テンプレートは本スキルの `references/plan-template.md` にあり、メインはプロンプトにその**絶対パス**を埋めて渡す（テンプレート本文は転記しない）。

計画が決めるのは方針で、コードの書き方ではない。plan.md は契約（目安 5KB）、steps.md は設計の決定と手順の意図（目安 10KB）に収める。実装レベルの記述（コードの書き方・モック配線・呼び出し件数・行番号・テスト名）は書かない。実装フェーズがコードを読んで決め、実装レビューが結果を見る。

### エージェントへのプロンプト

```
あなたはIssueの実装計画を立てるエンジニアです。
Issueの要件を満たし、**プロジェクトとしてあるべきアーキテクチャ**に沿った実装計画を立ててください。

## 対象Issue
- Issue番号: #{Issue番号}
- タイトル: {タイトル}
- 内容:
{Issueの本文}
- コメント・議論の要点:
{関連するコメントの要約 — 方針変更や合意事項があれば必ず含める}

## やること
1. `gh issue view {Issue番号}` でIssueの詳細とコメントを確認する
2. **プロジェクトのあるべきアーキテクチャを把握する** — `spec/` 配下の設計ドキュメント、`CLAUDE.md`、`README.md`、アーキテクチャ関連ドキュメントを読み、プロジェクトが目指している設計・レイヤー構造・規約を理解する
3. Issueに関連する既存のコードを調査する。読むのは変更に関わる範囲（対象のユースケース・ポート・画面と、その呼び出し元）に絞る
4. 既存コードが「あるべき姿」と一致しているか、それとも乖離しているかを判断する
5. 実装計画を立て、{plan-template.md の絶対パス} のテンプレートに従って**直接書き込む**（規模メタデータは「{規模}」と記載）:
   - `.thread/{Issue番号}/plan.md` — 契約。目安 5KB
   - `.thread/{Issue番号}/steps.md` — 設計の決定と手順の意図。目安 10KB
   テンプレートに無いセクションは足さない
6. 技術的な設計判断（アーキテクチャ・データモデル・ライブラリ選定など、トレードオフのある選択）があれば、同テンプレートの形式で `.thread/{Issue番号}/adr.md` にも書く。なければ作らない。**設計判断の記録先は adr.md だけ** — plan.md / steps.md に要約を重複させない

## 重要な原則
- **Issueの要件を満たすことに集中する** — スコープ外の改善やリファクタリングは含めない
- **計画が決めるのは方針** — 何を満たすか（受け入れ基準）、どこまでやるか（スコープ）、何をどのレイヤーに置くか、型と契約の形（DTO の形・ポートのシグネチャ・エラーの種別）。分岐の書き方・境界値・処理手順・モックの配線・テストの中身・呼び出し箇所の件数・行番号は書かない。実装フェーズがコードを読んで決める
- **設計はレイヤーの内側から考える** — ファイル変更の列挙から入らない。バックエンドに触れる変更ならまずドメインモデルへの影響（エンティティ・値オブジェクト・不変条件・ポート）から設計し、ユースケース → アダプター → UI の順に外側へ広げ、実装ステップはその設計から導出する
- **spec に無いことは設計漏れではない** — `spec/` が持つのは Issue をまたぐ決定（用語・ドメインと境界・ビジネスルール・ポート契約・画面構成）だけ。型と契約の形はこの計画が決める。決めた結果が spec の持ち分（境界・用語・ルール・契約）を変えるなら、それは spec-revise の領分なので adr.md に記録して報告する
- **既存コードを盲目的に模倣しない** — 既存コードはあくまで現状の参考。プロジェクトのあるべきアーキテクチャ・設計ドキュメントが正であり、既存実装がそれと乖離している場合は、Issue範囲内で理想形に寄せる
- 既存コードと理想形が一致している箇所では、確立されたパターンを尊重する
- 変更の影響範囲を明確にする

## 返答（計画全文は返さない）
ファイルへの書き込みが済んだら、返答には**サマリーだけ**を返す:
- 実装方針の要約（1-2文）
- 実装ステップ数
- 設計判断の有無（adr.md を作成したか）
- 主要なリスク（一行ずつ）
- 判断に迷った点（あれば）
```

エージェントが失敗・タイムアウトした場合は、自分で同じ手順をなぞって計画ファイルを作成する。

## Step 3: ADR の確認

ADR はプランナーが Step 2 で必要に応じて作成済み。メインはサマリーで有無を把握するだけでよい（内容の転記・整形はしない）。方針レビューの反映で新たな設計判断が生じた場合は、反映を担当するサブエージェントが adr.md に追記する。

## Step 4: 方針レビュー（1周）

計画ファイルが揃ったら、レビュアー1体（**審査区分**）に方針だけを見させ、取り込む問題点を反映用サブエージェント（**判断区分**）で反映して終える。**反映後の再レビューは行わない**（委譲方式とモデル選択は `../_shared/references/subagent-policy.md` に従う）。

方針の誤りは実装を丸ごと無駄にするため、実装前に 1 周で確かめる。plan.md と steps.md の相互整合・ステップの順序・文言・観測方法の手段は実装フェーズと実装レビューが吸収するため、ここでは見ない。

### 流れ

1. レビュアー1体を起動する。レビュー全文を `.thread/{Issue番号}/plan-review/round-1.md` に**直接書き**、メインには件数と指摘の一行リストだけを返す
2. メインは一行リストを見て、取り込む問題点と見送る問題点を決める（同じ問題の指摘は1件として扱う）。判定を `.thread/{Issue番号}/plan-review/triage.md` に `_shared/references/review-loop.md` の指摘台帳方式で記録する（「取り込む」= `fix`、「見送る」= `wont-fix`）。判断が割れる問題点はユーザーに確認する
3. 取り込む問題点があれば、**反映用サブエージェント（判断区分）を1つ起動**して修正させる。渡すもの: レビューファイルのパス、plan.md / steps.md / adr.md のパス、取り込む問題点の ID と対応方針。サブエージェントは該当ファイルを修正し、設計判断があれば adr.md に追記し、変更点の一行サマリーだけ返す。反映で plan.md / steps.md が目安のサイズを超えた場合は、削って収める
4. 見送った問題点のうち実装フェーズが知るべきものは、plan.md 末尾の「未解決事項」に反映用サブエージェントが書く

レビュアーが中断した場合は1回だけ再委譲する。それでも中断したらレビューなしで Step 5 に進み、完了報告に「方針レビュー未実施」と記す。

### レビュアーのテンプレート

```
あなたはIssueの実装計画の方針をレビューするエンジニアです。

## レビュー対象（.thread/{Issue番号}/ 配下）
- `plan.md` — 契約
- `steps.md` — 設計と手順の意図
- `adr.md` — 設計判断（存在する場合）

## やること
1. `gh issue view {Issue番号}` でIssueの要件とコメントでの議論を確認する
2. `plan.md` と `steps.md`（あれば `adr.md`）を読む
3. `spec/` 配下の設計ドキュメント・`CLAUDE.md` を読み、プロジェクトが目指している設計・レイヤー構造・規約を把握する
4. 計画が前提にしている既存コードの事実（呼び出し関係・既存の型・契約）を、該当ファイルを読んで確かめる
5. 下記の観点でレビューし、結果を `.thread/{Issue番号}/plan-review/round-1.md` に**直接書き込む**

## 観点（これ以外は指摘しない）
- **要件の漏れ・逸脱**: Issue 本文・コメントで合意された要件が受け入れ基準に落ちているか。受け入れ基準が Issue の意図と違うものを満たそうとしていないか。スコープ外の作業が紛れていないか
- **実コードと矛盾する前提**: 計画が前提にしている既存コードの事実（呼び出し関係・型・契約・挙動）が実物と合っているか。計測せず推定を事実として書いた箇所がないか
- **アーキテクチャ・spec との矛盾**: ロジックの置き場所がレイヤーの責務に合っているか。spec の持ち分（用語・境界・ビジネスルール・ポート契約・画面構成）に矛盾していないか。持ち分を変えるのに adr.md に記録がない箇所はないか
- **設計判断の選択肢漏れ**: adr.md の判断で、検討すべき選択肢（ドメイン層に置く等）が抜けていないか。トレードオフの評価が事実に基づいているか
- **実装の前提が成立しない箇所**: そのステップに着手できない、または着手すると既存機能が壊れる箇所

## 指摘しないもの
- 受け入れ基準と実装ステップの紐づけ、ステップの順序、件数・文言・見出しの不一致
- 観測方法の手段（実行できるか・セレクタ・コマンド）— testing.md と Phase 4 が扱う
- 記述の追加・具体化の提案。計画は方針を決める文書で、実装レベルの記述は実装フェーズが決める
- `spec/` に無い型と契約の形を計画が決めていること。spec は Issue をまたぐ決定だけを持つ

## 重要な原則
- Issueのコメント欄での議論・合意事項と計画が矛盾していないか確認する
- 問題点が見当たらない場合は「問題点ゼロ」と明示する
- 指摘は方針の誤りだけ。細部の整合は書かない

## レビューファイルのフォーマット

#### 問題点
- **[P-001]** {問題の説明}
  - 場所: {plan.md / steps.md 等のファイルとセクション}
  - 理由: {なぜ方針として誤りか。実コード・spec・Issue のどれと矛盾するか}
  - 提案: {どう修正すべきか}

（問題点がなければ「問題点ゼロ」と明記）

## 返答（レビュー全文は返さない）
ファイルへの書き込みが済んだら、返答には**サマリーだけ**を返す:
- 問題点: {数}
- 各指摘の一行リスト: `[P-001] {場所} — {タイトル}`

**この2項目だけ。** 分析の経緯・引用・提案の再掲は返さない（詳細はレビューファイルにある）。
```

## Step 5: 計画の凍結・完了報告

完了報告の前に足場ファイルを削除する。残したままにすると後続セッションの検索に紛れ込んでコンテキストを浪費する。

```bash
rm -rf .thread/{Issue番号}/plan-review/
```

削除の前に、恒久的に残す価値があるものを転記済みか確認する:

- **設計判断** → adr.md に書かれているか
- **見送った問題点のうち実装フェーズが知るべきもの** → plan.md 末尾の「未解決事項」に書かれているか

**成果物（plan.md / steps.md / adr.md）は残す。**

計画が完成したら、サマリーを出す。小規模Issueの場合は該当しない項目を省略する。

```
Issue #{Issue番号} の実装計画が完成しました！

- 契約: .thread/{Issue番号}/plan.md（{KB}）
- 設計と手順: .thread/{Issue番号}/steps.md（ステップ数: {数}、{KB}）
- 設計判断: .thread/{Issue番号}/adr.md（{あり/なし}）
- 方針レビュー: 問題点 {数}件（取り込み {数} / 見送り {数}） / 小規模のため省略 / 未実施（レビュアー中断）
- 未解決事項: {数}件（あれば plan.md 末尾を参照）
- 足場: 削除済み（plan-review/）
```
