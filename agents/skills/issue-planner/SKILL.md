# Issue Planner

GitHub Issueに対する実装計画を、1人のプランナーが初稿を作成し、2視点並列レビュー → 修正のループ（最大3周）で磨き込むスキル。

## Workflow Overview

```
Issue取得 → 複雑度判定
  → [小規模] 直接プランニング → plan.md / steps.md 作成 → testing.md作成 → 完了
  → [中〜大規模] 1プランナーで初稿作成 → plan.md / steps.md / research.md 作成
    → 設計判断があれば adr.md に記録
    → レビューループ（最大3周）:
       2視点並列レビュー（要件カバレッジ / アーキ・リスク）
       → 問題点を plan.md / steps.md に反映
       → 全レビュアーが「問題なし」なら終了、未解決なら再レビュー
    → 動作確認計画を testing.md に作成
    → 足場（research.md / plan-review/）を削除して完了
```

計画の成果物はライフサイクルで分ける（詳細は `references/plan-template.md`）:

| ファイル | 役割 | 寿命 |
| --- | --- | --- |
| `plan.md` | 契約 — 目的 / 受け入れ基準 / スコープ / リスク / テスト方針 | 全フェーズが読む |
| `steps.md` | 手順 — 設計 / 実装ステップ | 実装フェーズまで |
| `research.md` | 足場 — 調査結果 | 凍結時に削除 |
| `plan-review/` | 足場 — レビューファイル・台帳・履歴 | 凍結時に削除 |
| `adr.md` | 設計判断の唯一の記録先 | 恒久 |

## Step 1: Issue の取得と分析

Issue番号またはURLを受け取ったら、まず内容を把握する。

```bash
gh issue view <Issue番号> --json title,body,labels,assignees,milestone,comments
```

Issueが取得できない場合（番号違い、権限不足、リポジトリ違いなど）はユーザーに確認して正しい情報を得る。推測で進めない。

Issueの内容を読み、以下を整理する:
- **目的**: このIssueは何を達成したいのか
- **要件**: 具体的に何が求められているか
- **制約**: 明示的・暗黙的な制約はあるか
- **スコープ**: Issueの範囲に含まれるもの・含まれないもの
- **コメントの要点**: コメント欄での議論・方針変更・合意事項があれば要約する（コメントには最新の合意や却下されたアプローチなど重要な情報が含まれることが多い）

### 既存計画の確認

`.thread/{Issue番号}/plan.md` が既に存在するかチェックする。存在する場合はユーザーに以下を確認する:
- 既存の計画を上書きして新しく作り直すか
- 既存の計画をベースに更新するか

ユーザーの指示に従って進める。

### 複雑度の判定

Issueの内容から複雑度を判定する:

- **小規模**: 変更対象が1-2ファイル程度で、修正内容が明確（typo修正、設定値変更、小さなバグ修正など）
- **中〜大規模**: 複数ファイルにまたがる変更、設計判断が必要、新機能追加、リファクタリングなど

**小規模の場合**: サブエージェントの委譲は行わず、自分で直接コードを調査して `references/plan-template.md` に沿って plan.md と steps.md を出力する（research.md は作らない。**複雑度メタデータには「小規模」と記録する** — 後段の issue-implement Phase 3 がこれを読んでレビューを単発化する）。Step 3（ADR）は不要、Step 4（レビューループ）もスキップし、Step 5（testing.md）→ Step 6（完了報告）に進む。

**中〜大規模の場合**: Step 2 に進み、1プランナーで初稿を作成する。**複雑度メタデータには「中〜大規模」と記録する**。

## Step 2: 実装計画の作成

サブエージェントを1つ起動して初稿を作成する（**判断区分**。委譲方式とモデル選択は `../_shared/references/subagent-policy.md` に従う）。後続のレビューループで品質を担保するため、プランナーには特定の視点を強く与えず、Issueの要件を満たすバランスの取れた計画を立てさせる。

トークン効率の原則: プランナーは各ファイルを**直接書き込み**、メインには短いサマリーだけを返す。計画全文をメインのコンテキストに往復させない。テンプレートは本スキルの `references/plan-template.md` にあり、メインはプロンプトにその**絶対パス**を埋めて渡す（テンプレート本文は転記しない）。

### エージェントへのプロンプト

```
あなたはIssueの実装計画を立てるエンジニアです。
Issueの要件を満たし、**プロジェクトとしてあるべきアーキテクチャ**に沿った実装計画を立ててください。

## 対象Issue
- Issue番号: #{Issue番号}
- タイトル: {タイトル}
- 内容:
{Issueの本文}
- コメント・議論の要点:
{関連するコメントの要約 — 方針変更や合意事項があれば必ず含める}

## やること
1. `gh issue view {Issue番号}` でIssueの詳細とコメントを確認する
2. **プロジェクトのあるべきアーキテクチャを把握する** — `spec/` 配下の設計ドキュメント、`CLAUDE.md`、`README.md`、アーキテクチャ関連ドキュメントを読み、プロジェクトが目指している設計・レイヤー構造・規約を理解する
3. Issueに関連する既存のコードを調査する（検索ツールやファイル参照ツールを使って徹底的に）
4. 既存コードが「あるべき姿」と一致しているか、それとも乖離しているかを判断する
5. 調査でわかったことを `.thread/{Issue番号}/research.md` に書く（ディレクトリがなければ作成）
6. 実装計画を立て、{plan-template.md の絶対パス} のテンプレートに従って**直接書き込む**（複雑度メタデータは「{複雑度}」と記載）:
   - `.thread/{Issue番号}/plan.md` — 契約
   - `.thread/{Issue番号}/steps.md` — 手順
   テンプレートは下限であって上限ではない — 必須項目を満たした上で、必要なセクション・分析は自由に足してよい
7. 技術的な設計判断（アーキテクチャ・データモデル・ライブラリ選定など、トレードオフのある選択）があれば、同テンプレートの形式で `.thread/{Issue番号}/adr.md` にも書く。なければ作らない。**設計判断の記録先は adr.md だけ** — plan.md / steps.md に要約を重複させない

## 重要な原則
- **Issueの要件を満たすことに集中する** — スコープ外の改善やリファクタリングは含めない
- **設計はレイヤーの内側から考える** — ファイル変更の列挙から入らない。バックエンドに触れる変更ならまずドメインモデルへの影響（エンティティ・値オブジェクト・不変条件・ポート）から設計し、ユースケース → アダプター → UI の順に外側へ広げ、実装ステップはその設計から導出する
- **既存コードを盲目的に模倣しない** — 既存コードはあくまで現状の参考。プロジェクトのあるべきアーキテクチャ・設計ドキュメントが正であり、既存実装がそれと乖離している場合は、Issue範囲内で理想形に寄せる
- 既存コードと理想形が一致している箇所では、確立されたパターンを尊重する
- 変更の影響範囲を明確にする

## 返答（計画全文は返さない）
ファイルへの書き込みが済んだら、返答には**サマリーだけ**を返す:
- 実装方針の要約（1-2文）
- 実装ステップ数
- 設計判断の有無（adr.md を作成したか）
- 主要なリスク（一行ずつ）
- 判断に迷った点（あれば）
```

エージェントが失敗・タイムアウトした場合は、自分で同じ手順をなぞって計画ファイルを作成する。

## Step 3: ADR の確認

ADR はプランナーが Step 2 で必要に応じて作成済み。メインはサマリーで有無を把握するだけでよい（内容の転記・整形はしない）。レビューループ中に新たな設計判断が生じた場合は、反映を担当するサブエージェントが adr.md に追記する。

## Step 4: レビューループ（最大3周）

計画ファイルが揃ったら、**2つのサブエージェントを並列に起動してレビュー → 反映** を最大3周繰り返す（レビュー・反映とも**判断区分**。委譲方式とモデル選択は `../_shared/references/subagent-policy.md` に従う）。各エージェントには異なる視点を与えることで、同一プロンプトで収束する問題を回避する。

レビューの観点は「要件カバレッジ」と「アーキテクチャ整合性・リスク」の2つに絞る — 計画段階で最も致命的になりやすい2点を集中的に検証する。Phase 3（実装後の PR レビュー）でレイヤー別の多角レビューが入る前提で、ここは要件と実現可能性の確認に振り切る。

### 終了条件

以下のいずれか先に到達したら終了:

- **その周で「取り込む」と仕分けた指摘がゼロ** — 全レビュアーが「問題点ゼロ」を報告した場合に加え、残った指摘がすべて見送り判定（台帳に記録済み）の場合も終了とする
- **3周完了** — 残課題があれば plan.md 末尾の「未解決事項」セクションに明記して終了し、実装フェーズに引き継ぐ

### 各周の流れ

1. 2エージェント並列でレビュー実施。各レビュアーはレビュー全文を `.thread/{Issue番号}/plan-review/round-{N}-{視点キー}.md` に**直接書き**、メインには件数と指摘の一行リストだけを返す（視点キー: `coverage` / `arch-risk`）
2. メインは一行リストを見て対応方針を決める（同じ問題の指摘は1件として扱う。改善提案はスコープ内で妥当なもののみ取り込む）。仕分けの判定は `_shared/references/review-loop.md` の指摘台帳方式で `.thread/{Issue番号}/plan-review/triage.md` に記録する（「取り込む」= `fix`、「見送る」= `wont-fix`）。Key が一致する既出指摘は判定を継承して再審議しない
3. 問題点があれば、**反映用サブエージェント（判断区分）を1つ起動**して修正させる。渡すもの: 該当周のレビューファイルのパス（2つ）、plan.md / steps.md / adr.md のパス、メインが決めた対応方針（取り込む/見送る指摘のIDと理由）。サブエージェントは該当ファイルを修正し、設計判断があれば adr.md に追記し、`.thread/{Issue番号}/plan-review/history.md` に反映内容を追記して（書式は `references/plan-template.md`）、変更点の一行サマリーだけ返す
4. その周で「取り込む」と仕分けた指摘がゼロなら終了（history.md に「{N}周目: 取り込む指摘ゼロで終了」と追記）、`fix` と仕分けた未解決の問題が残れば次の周に進む

いずれかのレビュアーが失敗・タイムアウトした場合は、成功した結果だけで進める。両方失敗した場合はその周をスキップして次の周に進む（連続2周失敗ならレビューループを打ち切り、未解決事項として記録）。

### 共通テンプレート

各エージェントには以下のテンプレートを渡す（**視点** の部分だけ差し替える）:

```
あなたはIssueの実装計画をレビューするエンジニアです。
あなたの視点: **{視点}**

## レビュー対象（.thread/{Issue番号}/ 配下）
- `plan.md` — 契約
- `steps.md` — 手順
- `research.md` — プランナーの調査結果（存在する場合）
- `adr.md` — 設計判断（存在する場合）

## やること
1. `gh issue view {Issue番号}` でIssueの要件とコメントでの議論を確認する
2. `plan.md` と `steps.md` を読む
3. `research.md` / `adr.md` が存在すれば読み、調査の妥当性・設計判断の妥当性も確認する
4. 計画に関連する既存コードを調査する
5. 上記の視点で計画をレビューし、結果を `.thread/{Issue番号}/plan-review/round-{周番号}-{視点キー}.md` に**直接書き込む**

## 重要な原則
- **Issueの要件を満たすかどうかが最重要** — スコープ外の提案はしない
- Issueのコメント欄での議論・合意事項と計画が矛盾していないか確認する
- 具体的で実行可能なフィードバックを出す
- 問題点が見当たらない場合は「問題点ゼロ」と明示する（無理に粗探しをしない）

## レビューファイルのフォーマット

#### 問題点（要修正）
- **[P-001]** {問題の説明}
  - 場所: {plan.md / steps.md 等のファイルとセクション}
  - 理由: {なぜ問題か}
  - 提案: {どう修正すべきか}

（問題点がなければ「問題点ゼロ」と明記）

#### 改善提案（検討推奨）
- **[S-001]** {提案の説明}
  - 場所: {対象のファイルとセクション}
  - 理由: {なぜ改善になるか}

このフォーマットは下限であって上限ではない。必須なのは ID 付きの指摘（P-/S-、理由・提案）だけ。
分析の過程・前提・調査で得た知見など、伝えるべきことがあれば自由にセクションを足して深く書いてよい。

## 返答（レビュー全文は返さない）
ファイルへの書き込みが済んだら、返答には**サマリーだけ**を返す:
- 問題点: {数} / 改善提案: {数}
- 各指摘の一行リスト: `[P-001] {場所} — {タイトル}` / `[S-001] {場所} — {タイトル}`
```

### 視点1: 要件カバレッジ・スコープ整合性

```
**Issueの要件カバレッジ・スコープ整合性** を重視してレビューしてください。plan.md の「受け入れ基準」表を起点に、(1) Issue本文・コメントで合意された要件がすべて基準に落ちているか（漏れた要件はないか）、(2) 各基準が検証可能な形で書かれているか、(3) 基準と steps.md の実装ステップの紐づけが正しいか、(4) スコープ外の作業が紛れ込んでいないか、を徹底的に確認してください。
```

### 視点2: アーキテクチャ整合性・リスク

```
**プロジェクトのあるべきアーキテクチャとの整合性・実現可能性・リスク** を重視してレビューしてください。`spec/` 配下の設計ドキュメント・`CLAUDE.md`・アーキテクチャ関連ドキュメントを読み、プロジェクトが目指している設計・レイヤー構造・規約に計画が沿っているかを確認してください。research.md があれば、プランナーのコード理解そのものが正しいかも検証してください。steps.md の「設計」セクションがレイヤーの内側（ドメインモデル）から考えられているか — ドメインに置くべきロジックがユースケースやアダプターに漏れていないか、実装ステップが依存方向の順になっているか — も確認してください。既存コードに合わせるだけで「あるべき姿」から外れていないか、逆にIssue範囲を超えて理想形を追求しすぎていないかを両方向で見てください。加えて、提案された手順が現実的に動くか、見落とされた依存関係や副作用はないか、エッジケースは考慮されているか、設計判断のトレードオフは適切かを徹底的に確認してください。
```

### レビュー履歴・未解決事項

各周の反映内容は `plan-review/history.md` に、3周完了しても残った問題は plan.md 末尾の「未解決事項」セクションに記録する。書式は `references/plan-template.md` を正とし、追記は反映用サブエージェントが行う（3周到達時の未解決事項はメインが反映用サブエージェントに指示して書かせる）。

恒久的に残す価値があるもの（設計判断 → adr.md、未解決の問題 → 未解決事項）だけを転記し、残りは plan-review/ ごと凍結時に捨てる。

## Step 5: 動作確認計画の作成

計画ファイルの修正が完了したら、実装後に実機で動作確認すべき観点とその方法を `.thread/{Issue番号}/testing.md` にまとめる。

自動テスト（ユニットテスト等）で担保できる範囲ではなく、実際にアプリケーションを動かして人間が確認すべき項目に焦点を当てる。確認項目は plan.md の「受け入れ基準」から導出する — 各基準を実機でどう確認すれば満たしたと言えるかを具体的な操作手順に落とす。

### Step 5a: 確認に必要な実行コマンドの特定（testing.md を書く前に必ず実行）

testing.md の「確認環境」セクションには、このIssueの変更を確認するために必要な実行コマンドだけを書く。プロジェクト全体のセットアップ手順（依存パッケージのインストール等）は不要。

まず steps.md の実装ステップから「この変更を確認するには何を動かす必要があるか」を特定する。次に、そのコマンドを以下のソースから実際にファイルを読んで確認する:

1. **CLAUDE.md** — プロジェクトルートと変更対象パッケージの CLAUDE.md
2. **README.md**
3. **package.json** — `scripts` セクションの**全項目**に目を通す。ローカル実行系のキーワード（dev, start, build）だけで止めない
4. **リポジトリルートの設定ファイル** — Makefile やデプロイ設定ファイルが存在すれば読む
5. **既存の `.thread/*/testing.md`** — Glob で探し、過去の記載を参考にする

testing.md に書く前に、各コマンドが上記ソースに実在するかを実際に確認すること。記憶や推測でコマンドを書いてはいけない。このソース走査は事実の収集に徹する作業なので、サブエージェント（**探索区分**。`../_shared/references/subagent-policy.md`）に委譲してよい。

**変更確認の流れの全体像を考えること**: 変更箇所を検証環境で確認するために必要なステップを、抜けなく洗い出す。検証環境のサーバー起動方法と、デプロイ方法（ステージングや本番環境への反映手順）は別セクションとして分けて記載する。マイグレーションやシードが必要かもプロジェクトの実態から判断する。

**禁止事項**:

- 「手動でデプロイしてください」「環境に応じて適宜実行してください」のような曖昧な逃げ文句は書かない。該当するコマンドがドキュメントに存在するなら、確認した上でそのコマンドを記載する。
- 上記ソースで確認できないコマンドは testing.md に書かない。
- どうしても該当手順が見つからなかった場合のみ「要確認: {具体的に何の手順が見つからなかったか}」と明記する。

### Step 5b: testing.md の作成

Step 5a で確認した情報を使って testing.md を作成する。

```markdown
# 動作確認計画 — Issue #{Issue番号}: {タイトル}

**Issue:** #{Issue番号}
**作成日:** {日付}

---

## 確認環境
```

## Step 6: 計画の凍結・完了報告

完了報告の前に足場ファイルを削除する。残したままにすると後続セッションの検索に紛れ込んでコンテキストを浪費する。

```bash
rm -rf .thread/{Issue番号}/plan-review/ .thread/{Issue番号}/research.md
```

削除の前に、恒久的に残す価値があるものを転記済みか確認する:

- **設計判断** → adr.md に書かれているか
- **3周到達で残った問題** → plan.md 末尾の「未解決事項」に書かれているか
- **research.md の内容** → 転記不要。設計は steps.md、影響範囲・注意点は plan.md のリスクに消費済みで、後続フェーズは `spec/`・`CLAUDE.md`・コード本体を直接読む

**成果物（plan.md / steps.md / adr.md / testing.md）は残す。**

計画が完成したら、サマリーを出す。小規模Issueの場合は該当しない項目を省略する。

```
Issue #{Issue番号} の実装計画が完成しました！

- 契約: .thread/{Issue番号}/plan.md
- 実装手順: .thread/{Issue番号}/steps.md（ステップ数: {数}）
- 設計判断: .thread/{Issue番号}/adr.md（{あり/なし}）
- 動作確認計画: .thread/{Issue番号}/testing.md（{数}件）
- レビューループ: {N}周（終了理由: {問題点ゼロ / 最大ラウンド到達}）
- 反映した修正: {数}件 / 取り込んだ改善提案: {数}件
- 未解決事項: {数}件（あれば plan.md 末尾を参照）
- 足場: 削除済み（plan-review/ / research.md）
```
