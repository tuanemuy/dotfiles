# 計画ファイルのテンプレート

プランナー（および計画修正のサブエージェント）はこのテンプレートに従って `.thread/{Issue番号}/` 配下にファイルを直接書き込む。

`.thread/{Issue番号}/` のファイルは**何に対して真か**で分ける。

| ファイル | 役割 | 何に対して真か | 寿命 |
| --- | --- | --- | --- |
| `plan.md` | 契約 — 何ができたら完了か | 書かれた時点 | 全フェーズが読む |
| `steps.md` | 手順 — どう作るか | 書かれた時点 | 実装フェーズまで |
| `adr.md` | 設計判断の経緯の唯一の記録先 | 書かれた時点 | 恒久 |
| `testing.md` | 実行される動作確認手順（Phase 2 の末に作成） | 現在のツリー | 検証フェーズまで |
| `manual-test/` | 観測の記録 | 実行した事実 | 恒久 |
| `plan-review/` | 足場 — レビューファイル・台帳 | — | 計画凍結時に削除 |

**「書かれた時点」に対して真なファイルは、実装後のツリーに合わせて更新しない。** 実装が計画から外れたときに直すのは契約そのもの（受け入れ基準・スコープ）であって、行番号やコード引用のような装飾ではない — 装飾は最初から書かない。

**「現在のツリー」に対して真なファイルは逆で、ツリーとズレたまま残すと動作検証が偽の FAIL を出す。**

**「実行した事実」に対して真なファイルは書き換えない。**

**計画が決めるのは方針で、コードの書き方ではない。** plan.md は 5KB、steps.md は 10KB を目安に収める。後続フェーズが機械的に参照する見出し（plan.md の「受け入れ基準」「スコープ」「テスト方針」、steps.md の「設計」「実装ステップ」）は必ず含め、テンプレートに無いセクションは足さない。コードの書き方・モック配線・呼び出し箇所の件数・行番号・テスト名・セレクタ・コマンドは書かない。実装フェーズがコードを読んで決め、testing.md が手順を持つ。

**規模は `小規模` / `通常` の2値。** 小規模と言い切れなければ通常。この値が決めるのは「方針レビューを回すか」と「プランナーの区分」で、後続フェーズは参照しない。

**該当しないセクションは省略する。** 埋めるための作文はしない。

## plan.md（契約）

全フェーズが読む。PRレビュー・testing.md・implement-audit はこのファイルだけを必読とする。

```markdown
# 実装計画 — Issue #{Issue番号}: {タイトル}

**Issue:** #{Issue番号}
**作成日:** {日付}
**規模:** {小規模 / 通常}
**実装方針:** steps.md

---

## 目的

{Issueが達成したいことを1-2文で。受け入れ基準と重複させない}

## 受け入れ基準

Issue 本文・コメントの要件を「何ができたら満たしたと言えるか」の検証可能な基準に分解する。**Issue の要件 1 つにつき 1 行**。目安は 10 行以内。実装制約（どう作るか）は基準にしない — steps.md の設計に書く。

**観測方法**は満たしたと判定する手段（ブラウザで観測できる基準は `browser`、できない基準は `自動テスト` — testing.md には対象外として載る）と、何を見れば満たしたと言えるかを一言で書く。手順・セレクタ・行番号・数値の閾値・コマンドの出力文字列は書かない — それは実装後に testing.md が持つ。観測方法が書けない基準は、基準の立て方が観測可能になっていない。

| # | 基準（検証可能な形で） | 観測方法 | 由来 |
|---|---|---|---|
| AC-1 | {例: 一覧画面で◯◯がソートできる} | {browser / 列ヘッダ押下後の並び順} | {Issue本文 / コメントの合意} |

## スコープ

### 含まれないもの
- {明示的にスコープ外とするもの — 理由があれば一言添える}

（「含まれるもの」は受け入れ基準が兼ねるので書かない）

## リスクと注意点

- {設計の前提が崩れる条件・影響を受ける既存機能。実装上の注意点は steps.md の設計に書く}

## テスト方針

- {レーン（node / jsdom / E2E）と、そのレーンで守る挙動。テスト名・アサーションは書かない}
```

## steps.md（設計と手順の意図）

Phase 1.5（デザインゲート）と Phase 2（実装）が読む。レビュアーは必読ではなく、設計意図を確かめたいときだけ読む。

```markdown
# 実装手順 — Issue #{Issue番号}

## 設計

**レイヤーの内側から外側へ**設計する（プロジェクトのアーキテクチャ — `spec/`・`CLAUDE.md` — を正とする）。該当しないレイヤーは省略する。

`spec/` は Issue をまたぐ決定（用語・ドメインと境界・ビジネスルール・ポート契約・画面構成）だけを持つ。**ここで決めるのは、何をどのレイヤーに置くかと、型と契約の形（DTO の形・ポートのシグネチャ・エラーの種別）。** 分岐の書き方・境界値・処理手順・テストの中身は実装フェーズが決める。決定が spec の持ち分を変える場合だけ adr.md に記録する。

### ドメインモデルへの影響
{エンティティ・値オブジェクト・不変条件・ドメインルール・ポートに何を追加/変更するか}

### ユースケース / アプリケーションロジック
{どのユースケースを追加/変更するか。入出力の形。ドメインに置くべきロジックが紛れ込んでいないか}

### アダプター / 永続化 / 外部連携
{リポジトリ実装・スキーマ変更・マイグレーション・外部API}

### UI / プレゼンテーション
{画面・コンポーネント・ルーティングへの影響。Phase 1.5 のデザインゲートはここを見る}

### 既存ドキュメントへの影響
{挙動の変更が既存の設計ドキュメント（spec/domains・usecases・pages・testcases、docs/）の記述を古くする場合、どのファイルをどう更新するか。影響がなければ省略。`spec/manual-tests/` と他 Issue の `.thread/` はスコープ外 — 古くなるなら Phase 5 で起票する}

## 実装ステップ

上の設計から導出し、**依存方向の順（内側のレイヤーが先）**に並べる。1 ステップは対象と意図を 3〜5 行で書く。コードの書き方・モック配線・呼び出し箇所の件数・行番号・テスト名は書かない。

`束` は実装フェーズが並列に分けるための印。`contract`（ドメイン型・ポート・DTO の形を変える）/ `backend`（ユースケース・アダプター・そのテスト・`spec/usecases`）/ `frontend`（routes・components・そのテスト・`spec/pages`）/ `docs` のいずれか。

### 1. {ステップタイトル}

- **束:** {contract / backend / frontend / docs}
- **対象:** {変更するモジュール・ファイル}
- **変更:** {何を変えるか}
- **理由:** {この変更が必要な理由}
```

## adr.md

技術的な設計判断（アーキテクチャ・データモデル・ライブラリ選定・抽象化粒度など、トレードオフのある選択）があった場合のみ作成する。**設計判断の記録先はここだけ** — plan.md / steps.md に要約を重複させない。要件・スコープの取捨選択は plan.md の「スコープ」で扱う。些細な実装詳細、測定手順や係数の導出、ライブラリ内部の挙動の記録は対象外（測定手順は testing.md、コードに閉じる理由は現場のコメントが持つ）。1 エントリは Context / Decision / Consequences あわせて 20 行以内に収める。

adr.md は Issue 単位の**作業ログ**で、判断の経緯が残る唯一の場所であり、既定の置き場所。書く時点では気軽に記録してよく、昇格の要否はここで判定しない — spec / docs / CLAUDE.md に上げるべきものがあるかは issue-implement の片付けフェーズで昇格ゲートに照らす（`_shared/references/adr-guide.md`）。

```markdown
# ADR — Issue #{Issue番号}: {タイトル}

## ADR-001: {判断のタイトル}

### Context
{なぜこの判断が必要になったか — どのような選択肢があったか}

### Decision
{何を選んだか、なぜそれを選んだか}

### Consequences
- 良い点: {メリット}
- トレードオフ: {あれば}

---
```

既に adr.md がある場合は既存の連番の続きに追記する（連番の調べ方は `_shared/references/adr-guide.md` の「作業ログへの追記」。全文は読まない）。

## 未解決事項（plan.md 末尾に追記）

方針レビューで見送った問題点のうち、実装フェーズが知るべきものだけ書く。

```markdown
## 未解決事項

- **[P-XXX]** {問題}
  - 引き継ぎ: {実装フェーズでどう扱うか}
```
