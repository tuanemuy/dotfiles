# 計画ファイルのテンプレート

プランナー（および計画修正のサブエージェント）はこのテンプレートに従って `.thread/{Issue番号}/` 配下にファイルを直接書き込む。

ファイルはライフサイクルで分ける。実装後まで残るのは plan.md / steps.md / adr.md / testing.md だけで、足場は計画凍結時（issue-planner Step 6）に削除する。

| ファイル | 役割 | 寿命 |
| --- | --- | --- |
| `plan.md` | 契約 — 何ができたら完了か | 全フェーズが読む |
| `steps.md` | 手順 — どう作るか | 実装フェーズまで |
| `research.md` | 足場 — 調査の記録 | 計画凍結時に削除 |
| `plan-review/` | 足場 — レビューファイル・台帳・履歴 | 計画凍結時に削除 |
| `adr.md` | 設計判断の経緯の唯一の記録先 | 恒久 |

**テンプレートは下限であって上限ではない。** 後続フェーズが機械的に参照する項目（plan.md の見出し「受け入れ基準」「スコープ」「テスト方針」、steps.md の見出し「設計」「実装ステップ」）は必ず含める。それ以外は Issue の性質に応じて自由に足してよい。

**規模は `小規模` / `通常` の2値。** 小規模と言い切れなければ通常。この値が決めるのは「計画づくりに調査とレビューループを回すか」だけで、後続フェーズは参照しない（レビューの周回数・観点数には効かない）。

**小規模 Issue では該当しないセクションを省略してよい。** 埋めるための作文はしない。小規模なら research.md は作らなくてよい。

## plan.md（契約）

全フェーズが読む。PRレビュー・testing.md・implement-audit はこのファイルだけを必読とする。

```markdown
# 実装計画 — Issue #{Issue番号}: {タイトル}

**Issue:** #{Issue番号}
**作成日:** {日付}
**規模:** {小規模 / 通常}
**実装方針:** steps.md

---

## 目的

{Issueが達成したいことを1-2文で。受け入れ基準と重複させない}

## 受け入れ基準

Issue 本文・コメントの要件を「何ができたら満たしたと言えるか」の検証可能な基準に分解する。

| # | 基準（検証可能な形で） | 由来 | 対応ステップ |
|---|---|---|---|
| AC-1 | {例: 一覧画面で◯◯がソートできる} | {Issue本文 / コメントの合意} | {steps.md のステップ番号} |

## スコープ

### 含まれないもの
- {明示的にスコープ外とするもの — 理由があれば一言添える}

（「含まれるもの」は受け入れ基準が兼ねるので書かない）

## リスクと注意点

- {リスク・影響を受ける既存機能・見落としやすい副作用}

## テスト方針

- {テスト項目}
```

## steps.md（手順）

Phase 1.5（デザインゲート）と Phase 2（実装）が読む。レビュアーは必読ではなく、設計意図を確かめたいときだけ読む。

```markdown
# 実装手順 — Issue #{Issue番号}

## 設計

**レイヤーの内側から外側へ**設計する（プロジェクトのアーキテクチャ — `spec/`・`CLAUDE.md` — を正とする）。該当しないレイヤーは省略する。

`spec/` は Issue をまたぐ決定（用語・ドメインと境界・ビジネスルール・ポート契約・画面構成）だけを持つ。**DTO のフィールド・エラー分岐・境界値・処理手順はここで決める** — spec に書かれていないのは設計漏れではなく分担。決定が spec の持ち分を変える場合だけ adr.md に記録する。

### ドメインモデルへの影響
{エンティティ・値オブジェクト・不変条件・ドメインルール・ポートに何を追加/変更するか}

### ユースケース / アプリケーションロジック
{どのユースケースを追加/変更するか。ドメインに置くべきロジックが紛れ込んでいないか}

### アダプター / 永続化 / 外部連携
{リポジトリ実装・スキーマ変更・マイグレーション・外部API}

### UI / プレゼンテーション
{画面・コンポーネント・ルーティングへの影響。Phase 1.5 のデザインゲートはここを見る}

### 既存ドキュメントへの影響
{挙動の変更が既存の spec/ の記述や spec/manual-tests/ の手順・期待結果を古くする場合、どのファイルをどう更新するか。手順書の stale は動作検証（Phase 4）で正しい実装を FAIL 判定にするため、更新を実装ステップに含める。影響がなければ省略}

## 実装ステップ

上の設計から導出し、**依存方向の順（内側のレイヤーが先）**に並べる。

### 1. {ステップタイトル}

- **対象ファイル:** `パス`
- **変更内容:** {具体的な変更}
- **理由:** {この変更が必要な理由}
```

## research.md（足場）

プランナーの調査記録。レビューループの視点2（アーキ整合・リスク）がプランナーのコード理解を検証するために読む。

計画凍結時に削除する — 内容は steps.md の設計と plan.md のリスクに消費済みで、後続フェーズは `spec/`・`CLAUDE.md`・コード本体を直接読む。

```markdown
# 調査結果 — Issue #{Issue番号}

- 関連ファイル: {見つけた関連ファイルとその役割}
- あるべきアーキテクチャ: {`spec/` や `CLAUDE.md` から読み取った設計方針・レイヤー構造・規約}
- 既存実装の状態: {あるべき姿と一致している箇所 / 乖離している箇所 / 乖離があれば本Issueでどう扱うか}
- 依存関係: {この変更が影響する他のコンポーネント}
```

## adr.md

技術的な設計判断（アーキテクチャ・データモデル・ライブラリ選定・抽象化粒度など、トレードオフのある選択）があった場合のみ作成する。**設計判断の記録先はここだけ** — plan.md / steps.md に要約を重複させない。要件・スコープの取捨選択は plan.md の「スコープ」で扱う。些細な実装詳細も対象外。

adr.md は Issue 単位の**作業ログ**で、判断の経緯が残る唯一の場所であり、既定の置き場所。書く時点では気軽に記録してよく、昇格の要否はここで判定しない — spec / docs / CLAUDE.md に上げるべきものがあるかは issue-implement の片付けフェーズで昇格ゲートに照らす（`_shared/references/adr-guide.md`）。

```markdown
# ADR — Issue #{Issue番号}: {タイトル}

## ADR-001: {判断のタイトル}

### Context
{なぜこの判断が必要になったか — どのような選択肢があったか}

### Decision
{何を選んだか、なぜそれを選んだか}

### Consequences
- 良い点: {メリット}
- トレードオフ: {あれば}

---
```

既に adr.md がある場合は既存の連番の続きに追記する（連番の調べ方は `_shared/references/adr-guide.md` の「作業ログへの追記」。全文は読まない）。

## レビュー履歴（`plan-review/history.md`）

計画レビューループの推敲ログ。反映結果は plan.md / steps.md 本文に焼き込まれるため、履歴自体は plan-review/ ごと凍結時に削除する。

削除前に、**設計判断は adr.md へ、周回の上限までに解けなかった問題は plan.md の「未解決事項」へ**転記する（`_shared/references/review-loop.md` の後片付けと同じ扱い）。

```markdown
## {N}周目

**修正した点**: {P-001への対応: 何をどう修正したか}
**取り込んだ改善提案**: {S-001: 何を取り込んだか}
**見送った提案とその理由**: {S-002: 見送り理由}
```

レビュアーが「問題点ゼロ」を返した周は「{N}周目: 両視点とも問題点ゼロで終了」と記録する。

## 未解決事項（plan.md 末尾に追記）

周回の上限に達しても残った場合のみ書く。

```markdown
## 未解決事項

- **[P-XXX]** {未解決の問題}
  - 経緯: {なぜ上限までに解消できなかったか}
  - 引き継ぎ: {実装フェーズでどう扱うべきか}
```
