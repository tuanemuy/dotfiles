# Spec Manual Test

`spec/` から、人とエージェントが画面を操作して実行する手順書を `spec/manual-tests/` に作る。手順書が確かめるのは、利用者がシナリオどおりに目的を達成できることと、異常系で利用者の次の操作が決まっていること。コードの正しさは自動テストが確かめる。

段取り（シナリオの分け方・委譲の切り方・読ませる時期）は規模に合わせて自分で決める。このスキルが定めるのは、契約・成果物・完了の定義・独立した読み・不変条件・予算。着手時に、読んだ規模感と採る段取りを一言宣言する。

## 契約

出典は `spec/scenario/`。範囲のシナリオのフロー（正常系と異常系）を番号付きの台帳にし、`spec/manual-tests/review/contract.md` に置く。完了の定義の 1・2 は台帳の項目を分母にする。

範囲は次のとおり決まる。

- 既定は全シナリオ
- ユーザーがシナリオを指定していれば、そのシナリオだけ
- spec-revise から委譲されたときは、変えた spec に対応するシナリオだけ

`spec/scenario/` か `spec/pages/` が無ければ、先に `/spec` で設計が要ると伝えて止まる。

## 成果物

| ファイル | 内容 |
| --- | --- |
| `spec/manual-tests/index.md` | 手順書の一覧と実行記録 |
| `spec/manual-tests/{category}.md` | シナリオのカテゴリーごとの手順書 |

形式は `references/test-doc-guide.md` が定める。manual-test はこの形式をそのまま実行手順に変換するので、テストケースの見出し・種別・操作と期待結果の表の形を変えない。

## 完了の定義

次の 4 つが成り立ち、それぞれを根拠で示せること。成り立つとは反例が無いこと。

反例は条件ごとに決まった形を取り、手順書と spec の記述の引用を伴う。手順書には足す方向の指摘がいくらでも出せるため、引用のない指摘を反例に数えると、反例ゼロは書き尽くした状態でしか成立しない。形を取らない指摘は 4 条件の外の指摘として扱う。

### 1. シナリオを取りこぼしていない

- 台帳の各フローに、それを確かめるテストケースか、spec 未決の記録（下の「spec のすき間」）がある

反例の形: 台帳のフローの引用と、テストケースも spec 未決の記録も無いこと

根拠: 手順書ごとのフロー対応表

### 2. 足しすぎていない

- すべてのテストケースが台帳のフローに辿れる
- 期待結果は、spec（scenario / pages / usecases / domains）に書かれた事柄だけを確かめる
- 次を書かない
  - 境界値、入力バリデーションの組み合わせ
  - spec が決めていない表示・文面・並び順・レイアウト
  - UI から再現できない障害

反例の形: テストケースか期待結果の引用と、台帳に辿れないこと、spec に引用元が無いこと、または「書かない」のどれに当たるか

根拠: テストケースごとの対応フロー

### 3. 手順どおりに実行でき、結果が一つに決まる

- 各テストケースは、手順書の前提条件とテストデータだけから単独で実行できる。前のテストケースが残した状態に依存しない
- 各操作は、画面・要素・入力値が一つに決まる
- 各期待結果は spec から一つに決まり、画面を見て判定できる

反例の形: 実行できない操作の引用と欠けている前提、または操作か期待結果の引用と、取り得る 2 つの解釈

根拠: 前提条件とテストデータの一覧

### 4. spec と食い違わない

- 画面名・操作名・状態名は spec の語を使う
- 手順と期待結果が spec の記述と矛盾しない

反例の形: 食い違う手順書と spec の 2 か所の引用

根拠: 用語の突き合わせ結果

## spec のすき間

手順書を書く中で、フローの結果が spec から一つに決まらないと分かったら、spec を補わずに記録する。

- そのフローはフロー対応表で「spec 未決」とし、決まっていない問いを書く
- 完了報告に問いを並べ、spec-revise で直すよう勧める
- spec-revise から委譲されたときは、問いを spec-revise に返す

## 独立した読み

完了と判断する前に、新しいコンテキストのサブエージェントに読ませる（委譲方式と待ち方は `../_shared/references/subagent-policy.md`）。手順書が多いときは、カテゴリーで分けて複数体に読ませてよい。

- 台帳、範囲の手順書、`spec/` のパス、完了の定義の 4 条件（転記）を渡す
- 読み手の目的は 4 条件の反例を探すこと。成立の認定はさせず、反例の一覧だけを返させる
- 反例は条件ごとの形で返させる。形を取らない指摘は 4 条件の外として分けて返させる
- 自分の自己評価と作業の経緯は渡さない

4 条件への反例は自分で見送らない。見送ってよいのは 4 条件の外の指摘だけ。直した後に何を読ませるか（同じ読み手に増分を見せるか、新しい目に全量を読ませるか）は自分で決める。

## 不変条件

- 上流が正
  - 手順書は spec から決まる
  - `spec/` の手順書以外を書き換えない
  - spec が決めていないことを手順書の判断で補わず、すき間として記録する
- 範囲の外の手順書に触れない
- 未完了を完了と報告しない
  - サブエージェントの中断・空の返答は未了
  - 根拠を示せない条件は未達

## 予算

次のいずれかに達したら止め、成り立っていない条件と残っている反例をまとめてユーザーに渡す。

- 独立した読みの反例 → 修正 → 読み直し: 3 周まで（同じ読み手への追加の問いは数えない）
- 同じ作業の再委譲: 2 回まで（2 回目はスコープを分割する）

## ユーザーに聞く場面

次の場面だけユーザーに聞く。それ以外は聞かずに最後まで進める。

- 着手時。範囲にするシナリオが指定から決まらない
- 予算に達した

## 環境の事実

### `spec/manual-tests/review/`

実行中の作業ファイルの置き場所。名前が決まっているのは `contract.md` だけ。

- 途中再開は、`spec/manual-tests/review/` と既存の手順書を読んで続きから進める
- 完了したら `spec/manual-tests/review/` を削除する。残すと後続セッションの検索に紛れ込む
- 予算に達して止めたときは削除しない

### 委譲

カテゴリーごとの手順書は互いに独立しているので、並列に委譲できる。`spec/manual-tests/index.md` は全委譲先の完了後にまとめて更新する。`spec/index.md` に `spec/manual-tests/index.md` へのリンクが無ければ足す。

## 完了報告

spec-revise から委譲されたときは、この報告を出さず、spec-revise の完了報告の「派生物」に統合する。

```text
spec-manual-test: {完了 / 停止（理由）}
- 段取り: {採った進め方を一行で}
- 契約: シナリオ {数}本、フロー {数}件
- 成果物: 手順書 {数}ファイル、テストケース {数}件（正常系 {数}・異常系 {数}）
- 取りこぼし・足しすぎ: フロー {数}件すべてにテストケースか spec 未決の記録がある、台帳に辿れないテストケース {なし / 内容}
- spec のすき間: {問いの一覧 / なし}
- 独立した読み: 読み {数}回。回ごとの範囲（全量 / 増分）と 4 条件への反例の数。最後の回は反例ゼロ。4 条件の外で見送った指摘: {内容 / なし}
- 残存課題: {内容 / なし}
```
