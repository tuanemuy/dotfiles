# Review Dashboard — 区分ローテーションによる定期レビュー

プロジェクトを区分（レビュー単位）に分割し、**実行1回につき1区分だけ**を徹底的にレビューする。区分の定義とレビュー履歴は **GitHub Issue のダッシュボード**として管理し、リポジトリ上で共有・更新できるようにする。

プロジェクト全体を一度にレビューすると、広く浅くなって見落としが増え、毎回同じ指摘を拾い直す無駄も多い。そこで初期化時にアーキテクチャを読み取って区分を設計し、以降はローテーションで1区分ずつ深掘りする。1回は狭いが、周回すれば全体を確実に覆う。

見つかった問題は裏取りしたうえで、既存 Issue と重複しなければ Issue として起票する。**このスキルはコードを修正しない。** 修正は issue-implement 等に委ねる。

三兄弟（implement-audit / spec-sync / architecture-audit）との棲み分け:

| スキル | 見るもの | 範囲 |
|--------|---------|------|
| implement-audit | コードの完全性 | 全体 × 単一テーマ |
| spec-sync | ドキュメントの正確性 | 全体 × 単一テーマ |
| architecture-audit | 構造的健全性 | 全体 × 単一テーマ |
| **review-dashboard** | 区分に応じた多観点（正しさ・堅牢性・セキュリティ・品質等） | **1区分 × 多観点の深掘り** |

## Workflow

1. 既存のダッシュボード Issue を探す（Step 1）
2. なければ初期化する — 区分を設計してダッシュボードを作成し、終了（Step 2）
3. あればレビュー対象の区分を1つ選ぶ（Step 3）
4. 区分を徹底レビューする — 観点別サブエージェント並列 → 統合 → 裏取り（Step 4）
5. 重複チェックのうえ Issue を起票する（Step 5）
6. ダッシュボードを更新する（Step 6）
7. 完了報告する（Step 7）

## Step 1: 既存ダッシュボード Issue の確認

open な Issue から、タイトルが `Review Dashboard` のものを探す。

```bash
gh issue list --state open --search "Review Dashboard in:title" --json number,title,body
```

本文の先頭に `<!-- review-dashboard -->` マーカーがあるかで最終確認する（同名タイトルの誤検出を避けるため）。見つかればその Issue 番号と現在の本文を控えて Step 3 へ。見つからなければ初期化（Step 2）へ。

## Step 2: 初期化 — 区分の設計とダッシュボード作成

CLAUDE.md / README.md / spec/ / ディレクトリ構成を読み、プロジェクトのアーキテクチャを把握したうえで区分を設計する。設計の方法は `references/segmentation-guide.md` に従う。要点:

- 区分は **スコープ（対象ディレクトリ/ファイル群）＋ 観点（そのスコープで何を見るか）** の組で定義する
- レイヤー・機能領域を主軸にした区分と、セキュリティ等の横断観点の区分を組み合わせる
- 1区分は「1回の実行でスコープ内の全対象を読み切れる」サイズに収める。目安は 5〜12 区分
- すべてのソースコードがいずれかの区分のスコープに含まれるようにする
- 観点は `references/review-perspectives.md` のカタログから、そのスコープに効くものを 3〜6 個選ぶ

設計した区分を下記フォーマットでダッシュボード Issue として新規作成する。本文は一時ファイルに書き出してから反映する。

```bash
gh issue create --title "Review Dashboard" --body-file <一時ファイル>
```

**初期化した実行ではレビューまで進まない。** 区分の切り方はローテーション全体の質を決めるので、まずユーザーに区分を確認してもらう。作成したダッシュボードの URL と区分一覧を報告して終了する。ユーザーが「初期化してそのまま1区分レビューして」と明示した場合のみ Step 3 に続く。

### ダッシュボード本文のフォーマット

- 本文の先頭に `<!-- review-dashboard -->` マーカーを置く（次回の検出用）。
- 区分ごとに `## {番号}. {区分名}` セクションを作る。番号はローテーションの既定順で、基盤に近い区分を上に置く。
- 各セクションは次の 4 行のリストで構成する。
  - `- スコープ:` 対象ディレクトリ/ファイル群。横断区分は「プロジェクト全体（{重点}を重点）」のように重点を明記する。
  - `- 観点:` その区分で見る観点を読点区切りで列挙する。
  - `- 最終レビュー:` `YYYY-MM-DD` 形式。未レビューは `-`。
  - `- 起票:` その区分のレビューで起票した**オープンな** Issue 番号を空白区切りで列挙する。なければ `-`。
- テーブル・太字・絵文字・罫線・説明文などの装飾は使わない。構造だけで伝える。

### 本文の例

```markdown
<!-- review-dashboard -->

## 1. ドメイン層

- スコープ: src/core/domain/
- 観点: 設計準拠、正しさ、完全性、テスト品質
- 最終レビュー: 2026-07-10
- 起票: #141 #142

## 2. アダプター層

- スコープ: src/core/adapters/
- 観点: 設計準拠、エラーハンドリング・堅牢性、パフォーマンス
- 最終レビュー: 2026-07-14
- 起票: -

## 3. ユースケース層

- スコープ: src/core/application/
- 観点: 設計準拠、正しさ、エラーハンドリング・堅牢性
- 最終レビュー: -
- 起票: -

## 4. フロントエンド

- スコープ: src/app/, src/components/
- 観点: 正しさ、完全性、コード品質、パフォーマンス
- 最終レビュー: -
- 起票: -

## 5. セキュリティ横断

- スコープ: プロジェクト全体（認証・入力境界・シークレットを重点）
- 観点: セキュリティ
- 最終レビュー: -
- 起票: -

## 6. 依存・設定・ドキュメント

- スコープ: 設定ファイル、依存マニフェスト、README、spec/
- 観点: 依存・設定、ドキュメント整合
- 最終レビュー: -
- 起票: -
```

## Step 3: レビュー対象区分の選択

対象は次の優先順で1つだけ選ぶ。

1. **ユーザー指定**（「区分3をレビューして」「セキュリティの区分やって」等）があればそれ。
2. `最終レビュー: -`（未レビュー）の区分のうち、番号が最も小さいもの。
3. 未レビューがなければ、最終レビュー日が最も古い区分。同日なら番号が小さいもの。

選択したら、区分のスコープが現状と合っているか軽く確認する。スコープのパスが消えている・改名されている場合は区分定義を直してから進める（Step 6 でダッシュボードにも反映）。どの区分にも属さない大きな新領域を見つけた場合は、新しい区分を末尾に追加する。**区分全体の作り直しはしない** — ユーザーが明示的に「区分を作り直して」「再初期化して」と言ったときだけ Step 2 をやり直す。

対象区分（番号・名前・スコープ・観点）をユーザーに報告してからレビューを開始する。

## Step 4: 区分の徹底レビュー

### 検証用ブランチの準備

レビューは最新の `origin/main` の内容に対して行う。origin/main からブランチを切ってチェックアウトし、以降の読み取りはすべてその状態で行う。

```bash
ORIG_BRANCH=$(git branch --show-current)
git fetch origin
git switch -c "review-dashboard/$(date +%Y%m%d)" origin/main
```

- 作業ツリーに未コミット変更がある場合はブランチを切り替えず、その旨を報告して中断する（変更の退避はユーザーに委ねる）
- `origin/main` が存在しない場合（リモート未設定等）は、現在のブランチのままレビューする旨を完了報告に明記して続行する
- レビュー完了後（Step 6 まで終えたら）、元のブランチに戻して検証用ブランチを削除する:

```bash
git switch "$ORIG_BRANCH"
git branch -D "review-dashboard/$(date +%Y%m%d)"
```

### 観点別レビューの並列実行

区分に列挙された観点ごとにサブエージェント（**判断区分**）を**並列**起動する（委譲方式とモデル選択は `../_shared/references/subagent-policy.md`）。区分定義のためのファイル一覧収集は**探索区分**でよい。各観点の検査内容とプロンプトは `references/review-perspectives.md` に従う。

各サブエージェントには必ず以下を渡す:

- まずプロジェクトルートの CLAUDE.md を読む指示（規約・構成の情報源として）
- 区分のスコープ（このスコープの**全対象ファイルを読む**こと。diff や変更履歴に依存しない）
- 担当する観点と検出方法（`references/review-perspectives.md` の該当節）
- spec/ に該当する設計ドキュメントがあればそのパス

全観点の結果を統合し、同じ場所・同じ原因の検出をまとめる。各検出に重要度を付ける:

- **Critical** — 実害がある。バグ・脆弱性・データ破壊の可能性・設計の根幹を壊す違反
- **Warning** — 品質を下げる・将来の実害リスク。仮実装、握り潰されたエラー、重い重複
- **Info** — 意図的かもしれず確認が必要なもの。確信度が低い検出

### 裏取り

起票候補（Critical / Warning）は、起票前に**該当コードを実際に読んで裏取りする**。検出報告の根拠（該当行・import・コード抜粋）が実物と一致し、意図的な設計（spec/ または CLAUDE.md に規約として明記された判断、テストコード内の正当なスタブ等）でないことを確認する。裏取りできないもの・判断が割れるものは Info に落とす。偽陽性の起票はローテーション全体の信頼を損なう。

## Step 5: Issue 起票（重複がなければ）

まず既存のオープン Issue を取得し、起票候補と突き合わせる。

```bash
gh issue list --state open --limit 200 --json number,title,body,labels
```

**同じ問題（同じ場所・同じ原因）を指す Issue が既にあれば起票しない。** タイトルの一致ではなく内容で判断する。ダッシュボード各区分の「起票:」行も手がかりにする。重複でスキップしたものは完了報告に「既存 #N がカバー」と記録する。

裏取り済みの Critical / Warning を起票する。Info は起票しない（ノイズを避ける。ユーザーが「全部 Issue にして」と指定した場合はそれに従う）。独立して対応できる単位で 1 Issue とし、同じ原因から生じた複数箇所の問題は 1 つにまとめる。

```bash
gh issue create \
  --title "[review] {区分名}: {問題の概要}" \
  --body "$(cat <<'EOF'
## 概要
review-dashboard の定期レビュー（区分: {区分名} / 観点: {観点}）で検出された問題。

## 問題
| # | 場所 | 内容 |
|---|------|------|
| 1 | {パス:行} | {何が問題か} |

## 根拠
{該当コードの抜粋と、なぜ問題と判断したか}

## 推奨対応
{どう直すべきか}

## 参照
- ダッシュボード: #{ダッシュボード番号}
- 規約・設計: {CLAUDE.md / spec の該当箇所（あれば）}
EOF
)" \
  --label "review-dashboard"
```

`review-dashboard` ラベルが存在しない場合は事前に作成する:

```bash
gh label create review-dashboard --description "review-dashboard の定期レビューで検出された問題" --color "1d76db"
```

## Step 6: ダッシュボードの更新

旧本文をベースに、変わった分だけ手を入れる。本文を一時ファイルに書き出してから反映する。

1. 今回レビューした区分の `最終レビュー:` を今日の日付にする。
2. 同区分の `起票:` に今回起票した Issue 番号を追記する。
3. **全区分**の `起票:` 行から close 済みになった Issue 番号を外す（この付け直しは AI 判断を要さないので毎回全区分に行う）。すべて外れたら `-` にする。
4. Step 3 でスコープ修正・区分追加をした場合はそれも反映する。
5. それ以外の区分の定義・並び順には触れない。

```bash
gh issue edit <ダッシュボード番号> --body-file <一時ファイル>
```

## Step 7: 完了報告

```text
区分「{番号}. {区分名}」のレビューが完了しました！ → ダッシュボード: {URL}

- スコープ: {スコープ} / 観点: {観点}
- 検出: Critical {数} / Warning {数} / Info {数}
- 起票した Issue: {#番号一覧 / なければ「なし」}
- 重複でスキップ: {既存 #番号がカバー / なければ省略}
- 区分の変更: {スコープ修正・追加した区分 / なければ省略}
- 次回のレビュー対象: {番号}. {区分名}
```

初期化のみの実行では、ダッシュボード URL と区分一覧（番号・名前・スコープ・観点）を報告し、区分の切り方に過不足がないかユーザーに確認を求める。

## 原則

- **1回の実行で1区分だけ** — 狭く深く。全体は周回で覆う。複数区分をまとめてレビューしない
- **origin/main を基準にレビューする** — origin/main からブランチを切って確認し、実行時のブランチの状態に依存しない。終了時に元のブランチへ戻して検証用ブランチを削除する
- **スコープ内は隈なく読む** — diff や変更履歴に依存せず、区分スコープの全対象を読む。深掘りこそが全体監査系スキルとの差分
- **コードは修正しない** — 検出・起票・ダッシュボード更新まで。修正は issue-implement 等に委ねる
- **判定基準はプロジェクトから読み取る** — CLAUDE.md / spec/ の規約に照らして判定し、一般論のベストプラクティスを押し付けない。規約に明記がない事項は「正しさ」など規約に依存しない観点でのみ判定する
- **裏取りできたものだけ起票する** — 偽陽性は Info に落とす。ローテーションの信頼はここで決まる
- **重複起票しない** — 既存 Issue の内容と突き合わせてから起票する
- **ダッシュボードの構造を安定させる** — 区分の定義・並び順は原則引き継ぐ。作り直しはユーザー指示時のみ
- **意図的な設計と問題を区別する** — spec/ または CLAUDE.md に規約として明記された判断は問題としない。迷うものは Info
- 委譲方式・並列実行・中断時の再委譲は `../_shared/references/subagent-policy.md` に従う
