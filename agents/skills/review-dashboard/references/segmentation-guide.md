# 区分設計ガイド

review-dashboard の初期化（SKILL.md Step 2）で、プロジェクトをレビュー区分に分割するための方法。区分の切り方はローテーション全体の質を決める。**見落としのない被覆**と**1回で読み切れるサイズ**の両立が目標。

## 入力

区分を設計する前に、以下を読んでプロジェクトを把握する:

- **CLAUDE.md** — レイヤー構成・依存方向・規約・ソースディレクトリ
- **README.md** — プロジェクトの目的・技術スタック
- **spec/** — 設計ドキュメント（ドメイン・ユースケース・ページ構成）。存在すれば区分の主軸候補
- **ディレクトリ構成** — 実際のソースツリー（`node_modules` 等の除外対象を除く）と、各ディレクトリのファイル数・規模感
- **依存マニフェスト**（package.json 等）— 技術スタックと横断観点（フロントエンドの有無、DB の有無等）の判断材料

## 区分の定義

1つの区分は次の組で定義する:

- **区分名** — 内容を表す短い名前
- **スコープ** — 対象ディレクトリ/ファイル群。横断区分は「プロジェクト全体（{重点}を重点）」の形で重点を明記する
- **観点** — そのスコープで見るもの。`review-perspectives.md` のカタログから 3〜6 個選ぶ

## 3つの軸

区分は次の軸を組み合わせて作る。

### 軸1: レイヤー主軸（レイヤードアーキテクチャの場合）

CLAUDE.md / spec/ にレイヤー構成が定義されているプロジェクトでは、レイヤーをそのまま区分にするのが基本。レイヤーごとに効く観点が違うため、観点の割り当ても自然に決まる。

| レイヤー | 効きやすい観点の例 |
|---------|------------------|
| ドメイン | 設計準拠、正しさ、完全性、テスト品質 |
| アダプター | 設計準拠、エラーハンドリング・堅牢性、パフォーマンス |
| ユースケース | 設計準拠、正しさ、エラーハンドリング・堅牢性 |
| フロントエンド | 正しさ、完全性、コード品質、パフォーマンス |
| テスト | テスト品質、コード品質 |

### 軸2: 機能領域主軸（フィーチャーベース構成の場合）

feature ディレクトリや機能単位のモジュール構成のプロジェクトでは、機能領域（認証 / プロジェクト管理 / 通知 など）を区分にする。1つの機能を縦に貫いてレビューできるので、機能内の整合性（API とフロントの突き合わせ等）を見やすい。

レイヤー構成と機能構成が両方あるプロジェクトでは、規模の大きい方を主軸にする。レイヤーが大きすぎるならレイヤー×機能領域で分割する（例:「ドメイン層（タスク管理）」「ドメイン層（認証・ユーザー）」）。

### 軸3: 横断区分（常に追加を検討する）

スコープ主軸の区分は「その場所のコード」を見るが、場所に紐づかない問題は拾えない。次の横断区分を、プロジェクトに該当するものだけ追加する:

- **セキュリティ横断** — 認証・認可・入力境界・シークレット管理を重点に全体を見る。外部入力や認証があるプロジェクトでは必須
- **依存・設定・ドキュメント** — 依存マニフェスト、設定ファイル、CI 設定、README / spec/ の正確性。どのプロジェクトでも有効
- **パフォーマンス横断** — データ量・トラフィックが問題になりうるプロジェクトのみ。重点（DB アクセス経路、レンダリング等）を明記する

横断区分のスコープはレイヤー/機能区分と重複してよい。**見る観点が違えば重複は無駄ではない**（同じファイルでも、レイヤー区分では設計準拠を、セキュリティ区分では入力検証を見る）。

## サイズの調整

1区分は「1回の実行で、観点別サブエージェントがスコープ内の全対象ファイルを読み切れる」サイズに収める。目安:

- ソースファイル **〜50 ファイル / 〜1万行** 程度を上限の目安とする
- 超える場合は分割する。分割の単位は意味のあるまとまり（集約・機能領域・サブディレクトリ）を使い、機械的な等分はしない
- 逆に小さすぎる区分（数ファイル）は隣接する区分に併合する。ローテーション1周が長くなりすぎるのを防ぐ

区分数の目安は **5〜12**。少なすぎると1回が重く浅くなり、多すぎると1周が長くなって鮮度が落ちる。小規模プロジェクトなら 3〜4 でもよい。

## 被覆の確認

設計を終えたら、すべてのソースコード（生成物・依存・ロックファイルを除く）が**いずれかのスコープ主軸区分に含まれる**ことを確認する。横断区分は被覆に数えない（重点を絞って見るため、単独では被覆保証にならない）。

どの区分にも入らない領域（スクリプト、インフラ定義、CI 設定等）は「依存・設定・ドキュメント」区分に含めるか、独立した区分にする。

## 並び順

ダッシュボードの区分番号はローテーションの既定順になる。**基盤に近い区分を上に**置く（ドメイン → アダプター → ユースケース → フロントエンド → 横断、のように内側から外側へ）。基盤側の問題は波及が大きく、初回の周回で先に見つけたい。
