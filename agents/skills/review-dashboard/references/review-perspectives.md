# レビュー観点カタログ

review-dashboard の区分レビュー（SKILL.md Step 4）で使う観点のカタログ。区分の定義には、この中からスコープに効くものを 3〜6 個割り当てる。観点は独立しており、レビュー実行時は観点ごとにサブエージェント（**審査区分**。`../../_shared/references/subagent-policy.md`）を並列起動する。

すべての観点に共通する前提:

- 各サブエージェントには**区分のスコープ**を渡し、スコープ内の**全対象ファイルを読ませる**。diff や変更履歴に依存しない。
- 判定基準はプロジェクトの規約（CLAUDE.md / spec/）。各サブエージェントには「まず CLAUDE.md を読む」よう指示する。規約に明記がない事項について一般論のベストプラクティスを押し付けない。
- 検出は**根拠（該当コード行・import 文・抜粋）とともに**報告させる。「怪しそう」ではなく「このコードがこう壊れる / この規約に反する」という形にする。
- 意図的な例外（spec/ または CLAUDE.md に規約として明記された設計判断、テストコード内の正当なスタブ等）は問題としない。判断に迷うものは確信度を下げて報告する。

## サブエージェントへの指示テンプレート

各観点で `{役割}` `{前提の補足}` `{やること}` `{根拠の要件}` を差し替えて渡す。

```text
あなたは{役割}をレビューするエンジニアです。

## 前提
- まず CLAUDE.md を読み、プロジェクトの構成・規約を把握する
{前提の補足。なければ省略}

## 対象
{区分のスコープ}（全ファイルを読む）

## やること
{各観点の「やること」}

## 出力（検出ごと）
- 場所: ファイルパス:行番号
- 内容: 何が問題か
- 根拠: 該当コードの抜粋と判断理由{根拠の要件}
- 重要度の提案: Critical / Warning / Info（最終判定はメインエージェントが行う）
- 確信度: 高 / 中 / 低
```

観点の目次:

1. 設計準拠
2. 正しさ
3. 完全性
4. エラーハンドリング・堅牢性
5. セキュリティ
6. パフォーマンス
7. テスト品質
8. コード品質
9. ドキュメント整合
10. 依存・設定

## 1. 設計準拠

**問い:** スコープ内のコードが、プロジェクトのアーキテクチャ規約（レイヤー分離・依存方向・ポート準拠・責務・命名）と spec/ の設計に従っているか。

architecture-audit の観点群と同種だが、こちらは区分スコープに絞って深掘りする。全体横断の構造監査が必要なら architecture-audit を使う。

**役割:** アーキテクチャと設計への準拠 / **前提の補足:** レイヤー構成・依存方向・責務・命名の規約を把握する。spec/ に対象スコープの設計ドキュメントがあれば読む

**やること:**

1. 各ファイルの import / 参照が規約で許された依存方向か確認する
2. そのレイヤーに属さない責務（ドメインでの I/O、ユースケースでの永続化詳細等）が混ざっていないか確認する
3. spec/ の設計（エンティティ・ポート・ユースケース定義）と実装が一致しているか確認する
4. 命名・エラー処理方式・配置が規約に従っているか確認する
5. 規約に明記がない事項は判定しない

## 2. 正しさ

**問い:** ロジックにバグがないか。エッジケース・境界条件・並行性・状態遷移で壊れないか。

規約に依存しない普遍的な観点。どの区分にも割り当てられる。

**役割:** コードの正しさ（プロダクションで実際に壊れるバグを探す）

**やること:**

1. 各関数・メソッドのロジックを読み、入力の全パターンで正しく動くか検証する
2. 特に以下を重点的に見る:
   - 境界条件（空配列・null/undefined・0・負数・最大値・空文字）
   - off-by-one、比較演算子の向き、論理式の誤り
   - 状態遷移の考慮漏れ（不正な遷移が可能、途中失敗時の不整合）
   - 非同期処理の競合（await 漏れ、並行更新、レースコンディション）
   - 型の穴（キャストや any で型検査を迂回している箇所の実行時整合）
3. 「どういう入力・状態のときに何が起きるか」を具体的に示せるものだけ報告する

**根拠の要件:** 壊れる具体的なシナリオ（入力・状態 → 誤った結果）を必ず含める

## 3. 完全性

**問い:** TODO・FIXME・仮実装・未処理の分岐・スタブが残っていないか。

implement-audit の検出対象と同種だが、こちらは区分スコープに絞る。全体横断の完全性監査が必要なら implement-audit を使う。

**役割:** 実装の完全性

**やること:**

1. TODO / FIXME / HACK / PLACEHOLDER 等のマーカーを探す
2. 未実装シグナル（not implemented、空の関数ボディ、return null だけの実装）を探す
3. 仮実装（ハードコードされたダミーデータ、テスト外の stub/mock）を探す
4. 不完全な制御フロー（一部のケースだけ実装された分岐、空の catch）を探す
5. テストコード内の mock / stub は正当なので除外する

## 4. エラーハンドリング・堅牢性

**問い:** 失敗しうる操作の失敗が正しく処理されているか。異常系で壊れず、原因が追えるか。

**役割:** エラーハンドリングと堅牢性 / **前提の補足:** エラー処理の規約（例外 / Result 型等）を把握する

**やること:**

1. 失敗しうる操作（I/O・ネットワーク・パース・外部 API）の失敗が処理されているか確認する
2. エラーの握り潰し（空の catch、ログだけ出して継続、失敗を成功として返す）を探す
3. エラーメッセージ・ログに原因究明に足る情報があるか確認する
4. 部分的失敗の整合性（複数書き込みの途中失敗、トランザクション境界、ロールバック）を確認する
5. 外部入力・外部応答の想定外の形（欠けたフィールド、想定外の型）への耐性を確認する
6. エラー処理の方式が規約と一致しているか確認する

**根拠の要件:** どの失敗が起きたときに何が壊れる/追えなくなるかを含める

## 5. セキュリティ

**問い:** 認証・認可・入力検証・シークレット管理に穴がないか。

**役割:** セキュリティ / **前提の補足:** 認証・認可の仕組みと外部入力の経路を把握する。対象は横断区分の場合、重点箇所から広げる

**やること:**

1. 認可の漏れ — 各エンドポイント・操作が適切な認証/認可チェックを通るか。他ユーザーのリソースに ID 指定でアクセスできないか（IDOR）
2. 入力検証 — 外部入力（リクエスト・フォーム・クエリ・ファイル）が検証・エスケープされているか。SQL/コマンド/パスのインジェクション、XSS の余地がないか
3. シークレット管理 — API キー・トークン・パスワードのハードコード、ログへの出力、クライアントへの露出がないか
4. セッション・トークンの扱い — 有効期限、失効、権限昇格の余地
5. 攻撃者の視点で「この入力・この順序で操作したら何ができてしまうか」を考える

**根拠の要件:** 攻撃シナリオ（誰が・何をすると・何ができてしまう）を必ず含める

## 6. パフォーマンス

**問い:** データ量・呼び出し回数が増えたときに破綻する構造がないか。

**役割:** パフォーマンス（マイクロ最適化ではなく構造的に破綻する箇所を探す） / **前提の補足:** データアクセスの構成（ORM・クエリ層）を把握する

**やること:**

1. N+1 クエリ（ループ内の DB アクセス・API 呼び出し）を探す
2. 全件取得してからメモリ上でフィルタ/ページングしている箇所を探す
3. 不要な再計算・再レンダリング（キャッシュ可能な重い計算の毎回実行、依存配列の誤り等）を探す
4. 無制限の読み込み（ページネーションなしの一覧、サイズ制限なしのファイル/リクエスト処理）を探す
5. 「データが1万件になったら」「同時アクセスが増えたら」を想定して読む
6. 計測なしに断定できない微差は報告しない

**根拠の要件:** 何が増えるとどうスケールしなくなるかを含める

## 7. テスト品質

**問い:** テストが仕様を守れているか。カバレッジの穴・検証しないテスト・壊れやすいテストがないか。

**役割:** テスト品質 / **前提の補足:** テストの構成・実行方法を把握する。spec/testcases/ があれば読み、定義されたテストケースを把握する。対象は対象コードとそのテストの両方

**やること:**

1. spec/testcases/ 定義とテスト実装を突き合わせ、未実装のケースを探す（spec がなければ主要な公開関数の正常系・異常系・境界のカバーを確認する）
2. アサーションが実質何も検証していないテスト（実行するだけ、自明な等式、モックの返り値をモックと比較）を探す
3. 異常系・境界条件のテスト欠落を探す
4. 壊れやすいテスト（実行順依存、時刻・乱数依存、外部環境依存）を探す
5. テスト対象の実装ではなくモックの動作をテストしているものを探す

## 8. コード品質

**問い:** 重複・過剰な複雑さ・デッドコード・不適切な抽象化が蓄積していないか。

**役割:** コード品質（好みの問題ではなく保守を実際に妨げるものを探す） / **前提の補足:** プロジェクトの規約・イディオムを把握する

**やること:**

1. 実質同じロジックの重複（コピーされて片方だけ直る危険があるもの）を探す
2. 使われていないコード（呼ばれない関数、到達しない分岐、使われない export）を探す
3. 過剰な複雑さ（深いネスト、1関数に詰め込まれた複数の責務、不要な間接層）を探す
4. 既存のユーティリティ・イディオムを使わず車輪を再発明している箇所を探す
5. スタイルの好み・些末な命名の趣味は報告しない

**根拠の要件:** 重複は両方の場所を示す

## 9. ドキュメント整合

**問い:** README・spec/・コメントが実装と一致しているか。

spec-sync の対象と同種だが、こちらは区分スコープに絞った検出のみ（spec の修正は行わない）。全体の同期が必要なら spec-sync を使う。

**役割:** ドキュメントと実装の整合性 / **前提の補足:** ドキュメントの構成を把握する。対象はドキュメントと、それが記述する実装の両方

**やること:**

1. README のセットアップ手順・コマンドが現在も動くか（存在するスクリプト・ファイルと突き合わせる）
2. spec/ の記述（エンティティ・API・画面・フロー）が実装と一致しているか
3. コード内のドキュメンテーションコメントが実装の現状と食い違っていないか
4. CLAUDE.md に書かれた規約・構成が実態と一致しているか

**根拠の要件:** どちらが正か（実装に合わせて直すべきか、実装側の誤りか）の見立ても添える

## 10. 依存・設定

**問い:** 依存関係・設定ファイル・CI 設定が健全か。

**役割:** 依存関係と設定 / **前提の補足:** ビルド・実行・CI の構成を把握する。対象は依存マニフェスト・設定ファイル・CI 定義

**やること:**

1. 使われていない依存、同じ用途の重複した依存を探す
2. 既知の脆弱性・非推奨（deprecated）が告知された依存を確認する（`npm audit` 等の監査コマンドが使えれば実行する）
3. 設定の重複・矛盾（環境間で食い違う設定、コードと設定ファイルの二重定義）を探す
4. コミットすべきでないもの（認証情報、ローカル固有のパス）が設定に混ざっていないか確認する
5. CI 定義が現在のプロジェクト構成（コマンド・パス）と一致しているか確認する
