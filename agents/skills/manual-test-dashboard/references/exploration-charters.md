# 探索チャーターカタログ

manual-test-dashboard の区分探索（SKILL.md Step 5）で使うチャーターのカタログ。区分の定義には、この中からスコープに効くものを 3〜5 個割り当てる。チャーターは独立しており、探索実行時はチャーターごとにサブエージェント（**判断区分** — 事象がバグかどうかの見極めを伴う。`../../_shared/references/subagent-policy.md`）を起動する（原則として順次）。

チャーターとは「この範囲で・この種類の問題を・この時間内に探す」という探索の依頼書。手順書とは違い、具体的な操作はサブエージェントがその場の画面を見て決める。

## 共通の指示テンプレート

各チャーターのサブエージェントには、以下のテンプレートに「チャーター固有の指示」（後述の各節）を埋め込んで渡す:

```text
あなたは agent-browser を使って探索的テストを行うテストエンジニアです。
手順書はありません。チャーターに従って自分で操作を選び、バグ・不整合を探します。

## 前提
- まずプロジェクトルートの CLAUDE.md を読む
- {spec/pages/ / spec/usecases/ 等、期待動作の根拠になるドキュメントのパス}を読む（あれば）

## 探索情報
- 対象区分: {区分名}
- スコープ: {画面・URL群と主要操作}
- サーバーURL: http://localhost:{port}
- セッション名: explore-{区分番号}-{チャーター番号}

## シードデータ情報
{seed-data.md から該当するアカウント・データを抽出して記載}

## チャーター
{チャーター固有の指示（下記カタログの該当節）}

## 制限時間
- このチャーターの探索制限時間は **15分**。超えたら探索を打ち切り、それまでの結果を返す。
- 各 agent-browser コマンドが20秒以上応答しない場合は、その操作を記録して別の操作に移る。
- 発見を深追いしすぎない — 再現できる最小手順を確立したら記録して探索に戻る。

## 進め方
1. セッションを開始する
   agent-browser --session explore-{区分番号}-{チャーター番号} --restore open http://localhost:{port}{開始パス}
2. ログインが必要なら、シードデータのアカウントでログインする
   （fill → press Tab → fill → press Tab → click。遷移後は wait --load networkidle）
3. スコープ内の画面を巡回しながら、チャーターに沿った操作を試す:
   - 操作前に snapshot --max-output 8000 で画面を把握し、操作対象は ref（@eN）で指定する
   - ページ遷移・操作の後は wait --load networkidle か wait --text で待つ（sleep は使わない）
   - 何を試したか（画面・操作・結果）を逐一記録する。問題がなかった操作も探索ログに残す
4. 問題らしき事象を見つけたら:
   - その時点の snapshot を取り、画面状態の要点（エラーメッセージ・表示内容）を記録する
   - 再現できる最小手順を確立する（もう一度同じ手順で起きるか確かめる）
   - 期待動作と、その根拠（spec / 画面表示 / データの整合性）を言語化する
5. 完了したらセッションを閉じる
   agent-browser --session explore-{区分番号}-{チャーター番号} --restore close

## 重要な原則
- スコープ外の画面には踏み込まない（リンクがあっても対象区分の画面に留まる）
- 破壊的な操作（削除・退会・全件クリア等）はテスト用とわかるデータに対してのみ行う
- スクリーンショットは確認用のみ。成果物として保存・添付しない。証跡は操作ログと snapshot（テキスト）。スクリーンショット・録画は実 Chrome でないと動かない
- snapshot は --max-output 8000 でコンテキストを保護する
- フォーム操作の注意点（fill → Tab、カスタム Select、ダイアログ内の snapshot 取り直し等）は
  agent-browser が期待通り動かないときに ../manual-test/references/test-execution.md の
  操作パターンを参照する

## 出力

以下の形式で結果を返すこと:

# チャーター: {チャーター名}（区分: {区分名}）

**探索時間**: {分}
**巡回した画面**: {URL一覧}

## 探索ログ

| # | 画面 | 試した操作 | 結果 |
|---|------|-----------|------|
| 1 | {URL} | {操作} | 問題なし / 発見#1 |

## 発見

### 発見#{連番}: {事象の一言サマリー}
- 画面: {URL}
- 再現手順: {最小手順。使ったデータ・アカウントも明記}
- 実際の動作: {起きたこと。snapshot から読み取れた画面の要点}
- 期待される動作: {期待と、その根拠}
- 重要度の提案: Critical / Warning / Info
- 確信度: 高 / 中 / 低

（発見がなければ「発見なし」と、試したのに問題が出なかった注目操作を挙げる）
```

チャーターの目次:

1. 主要フロー
2. 入力・バリデーション
3. データ整合
4. ナビゲーション・状態遷移
5. エラー・異常系
6. 認可・アクセス制御
7. 二重送信・冪等性
8. 表示・フィードバック

## 1. 主要フロー

**問い:** この区分の主要なユーザータスクが最初から最後まで完遂できるか。

どの区分にも割り当てられる基本チャーター。最初に実行すると、以降のチャーターが使う画面の土地勘にもなる。

```text
スコープの画面群でユーザーが達成したい主要タスク（作成→確認→編集→削除のような
ライフサイクル全体）を、普通のユーザーとして最後まで通す。

1. spec/scenario/ や画面の導線から、この区分の主要タスクを 2〜4 本特定する
2. 各タスクを最初から最後まで実行する。途中で詰まる・迷う・結果が確認できない箇所を探す
3. 完了後の状態を必ず確認する — 作成したものが一覧に出るか、編集が反映されるか、
   削除したものが消えるか
4. 成功メッセージ・リダイレクト先が操作の結果と合っているか確認する
```

## 2. 入力・バリデーション

**問い:** フォームが不正・極端な入力を正しく拒否し、正当な入力を正しく受け付けるか。

フォームを持つ区分に割り当てる。

```text
スコープ内の全フォームで、境界と不正入力を試す。

1. 各フォームで以下を試す:
   - 全項目空のまま送信 / 必須項目だけ空にして送信
   - 極端に長い文字列（500文字以上）、空白のみ、前後の空白付き
   - 特殊文字（<script>alert(1)</script>、'; DROP TABLE、絵文字、改行、日本語・多言語）
   - 数値項目に 0・負数・小数・巨大値・数値以外
   - 日付項目に過去・未来・不正な形式、期間指定なら開始 > 終了
2. 拒否される入力で: エラーメッセージが項目のそばに出るか、何が悪いか伝わるか、
   入力済みの他の項目が消えないか
3. 受け付けられた入力で: 保存後の表示が入力と一致するか（エスケープ漏れで
   HTML が実行される・壊れるはCritical）
4. クライアント側で拒否される入力が、URL 直接操作等でサーバーに届いた場合の挙動も
   可能な範囲で確認する
```

## 3. データ整合

**問い:** 同じデータがどの画面でも一致して表示されるか。操作の結果が正しく反映されるか。

CRUD・一覧・集計を持つ区分に割り当てる。

```text
データの流れを追いかけ、画面間の食い違いを探す。

1. 一覧と詳細で同じレコードの値（名前・状態・日付・金額）が一致するか突き合わせる
2. 件数・集計値を検算する — 一覧の件数表示と実際の行数、合計金額と明細の和
3. 作成・編集・削除の反映を確認する — 操作直後の一覧・詳細・関連画面（ダッシュボードの
   カウント等）に反映されるか。リロードしないと反映されないものはないか
4. 並び順・フィルタ・検索が宣言通りか — 「更新日順」が本当に更新日順か、フィルタ結果に
   条件外のものが混ざらないか、検索が該当するはずのものを取りこぼさないか
5. ページネーションの境界 — ページをまたぐ重複・欠落、最終ページ、0件時の表示
```

## 4. ナビゲーション・状態遷移

**問い:** 順当でない経路（戻る・リロード・直リンク・中断）で画面を行き来しても壊れないか。

どの区分にも割り当てられる。横断区分の主力チャーター。

```text
ユーザーが実際にやる「行儀の悪い」ナビゲーションを試す。

1. 各画面で URL 直打ちアクセス（ブックマーク相当）が正しく表示されるか。
   途中ステップ前提の画面（ウィザードの2枚目等）に直接入った場合の挙動
2. フォーム入力・送信の直後にブラウザバックする — 二重送信の警告、入力の消失、
   古い画面の表示
3. 操作の途中でリロードする — 編集途中、モーダルを開いた状態、送信直後
4. 多段の遷移を往復する — 一覧 → 詳細 → 編集 → 戻る → 戻る で状態（フィルタ・
   ページ位置・スクロール）が妥当に保たれるか
5. 処理中の二度押し・別画面への離脱 — ローディング中にリンクをクリックした場合の挙動
```

## 5. エラー・異常系

**問い:** 存在しないもの・不正なパラメータ・欠けたデータに対して、壊れずに適切なエラーを返すか。

どの区分にも割り当てられる。横断区分の主力チャーター。

```text
アプリが想定していなさそうな入力・状態を意図的に作る。

1. 存在しない ID の URL（/tasks/999999、/tasks/abc、/tasks/../etc）にアクセスする —
   404 相当の画面になるか。スタックトレース・生のエラーが露出したら Critical
2. クエリパラメータの改ざん — ?page=-1、?page=99999、?sort=不正値、?filter= に特殊文字
3. データが欠けた状態の画面 — 関連データが 0 件のときの詳細画面、集計対象がない
   レポート。空状態の表示があるか、クラッシュしないか
4. 想定外の順序 — 削除済みのものへの編集リンク（別タブ相当: 一覧を開いたまま削除して
   から古い詳細 URL を開く）
5. エラー画面から復帰できるか — エラー後に正常なページへ戻る導線があるか
```

## 6. 認可・アクセス制御

**問い:** ログインしていない・権限のないユーザーが、見えてはいけないもの・できてはいけない操作に到達できないか。

認証があるアプリでは必須。認可横断区分の主力チャーター。シードデータに**2人以上のユーザー**が必要。

```text
攻撃者の視点で、境界を越えられないか試す。

1. 未ログインで各画面の URL に直接アクセスする — ログインへリダイレクトされるか。
   API っぽい URL やファイルダウンロード URL も試す
2. ユーザーA でリソースを作成し、その詳細・編集・削除 URL をユーザーB のセッションで
   開く（IDOR）— 他人のデータが見える・操作できるなら Critical
3. 画面に出ないだけの操作を直接叩く — 一般ユーザーのセッションで管理者用 URL を開く
4. ログアウト後にブラウザバックする — 保護された画面のキャッシュが表示されないか。
   ログアウト後に古い画面からフォームを送信できてしまわないか
5. 発見の報告には「誰が・何をすると・何ができてしまうか」の攻撃シナリオを必ず含める

セッションの使い分け: ユーザーA・B・未ログインはそれぞれ別の agent-browser セッション
（explore-{区分番号}-{チャーター番号}-a / -b / -anon）を使う。
```

## 7. 二重送信・冪等性

**問い:** 同じ操作を素早く繰り返したとき、データが重複・破損しないか。

作成・決済・送信などの書き込み操作を持つ区分に割り当てる。

```text
せっかちなユーザーを演じる。

1. 送信ボタンを素早く2回クリックする（click @eN を間を置かず2連発）— レコードが
   2件できたら Warning 以上。金銭・通知が絡むなら Critical
2. 送信中にボタンが無効化・ローディング表示になるか確認する
3. 送信直後にリロードして「再送信しますか」相当の挙動を確認する。リロードで
   もう1件できるか
4. 同じ対象への操作を続けざまに行う — 完了→完了、削除→削除。2回目が適切に
   無視・エラーになるか
5. 作成後に戻るボタンでフォームに戻り、そのまま再送信する
```

## 8. 表示・フィードバック

**問い:** 画面がユーザーに正しく状況を伝えているか。極端なデータで表示が崩れないか。

閲覧中心の区分や、ユーザー向けの完成度を重視するプロジェクトに割り当てる。発見の多くは Info〜Warning。

```text
表示の品質と、状況の伝わりやすさを見る。

1. 空状態 — データが 0 件の一覧・ダッシュボードに、白紙ではなく案内（空である旨と
   次にすべきこと）が表示されるか
2. 極端なデータでの表示 — 極端に長い名前・大きな数値・多数の項目を持つデータを作り、
   レイアウト崩れ・オーバーフロー・省略表示を確認する
3. ローディング — 重そうな画面で読み込み中の表示があるか。何も出ずに固まって見えないか
4. フィードバック — 操作の成功・失敗が画面から分かるか。silent に何も起きない操作がないか
5. 表記の整合 — 同じ概念が画面によって別の名前で呼ばれていないか。日付・金額の
   フォーマットが画面間で揃っているか
6. ブラウザコンソールのエラー — 巡回中に console のエラー・警告が出ていないか確認する
```
