# 探索区分設計ガイド

manual-test-dashboard の初期化（SKILL.md Step 2）で、アプリを探索区分に分割するための方法。区分の切り方はローテーション全体の質を決める。**到達可能な全画面の被覆**と**1回で探索し切れるサイズ**の両立が目標。

review-dashboard の区分がコードの構造（レイヤー・ディレクトリ）で切るのに対し、manual-test-dashboard の区分は**ユーザーから見た画面・機能のまとまり**で切る。コードの構造は探索では見えない。

## 入力

区分を設計する前に、以下を読んでアプリの画面・機能構成を把握する:

- **spec/pages/** — 画面一覧・画面設計。存在すれば区分の主軸候補
- **spec/scenario/** — ユーザーシナリオ。基幹フローの特定に使う
- **ルーティング定義** — 実際の到達可能画面の一覧（app/routes/, pages/, ルーター設定等）。spec と実装がずれている場合はこちらが正
- **CLAUDE.md / README.md** — プロジェクトの目的・技術スタック・認証の有無
- **testing.md / spec/manual-tests/** — 既存の手順書。手順書が厚くカバーしている操作は探索の優先度を下げてよい

上記のドキュメントが乏しい場合のみ、サーバーを起動してトップページから主要リンクを辿る軽いクロールで画面一覧を得る（本格的な網羅調査が必要なら web-spec-explorer / web-spec-crawler を先に実行するようユーザーに提案する）。

## 区分の定義

1つの区分は次の組で定義する:

- **区分名** — ユーザーのタスクを表す短い名前
- **スコープ** — 対象の画面・URL群と、そこでできる主要操作。横断区分は「全画面（{重点}を重点）」の形で重点を明記する
- **チャーター** — そのスコープで探すもの。`exploration-charters.md` のカタログから 3〜5 個選ぶ

## 3つの軸

区分は次の軸を組み合わせて作る。

### 軸1: 機能領域主軸（基本）

ユーザーのタスク単位（認証・アカウント / タスク管理 / 請求 / 通知設定 など）で切るのが基本。1つのタスクを縦に貫いて探索できるので、作成→一覧→詳細→編集→削除のようなデータのライフサイクル全体の整合を見やすい。

spec/scenario/ があればシナリオ単位が自然な候補。CRUD を持つ機能領域には「主要フロー」「データ整合」「入力・バリデーション」が、閲覧中心の領域には「データ整合」「表示・フィードバック」「エラー・異常系」が効きやすい。

### 軸2: 画面グループ主軸（機能の切れ目が曖昧な場合）

管理画面 / 公開ページ / 設定画面群のように、機能よりレイアウト・利用者の切れ目が明確なアプリでは画面グループで切る。1つの画面グループ内でナビゲーションと表示の一貫性を見やすい。

### 軸3: 横断区分（常に追加を検討する）

機能領域の区分は「その領域の中」を見るが、領域をまたぐ問題は拾えない。次の横断区分を、プロジェクトに該当するものだけ追加する:

- **認可横断** — 未ログインアクセス・他ユーザーのリソースへの直リンク・権限外操作を全画面で試す。認証があるアプリでは必須
- **ナビゲーション・エラー横断** — 戻る・リロード・不正URL・存在しないIDへの耐性を全画面で試す。どのアプリでも有効
- **入力横断** — 特殊文字・長大入力・多言語をアプリ中のフォームで試す。フォームの多いアプリのみ

横断区分のスコープは機能区分と重複してよい。**試す操作が違えば重複は無駄ではない**（同じ画面でも、機能区分では主要フローを、認可区分では他人のデータへの直リンクを試す）。

## サイズの調整

1区分は「1回の実行で、チャーター別サブエージェントがスコープ内の全画面・全主要操作を試し切れる」サイズに収める。目安:

- **画面 3〜8 / 主要操作 〜15** 程度を上限の目安とする
- 超える場合は分割する。分割の単位は意味のあるまとまり（サブ機能・画面グループ）を使い、機械的な等分はしない
- 逆に小さすぎる区分（画面1つ）は隣接する区分に併合する。ローテーション1周が長くなりすぎるのを防ぐ

区分数の目安は **4〜10**。少なすぎると1回が重く浅くなり、多すぎると1周が長くなって鮮度が落ちる。小規模アプリなら 3 でもよい。

## 被覆の確認

設計を終えたら、到達可能なすべての画面（認証前・認証後の両方）が**いずれかの機能領域/画面グループ区分に含まれる**ことを確認する。横断区分は被覆に数えない（重点を絞って見るため、単独では被覆保証にならない）。

見落としやすいもの: エラーページ、メール経由でしか到達しない画面（パスワードリセット等）、モーダル・ウィザードの途中状態、管理者専用画面。どの区分にも入らない画面は最も近い区分に含めるか、独立した区分にする。

## 並び順

ダッシュボードの区分番号はローテーションの既定順になる。**ユーザーの基幹フローに近い区分を上に**置く（認証 → 主要タスク → 周辺機能 → 横断、のように）。基幹フローの問題はユーザー影響が大きく、初回の周回で先に見つけたい。
