# Manual Test Dashboard — 区分ローテーションによる定期探索的テスト

プロジェクトを区分（探索単位）に分割し、**実行1回につき1区分だけ**を agent-browser で徹底的に探索する。区分の定義と探索履歴は **GitHub Issue のダッシュボード**として管理し、リポジトリ上で共有・更新できるようにする。

アプリ全体を一度に探索すると、広く浅くなって見落としが増え、毎回同じ画面を撫でるだけになる。そこで初期化時に画面・機能構成を読み取って区分を設計し、以降はローテーションで1区分ずつ深掘りする。1回は狭いが、周回すれば全体を確実に覆う。

見つかった問題は再現確認したうえで、既存 Issue と重複しなければ Issue として起票する。このスキルは**コードを修正しない**。修正は issue-implement 等に委ねる。

近縁スキルとの棲み分け:

| スキル | やること | 入力 |
|--------|---------|------|
| manual-test | 手順書の忠実な実行（スクリプトテスト） | testing.md / spec/manual-tests/ |
| review-dashboard | コードの定期レビュー（静的） | ソースコード |
| **manual-test-dashboard** | 手順書のない探索でバグを発見（動的） | **動いているアプリ + 探索チャーター** |

## 前提条件

`agent-browser` CLI が必要。

```bash
agent-browser --version  # 確認
agent-browser install     # Chrome for Testing のセットアップ（初回のみ）
```

## アーキテクチャ

```text
メインエージェント（オーケストレーション）
  ├── サブエージェント: seed-data（シードデータ整備）
  ├── サブエージェント: explore-{区分番号}-{チャーター番号}（探索実行）× N
  └── サブエージェント: verify-{発見番号}（再現確認）× M
```

メインエージェントはオーケストレーションに集中する。ブラウザ操作はサブエージェントに委譲する。

## Workflow

1. 既存のダッシュボード Issue を探す（Step 1）
2. なければ初期化する — 区分を設計してダッシュボードを作成し、終了（Step 2）
3. あれば探索対象の区分を1つ選ぶ（Step 3）
4. テスト環境を準備する — サーバー起動・シードデータ・agent-browser（Step 4）
5. 区分を徹底探索する — チャーター別サブエージェント → 統合（Step 5）
6. 発見を再現確認する（Step 6）
7. 重複チェックのうえ Issue を起票する（Step 7）
8. ダッシュボードを更新する（Step 8）
9. レポート生成・クリーンアップ・完了報告（Step 9）

## Step 1: 既存ダッシュボード Issue の確認

open な Issue から、タイトルが `Manual Test Dashboard` のものを探す。

```bash
gh issue list --state open --search "Manual Test Dashboard in:title" --json number,title,body
```

本文の先頭に `<!-- manual-test-dashboard -->` マーカーがあるかで最終確認する（同名タイトルの誤検出を避けるため）。見つかればその Issue 番号と現在の本文を控えて Step 3 へ。見つからなければ初期化（Step 2）へ。

## Step 2: 初期化 — 区分の設計とダッシュボード作成

spec/pages/ / spec/scenario/ / ルーティング定義 / CLAUDE.md / README.md を読み、アプリの画面・機能構成を把握したうえで区分を設計する。設計の方法は `references/segmentation-guide.md` に従う。要点:

- 区分は **スコープ（画面・URL群とそこでできる操作）＋ チャーター（そのスコープで何を探すか）** の組で定義する
- ユーザーのタスク単位の機能領域を主軸にした区分と、認可等の横断観点の区分を組み合わせる
- 1区分は「1回の実行でスコープ内の全画面・全主要操作を探索し切れる」サイズに収める。目安は 4〜10 区分
- 到達可能なすべての画面がいずれかの区分のスコープに含まれるようにする
- チャーターは `references/exploration-charters.md` のカタログから、そのスコープに効くものを 3〜5 個選ぶ

設計した区分を下記フォーマットでダッシュボード Issue として新規作成する。本文は一時ファイルに書き出してから反映する。

```bash
gh issue create --title "Manual Test Dashboard" --body-file <一時ファイル>
```

初期化した実行では**探索まで進まない**。区分の切り方はローテーション全体の質を決めるので、まずユーザーに区分を確認してもらう。作成したダッシュボードの URL と区分一覧を報告して終了する。ユーザーが「初期化してそのまま1区分探索して」と明示した場合のみ Step 3 に続く。

### ダッシュボード本文のフォーマット

- 本文の先頭に `<!-- manual-test-dashboard -->` マーカーを置く（次回の検出用）。
- 区分ごとに `## {番号}. {区分名}` セクションを作る。番号はローテーションの既定順で、ユーザーの基幹フローに近い区分を上に置く。
- 各セクションは次の 4 行のリストで構成する。
  - `- スコープ:` 対象の画面・URL群と主要操作。横断区分は「全画面（{重点}を重点）」のように重点を明記する。
  - `- チャーター:` その区分で使う探索チャーターを読点区切りで列挙する。
  - `- 最終探索:` `YYYY-MM-DD` 形式。未探索は `-`。
  - `- 起票:` その区分の探索で起票した**オープンな** Issue 番号を空白区切りで列挙する。なければ `-`。
- テーブル・太字・絵文字・罫線・説明文などの装飾は使わない。構造だけで伝える。

### 本文の例

```markdown
<!-- manual-test-dashboard -->

## 1. 認証・アカウント

- スコープ: /login, /signup, /settings/profile（ログイン・登録・プロフィール編集・ログアウト）
- チャーター: 主要フロー、入力・バリデーション、認可・アクセス制御、二重送信・冪等性
- 最終探索: 2026-07-10
- 起票: #141

## 2. タスク管理

- スコープ: /tasks, /tasks/:id, /tasks/new（一覧・詳細・作成・編集・削除・完了操作）
- チャーター: 主要フロー、データ整合、入力・バリデーション、ナビゲーション・状態遷移
- 最終探索: -
- 起票: -

## 3. レポート・集計

- スコープ: /reports, /reports/:id（集計表示・期間フィルタ・エクスポート）
- チャーター: データ整合、表示・フィードバック、エラー・異常系
- 最終探索: -
- 起票: -

## 4. 認可横断

- スコープ: 全画面（未ログインアクセス・他ユーザーのリソースへの直リンクを重点）
- チャーター: 認可・アクセス制御
- 最終探索: -
- 起票: -

## 5. ナビゲーション・エラー横断

- スコープ: 全画面（戻る・リロード・不正URL・存在しないIDを重点）
- チャーター: ナビゲーション・状態遷移、エラー・異常系
- 最終探索: -
- 起票: -
```

## Step 3: 探索対象区分の選択

対象は次の優先順で1つだけ選ぶ。

1. **ユーザー指定**（「区分3を探索して」「認可の区分やって」等）があればそれ。
2. `最終探索: -`（未探索）の区分のうち、番号が最も小さいもの。
3. 未探索がなければ、最終探索日が最も古い区分。同日なら番号が小さいもの。

選択したら、区分のスコープが現状と合っているか軽く確認する（ルーティング定義や spec/pages/ と突き合わせる）。画面が消えている・URLが変わっている場合は区分定義を直してから進める（Step 8 でダッシュボードにも反映）。どの区分にも属さない大きな新画面群を見つけた場合は、新しい区分を末尾に追加する。**区分全体の作り直しはしない** — ユーザーが明示的に「区分を作り直して」「再初期化して」と言ったときだけ Step 2 をやり直す。

対象区分（番号・名前・スコープ・チャーター）をユーザーに報告してから探索を開始する。

## Step 4: テスト環境の準備

### 検証用ブランチの準備

探索は最新の `origin/main` の内容に対して行う。origin/main からブランチを切ってチェックアウトし、以降のサーバー起動・シード整備・コード参照はすべてその状態で行う。

```bash
ORIG_BRANCH=$(git branch --show-current)
git fetch origin
git switch -c "manual-test-dashboard/$(date +%Y%m%d)" origin/main
```

- 作業ツリーに未コミット変更がある場合はブランチを切り替えず、その旨を報告して中断する（変更の退避はユーザーに委ねる）
- 切り替えで依存関係（ロックファイル等）が変わっている場合は、サーバー起動前にプロジェクトの手順に従って依存をインストールし直す
- `origin/main` が存在しない場合（リモート未設定等）は、現在のブランチのまま探索する旨を完了報告に明記して続行する
- 元のブランチへの復帰と検証用ブランチの削除は Step 9 のクリーンアップで行う

### 成果物ディレクトリ

```bash
TEST_DATE=$(date +%Y-%m-%d)
```

成果物は `.manual-test-dashboard/{YYYY-MM-DD}/` に保存する。以降、この保存先を `{output_dir}` と表記する。

### agent-browser の確認とクリーンアップ

```bash
agent-browser --version
```

利用できない場合はユーザーにインストールを案内して中断する。

別セッションで agent-browser が使用中でなければ、残存プロセスをクリーンアップする:

```bash
CURRENT_SID=$(ps -p $$ -o sid= | tr -d ' ')
OTHER=$(ps -eo sid,comm | awk -v sid="$CURRENT_SID" '$2 ~ /agent-browser/ && $1+0 != sid+0')
if [ -n "$OTHER" ]; then
  echo "別セッションで agent-browser が使用中のため、プロセスはそのままにします"
else
  agent-browser close --all 2>/dev/null || true
  pkill -f "agent-browser" 2>/dev/null || true
  echo "agent-browser の残存プロセスをクリーンアップしました"
fi
```

タイムアウトの環境変数を設定する:

```bash
export AGENT_BROWSER_DEFAULT_TIMEOUT=20000   # コマンド単位: 20秒
export AGENT_BROWSER_IDLE_TIMEOUT_MS=120000  # daemon無操作: 2分で自動終了
```

### サーバー起動

`../manual-test/references/server-detection.md` を読み、その手順に従ってサーバー起動コマンドとポートを検出する。検出ポートが使用中なら空きポートを探して変更する。

```bash
PORT={port} nohup {起動コマンド} > /tmp/manual-test-dashboard-server.log 2>&1 &
echo $! > /tmp/manual-test-dashboard-server.pid

timeout 90 bash -c 'for i in $(seq 1 30); do curl -s -o /dev/null -w "%{http_code}" http://localhost:{port}/ | grep -q "200\|301\|302" && exit 0; sleep 2; done; exit 1'
```

応答がなければサーバーログを確認してエラーを報告する。起動結果（PID、ポート、URL）を `{output_dir}/server-info.md` に記録する。

### シードデータ整備

対象区分の探索に必要なデータ・アカウントをサブエージェントで整備する:

```text
あなたはテスト環境のセットアップを行うエンジニアです。

## 前提
- まずプロジェクトルートの CLAUDE.md を読み、プロジェクトの構成を把握する
- README.md のセットアップ手順も確認する

## 探索対象
{区分名}（スコープ: {画面・URL群と主要操作}）

## やること
1. 対象スコープの探索に必要な前提を洗い出す:
   - ログインに使うテスト用アカウント（一般ユーザーと、認可検証用にもう1人の別ユーザー）
   - 一覧・詳細・集計の表示確認に必要な既存データ（0件・1件・複数件のバリエーションがあると望ましい）
   - DB マイグレーション・環境変数・設定ファイル
2. プロジェクトの既存のシード仕組み（seed スクリプト、fixtures 等）を優先的に使って整備する
3. 整備後、探索に使うデータ・アカウントの一覧をまとめる

## 重要な原則
- 既存の本番データを上書き・削除しない
- テスト用データは明確にテスト用とわかる値にする（test-user@example.com 等）

## 出力
- 実行した準備作業の一覧
- 探索で使用するアカウント情報（ユーザー名・パスワード）
- 用意したデータの概要（何がどの状態で何件あるか）
- 問題があった場合はその内容と対処
```

結果は `{output_dir}/seed-data.md` に記録する。整備が不要な場合（静的サイト等）はスキップする。

## Step 5: 区分の徹底探索

区分に列挙されたチャーターごとにサブエージェントを起動する（委譲方式は `../_shared/references/subagent-policy.md`）。各チャーターの探索内容とプロンプトは `references/exploration-charters.md` に従う。

### 実行戦略: 原則として順次実行

チャーターは **1つずつ順番に実行する（順次実行）** のがデフォルト。ブラウザテストの並列実行はリソース消費・セッション衝突・データ干渉（あるチャーターが作成したデータを別チャーターが壊す等）の原因になる。並列にするのはユーザーが明示的に指示した場合のみで、**同時実行数は最大2つ**とする。

各サブエージェントには必ず以下を渡す:

- まずプロジェクトルートの CLAUDE.md を読む指示
- サーバー URL（http://localhost:{port}）
- 区分のスコープ（対象画面・URL群と主要操作。**スコープ外の画面には踏み込まない**）
- 担当するチャーターの指示（`references/exploration-charters.md` の該当節）
- シードデータ情報（`{output_dir}/seed-data.md` から該当部分を抽出）
- セッション名 `explore-{区分番号}-{チャーター番号}` と、タイムアウト・証跡のルール（exploration-charters.md の共通テンプレートに含まれる）
- spec/ に該当する設計ドキュメント（spec/pages/ / spec/usecases/ 等）があればそのパス — 期待動作の根拠として

各チャーターの結果は `{output_dir}/findings/charter-{番号}.md` に保存する。

### 統合

全チャーターの結果を統合し、同じ画面・同じ原因の発見をまとめる。各発見に重要度を付ける:

- **Critical** — 実害がある。データ破壊・クラッシュ・認可漏れ・主要フローの完遂不能
- **Warning** — 機能が期待通り動かない。誤ったデータ表示、バリデーション漏れ、握り潰されたエラー
- **Info** — UX・表示の細部、意図的な仕様かもしれないもの、確信度が低い発見

期待動作の根拠は spec/ / CLAUDE.md / 画面自身の表示（ラベル・説明文）から取る。**仕様が読み取れない挙動を一般論だけで問題と断定しない** — 迷うものは Info。

## Step 6: 再現確認（裏取り）

起票候補（Critical / Warning）は、起票前に**別セッションで再現確認する**。発見したサブエージェントの報告を鵜呑みにしない。

1. 発見ごとに再現用サブエージェント（セッション名 `verify-{発見番号}`）を起動し、**最小の再現手順**で同じ事象が起きるか確認する
2. サーバーログ（/tmp/manual-test-dashboard-server.log）に対応するエラー・スタックトレースがあれば根拠に加える
3. 再現しないもの・判断が割れるものは Info に落とす。偽陽性の起票はローテーション全体の信頼を損なう

**クリックが無反応な系の発見**は要注意。agent-browser の `click @ref` が React の合成 onClick に届かない既知の偽陽性がある（詳細は `../manual-test/SKILL.md` の Known Issue）。`eval` 経由の `button.click()` で発火するか切り分け、発火するなら agent-browser 起因の可能性が高いので、実装バグと断定せず確信度を下げて Info に落とすか、起票する場合はその旨を注記する。

再現確認の結果（再現手順・画面状態の snapshot 要点・サーバーログ抜粋）を `{output_dir}/findings/verified.md` に記録する。

## Step 7: Issue 起票（重複がなければ）

まず既存のオープン Issue を取得し、起票候補と突き合わせる。

```bash
gh issue list --state open --limit 200 --json number,title,body,labels
```

同じ問題（同じ画面・同じ原因）を指す Issue が既にあれば**起票しない**。タイトルの一致ではなく内容で判断する。ダッシュボード各区分の「起票:」行も手がかりにする。重複でスキップしたものは完了報告に「既存 #N がカバー」と記録する。

再現確認済みの Critical / Warning を起票する。Info は起票しない（ノイズを避ける。ユーザーが「全部 Issue にして」と指定した場合はそれに従う）。独立して対応できる単位で 1 Issue とし、同じ原因から生じた複数画面の問題は 1 つにまとめる。

```bash
gh issue create \
  --title "[explore] {区分名}: {問題の概要}" \
  --body "$(cat <<'EOF'
## 概要
manual-test-dashboard の探索的テスト（区分: {区分名} / チャーター: {チャーター}）で発見された問題。

## 再現手順
1. {サーバー起動}
2. {最小の再現手順}

## 期待される動作
{期待動作と、その根拠（spec/ / 画面表示 / 一般的な整合性）}

## 実際の動作
{実際に起きたこと。失敗時点の snapshot から読み取れた画面の要点}

## サーバーログ
{対応するエラー・スタックトレースの抜粋（あれば）}

## 参照
- ダッシュボード: #{ダッシュボード番号}
- 探索レポート: {output_dir}/report.md
EOF
)" \
  --label "manual-test-dashboard"
```

`manual-test-dashboard` ラベルが存在しない場合は事前に作成する:

```bash
gh label create manual-test-dashboard --description "manual-test-dashboard の探索的テストで発見された問題" --color "d93f0b"
```

起票した Issue 一覧は `{output_dir}/issues.md` に記録する。

## Step 8: ダッシュボードの更新

旧本文をベースに、変わった分だけ手を入れる。本文を一時ファイルに書き出してから反映する。

1. 今回探索した区分の `最終探索:` を今日の日付にする。
2. 同区分の `起票:` に今回起票した Issue 番号を追記する。
3. **全区分**の `起票:` 行から close 済みになった Issue 番号を外す（この付け直しは AI 判断を要さないので毎回全区分に行う）。すべて外れたら `-` にする。
4. Step 3 でスコープ修正・区分追加をした場合はそれも反映する。
5. それ以外の区分の定義・並び順には触れない。

```bash
gh issue edit <ダッシュボード番号> --body-file <一時ファイル>
```

## Step 9: レポート・クリーンアップ・完了報告

### レポート生成

探索の全体像を `{output_dir}/report.md` にまとめる: 対象区分、実行チャーターと探索した画面・操作の一覧、発見（重要度別）、起票した Issue、Info として残した気づき、恒常的にチェックすべきと感じた操作（testing.md / spec/manual-tests/ への追加候補として提案）。

### クリーンアップ

```bash
agent-browser close --all 2>/dev/null

kill $(cat /tmp/manual-test-dashboard-server.pid) 2>/dev/null
rm /tmp/manual-test-dashboard-server.pid /tmp/manual-test-dashboard-server.log 2>/dev/null

git switch "$ORIG_BRANCH"
git branch -D "manual-test-dashboard/$(date +%Y%m%d)"
```

その後、Skill ツールで `/agent-browser-cleanup` を呼び出し、別セッションで使用中でなければ残存プロセスをすべて終了してクリーンな状態に戻す。

### 完了報告

```text
区分「{番号}. {区分名}」の探索的テストが完了しました！ → ダッシュボード: {URL}

- スコープ: {スコープ} / チャーター: {チャーター}
- 探索: {探索した画面数}画面 / {実行した操作の概数}
- 発見: Critical {数} / Warning {数} / Info {数}
- 起票した Issue: {#番号一覧 / なければ「なし」}
- 重複でスキップ: {既存 #番号がカバー / なければ省略}
- 区分の変更: {スコープ修正・追加した区分 / なければ省略}
- 回帰テスト手順への追加候補: {あれば1行で / なければ省略}
- 次回の探索対象: {番号}. {区分名}
```

初期化のみの実行では、ダッシュボード URL と区分一覧（番号・名前・スコープ・チャーター）を報告し、区分の切り方に過不足がないかユーザーに確認を求める。

## 原則

- **1回の実行で1区分だけ** — 狭く深く。全体は周回で覆う。複数区分をまとめて探索しない
- **origin/main を基準に探索する** — origin/main からブランチを切ってサーバーを起動して確認し、実行時のブランチの状態に依存しない。終了時に元のブランチへ戻して検証用ブランチを削除する
- **手順書に縛られず、スコープには縛られる** — 探索の中身はチャーターに従って自由に。ただしスコープ外の画面には踏み込まない（それは別の区分の番）
- **コードは修正しない** — 発見・起票・ダッシュボード更新まで。修正は issue-implement 等に委ねる
- **期待動作の根拠を持つ** — spec/ / CLAUDE.md / 画面自身の表示から期待を導く。根拠のない「こうあるべき」で断定せず、迷うものは Info
- **再現確認できたものだけ起票する** — 別セッションで最小手順の再現を確認する。偽陽性は Info に落とす
- **重複起票しない** — 既存 Issue の内容と突き合わせてから起票する
- **ダッシュボードの構造を安定させる** — 区分の定義・並び順は原則引き継ぐ。作り直しはユーザー指示時のみ
- **環境を汚さない** — 探索で作成したデータは記録し、破壊的な操作（削除・退会等）はテスト用データに対してのみ行う
- **サーバーは必ず停止する** — 探索終了後（成功・失敗問わず）サーバーを停止し、ポートを解放する
- **スクリーンショットは成果物にしない** — 確認用に撮るのはよいが、レポートへの保存・添付はしない。証跡は操作ログと snapshot（テキスト）で残す。なお、スクリーンショット・録画は実 Chrome でないと動かない
- **セッションは分離する** — チャーター・再現確認ごとに別セッションを使い、状態の干渉を防ぐ
- **タイムアウトを必ず設定する** — チャーターは15分、コマンドは20秒を上限とし、超過したら打ち切って結果を返す
- **順次実行がデフォルト** — チャーターは1つずつ実行。並列は明示指示があるときだけ、最大2つまで
- 委譲方式・並列実行・失敗時の扱いは `../_shared/references/subagent-policy.md` に従う
