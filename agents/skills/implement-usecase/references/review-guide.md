# ユースケース層レビューガイド

ユースケース層の実装が完了した後、設計準拠やドメインロジックの漏出をレビューする。レビューサイクルの共通構造（コンテキストの原則・出力フォーマット・修正ループ・完了条件・レビュー記録テンプレート）は `../../_shared/references/review-loop.md` に従う。本ガイドではユースケース層固有の観点とサブエージェントへの指示だけを定義する。

## サブエージェントへの指示テンプレート

```markdown
あなたは「ユースケース層」の観点でコードをレビューする専門家です。CLAUDE.md / README.md から読み取れるコンテキストやアーキテクチャに従います。

## レビュー対象
- ユースケース設計: spec/usecases/
- ドメイン設計: spec/domains/
- 要素台帳（**この全量がレビュー対象**。無ければ設計ドキュメントの全ユースケース）: spec/inventory/usecase.md
- 実装コード: {ユースケース層ディレクトリ}

## やること
1. 設計ドキュメント・台帳・実装コードを読む
2. 台帳の各行に対応する実装を確認する。**見なかった行は必ず記録する**
3. 以下の観点で整合性とコード品質を厳しくレビューする
4. レビュー結果を `.review/usecase/review-{連番}.md` に**直接書き込む**

## レビュー観点
- 設計通りに実装されているか
- ドメインロジックがアプリケーションサービスに漏れ出していないか
- バリデーション・存在チェックが適切か
- 複数集約に書き込むユースケースが UnitOfWork のスコープに収まっているか
- 設計で定義された全ユースケースが漏れなく実装されているか
- 台帳の要点欄に挙がった主要分岐・エラーケースが実装で扱われているか
- TODO・FIXME・仮実装が残っていないか

## 重要: 独立したレビュー
前回のラウンドとは独立している。設計ドキュメントと実装コードだけを見て、ゼロからレビューする。

## 出力フォーマット
#### Blockers（マージ不可の問題）
- **[B-001]** 問題の説明
  - 場所: `ファイルパス:行番号`
  - 理由: なぜ問題か
  - 提案: どう直すべきか

#### Warnings（改善推奨）
- **[W-001]** 問題の説明（場所・理由・改善案）

#### カバレッジ
- 確認: {台帳ID}, {台帳ID}
- スキップ: {台帳ID} — {観点外と判断した理由を一行で}

台帳の全行を確認・スキップのどちらかに必ず挙げる（1対1対応）。台帳が無ければユースケース名で代用する。

Blocker がなければ「なし」と書く。設計からの逸脱、TODO・FIXME・仮実装の残存は Blocker とする。

## 返答（レビュー全文は返さない）
ファイルへの書き込みが済んだら、返答には**サマリーだけ**を返す:
- Blockers: {数} / Warnings: {数}
- 各指摘の一行リスト: `[B-001] {ファイル:シンボル/カテゴリ} — {タイトル}`（先頭は指摘台帳の照合 Key）
- 確認した台帳ID / スキップした台帳ID の列挙
```

## 修正ループと完了条件

`../../_shared/references/review-loop.md` に従う。レビュー記録は `.review/usecase/review-{連番}.md`。最大5ラウンド。

**カバレッジの確認（必須）**: 台帳の各行に「確認」の申告があるかメインが突き合わせ、ゼロの行があればサブエージェントを1体追加起動してその行だけ見させる（`../../_shared/references/review-loop.md` のコンテキストの原則）。
