ドキュメントは対象の現在を述べる。書き手と過去に言及しない。

読者が知りたいのは、対象が今どうあるかと、自分が今どうすべきかであって、そこに至った道のりや書き手の気持ちではない。文ごとに、主語が対象か、書き手や過去かを問い、後者なら削る。この一つの問いで、経緯・弁明・言い直し・ぼかしはすべて落ちる。

- 経緯（「当初は〜だったが」「議論の結果〜になった」）は過去を語っている。今の状態だけを書く
- 弁明（「本来は〜すべきだが」「暫定的に」「〜で申し訳ないが」）は書き手を語っている。決めたことを書く
- 言い直し（「つまり」「言い換えると」、規則をなぞるだけの例）は書き手が二度言っている。よい方を一つ残す
- ぼかし（「基本的に」「原則として」「〜かもしれない」「〜が望ましい」）は書き手の迷いを語っている。「する」「しない」で書く

## 残るもの

削るのは言葉であって事実ではない。

- 理由は、今も成り立つ制約なら残る。「Bがサポートされないため、Aが必要」は対象の現在を述べている。「Bが遅かったのでAを入れた」は過去を述べている。今も成り立つなら「Bが遅いため、Aを使う」と現在形に書き直す。成り立たないならユーザーに確認する
- 未決は、結論を補わずに何が決まっていないかを書く
- 例外は、条件を列挙した断定文にする

経緯を消すと論理がつながらなくなる箇所では、経緯が現在の事実を隠し持っている。その事実を現在形で書き足す。書き足せないなら、推測で補わずユーザーに確認する。

## IssueとPR

- Issueの対象は問題だ。今起きていること、再現手順、閉じる条件を書く
- PRの対象は変更だ。変わること、変える理由、確かめた方法と結果を書く

## 例

悪い例:

```markdown
当初はRedisを検討していたが、運用負荷の観点から議論した結果、現時点では暫定的にSQLiteを使うこととしている。つまり、基本的にはSQLiteで問題ないはずだが、将来的に見直す可能性がある。
```

良い例:

```markdown
運用対象を増やさないため、ストレージはSQLiteを使う。Redisへ移行するかは決まっていない。
```

## 文章

文の単位では[明快な文](../_shared/references/clear-writing.md)に従う。語調は既存のドキュメントに合わせ、新規なら常体で書く。

## 進め方

1. 直す範囲を決める。引数`target`があれば指定されたものを、なければgit diffの変更分や会話中で扱っているドキュメントを範囲にする
2. 文ごとに主語を問い、書き手と過去を削る
3. 明快な文に従って、残った文を整える
4. 削る前と後を比べ、対象についての現在の事実が減っても変わってもいないことを確かめる
5. 記法の整形が必要ならmarkdown-styleに渡す

削ると意味が変わる箇所は、ユーザーに確認する。
