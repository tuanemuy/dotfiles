ドキュメントは対象の今の姿を述べる。書き手と経緯を語らない。

読者が知りたいのは、対象が今どうあるかと、自分が今どうすべきかである。書き手の気持ちや、そこに至った道のりは読者の役に立たない。いつ誰が読んでも同じ意味になるように書く。文ごとに、対象の今について述べているかを問い、述べていなければ削る。

- 経緯（「当初は〜だったが」「以前は〜だった」「議論の結果〜になった」）は対象の過去や、書き手がたどった道のりを語っている
- 書いた時点に寄りかかる記述（「現時点では」「先月」）は読む時点で意味が変わる
- 弁明（「本来は〜すべきだが」「〜で申し訳ないが」）は書き手の事情を語っている
- 言い直し（「つまり」「言い換えると」、規則をなぞるだけの例）は書き手が二度言っている
- ぼかし（「基本的に」「〜かもしれない」「〜と思う」）は書き手の迷いを語っている

## 残るもの

言葉を削り、内容は残す。読者はドキュメントから、対象がどうあるか、なぜそうなのか、自分が何をどれほど強く求められているかを受け取る。経緯・弁明・ぼかしの中にあっても、これらを伝えている言葉は残す。

指示の文書では、求める強さも内容に含まれる。「しない」と「絶対にしない」は別の指示で、強さを伝える言葉を削ると指示が変わる。

今も成り立つかわからない事実や理由は、元の言い方のまま残す。

## 例

悪い例:

```markdown
当初はRedisを検討していたが、運用負荷の観点から議論した結果、現時点では暫定的にSQLiteを使うこととしている。つまり、基本的にはSQLiteで問題ないはずだが、将来的に見直す可能性がある。
```

良い例:

```markdown
運用対象を増やさないため、ストレージはSQLiteを使う。Redisへ移行するかは決まっていない。
```

## 文章

経緯や弁明を取り除いても、文が読みにくければ対象の姿は読者に伝わらない。文章は[明快な文](../_shared/references/clear-writing.md)に従って書く。

## 範囲

対象の今の状態を述べるドキュメントに使う。仕様書・設計メモ・READMEと、CLAUDE.md・SKILL.mdのような指示の文書がこれにあたる。

引数`target`があれば指定されたものを直す。なければgit diffの変更分か、会話中で扱っているドキュメントを直す。記法の整形が必要ならmarkdown-styleに渡す。

## 完了の条件

直したあと、次のすべてを確かめる。

- ドキュメントと各部分の目的を言える。目的のために必要な情報がそろい、どの変更も目的を損なっていない
- 書き手や経緯について述べる文と、書いた時点に寄りかかる記述がない
- 直す前にあった、対象の今についての事実が、減っても変わってもいない
- 推測で足した文と、わからないことを言い切りに変えた文がない
- 変えた文は、どれも変える前より読みやすい
- 読者として通して読み、引っかかる箇所がない

## 報告

直した後に次を伝える。確かめることや誤りを直すこと、構成を組み替えることは、このスキルでは行わない。

- 今も成り立つかわからず、元の言い方のまま残した箇所
- 誤りや抜けに気づいた箇所
- 全体の論理や構成で気になった箇所。節の重複、順序、論理の飛びなど
