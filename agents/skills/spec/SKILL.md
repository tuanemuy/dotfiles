# Spec

`spec/idea.md` の初期アイデアをもとに、段階的に設計ドキュメントを作成する。
体験設計（シナリオ・ページ設計）は本スキルで行い、技術設計（ドメイン以降）は spec-domain スキルに引き継ぐ。
各フェーズは前フェーズの成果に基づいて進む。レビューで見つかった問題を修正し、レビューが完了してから次へ進む（完了条件は「レビューの共通原則」参照）。

## 設計思想

### 決めるべきことだけを決める

spec が持つのは**複数の Issue にまたがって効く決定**（用語・ドメインと境界・ビジネスルール・ポートの契約・シナリオ・画面構成）。ここがブレると実装が Issue ごとに食い違い、後から直すコストが高い。

**1つの Issue の中で閉じる詳細**（入出力の全フィールド、エラー分岐の網羅、境界値、処理手順）は spec に書かない。実装時に issue-planner がコードを読んで決めるほうが正確で、先回りしても実装で決め直すことになる。

ゴールは「実装者が質問なしにコードを書ける」ことではなく、**「実装者が設計を判断し直さずにコードを書ける」**こと。

### ユーザー体験を起点にする

シナリオ → 画面構成 → ドメイン → ユースケース → テストケースの順で具体化する。永続化も物理スキーマではなくポートの契約として設計し、インフラの選択を実装時まで遅延させる。

### 決定は spec に現在形で表す

設計判断の唯一の記録は spec/ 本体。採用した設計・規約・意図的な例外を現在形で書き、経緯・代替案・変更履歴は spec に書かない（旧仕様は git 履歴が持つ）。検討した代替案とトレードオフはコミットメッセージと完了サマリーで報告する（`../_shared/references/adr-guide.md`）。

## Phase 0: 準備

### idea.md が存在する場合

`spec/idea.md` を読み、設計を進めるうえで不明な点・曖昧な点を洗い出す。
質問がある場合はすべてまとめて一度にユーザーに確認する。回答を得たら `spec/idea.md` に反映し、Phase 1 へ進む。

### idea.md が存在しない場合

ユーザーにヒアリングを行い、以下を明らかにする:
- プロダクトの目的・解決したい課題
- 想定するユーザー
- 主要な機能・やりたいこと
- 技術的な制約や前提（あれば）

回答をもとに `spec/idea.md` を作成し、ユーザーに確認する。OKが出たら Phase 1 へ進む。

### 共通

- `spec/index.md` を設計のインデックスとして使用する（各フェーズの成果物へのリンクと現在の進捗を記載する）
- なければ作成してから開始する
- Phase 0 の確認が完了したら、以降は最後まで自走する（フェーズ間でユーザー承認を挟まない）

## Workflow Overview

```
Phase 0: 準備
  spec/idea.md の確認（なければヒアリングして作成）
  → 不明点をまとめてユーザーに一括確認
  → 確認完了後、以降は自走

Phase 1: シナリオ設計
  spec/idea.md → spec/scenario/index.md → spec/scenario/${category}.md
  → レビュー・修正 → spec/index.md 更新

Phase 2: ページ設計
  シナリオ → spec/pages/index.md（画面一覧と機能）
  → レビュー・修正 → spec/index.md 更新

Phase 3: 技術設計（spec-domain スキルに委譲）
  ドメイン設計 → ユースケース設計 → テストケース定義 → クロスフェーズ検証

Phase 4: マニュアルテストドキュメント生成（spec-manual-test スキルに委譲）
  spec/ の成果物からシナリオ単位のテスト手順書を生成 → spec/manual-tests/
```

途中のフェーズから再開する場合は、既存の成果物を確認して該当フェーズから開始する。

## 各フェーズの手順と成果物

各フェーズは指定のガイド（または委譲先スキル）に従って進め、完了ごとに `spec/index.md` を更新する。

| フェーズ | 手順 | 成果物 |
| --- | --- | --- |
| 1. シナリオ設計 | `references/scenario-guide.md` | `spec/scenario/index.md`（一覧）、`spec/scenario/${category}.md`（カテゴリ別詳細） |
| 2. ページ設計 | `references/pages-guide.md` | `spec/pages/index.md`（画面構成） |
| 3. 技術設計 | spec-domain スキルに委譲 | `spec/domains/`、`spec/usecases/`、`spec/flows/`、`spec/testcases/` |
| 4. マニュアルテスト | spec-manual-test スキルに委譲 | `spec/manual-tests/index.md`（一覧と実行管理表）、`spec/manual-tests/${category}.md` |

## レビューの共通原則

`../_shared/references/spec-review.md` に従う。とくに**指摘の受理基準** — 上流の記述を引用できない「こういうケースも考えられる」系の指摘は受理せず実装フェーズに委ねる — を各フェーズのレビュー委譲プロンプトで必ず伝える。

## 完了報告

完了時は、実施した範囲に応じて以下を簡潔に報告する。

- 作成・更新した設計ドキュメント
- 主要な設計判断と、検討した代替案・トレードオフ
- 未収束のレビュー指摘とレビュー記録の参照先（ある場合）
- 実装に進む場合の推奨手順

小規模な実装には implement を使う。それ以上の実装は spec-to-issues で縦スライス Issue に分割し、issue-implement で Issue ごとに進める。使い分けは implement スキルに従う。

---

## 原則

- 各フェーズは前フェーズの成果に基づいて進める — 飛ばさない
- レビューで見つかった問題は即座に修正する — 先送りにしない
- スコープクリープを避け、idea.md の範囲に集中する
- 要件に対応しない記述を足さない — 実装時に決まる詳細は issue-planner に委ねる
