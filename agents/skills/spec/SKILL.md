# Spec

`spec/idea.md` の初期アイデアをもとに、段階的に設計ドキュメントを作成する。
体験設計（シナリオ・ページ設計）は本スキルで行い、技術設計（ドメイン以降）は spec-domain スキルに引き継ぐ。
各フェーズは前フェーズの成果に基づいて進む。レビューで見つかった問題を修正し、レビューが完了してから次へ進む（完了条件は「レビューの共通原則」参照）。

## 設計思想

### 実装可能な設計を出す

このスキルのゴールは「設計フェーズを完了すること」ではなく、「実装者が設計書だけを読んで、質問なしにコードを書ける状態を作ること」。

### ユーザー体験を起点にする

シナリオ → 画面構成 → ドメイン → ユースケース → テストケースの順で具体化する。永続化も物理スキーマではなくポートの契約として設計し、インフラの選択を実装時まで遅延させる。

### 決定を記録する

設計中に下した非自明な判断は ADR として記録する。「なぜそうしたか」が残っていれば、実装者が迷わず、将来の変更時にも意図を追える。

## ADR（Architecture Decision Records）

設計中に非自明な判断を下したら、プロジェクトルートの `.adr/NNN-title.md` に記録する。記録基準・記載項目・supersede の扱いは `../_shared/references/adr-guide.md` を参照。

## Phase 0: 準備

### idea.md が存在する場合

`spec/idea.md` を読み、設計を進めるうえで不明な点・曖昧な点を洗い出す。
質問がある場合はすべてまとめて一度にユーザーに確認する。回答を得たら `spec/idea.md` に反映し、Phase 1 へ進む。

### idea.md が存在しない場合

ユーザーにヒアリングを行い、以下を明らかにする:
- プロダクトの目的・解決したい課題
- 想定するユーザー
- 主要な機能・やりたいこと
- 技術的な制約や前提（あれば）

回答をもとに `spec/idea.md` を作成し、ユーザーに確認する。OKが出たら Phase 1 へ進む。

### 共通

- `spec/index.md` を設計のインデックスとして使用する（各フェーズの成果物へのリンクと現在の進捗を記載する）
- なければ作成してから開始する
- Phase 0 の確認が完了したら、以降は最後まで自走する（フェーズ間でユーザー承認を挟まない）

## Workflow Overview

```
Phase 0: 準備
  spec/idea.md の確認（なければヒアリングして作成）
  → 不明点をまとめてユーザーに一括確認
  → 確認完了後、以降は自走

Phase 1: シナリオ設計
  spec/idea.md → spec/scenario/index.md → spec/scenario/${category}.md
  → レビュー・修正 → spec/index.md 更新

Phase 2: ページ設計
  シナリオ → spec/pages/index.md（画面一覧と機能）
  → レビュー・修正 → spec/index.md 更新

Phase 3: 技術設計（spec-domain スキルに委譲）
  ドメイン設計 → ユースケース設計 → テストケース定義 → クロスフェーズ検証

Phase 4: マニュアルテストドキュメント生成（spec-manual-test スキルに委譲）
  spec/ の成果物からシナリオ単位のテスト手順書を生成 → spec/manual-tests/

※ ADR は全フェーズを通じて随時作成 → .adr/
```

途中のフェーズから再開する場合は、既存の成果物を確認して該当フェーズから開始する。

## Phase 1: シナリオ設計

`references/scenario-guide.md` を読み、その手順に従ってシナリオ設計を行う。

成果物:
- `spec/scenario/index.md` — シナリオ一覧
- `spec/scenario/${category}.md` — カテゴリ別の詳細シナリオ

完了後、`spec/index.md` を更新する。

## Phase 2: ページ設計

`references/pages-guide.md` を読み、その手順に従ってページ設計を行う。

成果物:
- `spec/pages/index.md` — 画面構成

完了後、`spec/index.md` を更新する。

## Phase 3: 技術設計

Phase 2 が完了したら、spec-domain スキルを使ってドメイン設計以降の技術設計を進める。
spec-domain がドメイン設計 → ユースケース設計 → テストケース定義 → クロスフェーズ検証を実行する。

---

## Phase 4: マニュアルテストドキュメント生成

Phase 3 が完了したら、spec-manual-test スキルを使ってマニュアルテストドキュメントを生成する。
spec-manual-test がシナリオ・ページ・ユースケース・テストケースをもとに、人間が実行可能な手順書を `spec/manual-tests/` に生成する。

成果物:
- `spec/manual-tests/index.md` — テスト一覧と実行管理表
- `spec/manual-tests/{scenario-category}.md` — シナリオ別テストドキュメント

完了後、`spec/index.md` を更新する。

## レビューの共通原則

各フェーズのレビューでは以下を守る:

- 対象ディレクトリの `review/` 配下に連番ファイル（`001.md`, `002.md`, ...）で記録する
- 無駄な情報を省き、対応が必要な問題点のみ記載する
- ドキュメントの責任範囲をそのレビューの対象に限定する
- 指摘は Blocker（前フェーズとの矛盾・欠落など、設計として成立しない問題）と Warning（改善推奨）に分類する
- **問題が見当たらなければ「指摘ゼロ」と明示してよい** — 無理に粗探しをしない。厳しく見ることと、出す指摘がなくなるまで深掘りの粒度を下げ続けることは別。そのフェーズの責務範囲で設計が成立していれば、より細かい記述の余地があること自体は指摘にしない

### トリアージと完了条件

指摘の仕分けは `../_shared/references/review-loop.md` の指摘台帳方式に従う。台帳は対象ディレクトリの `review/triage.md` に置く。

- 各ラウンドの指摘はまず台帳と突き合わせ、Key が一致する既出指摘は判定を継承して再審議しない
- 新規の指摘は `fix` / `wont-fix`（一行理由を記録）に仕分け、`fix` を修正して再レビューする
- **`fix` と仕分けた指摘が0件のラウンドでレビュー完了**（台帳に記録済みの指摘は件数に含めない）。最大5ラウンド。収束しない場合は残った指摘をまとめてユーザーに報告し、判断を委ねる

### 後片付け

フェーズのレビューが完了条件を満たしたら、対象ディレクトリの `review/` を削除する（`../_shared/references/review-loop.md` の「後片付け」参照）。指摘は成果物に反映済みか台帳で決着しており、残すと後続セッションの検索に紛れ込んでコンテキストを浪費する。最大ラウンドに達して収束しなかったフェーズの `review/` は削除せず残し、完了報告に明記する。

### 各ラウンドの独立性

レビューの各ラウンドは独立した完全なレビューとして実施する。前回のレビューファイルを読まずに、成果物とチェックリストだけを見て一から評価する。前回の指摘への対応確認ではなく、毎回ゼロベースで見直す。再登場する既出指摘は台帳の判定継承で吸収して収束させる。

### レビューの3軸

すべてのフェーズで以下の3軸を確認する（各ガイドに詳細なチェック項目がある）:

1. **実装可能性**: 実装者がこの設計書だけ見てコードを書けるか。型、シグネチャ、制約が揃っているか
2. **アーキテクチャ適合性**: ルールに違反していないか
3. **トレーサビリティ**: 前フェーズの成果物と整合しているか。漏れているシナリオ・要件がないか

## 完了報告

すべてのフェーズが完了したら、作成した設計ドキュメントのサマリーを出す。

```
設計が完了しました！

## 成果物

### シナリオ
- spec/scenario/index.md
- spec/scenario/${category}.md (x{数})

### ページ設計
- spec/pages/index.md

### 技術設計（spec-domain）
- spec/domains/
- spec/usecases/
- spec/flows/
- spec/testcases/

### マニュアルテスト（spec-manual-test）
- spec/manual-tests/index.md
- spec/manual-tests/${category}.md (x{数})

### ADR
- .adr/ (x{数} 件)
```

実装に進む場合の次のステップも添える: 小規模なら implement で一括実装、それ以上なら spec-to-issues で縦スライス Issue 化 → issue-implement で 1 Issue ずつ実装（使い分けの目安は implement スキル参照）。

## 原則

- 各フェーズは前フェーズの成果に基づいて進める — 飛ばさない
- レビューで見つかった問題は即座に修正する — 先送りにしない
- スコープクリープを避け、idea.md の範囲に集中する
- 非自明な判断は ADR に記録する
- `spec/index.md` はフェーズ完了ごとに更新し、成果物と進捗を反映する
