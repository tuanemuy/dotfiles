# Spec

`spec/idea.md` の初期アイデアを受け、Implementation Ready な `spec/` を作る。完了の定義・層・独立した読み・不変条件・予算は `../_shared/references/spec-ready.md` に従う。このスキルが定めるのは契約と範囲。

設計はユーザー体験を起点にする。シナリオと画面構成が上流で、ドメイン・ユースケース・テストケースはそこから決まる。永続化は物理スキーマではなくポートの契約として設計し、インフラの選択を実装時まで遅らせる。

## 契約

出典は `spec/idea.md`。`idea.md` の要求を番号付きの台帳にし、範囲にする層を添えて `spec/review/contract.md` に置く。

`idea.md` が無ければ、次をユーザーに聞いて `idea.md` を作り、内容の確認を取る。

- プロダクトの目的・解決したい課題
- 想定するユーザー
- 主要な機能
- 技術的な制約や前提

着手時の質問への回答は `idea.md` に反映する。

## 範囲

既定は全層（scenario / pages / domains / usecases / flows / testcases）。ユーザーが層を指定していれば、その層だけを範囲にする。

技術設計の層（domains 以降）は `../spec-domain/SKILL.md` の「アーキテクチャ制約」に従う。

## 派生物

Implementation Ready になった後、`../spec-manual-test/SKILL.md` で `spec/manual-tests/` を生成する。前提は scenario と pages が範囲にあること。

## 完了報告

```text
spec: {Implementation Ready / 停止（理由）}
- 段取り: {採った進め方を一行で}
- 契約: 要求 {数}件、範囲 {層の一覧}
- 成果物: {層ごとのファイル数}
- 取りこぼし・足しすぎ: 要求 {数}件すべてが最下流まで辿れる、上流のない要素 {なし / 内容}
- またぐ決定: 動的フロー {数}本をトレース、未決の問い {なし / 内容}
- 体験: {シナリオごとに比べた代案を一行で / 範囲外}
- 制約: {アーキテクチャ制約と差し替え可能性の確認結果を一行で / 範囲外}
- 設計: {想定した次の要求と、その改訂の広がりを一行で}
- 主要な設計判断: {採用案と、検討した代替案・トレードオフ}
- 独立した読み: 台帳 {指摘 {数}件を反映 / 指摘なし}、spec {読み {数}回。回ごとの範囲（全量 / 増分）と 7 条件への反例の数、直した内容を一行で。最後の回は反例ゼロ}。7 条件の外で見送った指摘: {内容 / なし}
- 派生物: manual-tests {生成済み / 対象外（理由）}、inventory {同期済み / なし}
- 残存課題: {内容 / なし}
```

実装は、一括なら spec-implement、縦スライスに分けるなら spec-to-issues で起票して issue-implement で進める。
