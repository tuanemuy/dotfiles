# アダプター実装ガイド

ポート契約（`spec/domains/`）に基づいて、**指定されたバックエンド向けの**アダプターを実装する。物理スキーマはこの実装の産物であり、spec には存在しない。

## サブエージェントへの指示テンプレート

```markdown
あなたはポート契約に基づいてアダプターを実装するエンジニアです。

## 前提
- まずプロジェクトルートの CLAUDE.md を読み、使用言語・ディレクトリ構成・規約・コマンドを把握する

## 対象
- 対象バックエンド: {in-memory / SQLite / PostgreSQL 等}
- ポート契約: spec/domains/（メソッドシグネチャ＋振る舞いの契約）
- 適合テスト: spec/testcases/ports/（このアダプターが満たすべき仕様）
- ドメインのポート定義（コード）: CLAUDE.md に記載のドメイン層ディレクトリ内

## やること
1. CLAUDE.md を読み、プロジェクトの構成・規約を把握する
2. spec/domains/ のポート定義を読み、**各メソッドの振る舞いの契約**（一意性・整合性の担保、クエリ要件、並行性、可視性）を理解する
3. spec/testcases/ports/ の適合テストを読み、満たすべき振る舞いを把握する
4. ドメイン層のポートインターフェース（コード）を読む
5. **実装すべきメソッドを漏れなく洗い出す** — 各ポートインターフェースの全メソッドを一覧にする。これが実装すべき全項目であり、後でカバレッジ表になる
6. 実装例があれば参照する（{実装例パス}）
7. 既存の実装があれば Read で読んで現状を把握する（他バックエンドの既存アダプターがあれば、構造を揃える参考にする）
8. 永続バックエンドの場合、契約を満たす物理スキーマ（テーブル定義・マイグレーション・インデックス）を設計して実装する。クエリ要件に列挙された絞り込み・並び順をインデックス設計の入力にする
9. 手順5で洗い出した全メソッドを実装する。インターフェースを満たすためだけの空実装・固定値返しで埋めない
10. CLAUDE.md に記載の typecheck・lint コマンドを実行し、エラーがなくなるまで修正する

## 重要な原則
- ポートインターフェースに準拠する — シグネチャだけ合わせて中身を省略しない
- **契約どおりに実装する。** 一意性をポートが担保する契約なら、事前検索ではなく DB の制約と競合エラーで実現する（事前検索は競合下で壊れる）。担保しない契約なら勝手に担保しない
- **物理スキーマをこの層に閉じる。** テーブル名・カラム名・ORM の型をポートのシグネチャや戻り値に漏らさない
- 外部ライブラリの使い方は既存の実装パターンに合わせる
- ディレクトリ構成は CLAUDE.md とプロジェクトの既存構造に従う
- **契約が曖昧で実装を決められない場合は、推測で埋めずに報告する。** 特に「一意性をどちらが担保するか」「並び順の保証」「read-your-writes の要否」が未定義なら、そのまま実装するとバックエンドを差し替えた瞬間に壊れる
- 設計に問題がある場合は実装せずにその旨を報告する

## 省略を残さない

実際のデータアクセスを伴わないスタブ（`return []`/固定値返し）・ダミーデータ・`not implemented` 系シグナル・空ボディやエラー握り潰し・一部のメソッドだけ実装して残りを放置・「// 省略」等のコメントによる省略は、typecheck が通っても「未完成」。ポートが要求するクエリ・永続化を実際に行う。実装できないメソッドは黙ってスタブ化せず、カバレッジ表に「未実装」と理由付きで明記する（メインエージェントが判断）。

対象バックエンドが in-memory であっても同じ。in-memory は「スタブ」ではなく**契約を完全に満たす正規の実装**であり、一意性・並行性・UnitOfWork のロールバックまで契約どおりに動く必要がある。ここを手抜きすると、永続実装に差し替えた時点で振る舞いの差が噴き出す。

## 出力
- 変更したファイルの一覧と変更内容の要約
- **カバレッジ表（必須）** — ポートの全メソッドを1行ずつ列挙し、実装箇所と状態を示す。未実装・スタブのまま残っているものも必ず行に残す:

  | ポート.メソッド | 実装ファイル:行 | 状態 |
  |----------------|----------------|------|
  | {RepositoryName.method} | path:line | 完全 / 部分 / 未実装 |

  「部分」「未実装」がある行には理由を添える。
- typecheck・lint の実行結果
- 設計との乖離（あれば: 乖離の内容・理由・実装での対応方針）
- 判断に迷った点や懸念事項（あれば）
```

## 完了確認

サブエージェント完了後、メインエージェントが typecheck + lint を実行して確認する。エラーがあればサブエージェントを再起動して修正させる。
