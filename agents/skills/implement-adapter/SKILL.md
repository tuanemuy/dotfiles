# Implement Adapter — アダプター実装＋レビュー

ポート契約とポート適合テストに基づき、**特定のバックエンド向けのアダプター**をサブエージェントで実装する。実装後にアダプター層に特化したレビューサイクルを回す。

物理スキーマ（テーブル定義・マイグレーション・インデックス）は spec の成果物ではなく、このスキルがバックエンドごとに決める実装の産物。同じポートに対する in-memory 版と PostgreSQL 版は別々の実行で作られ、**同じ適合テストを通すことで差し替え可能性が保証される**。

**メインエージェントの役割はオーケストレーションのみ。** コードの読み書きはすべてサブエージェントに委譲する。

## Phase 1: 準備

### spec/ の確認

以下が存在するか確認する:

- `spec/domains/` — ポート定義（メソッドシグネチャ＋振る舞いの契約）。**本スキルの一次入力**
- `spec/testcases/ports/` — ポート適合テスト。実装の完了判定に使う

`spec/domains/` のポート定義に振る舞いの契約（一意性・クエリ要件・並行性・可視性）が欠けている場合、そのままでは差し替え可能なアダプターを書けない。推測で埋めずにユーザーに報告し、spec-revise で契約を補完するか判断を仰ぐ。

### 対象バックエンドの確定

どのバックエンド向けに実装するかを確定する。

- 呼び出し元（implement オーケストレーター・Issue 本文）で指定されていればそれに従う
- CLAUDE.md・既存の依存関係・既存アダプターの実装から判別できればそれに従う
- どちらでも決まらない場合はユーザーに確認する。**推測で選ばない** — バックエンドの選択はプロジェクト全体に影響する決定なので、決まったら `spec/progress.md` に対象バックエンドとして記録する

永続バックエンド（SQLite / PostgreSQL 等）の場合、物理スキーマとマイグレーションもこのフェーズ以降の成果物に含まれる。in-memory の場合は含まれない。

### プロジェクトコンテキストの把握

CLAUDE.md と README.md を読み、以下を確認する:

- 使用言語・フレームワーク
- ディレクトリ構成（アダプター層の配置先、ドメイン層のポート定義場所）
- typecheck・lint コマンド
- コーディング規約

既存コードの下調べ（既存アダプター実装、ポート定義の所在、DB クライアントやマイグレーションの構成の収集）が必要な場合は、サブエージェント（**探索区分**。`../_shared/references/subagent-policy.md`）に委譲する。

### 進捗管理

`spec/progress.md` を確認し、アダプター層の状態を把握する。ドメイン層が実装済みであることを確認する。

### 実装例の確認

`docs/backend_implementation_example.md` が存在するか確認する。存在する場合はサブエージェントに参照先として渡す。

## Phase 2: 実装

`references/impl-guide.md` を読み、その手順に従ってアダプターを実装する（実装は**判断区分**）。

サブエージェント完了後:

1. 報告を確認する
2. typecheck + lint を実行する
3. エラーがあればサブエージェントを再起動して修正させる
4. `spec/progress.md` を更新する

## Phase 2.5: 完全性ゲート

全アダプターの実装が完了したら、レビューサイクルに進む前に `../_shared/references/completeness-gate.md` を読み、その手順に従って完全性ゲートを実行する。

typecheck + lint はインターフェースを満たすだけの空実装・固定値返しを素通りさせる。このゲートで、独立したサブエージェントがポートの全メソッド vs 実コードを照合し、実際の DB アクセスを伴わないスタブや未実装メソッドを検出する。欠落があればその項目だけを埋めさせて再ゲートし、欠落 0 件になってから Phase 3 へ進む。

- 対象レイヤー: adapter
- spec: `spec/domains/` のポート定義（メソッドと振る舞いの契約）
- 入力: 実装したファイル群＋各サブエージェントのカバレッジ表

## Phase 2.7: 適合テスト

完全性ゲートを通過したら、`spec/testcases/ports/` の適合テストを**対象バックエンドの実装に対して**実行する。

- スイートが未整備なら、まず適合テストの実装をサブエージェント（**判断区分**）に委譲して用意する（既存の in-memory 版などで整備済みなら再利用し、バックエンドを差し替えて流す）
- 全ケースが通るまで修正する。落ちたケースは実装のバグか、ポート契約の曖昧さのどちらか
- **契約の曖昧さが原因で落ちた場合は実装を辻褄合わせしない。** 契約の解釈をユーザーに報告し、`spec/domains/` の該当ポート定義を更新してから実装を直す
- 適合テストの通過が、このバックエンドのアダプターが差し替え可能であることの唯一の根拠になる

## Phase 3: レビューサイクル

完全性ゲートを通過したら、`references/review-guide.md` を読み、その手順に従ってレビューと修正を行う。

**`fix` と仕分けた指摘が0件のラウンド**でレビュー完了（指摘台帳の記録済み指摘は除外。`../_shared/references/review-loop.md` 参照）。最大5ラウンド。5ラウンドで収束しない場合はユーザーに報告して判断を委ねる。

レビュー記録は `.review/adapter/review-{連番}.md` に保存する。レビュー完了後の後片付けは `../_shared/references/review-loop.md` の「後片付け」に従う — スキル単体で呼ばれた場合は Phase 4 で `.review/adapter/` を削除し、implement オーケストレーター経由の場合は削除しない（オーケストレーターの完了フェーズが担う）。

## Phase 4: 完了

1. サブエージェントから報告された設計との乖離を確認し、必要に応じて:
   - `spec/domains/` の該当ポート定義（契約）を更新する
   - `spec/testcases/ports/` の適合テストを更新する
   - 更新は現在形のみ — 経緯・代替案は spec に書かない
2. git commit する
3. `spec/progress.md` を更新する（どのバックエンドのアダプターが揃っているかを記録する）
4. サマリーを出す（対象バックエンド・適合テストの結果を含める）

## 原則

共通原則は `../_shared/references/implement-principles.md` に従う。本レイヤー固有:

- ポートインターフェースに準拠する（シグネチャだけ合わせて中身を省略しない）
- **契約に書かれていない振る舞いに依存しない。** 呼び出し側が特定バックエンドの副次的な挙動（暗黙の並び順、自動採番の連続性など）を当てにできる状態を作らない
- **物理スキーマはこの層に閉じる。** テーブル名・カラム名・ORM の型がポートのシグネチャや戻り値に漏れ出さない
- **適合テストは実装に合わせて緩めない。** 落ちたら実装を直すか、契約を明確化して spec を直す
