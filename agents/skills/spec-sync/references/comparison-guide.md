# 照合ガイド — レイヤー×ドメインの比較手順

各レイヤーの spec ファイルと実装コードを照合するための手順とサブエージェントテンプレート。

照合の目的は「spec が実装の現状を正しく反映しているか」の検証であり、「実装が spec 通りか」の検証ではない。つまり、乖離が見つかったとき「spec を直すべきか、コードを直すべきか」を判断する材料を集める作業。

## 照合の粒度

各レイヤーで以下の粒度で照合する:

| レイヤー | 照合単位 | spec ファイル | 照合対象 |
|---------|---------|-------------|---------|
| ドメイン | ドメインごと | spec/domains/{name}.md | エンティティ、値オブジェクト、ドメインサービス、ポートインターフェースと振る舞いの契約 |
| アダプター | ポートごと | spec/domains/{name}.md#ポート | 各ポートメソッドの実装、契約（一意性・クエリ要件・並行性・可視性）への準拠 |
| ユースケース | ユースケースごと | spec/usecases/{name}.md | ユースケースの存在、依存するドメイン/ポート、トランザクション境界 |
| フロントエンド | ページごと | spec/pages/{name}.md | ページ構成、コンポーネント、props、API接続 |
| テスト | テストスコープごと | spec/testcases/{name}.md | テストケースのカバレッジ |

## サブエージェントテンプレート

照合はすべて**審査区分**として起動する（`../../_shared/references/subagent-policy.md`）。乖離か否かの見極めを伴う。

各レイヤーで `{読むもの}` `{照合観点}` を差し替えて渡す。

```text
あなたは設計ドキュメントと実装コードの乖離を検出するエンジニアです。

## 前提
- まずプロジェクトルートの CLAUDE.md を読み、ディレクトリ構成と命名規約を把握する

## やること
1. {読むもの}
2. 対応する実装コードを Glob/Grep で探し、読む
3. 下記の観点で照合する

## 照合観点
{照合観点}

## 乖離の報告形式
各乖離について:
- **場所**: spec のセクション ↔ 実装のファイル:行番号
- **内容**: 何が異なるか（具体的に）
- **推定分類**: 設計判断 / 実装誤り / 実装漏れ / 不明
- **推定根拠**: なぜその分類と判断したか（git log のコミットメッセージ、コードコメント等の手がかり）

乖離がない場合は「一致」とだけ報告する。
```

### ドメイン層

**読むもの:** `spec/domains/{ドメイン名}.md`（ドメインごとに1つのサブエージェントを起動する）

**照合観点:**

- **エンティティ**: spec に定義されたエンティティが実装に存在するか。プロパティ（名前・型）が一致するか。メソッドが一致するか
- **値オブジェクト**: spec に定義された VO が実装に存在するか。バリデーションルールが一致するか
- **ドメインサービス**: spec に定義されたサービスが実装に存在するか。メソッドのシグネチャが一致するか
- **ポートインターフェース**: spec に定義されたポートが実装に存在するか。メソッドのシグネチャが一致するか
- **実装にあるが spec にないもの**: 実装で追加されたプロパティ・メソッド・クラスがないか

### アダプター層

**読むもの:** `spec/domains/` のポート定義（メソッドシグネチャ＋振る舞いの契約）と `spec/testcases/ports/` の適合テスト。実装側はバックエンドごとのアダプターと適合テストの実装を読む

物理スキーマ（テーブル定義・マイグレーション・インデックス）は spec の要素ではないため、それ自体は乖離の対象にしない。**契約を満たしているか**だけを見る。

**照合観点:**

- **メソッドの網羅**: spec のポートに定義された全メソッドがアダプターに実装されているか
- **契約への準拠**: 一意性・整合性の担保、クエリ要件（絞り込み・並び順・ページング・件数上限）、並行性、可視性が契約どおりか
- **UnitOfWork**: spec でスコープが要求されているユースケースの書き込みが、実装でも同一トランザクション内にあるか
- **適合テスト**: spec/testcases/ports/ の全ケースが実装され、存在する全バックエンドに対して実行されているか
- **差し替え可能性**: 物理スキーマの語彙（テーブル名・カラム名・ORM の型）がポートのシグネチャや戻り値に漏れていないか
- **実装にあるが spec にないもの**: 契約に書かれていないメソッド・振る舞いが実装され、呼び出し側から使われていないか

### ユースケース層

**読むもの:** `spec/usecases/{ユースケース名}.md`

**照合観点:**

spec/usecases/ は DTO の全フィールド・処理手順・技術的なエラー分岐を意図的に持たない（実装時に決まる詳細のため）。**spec が沈黙している事柄は乖離として報告しない。**

**照合観点:**

- **関数/メソッド**: spec に定義されたユースケースが実装に存在するか
- **入出力の意味**: 受け取るもの・返すものが spec の記述と食い違っていないか（フィールド単位の照合はしない）
- **依存するドメイン/ポート**: spec が挙げたドメインの振る舞い・ポートメソッドを正しく使っているか
- **トランザクション境界**: spec の UnitOfWork の要否と実装が一致するか
- **要件由来のエラー**: spec に列挙されたエラーケースが実装で扱われているか
- **実装にあるが spec にないもの**: 追加されたユースケースがないか（引数の増減は対象外）

### フロントエンド層

**読むもの:** `spec/pages/{ページ名}.md`。`spec/design/` にデザイン成果物（HTML、デザイントークン）があれば併せて読む

**照合観点:**

- **ページ構成**: spec に定義されたページ/ルートが実装に存在するか
- **コンポーネント**: spec に定義されたUIコンポーネントが実装に存在するか。props が一致するか
- **画面要素**: フォーム項目、テーブルカラム、ボタン、ナビゲーション等が spec と一致するか
- **API接続**: spec で定義されたデータ取得・更新処理が正しいバックエンド API に接続されているか
- **状態管理**: spec で定義された画面状態（ローディング、エラー、空状態等）が実装されているか
- **実装にあるが spec にないもの**: 追加されたページ・コンポーネント・props がないか

### テスト層

**読むもの:** `spec/testcases/{テストスコープ}.md`。実装側は対応するテストファイルを読む

**照合観点:**

- **テストケースカバレッジ**: spec に定義されたテストケースが実装に存在するか
- **テスト条件**: テストの前提条件・入力・期待出力が spec と一致するか
- **テスト対象**: spec で指定されたドメイン・ユースケース・ページに対するテストが存在するか
- **実装にあるが spec にないもの**: 追加されたテストケースがないか（これ自体は良いことだが記録する）

## 推定分類の判断基準

サブエージェントが乖離の分類を推定するための手がかり:

### 設計判断の手がかり
- git log で意図的なコミットメッセージがある（「〜に変更」「〜を追加」等）
- コードコメントに理由が書かれている
- 作業ログ（`.thread/{番号}/adr.md`）に判断の記録がある
- Issue や PR で議論された形跡がある
- 実装がより合理的・効率的な構造になっている

### 実装誤りの手がかり
- 型の不一致（spec: string → 実装: number 等）
- メソッド名のタイポやケース違い
- 引数の順序が異なる
- spec の制約（必須/任意、バリデーション等）が守られていない

### 実装漏れの手がかり
- spec にある要素が実装に見つからない
- TODO コメントで「後で実装」と書かれている
- 空の関数ボディや未実装のメソッドがある

### 不明
- 上記のどれにも当てはまらない、または複数の可能性がある場合
- ユーザーに確認が必要
