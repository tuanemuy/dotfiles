# 区分設計ガイド

spec-sync-dashboard の初期化（SKILL.md Step 2）で、プロジェクトを同期区分に分割するための方法。区分の切り方はローテーション全体の質を決める。**spec/ の漏れのない被覆**と**1回で読み切れるサイズ**の両立が目標。

## 入力

区分を設計する前に、以下を読んでプロジェクトを把握する:

- **CLAUDE.md** — レイヤー構成・依存方向・命名規約・ソースディレクトリ（spec のドメイン名と実装のモジュール名の対応を取るため）
- **README.md** — プロジェクトの目的・技術スタック
- **spec/** — 全ディレクトリとファイル一覧。どのレイヤー（domains / database / usecases / pages / testcases 等）が存在し、それぞれ何ファイルあるか
- **実装のディレクトリ構成** — 各 spec レイヤーに対応する実装パスと、その規模感
- **.adr/** — 既存の設計判断。過去にどんな乖離が設計判断として記録されてきたかの手がかり

## 区分の定義

1つの区分は次の組で定義する:

- **区分名** — 内容を表す短い名前
- **spec スコープ** — 対象の spec ファイル/ディレクトリ群。逆方向検出の横断区分は `spec/ 全体` とする
- **実装スコープ** — 対応する実装パス群。横断区分は「プロジェクト全体（{重点}を重点）」の形で重点を明記する

照合の観点はレイヤーで決まる（`../../spec-sync/references/comparison-guide.md` のレイヤー別テンプレートを使う）ため、区分ごとに観点を選ぶ必要はない。区分設計の仕事は「spec と実装の対応を正しく引き、読み切れるサイズに割る」こと。

## 3つの軸

区分は次の軸を組み合わせて作る。

### 軸1: spec レイヤー主軸（基本）

spec/ のディレクトリ構成（domains / database / usecases / pages / testcases）をそのまま区分にするのが基本。照合単位・観点がレイヤーで決まるため、区分とテンプレートの対応が自然に取れる。

| 区分 | spec スコープ | 実装スコープの例 |
|------|-------------|----------------|
| ドメイン層 | spec/domains/ | src/core/domain/ |
| アダプター層 | spec/domains/ のポート定義, spec/testcases/ports/ | src/core/adapters/, マイグレーション |
| ユースケース層 | spec/usecases/ | src/core/application/ |
| フロントエンド | spec/pages/ | src/app/, src/components/ |
| テスト | spec/testcases/ | テストファイル群 |

存在しないレイヤーは区分にしない（フロントエンドがないプロジェクトでは spec/pages/ の区分を作らない）。

### 軸2: 機能領域による分割（レイヤーが大きい場合）

1つのレイヤーが読み切れるサイズを超える場合は、レイヤー×機能領域で分割する（例:「ドメイン層（タスク管理）」「ドメイン層（認証・ユーザー）」）。分割の単位は spec のファイル境界（ドメイン・ユースケースのまとまり）を使い、機械的な等分はしない。

逆に、プロジェクトが小さくレイヤー単位では細かすぎる場合は、機能領域で縦割りにしてもよい（例:「タスク管理（spec 全レイヤー ↔ 対応実装）」）。縦割りはレイヤーをまたぐ整合性（ドメイン定義と DB スキーマの突き合わせ等）を1回で見られる利点がある。どちらを主軸にするかは spec の分量が大きい方に合わせる。

### 軸3: 横断区分（常に追加を検討する）

spec スコープ主軸の区分は「spec に書かれていることが実装と一致するか」を見るが、**spec に書かれていないもの**は拾えない。次の横断区分を、プロジェクトに該当するものだけ追加する:

- **逆方向・全体整合** — 実装全体を歩いて「spec 未記載の新規実装」（新しいページ・ユースケース・テーブル・ドメイン概念）を洗い出す。spec が実装の現状を映す鏡である以上、この区分はほぼ必須
- **周辺ドキュメント** — README・CLAUDE.md・ADR の記述が実態と一致するか。spec/ 以外のドキュメントも同期対象にしたい場合に追加する（逆方向・全体整合の重点に含めてもよい）

横断区分の実装スコープはレイヤー区分と重複してよい。**見る方向が違えば重複は無駄ではない**（レイヤー区分は spec→実装の照合を、逆方向区分は実装→spec の検出を行う）。

## サイズの調整

1区分は「1回の実行で、サブエージェントがスコープ内の spec と対応実装の両方を読み切れる」サイズに収める。目安:

- spec **〜10 ファイル** ＋ 対応実装 **〜30 ファイル** 程度を上限の目安とする
- 超える場合は軸2の方法で分割する
- 逆に小さすぎる区分（spec 1〜2 ファイル）は隣接する区分に併合する。ローテーション1周が長くなりすぎるのを防ぐ

区分数の目安は **4〜10**。少なすぎると1回が重く浅くなり、多すぎると1周が長くなって鮮度が落ちる。小規模プロジェクトなら 3 でもよい。

## 被覆の確認

設計を終えたら、spec/ の全ファイルが**いずれかの spec スコープ主軸区分に含まれる**ことを確認する。横断区分は被覆に数えない（重点を絞って見るため、単独では被覆保証にならない）。

どの区分にも入らない spec ファイル（spec/idea.md、シナリオ、マニュアルテスト手順等）は、実装との照合対象になるものだけ「周辺ドキュメント」相当の区分に含める。実装と照合しようのないもの（アイデアメモ等）は対象外としてよいが、対象外にしたものを初期化の報告に明記する。

## 並び順

ダッシュボードの区分番号はローテーションの既定順になる。**基盤に近い区分を上に**置く（ドメイン → アダプター → ユースケース → フロントエンド → テスト → 横断、のように内側から外側へ）。基盤側の spec の乖離は下流の spec の読み方を誤らせるので、初回の周回で先に解消したい。
