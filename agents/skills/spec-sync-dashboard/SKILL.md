# Spec Sync Dashboard — 区分ローテーションによる定期 spec 同期

プロジェクトを区分（同期単位）に分割し、**実行1回につき1区分だけ**の spec と実装を徹底的に照合・同期する。区分の定義と同期履歴は **GitHub Issue のダッシュボード**として管理し、リポジトリ上で共有・更新できるようにする。

spec/ 全体を一度に照合すると広く浅くなり、定期実行するには1回が重すぎるため、初期化時に spec と実装の構成を読み取って区分を設計し、以降はローテーションで1区分ずつ深掘りする。

検出した乖離は分類して対応を分ける。**設計判断**（実装中に意図的に設計を変更した）は spec を更新する。**実装誤り・実装漏れ**（spec 側が正しい）は裏取りしたうえで、既存 Issue と重複しなければ Issue として起票する。**このスキルはコードを修正しない。** 修正は issue-implement 等に委ねる。

近縁スキルとの棲み分け:

| スキル | やること | 範囲 |
|--------|---------|------|
| spec-sync | spec と実装の照合・同期 | 全体 × 一度に |
| review-dashboard | コードの定期レビュー（多観点） | 1区分 × 多観点の深掘り |
| **spec-sync-dashboard** | spec と実装の定期同期 | **1区分 × 深い照合のローテーション** |

## Workflow

1. 既存のダッシュボード Issue を探す（Step 1）
2. なければ初期化する — 区分を設計してダッシュボードを作成し、終了（Step 2）
3. あれば同期対象の区分を1つ選ぶ（Step 3）
4. 区分を徹底照合する — 照合単位別サブエージェント並列 → 統合 → 分類 → 裏取り（Step 4）
5. 設計判断を spec に反映する（Step 5）
6. 重複チェックのうえ実装誤り・漏れを Issue 起票する（Step 6）
7. ダッシュボードを更新する（Step 7）
8. 完了報告する（Step 8）

## Step 1: 既存ダッシュボード Issue の確認

open な Issue から、タイトルが `Spec Sync Dashboard` のものを探す。

```bash
gh issue list --state open --search "Spec Sync Dashboard in:title" --json number,title,body
```

本文の先頭に `<!-- spec-sync-dashboard -->` マーカーがあるかで最終確認する（同名タイトルの誤検出を避けるため）。見つかればその Issue 番号と現在の本文を控えて Step 3 へ。見つからなければ初期化（Step 2）へ。

## Step 2: 初期化 — 区分の設計とダッシュボード作成

CLAUDE.md / README.md / spec/ の構成 / 実装のディレクトリ構成を読み、spec と実装の対応関係を把握したうえで区分を設計する。設計の方法は `references/segmentation-guide.md` に従う。要点:

- 区分は **spec 側のスコープ（対象 spec ファイル群）＋ 実装側のスコープ（対応する実装パス群）** の組で定義する
- spec のレイヤー（domains / database / usecases / pages / testcases）を主軸にした区分と、逆方向検出等の横断観点の区分を組み合わせる
- 1区分は「1回の実行でスコープ内の spec と対応実装をすべて読み切れる」サイズに収める。目安は 4〜10 区分
- spec/ の全ファイルがいずれかの区分のスコープに含まれるようにする
- 照合の観点・手順は `../spec-sync/references/comparison-guide.md` のレイヤー別テンプレートに従う

設計した区分を下記フォーマットでダッシュボード Issue として新規作成する。本文は一時ファイルに書き出してから反映する。

```bash
gh issue create --title "Spec Sync Dashboard" --body-file <一時ファイル>
```

**初期化した実行では同期まで進まない。** 区分の切り方はローテーション全体の質を決めるので、まずユーザーに区分を確認してもらう。作成したダッシュボードの URL と区分一覧を報告して終了する。ユーザーが「初期化してそのまま1区分同期して」と明示した場合のみ Step 3 に続く。

### ダッシュボード本文のフォーマット

- 本文の先頭に `<!-- spec-sync-dashboard -->` マーカーを置く（次回の検出用）。
- 区分ごとに `## {番号}. {区分名}` セクションを作る。番号はローテーションの既定順で、基盤に近い区分を上に置く。
- 各セクションは次の 4 行のリストで構成する。
  - `- spec:` 対象の spec ファイル/ディレクトリ群。逆方向検出の横断区分は `spec/ 全体` とする。
  - `- 実装:` 対応する実装パス群。横断区分は「プロジェクト全体（{重点}を重点）」のように重点を明記する。
  - `- 最終同期:` `YYYY-MM-DD` 形式。未同期は `-`。
  - `- 起票:` その区分の同期で起票した**オープンな** Issue 番号を空白区切りで列挙する。なければ `-`。
- テーブル・太字・絵文字・罫線・説明文などの装飾は使わない。構造だけで伝える。

### 本文の例

```markdown
<!-- spec-sync-dashboard -->

## 1. ドメイン層

- spec: spec/domains/
- 実装: src/core/domain/
- 最終同期: 2026-07-10
- 起票: #141 #142

## 2. アダプター層

- spec: spec/domains/ のポート定義, spec/testcases/ports/
- 実装: src/core/adapters/, drizzle/
- 最終同期: 2026-07-14
- 起票: -

## 3. ユースケース層

- spec: spec/usecases/
- 実装: src/core/application/
- 最終同期: -
- 起票: -

## 4. フロントエンド

- spec: spec/pages/
- 実装: src/app/, src/components/
- 最終同期: -
- 起票: -

## 5. テスト

- spec: spec/testcases/
- 実装: src/**/*.test.ts, tests/
- 最終同期: -
- 起票: -

## 6. 逆方向・全体整合

- spec: spec/ 全体
- 実装: プロジェクト全体（spec 未記載の新規実装・README / CLAUDE.md の正確性を重点）
- 最終同期: -
- 起票: -
```

## Step 3: 同期対象区分の選択

対象は次の優先順で1つだけ選ぶ。

1. **ユーザー指定**（「区分3を同期して」「ドメインの区分やって」等）があればそれ。
2. `最終同期: -`（未同期）の区分のうち、番号が最も小さいもの。
3. 未同期がなければ、最終同期日が最も古い区分。同日なら番号が小さいもの。

選択したら、区分のスコープが現状と合っているか軽く確認する。spec ファイルや実装パスが消えている・改名されている場合は区分定義を直してから進める（Step 7 でダッシュボードにも反映）。どの区分にも属さない大きな新しい spec 領域を見つけた場合は、新しい区分を末尾に追加する。**区分全体の作り直しはしない** — ユーザーが明示的に「区分を作り直して」「再初期化して」と言ったときだけ Step 2 をやり直す。

対象区分（番号・名前・spec スコープ・実装スコープ）をユーザーに報告してから照合を開始する。

## Step 4: 区分の徹底照合

### 検証用ブランチの準備

照合は最新の `origin/main` の内容に対して行う。origin/main からブランチを切ってチェックアウトし、以降の読み取りと Step 5 の spec 更新はすべてその状態で行う。

```bash
ORIG_BRANCH=$(git branch --show-current)
git fetch origin
BRANCH="spec-sync-dashboard/$(date +%Y%m%d)"
git switch -c "$BRANCH" origin/main
```

- 作業ツリーに未コミット変更がある場合はブランチを切り替えず、その旨を報告して中断する（変更の退避はユーザーに委ねる）
- `origin/main` が存在しない場合（リモート未設定等）は、現在のブランチのままで照合・更新する旨を完了報告に明記して続行する
- 終了時の扱いは変更の有無で分ける:
  - spec の変更がある場合: 検証用ブランチにチェックアウトしたまま**残し**、完了報告にブランチ名を明記してユーザーの確認に委ねる
  - 変更がない場合: `git switch "$ORIG_BRANCH" && git branch -D "$BRANCH"` で元に戻して削除する

### 照合単位別サブエージェントの並列実行

区分スコープ内の照合単位（レイヤー×ドメイン。ドメイン層ならドメインごと、アダプター層ならテーブル/リポジトリごと等）ごとにサブエージェント（**判断区分** — 乖離かどうかの見極めを伴う）を**並列**起動する（委譲方式とモデル選択は `../_shared/references/subagent-policy.md`）。区分定義のための spec / 実装パスの収集は**探索区分**でよい。各照合単位の観点とプロンプトは `../spec-sync/references/comparison-guide.md` のレイヤー別テンプレートに従う。

各サブエージェントには必ず以下を渡す:

- まずプロジェクトルートの CLAUDE.md を読む指示（ディレクトリ構成・命名規約の情報源として）
- 担当する spec ファイルと対応する実装パス（spec と実装の**両方をすべて読む**こと。diff や変更履歴に依存しない）
- 照合観点と報告形式（`../spec-sync/references/comparison-guide.md` の該当節）
- 逆方向・全体整合の区分では「実装にあるが spec にないもの」の洗い出しを主目的にする指示

全照合単位の結果を統合し、同じ場所・同じ原因の乖離をまとめる。各乖離を分類する:

- **設計判断** — 実装中に意図的に設計を変更した（より良い方法が見つかった、制約が判明した等）→ spec を更新
- **実装誤り** — コードが spec と異なるが、spec 側が正しい → Issue 起票
- **実装漏れ** — spec に定義されているが実装されていない → Issue 起票
- **不明** — 分類の根拠が足りない、または判断が割れる → spec も Issue も触らず、完了報告でユーザーに確認を求める

分類の判断基準は `../spec-sync/references/comparison-guide.md` の「推定分類の判断基準」に従う。

### 裏取り

spec 更新候補（設計判断）と起票候補（実装誤り・漏れ）は、対応前に**該当する spec とコードを実際に読んで裏取りする**。サブエージェントの報告の根拠（該当行・spec のセクション・コード抜粋）が実物と一致することを確認する。設計判断は、意図の手がかり（git log のコミットメッセージ、コードコメント、作業ログ（`.thread/{番号}/adr.md`）、Issue / PR の議論）が実在するかまで確認する。裏取りできないもの・判断が割れるものは不明に落とす。誤った spec 更新や偽陽性の起票はローテーション全体の信頼を損なう。

## Step 5: 設計判断 → spec 更新

裏取り済みの設計判断について、spec ファイルを実装に合わせて更新する。更新はサブエージェント（**判断区分**）に委譲する。プロンプトと更新の原則は `../spec-sync/SKILL.md` の「Phase 3: spec 更新 + Issue 起票」のテンプレートに従う。要点:

- 実装の現状を正確に反映する — spec は「あるべき姿」ではなく「現在の設計」を表す
- 既存の記述スタイル・フォーマットに合わせ、変更箇所の周辺も整合性を確認する
- 不要になった記述は削除する（コメントアウトで残さない）
- 更新は現在形のみ — 「以前は」「〜に変更した」といった経緯の文は spec に書かない（`../_shared/references/adr-guide.md`）。変更の理由は完了報告に含める

spec の変更は検証用ブランチ（Step 4 で作成）のワーキングツリーに残し、コミットはしない（コミットはユーザーの確認に委ねる）。

## Step 6: Issue 起票（重複がなければ）

まず既存のオープン Issue を取得し、起票候補と突き合わせる。

```bash
gh issue list --state open --limit 200 --json number,title,body,labels
```

**同じ乖離（同じ場所・同じ原因）を指す Issue が既にあれば起票しない。** タイトルの一致ではなく内容で判断する。ダッシュボード各区分の「起票:」行も手がかりにする。重複でスキップしたものは完了報告に「既存 #N がカバー」と記録する。

裏取り済みの実装誤り・実装漏れを起票する。不明は起票しない（完了報告でユーザーに確認を求める）。独立して対応できる単位で 1 Issue とし、同じ原因から生じた複数箇所の乖離は 1 つにまとめる。

```bash
gh issue create \
  --title "[spec-sync] {区分名}: {乖離の概要}" \
  --body "$(cat <<'EOF'
## 概要
spec-sync-dashboard の定期同期（区分: {区分名}）で検出された実装の乖離。

## 乖離内容
| # | 分類 | spec | 実装 | 内容 |
|---|------|------|------|------|
| 1 | {誤り/漏れ} | {spec パス} | {実装パス:行} | {何が異なるか} |

## 根拠
{spec の該当記述とコードの抜粋、なぜ spec 側が正しいと判断したか}

## 対応方針
{spec 側が正しいので、実装を spec に合わせて修正する}

## 参照
- ダッシュボード: #{ダッシュボード番号}
- spec: {関連する spec ファイルパス}
EOF
)" \
  --label "spec-sync-dashboard"
```

`spec-sync-dashboard` ラベルが存在しない場合は事前に作成する:

```bash
gh label create spec-sync-dashboard --description "spec-sync-dashboard の定期同期で検出された乖離" --color "d4c5f9"
```

## Step 7: ダッシュボードの更新

旧本文をベースに、変わった分だけ手を入れる。本文を一時ファイルに書き出してから反映する。

1. 今回同期した区分の `最終同期:` を今日の日付にする。
2. 同区分の `起票:` に今回起票した Issue 番号を追記する。
3. **全区分**の `起票:` 行から close 済みになった Issue 番号を外す（この付け直しは AI 判断を要さないので毎回全区分に行う）。すべて外れたら `-` にする。
4. Step 3 でスコープ修正・区分追加をした場合はそれも反映する。
5. それ以外の区分の定義・並び順には触れない。

```bash
gh issue edit <ダッシュボード番号> --body-file <一時ファイル>
```

## Step 8: 完了報告

```text
区分「{番号}. {区分名}」の spec 同期が完了しました！ → ダッシュボード: {URL}

- spec: {spec スコープ} / 実装: {実装スコープ}
- 乖離検出: {総数}件（設計判断 {数} / 実装誤り {数} / 実装漏れ {数} / 不明 {数}）
- spec 更新: {更新したファイルの一覧 / なければ「なし」}
- 作業ブランチ: {ブランチ名 / 変更がなく削除した場合は「なし（削除済み）」}
- 変更理由: {設計判断ごとの一行要約 / なければ省略}
- 起票した Issue: {#番号一覧 / なければ「なし」}
- 重複でスキップ: {既存 #番号がカバー / なければ省略}
- 要確認（不明）: {分類できなかった乖離の一覧と確認したいこと / なければ省略}
- 区分の変更: {スコープ修正・追加した区分 / なければ省略}
- 次回の同期対象: {番号}. {区分名}
```

初期化のみの実行では、ダッシュボード URL と区分一覧（番号・名前・spec スコープ・実装スコープ）を報告し、区分の切り方に過不足がないかユーザーに確認を求める。

## 原則

- **1回の実行で1区分だけ** — 狭く深く。全体は周回で覆う。複数区分をまとめて同期しない。蓄積した乖離の一括同期は spec-sync に委ねる
- **スコープ内は隈なく照合する** — diff や変更履歴に依存せず、区分スコープの spec と実装をすべて読む。深掘りこそが一括同期との差分
- **コードは修正しない** — 修正するのは spec だけ。実装誤り・漏れは Issue に起票し、issue-implement 等に委ねる
- **spec は「現在の設計」を表す** — あるべき姿ではなく実装の現状を正確に反映する。ただし spec 側が正しい乖離（実装誤り・漏れ）まで spec を曲げない
- **裏取りできたものだけ動かす** — spec 更新も起票も、実物の確認が取れたものだけ。迷うものは不明としてユーザーに委ねる
- **コミットしない** — spec の変更は検証用ブランチのワーキングツリーに残し、コミットはユーザーの確認に委ねる
- 委譲方式・並列実行・中断時の再委譲は `../_shared/references/subagent-policy.md` に従う
