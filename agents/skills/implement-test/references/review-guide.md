# テストレビューガイド

テストの実装が完了した後、仕様カバレッジとテスト品質をレビューする。レビューサイクルの共通構造（コンテキストの原則・出力フォーマット・修正ループ・完了条件・レビュー記録テンプレート）は `../../_shared/references/review-loop.md` に従う。本ガイドではテスト固有の観点とサブエージェントへの指示だけを定義する。

## サブエージェントへの指示テンプレート

```markdown
あなたは「テスト」の観点でコードをレビューする専門家です。CLAUDE.md / README.md から読み取れるコンテキストやアーキテクチャに従います。

## レビュー対象
- テストケース定義: spec/testcases/（`spec/testcases/ports/` のポート適合テストを含む）
- ユースケース設計: spec/usecases/
- 要素台帳（**この全量がレビュー対象**。無ければテストケース定義の全ケース）: spec/inventory/test.md
- テストコード: {テストディレクトリ}

## やること
1. テストケース定義・台帳・テストコードを読む
2. 台帳の各行に対応するテストの実装を確認する。**見なかった行は必ず記録する**
3. 以下の観点で仕様カバレッジとテスト品質を厳しくレビューする
4. レビュー結果を `.review/test/review-{連番}.md` に**直接書き込む**

## レビュー観点
- テストケース定義のカバレッジを満たしているか
- テストが仕様ベースか（実装ベースでないか）
- エッジケースがカバーされているか
- 定義された全テストが漏れなく実装されているか（`.skip` や空テストで形だけになっていないか）
- ポート適合テストが存在する全バックエンドに対して実行されているか
- TODO・FIXME・仮実装が残っていないか

## 重要: 独立したレビュー
前回のラウンドとは独立している。テストケース定義とテストコードだけを見て、ゼロからレビューする。

## 出力フォーマット
#### Blockers（マージ不可の問題）
- **[B-001]** 問題の説明
  - 場所: `ファイルパス:行番号`
  - 理由: なぜ問題か
  - 提案: どう直すべきか

#### Warnings（改善推奨）
- **[W-001]** 問題の説明（場所・理由・改善案）

#### カバレッジ
- 確認: {台帳ID}, {台帳ID}
- スキップ: {台帳ID} — {観点外と判断した理由を一行で}

台帳の全行を確認・スキップのどちらかに必ず挙げる（1対1対応）。台帳が無ければテストケース名で代用する。

Blocker がなければ「なし」と書く。テストケース定義のカバレッジ不足、TODO・FIXME・仮実装の残存は Blocker とする。

## 返答（レビュー全文は返さない）
ファイルへの書き込みが済んだら、返答には**サマリーだけ**を返す:
- Blockers: {数} / Warnings: {数}
- 各指摘の一行リスト: `[B-001] {ファイル:シンボル/カテゴリ} — {タイトル}`（先頭は指摘台帳の照合 Key）
- 確認した台帳ID / スキップした台帳ID の列挙
```

## 修正ループと完了条件

`../../_shared/references/review-loop.md` に従う（テストレビューの品質ゲートは typecheck + lint + test run）。レビュー記録は `.review/test/review-{連番}.md`。最大5ラウンド。

**カバレッジの確認（必須）**: 台帳の各行に「確認」の申告があるかメインが突き合わせ、ゼロの行があればサブエージェントを1体追加起動してその行だけ見させる（`../../_shared/references/review-loop.md` のコンテキストの原則）。
