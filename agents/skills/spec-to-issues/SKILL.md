# Spec to Issues — 縦スライス Issue 化

spec/ の設計を「1 つのシナリオが end-to-end で動く」縦スライスに分割し、各スライスを GitHub Issue として起票する。

一括実装（implement）は spec 全体をレイヤー横断で一気に進めるため、spec が大きいほど 1 回の実行スコープが肥大し、実装もその検証もコンテキストが薄まって漏れが生まれる。縦スライスなら 1 Issue のスコープが 1 つのシナリオに限定され、実装漏れはそのスライスの実装・レビュー・ブラウザ検証（issue-implement）の中で即座に表面化する。

各 Issue の実装チェックリストは台帳（`../_shared/references/spec-inventory.md`）の行から組み立てる。**台帳の全行がちょうど 1 つの Issue に割り当てられる**ことをスキルが機械的に保証するため、「どの Issue にも入っていない spec 要素」は構造的に存在しない。

## Workflow Overview

```text
Phase 0: 準備
  spec/ の存在確認 → gh の利用可否確認 → 既存スライス Issue の確認

Phase 1: 台帳の用意
  spec/inventory/ を生成 or 差分更新（spec-inventory.md の手順）

Phase 2: スライス設計
  walking skeleton + シナリオ単位の縦スライス → 台帳全行の割当 → 依存順の決定

Phase 3: ユーザー確認
  スライス一覧と割当を提示して承認を得る → 台帳をコミット

Phase 4: Issue 起票
  依存順に gh issue create（チェックリスト・依存・検証方法つき）

Phase 5: ダッシュボード生成・更新
  issue-dashboard スキルに委譲

Phase 6: 完了報告
```

## Phase 0: 準備

- spec/ の成果物（`spec/scenario/`・`spec/domains/`・`spec/usecases/` 等）が存在するか確認する。なければ spec スキルで設計を先に作る必要があることをユーザーに伝える
- `gh auth status` で GitHub CLI が使えるか確認する。使えなければ推測で進めず、ユーザーに確認する
- 既存のスライス Issue を探す。本文先頭の `<!-- spec-slice -->` マーカーで検出する

```bash
gh issue list --state all --limit 200 --search "spec-slice" --json number,title,state,body
```

既存スライス Issue がある場合は**差分起票モード**になる（spec 改訂後の再実行を想定）。全スライスを作り直さず、台帳と既存 Issue のチェックリストを ID で突き合わせて差分だけを扱う:

- **新規行**（どの Issue のチェックリストにもない台帳行）— 内容の近い未着手 Issue に追記する。追記先がなければ新規スライスとして起票する
- **消えた行**（Issue にあるが台帳にない行）— その Issue の本文から削除し、削除した旨をコメントに残す。放置すると実装者が存在しない spec 要素を実装しにいく
- **変わった行**（ID は同じで要素・定義場所・要点が変わった行）— 本文の該当行を台帳の内容で置き換える。チェック済みの行が変わった場合はチェックを外し、再実装が必要な旨をコメントに残す

## Phase 1: 台帳の用意

`../_shared/references/spec-inventory.md` を読み、その手順に従って `spec/inventory/{layer}.md` を用意する。

- 台帳がなければ生成する（**双方向のクロスチェックまで必ず行う**）
- あれば spec の最終変更と台帳の最終同期を比べ、必要なら差分を反映する（追加・修正・削除の 3 方向）

台帳はこのスキルの基準データになる。以降のフェーズは spec を直接読み直すのではなく、台帳の行を単位に進める。

### 実体確認（必須）

台帳の行はそのまま Issue のチェックリストになり、実装者は本文だけを見て実装する。台帳を Issue の外に持ち出すのはこのスキルだけなので、ここで実体を担保する。

新規生成した台帳は手順 2 の双方向クロスチェックで担保済み。既存の台帳を使う場合は、次の行について定義場所を Read し、対応する記述が spec に実在することを確認する（**判断区分**のサブエージェントに分割して並列で振ってよい）:

- 前回同期以降に変更された spec ファイルに対応する行（改訂で消えた要素の行が残りやすい）
- 差分反映で今回追加・修正した行

実体のない行は台帳から削除し、削除した ID を Phase 3 のユーザー確認で報告する。既存スライス Issue のチェックリストに載っている行なら、Phase 0 の「消えた行」として本文からも削除する。

## Phase 2: スライス設計

### walking skeleton を先頭に置く

最初のスライスは機能ではなく「骨格」にする。縦スライスの弱点は横断的な基盤・設計の一貫性が崩れやすいことなので、それを最初の 1 本で先に固める。

- 共通ドメイン基盤（エラー型・共通値オブジェクト等）、アプリの起動導線
- **本番の永続バックエンドをここで選び、物理スキーマ・マイグレーション・接続設定まで通す。** ポート適合テストの土台もここに置く
- 代表シナリオ 1 本を最小構成で end-to-end に通す（ドメイン → アダプター → ユースケース → ページまで貫通）

特定シナリオに属さない横断的な台帳行（共通基盤・共通コンポーネント等）は原則 walking skeleton に割り当てる。

**永続バックエンドを独立スライスにしない。** 機能スライスを in-memory で検証してから永続実装に差し替えると、差し替え時点で全スライスのブラウザ検証をやり直すことになる。適合テストは契約を保証するが、ORDER BY の欠落・一意制約の競合・トランザクション境界のように契約として書き切れなかった差は、差し替えたときに初めて出る。物理スキーマは台帳に載らない（`../_shared/references/spec-inventory.md`）ため、独立スライスにすると台帳行 0 のスライスが 1 本だけ生まれ、下の割当検証からも外れる。

in-memory アダプターが要る場合（テスト用のダブル等）は、それを最初に必要とするスライスの中で作る。台帳行を持たないので独立した Issue にはしない。

### シナリオ単位で縦に切る

`spec/scenario/` のシナリオを起点に、シナリオが動くために必要な台帳行（domain / adapter / usecase / frontend / test）を各スライスに束ねる。レイヤーで切らない — 1 スライスは必ず複数レイヤーを縦断し、単体でユーザー操作から検証できる形にする。

### スライスの数は 5 本前後に収める

**目標は全体で 5 本前後**（walking skeleton 1 本 + 機能スライス 4 本前後）。Issue が増えるほど issue-implement の起動回数と横断的な整合の負担が増えるので、細かく割るより束ねる方向に倒す。

- シナリオが 5 本を超えるときは、スライスを増やさずユーザー体験の領域（画面群・ロール・業務フェーズ）で束ねる
- 判定基準は台帳の行数ではなく、**issue-implement 1 回（レビュー最大 10 ラウンド + 検証最大 3 周）で完走できる規模か**。明らかに完走できない 1 本があるときだけ、そこを割って 5 本を超える
- 逆に 5 本に割ると 1 本あたりが薄い（台帳の総行数が 50 行以下）場合は、そもそも縦スライス化の対象ではない。implement スキルでの一括実装をユーザーに提案する

### 割当の検証（必須）

スライス設計が終わったら、機械的に検証する:

- 台帳の全行がちょうど 1 つのスライスに割り当てられている。**行数ではなく ID の集合で突き合わせる**（台帳の全 ID = 全スライスの ID。重複も未割当も 0）。行数の一致は、追加と削除が相殺すると素通りする
- 各スライスの依存先が特定されている（依存先スライスの成果物を使う場合のみ。弱い関連は依存にしない）
- 依存順に並べたとき循環がない

未割当行が残る場合は、まず既存スライスに吸収させる。どこにも収まらない行だけ独立スライスにする（本数の目標を優先する）。判断に迷う行はユーザー確認（Phase 3）で明示する。

## Phase 3: ユーザー確認

Issue の起票は外向きの操作なので、起票前に一度だけスライス一覧を提示して承認を得る。

```text
{数} スライスに分割しました（台帳 {総行数} 行をすべて割当済み）:

1. [skeleton] {タイトル} — {行数} 行（依存: なし）
2. {タイトル} — {行数} 行（依存: 1）
3. {タイトル} — {行数} 行（依存: 1）
...

判断に迷った点: {あれば}
```

承認を得たら `spec/inventory/` をコミットしてから Phase 4 へ。Issue 本文は台帳の ID を外部参照するため、起票より先に台帳が VCS に入っている必要がある（未コミットのまま起票すると、次回以降の再生成で ID がズレてチェックリストが対応を失う）。分割の調整を求められたら Phase 2 に戻る。

## Phase 4: Issue 起票

依存順（依存先が先）に `gh issue create` で起票する。後続 Issue の本文に依存先の Issue 番号を書くため、起票のたびに採番を控える。

本文フォーマット:

```markdown
<!-- spec-slice -->
## 目的

{このスライスが end-to-end で実現するユーザー価値を 1〜2 文}

## 対象シナリオ

- spec/scenario/{ファイル}#{セクション}

## 実装チェックリスト（spec/inventory/ 由来）

- [ ] DOM-user-001 User エンティティ — spec/domains/user.md#エンティティ
- [ ] DOM-user-002 UserRepository.save（契約） — spec/domains/user.md#ポート
- [ ] ADP-user-001 UserRepository.save（実装） — spec/domains/user.md#ポート
- [ ] UC-user-001 registerUser — spec/usecases/user.md#登録
- [ ] PAGE-signup-001 サインアップページ — spec/pages/signup.md
- [ ] TC-port-user-001 UserRepository 適合テスト — spec/testcases/ports/user-repository.md
- [ ] TC-user-001 登録の正常系 — spec/testcases/user.md#TC-user-001

## 完了条件

実装チェックリストの全行が実装されていること（スタブ・仮実装・部分実装は不可）。実装をレビューで確認できた行にのみチェックを付ける。見送る行はチェックせず、理由をこの Issue のコメントに残す。

## 依存

- #{依存先 Issue 番号}（なければ「なし」）

## 検証

{このスライス単体で動作確認する操作手順の要点。spec/manual-tests/ に該当ケースがあれば参照を書く}
```

- **チェックリストの行は台帳の ID・要素・定義場所をそのままの転記だけで構成する。** 起票時に行を書き足さない。台帳行を持たない作業（物理スキーマ・マイグレーション・接続設定・in-memory ダブル等）はチェックリストに載せず、「目的」か「検証」に書く
- **完了条件は Issue 本文に自己完結で書く。** 実装者（issue-implement でも人間でも他のエージェントでも）が spec-to-issues の存在を知らなくても、本文だけを読んで完了条件に従えるようにする。実装側のスキルにこのフォーマットへの特別な対応を求めない
- タイトルは `{スライスの内容}` を簡潔に。walking skeleton には `[skeleton]` を付ける
- 起票後、全 Issue のチェックリストに載った ID の集合が台帳の全 ID と一致することを最終確認する（差分起票モードでは既存 Issue のチェックリストも突き合わせに含める）。あわせて**台帳 ID を持たない行が混じっていないこと**も確認する — ID の集合比較は、ID のない行を素通りさせる

## Phase 5: ダッシュボード生成・更新

`../issue-dashboard/SKILL.md` を読み、その手順に従ってダッシュボード Issue を生成・更新する。スライス Issue の依存はダッシュボード上で「どれから着手すべきか」「どれを並行できるか」として可視化される。

## Phase 6: 完了報告

台帳の総行数と全行割当済みであること、起票した Issue の番号・タイトル・依存（先頭は `[skeleton]`）、ダッシュボード Issue の URL を報告する。次のステップは「walking skeleton から `issue-implement` で 1 Issue ずつ。依存のない Issue は並行可」。

## 原則

- 委譲方式・並列実行の原則は `../_shared/references/subagent-policy.md` に従う
