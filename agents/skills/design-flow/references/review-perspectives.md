# デザインレビュー観点カタログ

design-flow の Phase 4（`phase4-review.md`）で使う観点の定義。Step ごとに1体のレビュアー（**審査区分**、`../../_shared/references/subagent-policy.md`）を立て、**該当節だけ**を読ませる。

メインエージェントはこのファイルを読まない。委譲の手順・指示テンプレート・終了条件は `phase4-review.md` を参照。

すべての観点に共通する前提:

- 判定基準の土台は `../../frontend-design/SKILL.md` の **DON'T ガイドライン**。2024-2025年のAI生成デザインの指紋であり、このパイプラインで最も検出優先度が高い
- 加えて `spec/design/index.md`（デザイン方針・採用した様式）と `spec/design/tokens.md`（トークン定義）を判定基準にする。「このデザインが自分で定めた基準を満たしているか」を照合する
- コードだけ、または画像だけで判断しない。HTML と `{scratchpad}/design-screenshots/review/` のスクリーンショットを両方確認する
- 自分の節の観点だけでレビューする。他ステップの観点には踏み込まない（別のレビュアーが担当する）
- 指摘には必ず**根拠**（該当箇所のHTML抜粋、またはスクリーンショットで確認した事実）を添える

## Step 2: UX・デザイン品質

デザインディレクターがフィードバックするつもりで、「技術的に正しいか」ではなく「デザインされた体験として機能しているか」を評価する。

### AIスロップ判定（最優先）

**ここから始める。** 合格/不合格で判定する: これはAI生成に見えるか？

`../../frontend-design/SKILL.md` の DON'T すべてに照らして、該当する特徴を具体名でリストする。AIカラーパレット（ダーク上のシアン、パープル→ブルーのグラデーション）、グラデーションテキスト、グローイングアクセント付きダークモード、グラスモーフィズム、ヒーローメトリクスレイアウト、同一サイズのカードグリッド、汎用フォント（Inter / Roboto / Arial / Open Sans / システムデフォルト）、見出し上の丸角アイコン、色の上のグレーテキスト、ネストされたカード、bounce/elastic イージング、冗長なコピー。

判定テスト: これを誰かに見せて「AIが作った」と言ったら、すぐに信じるだろうか？ はいなら、それが問題。残酷なまでに正直に判定する。

### 様式とデザイン原則への準拠

- design-flow SKILL.md のデザイン原則を満たしているか
- `spec/design/index.md` に定めた様式の体系に忠実か。体系に根拠のない思いつきの装飾が混入していないか
- 様式の表現がユーザビリティを損なっていないか（可読性・操作性が優先）

### ビジュアル階層

- 視線は最も重要な要素に最初に向かうか
- 明確なプライマリアクションがあるか。2秒で見つけられるか
- サイズ・色・位置が重要度を正しく伝えているか
- 異なる重みを持つべき要素間で視覚的な競合が起きていないか
- すべてのボタンがプライマリになっていないか（ゴースト・テキストリンク・セカンダリの階層があるか）

### 情報アーキテクチャ

- 構造は直感的か。初見のユーザーが組織を理解できるか
- 関連するコンテンツが論理的にグループ化されているか
- 一度に提示する選択肢が多すぎないか（認知的過負荷）
- ナビゲーションは明確で予測可能か

### 構図・視覚的強度

装飾過多と単調さの**両方向**をチェックする。片側だけ見ていると、地味なデザインを「落ち着いている」と誤判定する。

- 過剰側: 目を引く要素が競合していないか、エフェクトが目的なく足されていないか、色数が多すぎて階層が壊れていないか
- 不足側: どこも同じ余白・同じ重みで単調になっていないか、記憶に残る一点があるか、安全すぎて無個性になっていないか
- ホワイトスペースは意図的か、単なる残りか
- スペーシングと反復にビジュアルリズムがあるか。非対称はデザインされたものか偶然か

### 色の役割

- 色が装飾ではなくコミュニケーションに使われているか（意味を持つか）
- パレットにまとまりがあるか。ドミナントカラーとアクセントの関係が成立しているか
- アクセントカラーが本当に注意を引くべきものに使われているか
- 色覚特性の異なるユーザーにも意味が伝わるか（色だけに情報を依存させていないか）

### 不要な複雑さ

- 削れる要素はないか。すべての要素がその存在価値を持っているか
- 同じ情報を繰り返していないか（冗長なヘッダー、見出しを言い換えただけのイントロ）
- すべてをカードで包んでいないか。コンテナが本当に必要か
- 操作手順を減らせないか

### 状態とエッジケース

- **空の状態**: 「ここには何もありません」で終わらず、次のアクションへ導いているか。インターフェースの使い方を教えているか
- **ローディング状態**: 体感待ち時間を減らす設計になっているか
- **エラー状態**: 有用で、ユーザーを非難しないか。回復手段が示されているか
- **成功状態**: 完了を確認し、次のステップへ案内しているか

### マイクロコピー

- ラベル・ボタン・見出しが曖昧でないか。何が起きるか読んで分かるか
- エラーメッセージが「何が起きたか」「どう直すか」を伝えているか。技術用語やエラーコードをそのまま出していないか
- 製品に詳しくない人が読んで理解できるか
- 全体のトーンが `spec/design/index.md` の方針と一致しているか

### トークンと方針との整合性

- `spec/design/tokens.md` の値が正しく使われているか
- `spec/design/index.md` の方針に沿っているか

## Step 3: ディテール・一貫性

大きなUX問題ではなく、良い仕上がりと素晴らしい仕上がりを分ける細部に焦点を当てる。ズームインして、目を細めて、ズレを探す。

構造やUXの問題を見つけても、それは Step 2 の担当なので指摘しない（既に収束している前提）。

### アラインメントとスペーシング

- すべての要素がグリッドに揃っているか
- すべてのギャップがスペーシングスケールを使っているか（`13px` のような場当たりな値がないか）
- 光学的アラインメント: アイコンなど視覚的重心がずれる要素が調整されているか
- スペーシングとアラインメントが全ブレークポイントで成立しているか

### タイポグラフィの洗練

- 同じ役割の要素が全画面で同じサイズ・ウェイトを使っているか
- 本文の行長が 45〜75 文字に収まっているか
- 行の高さがフォントサイズとコンテキストに対して適切か
- 最終行に単語が1つだけ残っていないか（ウィドウ・オーファン）
- 見出しレベル間に十分なコントラストがあるか

### 色とコントラストのディテール

- ハードコードされた色がないか。すべてトークン経由か
- 同じ色が全画面で同じ意味を持っているか
- ピュアグレー・ピュアブラック・ピュアホワイトを使っていないか（微妙なティントがあるか）
- 色付き背景の上にグレーテキストを置いていないか

### インタラクション状態

すべてのインタラクティブ要素に、必要な状態が揃っているか:

デフォルト / ホバー / フォーカス / アクティブ / 無効 / ローディング / エラー / 成功

欠けている状態は、そのまま実装時の抜け漏れになる。

### モーション

- 状態変化が適切にアニメーションされているか（150〜300ms）
- イージングが `ease-out-quart / quint / expo` 系か。**bounce / elastic を使っていないか**
- `transform` と `opacity` のみをアニメーションしているか（width / height / padding / margin をアニメーションしていないか）
- モーションが装飾ではなく目的に奉仕しているか
- `prefers-reduced-motion` を尊重しているか

### コピーの一貫性

- 同じものが全画面で同じ名前で呼ばれているか
- タイトルケース／センテンスケースの使い分けが一貫しているか
- 句読点の扱いが一貫しているか（文には句点、ラベルには付けない等）
- 誤字脱字がないか

### アイコンと画像

- すべてのアイコンが同じファミリー、または調和するスタイルか
- アイコンのサイズがコンテキストに対して一貫しているか
- アイコンが隣接テキストに光学的に揃っているか
- 画像にアスペクト比が指定され、レイアウトシフトを起こさないか

### 画面間の反復パターン

- 複数画面で繰り返される要素（ボタン、カード、テーブル、ナビ、フォーム行など）が同じ姿になっているか
- 同じ役割なのに微妙に違う実装になっているものがあれば、共通パターンとして統一する
- 統一した結果 `spec/design/tokens.md` に追加すべきトークンが出てきたら、指摘に含める

## Step 4: アクセシビリティ・堅牢性

「誰にでも使えるか」「どんなデータでも壊れないか」に焦点を当てる。

見た目の好みやディテールのズレは Step 2〜3 の担当なので指摘しない。

### アクセシビリティ

- **コントラスト比**: テキストが WCAG AA（4.5:1、大きいテキストは 3:1）を満たしているか
- **フォーカス表示**: キーボードフォーカスが視認でき、十分なコントラストがあるか。`outline: none` で消していないか
- **キーボード操作**: タブ順序が論理的か。キーボードトラップがないか
- **セマンティックHTML**: 見出し階層が正しいか（h1 から飛び級していないか）、ランドマークがあるか、ボタンを div で作っていないか
- **ARIA**: ロール・ラベル・状態が必要な箇所に付いているか
- **alt テキスト**: 画像に説明的な alt があるか。装飾画像は空 alt になっているか
- **フォーム**: `label` と入力が正しく紐づいているか。必須インジケーターが明確で一貫しているか。エラーメッセージの表示位置と書式が一貫しているか

### レスポンシブ完全性

- モバイル・タブレット・デスクトップで、横スクロール・要素の重なり・はみ出しがないか
- タッチターゲットが指でタップしやすい大きさを確保しているか
- モバイルで重要な機能を隠していないか（適応させる。切り捨てない）
- 流動的タイポグラフィ・スペーシング（`clamp()` 等）が両端で破綻していないか
- `<meta name="viewport">` の設定が妥当か

### 表示の堅牢性

ダミーデータは常に都合の良い長さになっている。**現実のデータで壊れないか**を確認する。

- **長いテキスト**: 極端に長い名前・タイトル・説明文を入れてもレイアウトが壊れないか。省略（ellipsis）か折り返しが効いているか
- **空・欠落データ**: 値が無い項目、0件のリスト、画像が無いカードが破綻しないか
- **数値の桁**: 大きい数値・小数・マイナス値でカラム幅が崩れないか
- **多言語**: 日本語と英語で文字列長が大きく変わる箇所（ボタンラベル、ナビ）が耐えられるか。ドイツ語のような長い言語を想定しても致命的に崩れないか
- **改行できない文字列**: URL・メールアドレス・ID などがはみ出さないか

### 描画パフォーマンス

- 読み込み後に要素が飛び跳ねないか（レイアウトシフト）。画像・埋め込みにサイズ指定があるか
- 画面外のコンテンツに遅延読み込みが効いているか
- 重いエフェクト（大量の blur、影、フィルタ）が過剰に積まれていないか
- レイアウトプロパティをアニメーションしていないか（全画面横断で確認する）
