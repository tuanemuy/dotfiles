# Phase 4: レビュー

## 目的

作成したHTMLデザインを複数の観点で評価し、品質を担保する。
段階的に焦点を絞ってレビューし、各ラウンドで改善する。

## レビューパイプライン

```
Step 1: スクリーンショット取得と破綻チェック
  → 致命的な崩れがあれば修正
Step 2: UX・デザイン品質（体験として機能しているか）
  → 修正
Step 3: ディテール・一貫性（仕上がりの精度）
  → 修正
Step 4: アクセシビリティ・堅牢性（誰にでも・どんなデータでも壊れないか）
  → 修正
```

Step 2〜4 はそれぞれ独立したレビュアーに委譲する。観点の定義は `review-perspectives.md` にあり、**メインエージェントは観点本文を読まない** — 各レビュアーに該当節を読ませ、指摘の一行リストだけ受け取る。

大きい問題から順に潰す構成になっている。Step 2 で構造やUXを直すと Step 3 のディテールはやり直しになるため、**Step 2〜4 は並列化せず、前ステップの `fix` を修正してから次へ進む**。

各ステップの指摘は `spec/design/review/${連番}.md` に記録し、指摘台帳（`spec/design/review/triage.md`、SKILL.md「レビューの原則」参照）で仕分ける。仕分けと修正ループは `../../_shared/references/review-loop.md` に従う。

## Step 1: スクリーンショット取得と破綻チェック

レビュアーを立てる前に、全画面を**モバイル・タブレット・デスクトップの3サイズ**で撮影する。ここで撮った画像を Step 2〜4 のレビュアーが共有して読むので、**パスを固定する**。

撮影は機械的な作業なので、サブエージェント（**探索区分**、`../../_shared/references/subagent-policy.md`）に委譲してよい。

各画面について、Phase 3 と同じ3ビューポート（モバイル 375×667 / タブレット 768×1024 / デスクトップ 1280×800）で撮る:

```bash
agent-browser --session design-review open file:///absolute/path/to/spec/design/pages/{画面名}.html

agent-browser --session design-review viewport 375 667
agent-browser --session design-review screenshot /tmp/design-screenshots/review/{画面名}-mobile.png

agent-browser --session design-review viewport 768 1024
agent-browser --session design-review screenshot /tmp/design-screenshots/review/{画面名}-tablet.png

agent-browser --session design-review viewport 1280 800
agent-browser --session design-review screenshot /tmp/design-screenshots/review/{画面名}-desktop.png
```

撮り終えたらセッションを閉じる:

```bash
agent-browser --session design-review close
```

### 破綻チェック（メインが行う）

撮影後、メインエージェントが**1画面ずつではなく全体をざっと**見て、レビュアーを立てる価値があるかだけ判断する。細かい評価はしない — それは Step 2〜4 の仕事。

- レンダリング自体が失敗していないか（真っ白、CSS未適用、画像が全滅）
- どのビューポートかで横スクロールや要素の重なりが起きていないか
- 画面数と撮影枚数が一致しているか（撮り漏れがないか）

致命的な崩れがあればここで直し、撮り直してから Step 2 へ進む。**問題がなければメインは画像をコンテキストに抱え込まず、パスだけ持って次へ進む。**

## Step 2〜4: 観点別レビューの委譲

各ステップで1体のレビュアー（**判断区分**）を立てる。ステップ間は直列。

| Step | 観点 | `review-perspectives.md` の該当節 |
| --- | --- | --- |
| 2 | UX・デザイン品質 | 「Step 2: UX・デザイン品質」 |
| 3 | ディテール・一貫性 | 「Step 3: ディテール・一貫性」 |
| 4 | アクセシビリティ・堅牢性 | 「Step 4: アクセシビリティ・堅牢性」 |

### レビュアーへの指示テンプレート

`{Step番号}` `{観点名}` `{節見出し}` `{連番}` を差し替えて渡す。

```text
あなたはHTMLデザインをレビューするデザインレビュアーです。

## 前提として読むもの
1. {スキルパス}/references/review-perspectives.md の「{節見出し}」節 — これがあなたの観点
2. {スキルパス}/../frontend-design/SKILL.md の DON'T ガイドライン — 判定基準の土台
3. spec/design/index.md — デザイン方針と採用した様式
4. spec/design/tokens.md — トークン定義
5. spec/design/review/triage.md（あれば） — 既出指摘の判定。Key が一致する指摘は再指摘しない

## 対象（全量）
- HTML: spec/design/pages/ 配下の全ファイル
- スクリーンショット: /tmp/design-screenshots/review/{画面名}-{mobile|tablet|desktop}.png

対象の全ファイルを読み、スクリーンショットは Read ツールで画像として確認する。
コードだけ・画像だけで判断しない。

## やること
「{節見出し}」節の観点だけでレビューする。他ステップの観点には踏み込まない
（他のレビュアーが担当する）。

## 出力
レビュー全文を spec/design/review/{連番}.md に**自分で書く**。
メインには次だけを返す:
- 指摘件数
- 各指摘の一行サマリー（対象画面 + 何が問題か）
- カバレッジ: 確認した画面 / 観点外としてスキップした画面（理由を一行）
```

### 委譲時の注意

- 対象の**全量（全画面）を決定的に渡す**。「主要な画面だけ」のように LLM の判断で先に絞らせない
- 各ラウンドのレビューは**ゼロベース**で行わせる。前ラウンドの指摘を前提にしない（既出の吸収は台帳の Key 照合で行う）
- レビュー全文をメインに返させない。ファイルに書かせ、一行リストだけ受け取る

## 指摘の書き方

`spec/design/review/${連番}.md` には**対応が必要な問題点のみ**を記載する。各指摘に次を書く:

- **対象**: 画面名と該当箇所（「送信ボタン」のように具体的に。「いくつかの要素」は不可）
- **何が**: 問題を明確に名付ける
- **なぜ重要か**: ユーザーや目標にどう悪影響するか
- **修正**: どうすべきか。「探索を検討してみて」ではなく具体的な指示を書く

書くときの原則:

- 容赦なく優先度付けする。すべてが重要なら、何も重要ではない
- 批判を和らげない。曖昧なフィードバックは誰の時間も節約しない
- 検証せずに偽陽性を報告しない（スクリーンショットまたはコードで確認してから書く）
- うまくいっている点を1〜2行添えてよい。ただし指摘の水増しはしない

## 終了条件

- Step 4 まで完了し、**そのラウンドで `fix` と仕分けた指摘が0件**になったら完了（台帳に記録済みの指摘は件数に含めない）
- 「好みの範囲」「実装時に調整可能」レベルの軽微な指摘は `wont-fix` として台帳に一行理由つきで記録し、完了判定から除外する
- 最大3ラウンド。収束しない場合は残課題をまとめてユーザーに報告し、方針を相談する

次ラウンドに入る場合は Step 1 の撮影からやり直す（修正後の見た目で評価するため）。
