# Phase 2: 実装ガイド

## Step 1: ブランチの作成

```bash
DEFAULT_BRANCH=$(gh repo view --json defaultBranchRef --jq '.defaultBranchRef.name')

git fetch origin
git checkout -b issue/{Issue番号}/{短い説明} "origin/${DEFAULT_BRANCH}"
```

`gh` が使えない場合は `git remote show origin` の "HEAD branch" や `git symbolic-ref refs/remotes/origin/HEAD` からデフォルトブランチ名を得てもよい。

ブランチ名の `{短い説明}` はIssueのタイトルからケバブケースで生成する（英語・小文字・ハイフン区切り、30文字以内）。

既に同名のブランチがあればユーザーに確認する。

ブランチを作ったら、`.gitignore` を確認する。運用の判別は `git ls-files .thread/ | head -1` — 出力があれば `.thread/` をコミットする運用。コミットしない運用なら `.thread/` が、コミットする運用なら `.thread/*/review/` が ignore されているかを見て、無ければ追記してコミットに含める。

## Step 2: 計画に沿った実装

サブエージェント（**判断区分**）を起動し、steps.md の手順に沿って実装させる（委譲方式とモデル選択は `../../_shared/references/subagent-policy.md` に従う）。

Phase 1.5 でデザインモック（`spec/design/pages/*.html`）を作成している場合は、該当する画面のモックのパスをサブエージェントに渡し、それを完成イメージとして実装させる。モックは視覚的・構造的な仕様であって、そのまま貼り付けるものではない点（既存コンポーネントを使った実フレームワークのコードに落とし込む）を明記する。デザインモックが無い場合は下記の「デザインモック」項を省く。

サブエージェントに渡す内容:

```text
あなたは実装計画に基づいてコードを実装するエンジニアです。

## 対象Issue
- Issue番号: #{Issue番号}
- 実装手順: .thread/{Issue番号}/steps.md（設計と実装ステップ）
- 契約: .thread/{Issue番号}/plan.md（受け入れ基準とスコープ）
- デザインモック: spec/design/pages/{画面名}.html（Phase 1.5 で作成した場合のみ。完成イメージとして参照し、既存コンポーネントを使った実コードに落とし込む）

## やること
1. steps.md と plan.md を読む（デザインモックがあれば併せて確認する）
2. 各実装ステップについて、対象ファイルを読んで現状を把握する
3. 計画の指示に従って変更を適用する（UI はデザインモックの完成イメージに沿わせる）
4. CLAUDE.md や README.md にテスト・lint・型チェックの実行方法が記載されていれば、それに従って確認する
5. テストを追加・変更した場合、主要なアサーションについて**変異スポットチェック**を行う: 検証対象のコードに1点変異（条件反転・境界±1・ガード削除のいずれか）を一時的に入れ、テストが red になることを確認してから変異を戻す。green のままならそのテストに検出力がないので、テストを直してから先へ進む。`expect(x).toBeDefined()` や `not.toBe(...)` だけで済ませるアサーションは検証にならないので書かない
6. 実装中に非自明な設計判断を下した場合は、.thread/{Issue番号}/adr.md に追記する
   - adr.md は Issue 単位の作業ログで、判断の経緯が残る唯一の場所。書く時点では気軽に記録してよい。「あるべき」を変えた判断は、記録とは別に spec の該当ドキュメントを現在形で更新する（経緯・代替案は spec に書かない）
   - 既に adr.md がある場合は既存の連番の続きに追記、なければ新規作成。連番は `grep '^## ADR-' .thread/{Issue番号}/adr.md | tail -1` で調べる（全文は読まない）
   - 形式: 各決定ごとに「## ADR-{NNN}: {タイトル}」と「### Context」「### Decision」「### Consequences」を記載

## 重要な原則
- steps.md の指示に忠実に従い、plan.md のスコープを越えない — 勝手に範囲を広げない
- 既存コードのスタイル・規約に合わせる
- 不明点や判断に迷う点があれば、実装せずにその旨を報告する

## 出力
- 変更したファイルの一覧と変更内容の要約
- テスト・lint実行結果（実行した場合）
- 変異スポットチェックの結果（テストを追加・変更した場合は必須 — 対象にした挙動と、red を確認した変異。検出力不足でテストを直した場合はその内容）
- 記録した設計判断（adr.md に追記した場合）
- 判断に迷った点や懸念事項（あれば）
- 完了できなかった項目や既知の制限（あれば）
```

### 実装結果の確認

まず**中断か完了か**を判定する（基準は `../../_shared/references/subagent-policy.md` の「中断と完了の区別」）。実装の委譲は steps.md 全体を1体に任せるため、context 上限での中断が最も起きやすい箇所。

中断していた場合、**メインが残りを実装してはいけない**。同じ作業を再委譲する:

1. 1回目 — 同じスコープで再起動する。プロンプトに「前の実行が途中で中断している。まず `git status` / `git diff` で適用済みの変更を確認し、やり直さずに残りを進めること」を足す
2. 2回目 — steps.md の実装ステップをレイヤー・ファイルの切れ目で分割し、複数のサブエージェント（**判断区分**）に担当範囲を明示して振る。担当ファイルが重ならないものだけ並列にする
3. 3回目も中断 — 実装を止め、完了済みのステップ・残ステップ・中断理由をユーザーに報告して判断を委ねる。この状態でコミット・PR 作成に進まない

完了していた場合:

1. 報告を確認する
2. 判断に迷った点やエラーがあれば対処する（必要ならユーザーに確認）
3. steps.md の実装ステップと報告を突き合わせ、未着手のステップがないか確認する。あればその分だけを再委譲する（メインが埋めない）
4. テストを追加・変更したのに報告に変異スポットチェックの結果が無ければ、そのチェックだけを再委譲する
5. CLAUDE.md や README.md の手順に従い、全体のテスト・lint・型チェックで整合性を確認する

### 残存課題の記録

実装結果を確認した後、以下のいずれかに該当する項目があれば `.thread/{Issue番号}/progress.md` に記録する:

- steps.md の項目のうち、完全には実装できなかったもの
- 既知の制限事項やエッジケース
- 適用した回避策とその理由
- フォローアップが必要な作業

各項目には具体的な内容・理由・影響範囲を明記する。「TODO」「後で対応」のような曖昧な記述は避ける。

該当なしの場合は progress.md を作成しない。

## Step 3: 動作確認計画の作成

実装が確定したツリーに対して `.thread/{Issue番号}/testing.md` を作る。**Phase 4 はこのファイルをそのまま実行する**ので、記述が実体とズレていると正しい実装が FAIL 判定になる。

確認項目は plan.md の受け入れ基準と1対1で対応させる。各基準の「観測方法」欄が何を見るかを決めているので、ここで足すのは**どう操作すればそれが見られるか**だけ。**ブラウザで観測できる項目だけを書く** — ブラウザから観測できない基準（API レスポンスの形・CLI の出力など）は自動テストで担保し、「対象外の受け入れ基準」セクションに基準番号と担保先を一行で記す。**基準に紐づかない項目（既存機能の網羅確認・回帰の総ざらい）は書かない** — 変更と無関係な回帰は自動テストの担当。

### Step 3a: 確認に必要な実行コマンドの特定

「確認環境」セクションには、この Issue の変更を確認するために必要な実行コマンドだけを書く（プロジェクト全体のセットアップ手順は不要）。各コマンドは次のソースを実際に読んで実在を確認する。記憶や推測で書かない。

1. **CLAUDE.md** — プロジェクトルートと変更対象パッケージ
2. **README.md**
3. **package.json** — `scripts` の**全項目**に目を通す（dev / start / build だけで止めない）
4. **リポジトリルートの設定ファイル** — Makefile・デプロイ設定があれば読む

このソース走査はサブエージェント（**探索区分**。`../../_shared/references/subagent-policy.md`）に委譲してよい。

変更箇所を検証環境で触れる状態にするまでのステップを抜けなく洗い出す。検証環境のサーバー起動とデプロイ手順は別セクションに分ける。マイグレーション・シードの要否はプロジェクトの実態から判断する。

- 「手動でデプロイしてください」のような曖昧な逃げ文句は書かない
- 上記ソースで確認できないコマンドは書かない。どうしても見つからない場合だけ「要確認: {何の手順が見つからなかったか}」と明記する

### Step 3b: testing.md の作成

手順・セレクタ・ボタン文言・期待する出力は、**実装後のツリーを実際に読んで**書く。行番号を引く場合は現在のツリー基準であることを明記する。期待結果に書く値は、そのコマンド・画面が実際に出力する形でなければならない（`--list` でしか出ない件数を実行サマリーに探しに行かせる、等をしない）。

```markdown
# 動作確認計画 — Issue #{Issue番号}: {タイトル}

**Issue:** #{Issue番号}
**作成日:** {日付}

## 確認環境

### 検証環境の起動
{Step 3a で実在確認したコマンドのみ}

### デプロイ方法
{ステージング・本番への反映手順。不要なら「なし」}

## 確認項目

### 1. {確認項目のタイトル}

- **対応する受け入れ基準:** {AC-番号}
- **目的:** {何が正しく動くことを確認するか}
- **手順:**
  1. {具体的な操作手順}
- **期待結果:** {どうなれば正しいか}
- **確認ポイント:** {特に注意して見るべき箇所}

## エッジケース・異常系

### 1. {確認項目のタイトル}

- **目的:** {どんな異常系を確認するか}
- **手順:**
  1. {操作手順}
- **期待結果:** {エラー時にどう振る舞うべきか}

## 既存機能への影響確認

- {変更によって影響を受ける可能性のある既存機能と、その確認方法}

## 対象外の受け入れ基準

- {AC-番号}: {ブラウザで観測できない理由と担保先（自動テストのファイル・テスト名）。該当なしならセクションごと省略}
```

## Step 4: コミットとPR作成

動作検証はこのフェーズでは行わない。Phase 3 のレビュー・修正が完了した後、Phase 4 でレビュー済みのコードに対して実行する（`../SKILL.md` Phase 4 参照）。

1. 変更をステージング＆コミット

```bash
git add <変更ファイル>
git commit -m "$(cat <<'EOF'
{コミットメッセージ}

Issue #{Issue番号}
EOF
)"
```

2. リモートにプッシュ

```bash
git push -u origin issue/{Issue番号}/{短い説明}
```

3. PR作成（Draftで作成する）

```bash
gh pr create --draft --title "{PRタイトル}" --body "$(cat <<'EOF'
## Summary
- {変更内容の箇条書き}

## Issue
Closes #{Issue番号}

## Implementation Plan
Based on `.thread/{Issue番号}/plan.md` / `steps.md`

## Test plan

### デプロイ・動作確認方法
{testing.md の「確認環境」（検証環境の起動・デプロイ方法）から正確なコマンドを転記}

### 確認項目
- {testing.md からの主要確認項目}

🤖 Generated with [Claude Code](https://claude.com/claude-code)
EOF
)"
```
