# Phase 3: レビュー・修正ガイド

Phase 2 で作成した PR に対して、セルフレビュー・修正を繰り返し品質を担保する。レビューループの共通構造（コンテキストの原則・出力フォーマット・指摘台帳・修正ループ・完了条件）は `../../_shared/references/review-loop.md` を参照。渡すのは変更ファイルの一覧と差分ファイルのパス。差分本文はラウンド頭に1回だけ `{scratchpad}` へ書き出し、各レビュアーはそこから担当分を読む（レビュアーに `git diff` を引かせない）。

## 出力先

すべての成果物は `.thread/{Issue番号}/` 配下に保存する。

- レビューファイル: `.thread/{Issue番号}/review/review-{NNN}-{担当}.md`（各レビュアーが直接書く）
- ラウンドサマリー: `.thread/{Issue番号}/review/review-NNN.md`（メインが件数・Verdict だけ書く）
- 指摘台帳: `.thread/{Issue番号}/review/triage.md`（メインが仕分け結果を記録する。フォーマットは `../../_shared/references/review-loop.md` の「指摘台帳」参照）
- 台帳の薄いビュー: `.thread/{Issue番号}/review/triage-keys.md`（`wont-fix` / `defer` の Key・判定・Issue番号だけ。台帳と同時にメインが書き出し、レビュアーにはこちらを渡す）
- ADR: `.thread/{Issue番号}/adr.md`（作業ログ。既存ファイルに追記。「あるべき」を変えた判断の spec 反映確認は Phase 7）

## Step 1: 変更ファイル一覧の取得

```bash
git branch --show-current   # Phase 2 で作成した issue/{Issue番号}/... にいることを確認する
gh pr view <PR番号> --json title,baseRefName
git fetch origin && git diff --no-renames --name-status origin/{ベースブランチ}...HEAD
mkdir -p {scratchpad}/diff
git diff --no-renames origin/{ベースブランチ}...HEAD > {scratchpad}/diff/{Issue番号}-round-{NNN}.diff
```

`--name-status` の出力から **`.thread/` 配下を除外したもの**がこのラウンドの**レビュー対象の全量**。担当の判定に使い、Step 3 でレビュアーにもそのまま渡す。差分の本文はリダイレクトで `{scratchpad}` のファイルに落とすだけで、メインは読まない（`{scratchpad}` の定義は `../../_shared/references/scratchpad.md`。`{NNN}` はこのラウンドのレビューファイルと同じ連番）。一覧・差分ファイルとも再レビューの各ラウンドで取り直す（修正でファイルが増えるため）。

- **`.thread/` 配下は一覧から除外する。ただし `testing.md` だけは残す**（Phase 4 の自動実行を駆動するためレビュー対象）。plan.md は判定基準としてレビュアーに渡るが、それ自体はレビュー対象ではない
- ブランチ確認は飛ばさない（`...HEAD` で引くので、HEAD が違うと対象ごと取り違える）
- `--stat`（パスを切り詰める）・`gh pr view --json files`（100 件で打ち切り）は使わない
- `--no-renames` を付ける（`R` の1行2パスはカバレッジ照合を壊す）
- 差分本文をレビュアーに引かせず、差分ファイルのパスを配る（Step 3）

## Step 2: 担当の判定

レビューの体制は**担当**（レビュアーの体をどう分けるか）と**観点**（各レビュアーが何を見るか）を分けて決める。担当は Step 1 の**変更ファイル一覧だけ**から決める。plan.md の規模は読まない — コードが1行もない段階の自己申告より、実際に何を変えたかのほうが正確で、申告のブレがそのままレビューの体数に化けることもない。

### 担当 — 固定語彙から選ぶ

担当は次の固定語彙だけを使う。**新しい担当名を発明しない** — 表記ゆれはラウンドをまたぐ休止判定の照合を壊す:

- **`backend`** — ドメインモデル・ユースケース・アダプター・インフラを**1体で**見る。レイヤーで体を分けない — ポート契約の不一致（定義と実装、スキーマと spec の食い違い）は両側を同時に見ないと検出できない
- **`frontend`** — コンポーネント設計・ルーティング・状態管理・UX
- **`general`** — 差分が小さく1体で全体を見られる場合の単独レビュー、確認ラウンド、カバレッジ補完

**スケール規則:** backend の差分が複数のビジネスドメインにまたがり1体で注意深く読める量を超える場合（目安: 該当ファイル20超）、**`backend-{ドメイン名}`** にビジネスドメイン単位で分割する（例: `backend-billing` / `backend-inventory`。ドメイン名はプロジェクトの構造 — `core/domain/` 直下等 — から取る）。各体は担当ドメインの変更をエントリポイントから永続化までレイヤー横断で見る。frontend が大きい場合も同様に `frontend-{ドメイン名}` に割ってよい。

- **担当数の上限は5。** 差分に該当ファイルがない担当は立てない。1担当に閉じるなら `general` 1体でよい
- **性質（セキュリティ・パフォーマンス）・テスト・ドキュメント整合を担当にしない。** これらは全レビュアーが担当範囲の中で見る観点（次項）。`security` / `test` / `docs` のような担当名が候補に挙がったら立てずに差し戻す
- **初回ラウンドで決めた担当セットを台帳（triage.md）の先頭に記録し、以降のラウンドは同じスラッグだけを使う。** ラウンドを追って担当は減ることはあっても（休止）増えない — 修正で差分が伸びてスケール規則の目安を途中で越えても分割し直さない（増えたファイルのカバレッジは Step 4 の確認申告で担保される）。例外は Phase 4 戻りで修正が新しい担当に広がったときだけで、このときは Step 2 から担当を再判定し、更新後の担当セットを台帳に追記する（「Phase 4 からの戻り」参照）。共通ガイド（`review-loop.md`）の「観点の休止」にいう「観点」は、本ガイドでは担当を指す

### 観点 — 全レビュアーが共通で持つレンズ

観点は担当に紐づかない。各レビュアーは担当範囲の中で次の全観点を見る（Step 3 のプロンプトに含まれている）:

- **設計・モデリング** — 状態が直和型・判別ユニオンで組まれ不正な組み合わせが型で排除されているか（内部の `if (!x) throw` や非nullアサーションはモデルが不正状態を許すシグナル。境界での検証は正当）、ビジネスロジックの置き場所がレイヤーの責務と一致するか、外部データが境界でデコードされてドメイン型に変換されているか、状態遷移が明示されているか、副作用が隔離されているか
- **契約の整合** — ポート定義とアダプター実装、バリデーションスキーマと spec の記述、JSDoc と実装。**必ず両側を突き合わせる**
- **性質** — 担当範囲のセキュリティ（認証・認可、入力バリデーション、機密情報）とパフォーマンス（N+1、不要な計算、メモリ効率）
- **テストの実効性** — 確認した挙動が振る舞いを検証する実効的なテストで守られているか。検出力ゼロのアサーション（`toBeDefined()` 単独・`not.toBe(...)` 系）は検証と数えない
- **ドキュメント整合** — 差分が触れた・依拠している spec / docs の記述が本 PR の後も正しいか（本 PR が正本を誤りに変えていないか）

担当はレビュアーの割り当ての単位であって、ファイルの分割ではない（`../../_shared/references/review-loop.md` のコンテキストの原則）。ファイルの割り振りはしない。

## Step 3: サブエージェントでレビュー

判定した担当ごとに、サブエージェント（**判断区分**）を起動する（委譲方式とモデル選択は `../../_shared/references/subagent-policy.md` に従う）。

- 担当が**1つの場合**（小規模 Issue 等）→ サブエージェント1つを単発実行する。
- 担当が**2つ以上の場合** → サブエージェントを並列に起動する。

### レビュアーに渡す `.thread/` ファイル

渡すのは **`plan.md`（契約）と `triage-keys.md`（既出判定の薄いビュー）だけ**。他の `.thread/` 成果物はプロンプトに列挙せず、「読め」とも指示しない。レビュアーが自分の判断で引くのは自由だが、メインが全員に配ると同じファイルが担当数×ラウンド数だけコンテキストに乗る。

- `triage.md` — 全文は方針フェーズの1体だけ。ラウンドを追うごとに肥大する

- `steps.md` — 手順どおりかではなく結果が正しいかで見るため（Step 1 の一覧と plan.md で足りる）
- `testing.md` — 実機確認の計画。Phase 4 の担当で、コードレビューの判断材料ではない
- `adr.md` — 作業ログで、ラウンドを追うごとに肥大する。**既決の設計判断への再指摘は、レビュアーに事前共有するのではなく Step 5 の方針フェーズで照合して潰す**（レビューはゼロベースで行う原則どおり）

各サブエージェントには以下を渡す:

```text
あなたは「{担当名}」を担当するPRレビューの専門家です。

## レビュー対象
- PR: {PR番号} / ベースブランチ: {ベースブランチ}
- リポジトリ: {リポジトリパス}
- 契約: .thread/{Issue番号}/plan.md
- 既出判定: .thread/{Issue番号}/review/triage-keys.md（2ラウンド目以降のみ。`wont-fix` / `defer` 済みの指摘を蒸し返さない）
- 差分本文: {scratchpad}/diff/{Issue番号}-round-{NNN}.diff（このラウンドの全差分を書き出し済み）
- 変更ファイル一覧（**この全量がレビュー対象**。`A`追加 / `M`変更 / `D`削除）:
{Step 1 で .thread/ を除外した後の一覧}

## やること
1. CLAUDE.md / README.md（あれば `spec/` の該当分も）を読み、規約とアーキテクチャを把握する。**「設計からの逸脱」はこれと plan.md を基準に判定する**
2. plan.md の「受け入れ基準」で自分の担当に関わる基準が満たされているか、「スコープ / 含まれないもの」を越えた変更が紛れていないかを検証する
3. 一覧から自分の担当に関わるファイルを選び、担当分の差分を上記の差分本文ファイルから**1回にまとめて**読む（ファイルごとに読み直さない）。`git fetch` / `git diff` は実行しない（差分は上記ファイルに確定済み）。**スキップしたファイルは必ず記録する**
4. 判断に必要なら差分外の関連ファイルも読む。呼び出し側・呼び出し先が担当の外でも、判断に関わるなら引く。`.thread/` のファイル（`steps.md` / `testing.md` / `adr.md`）は必読ではない — 上記だけで判断できないときに、必要な箇所を絞って引く
5. 担当範囲を次の観点すべてで厳しくレビューする:
   - **設計・モデリング**: 不正状態が型で排除されているか（直和型・判別ユニオン。内部の `if (!x) throw` や非nullアサーションはモデルが不正状態を許すシグナル。境界での検証は正当）、ビジネスロジックの置き場所がレイヤーの責務と一致するか、外部データが境界でデコードされてドメイン型に変換されているか、状態遷移が明示されているか
   - **契約の整合**: ポート定義とアダプター実装、バリデーションスキーマと spec の記述、JSDoc と実装。**必ず両側を突き合わせて**食い違いを見る
   - **性質**: 担当範囲のセキュリティ（認証・認可、入力バリデーション、機密情報）・パフォーマンス（N+1、不要な計算、メモリ効率）
   - **テストの実効性**: 確認した挙動が振る舞いを検証する実効的なテストで守られているか。検出力ゼロのアサーション（`toBeDefined()` 単独・`not.toBe(...)` 系）は検証と数えない（テストコードのスタイルには踏み込まない）
   - **ドキュメント整合**: 差分が触れた・依拠している spec / docs の記述が本 PR の後も正しいか。**差分と無関係の既存の誤り**を見つけた場合も指摘してよいが、指摘に「既存の問題（本PRの変更起因ではない）」と明記する
   - **記述の衛生**: 指摘への弁明・修正の経緯など残す必要のない記述がコード・コメントに含まれていないか
6. **同種の欠陥を複数見つけたら、症状を個別に列挙せず、共通原因と集約先（1関数への集約等）を1件の指摘にまとめる**（例: 同じ正規化漏れが5箇所 → 5件ではなく「正規化を1関数に集約する」1件）
7. レビュー結果を `.thread/{Issue番号}/review/review-{NNN}-{担当名}.md` に**直接書き込む**

## レビューファイルのフォーマット
以下のフォーマットでファイルに書くこと:

### {担当名}

#### Blockers
- **[B-001]** 問題の説明
  - 場所: `ファイルパス:行番号`
  - 理由: なぜこれが問題か
  - 提案: どう直すべきか

#### Warnings
- **[W-001]** 問題の説明
  - 場所: `ファイルパス:行番号`
  - 理由: なぜ気になるか
  - 提案: 改善案

#### テスト保証
- `挙動（ファイル:シンボル）` — 守っているテスト: `テストファイル:テスト名`
- `挙動（ファイル:シンボル）` — 守られていない → [B-xxx / W-xxx]

**確認した主要な挙動ごとに1行書く（必須）。** 守られていない挙動はこの表に書くだけで済ませず、必ず対応する指摘（B/W）を立てる。

#### カバレッジ
- 確認: `パス`, `パス`
- スキップ: `パス` — {担当外と判断した理由を一行で}

**カバレッジは一覧と1対1で対応させること**（確認＋スキップの件数が一覧の件数と一致する）。一覧が大きい場合、スキップはディレクトリ単位でまとめてよい（確認は個別に列挙）。
BlockerがなければBlockersセクションに「なし」と書く。
厳しく見ること。妥協しない。でも的外れな指摘はしない。

このフォーマットは下限であって上限ではない。必須なのは ID 付きの指摘（B-/W-、場所・理由・提案）とテスト保証・カバレッジ。
分析の過程・前提・コード引用・代替案の比較など、伝えるべきことがあれば自由にセクションを足して深く書いてよい。

## 返答（レビュー全文は返さない）
ファイルへの書き込みが済んだら、返答には**サマリーだけ**を返す:
- Blockers: {数} / Warnings: {数}
- 各指摘の一行リスト: `[B-001] {ファイル:シンボル/カテゴリ} — {タイトル}`（先頭は指摘台帳の照合 Key）
- 確認したファイル: `パス` の列挙
- スキップしたファイル: `パス` の列挙（なければ「なし」）

**この4項目だけ。** 分析の経緯・コード引用・提案の再掲は返さない（詳細はレビューファイルにある）。
```

**中断したレビュアーの扱い**: サマリーが返らなかった・レビューファイルが作られていない担当は「指摘なし」ではない（判定基準は `../../_shared/references/subagent-policy.md`）。その担当だけを再委譲する。2回目も中断するならレビュー対象を分割して振り直す。3回目も中断したら、その担当が未実施であることをラウンドサマリーに明記して先へ進む（担当は独立なので、他担当の結果は使ってよい）。**メインが代わりにレビューして埋めない** — レビュー全文をメインのコンテキストに乗せない原則と真っ向からぶつかる。

## Step 4: ラウンドサマリーの作成

すべてのサブエージェントが完了したら、返ってきたサマリーから連番のラウンドサマリーを作る。レビュー全文を読み直したり転記したりしない。

**カバレッジの確認（必須）**: Step 1 の一覧の各パスに**「確認」の申告が1体以上あるか**を突き合わせ、ゼロ件のパスがあれば `general` を1体追加起動してそのファイルだけ見させる。スキップ側で突き合わせると申告漏れがすり抜けるので、必ず「確認されたか」で判定する。

保存先: `.thread/{Issue番号}/review/review-NNN.md`（NNNは001から始まる3桁の連番。担当別ファイル `review-NNN-{担当}.md` と同じ連番を使う）

```markdown
# PR Review #NNN — {PRタイトル}

**PR:** #{PR番号}
**Date:** {日付}
**Round:** {N}回目

## Summary

- Blockers: {数}
- Warnings: {数}
- Verdict: **BLOCKED**（Blocker 1件以上）/ **APPROVED**（Blocker ゼロ。完了判定は台帳の fix ゼロ）

## 担当別ファイル

- {担当名}: review-NNN-{担当}.md（B: {数} / W: {数}）

## カバレッジ

- 確認申告ゼロのファイル: {なし / パス一覧 → `general` で追跡}

## 指摘一覧

- [B-001] {ファイル:シンボル/カテゴリ} — {タイトル}（{担当}）
- [W-001] {ファイル:シンボル/カテゴリ} — {タイトル}（{担当}）
```

## Step 5: 指摘の修正

基本方針: **Blocker・Warning問わず、できる限りすべて修正する。** 後回しは最終手段。ただし修正がゴールではない — 直すべきでない指摘は台帳に記録して対応しない。

メインエージェントはここでもオーケストレーションに徹する。**「どの指摘を直すか／後回しにするか」という判断はメインが担い、実際のコード編集はサブエージェントに委譲する**（委譲方式は `../../_shared/references/subagent-policy.md` に従う）。

ラウンドサマリーに指摘がある場合:

1. メインが**指摘一覧（一行リスト）**を指摘台帳 `.thread/{Issue番号}/review/triage.md` と突き合わせる。Key が一致する既出指摘は判定を継承して再指摘カウントを +1 し、再審議しない
2. 新規の指摘は**修正方針フェーズ**（共通ガイドの同名節に従う）にかける。サブエージェント（**判断区分**）を1体立て、そのラウンドの全担当別レビューファイルと `.thread/{Issue番号}/plan.md`、台帳、`.thread/{Issue番号}/adr.md`（あれば）を渡して横断で読ませ、各指摘の妥当性判定（fix / wont-fix / defer）と修正の実行計画を返させる。メインはレビュー全文を読まない（省略条件も共通ガイドに従う）
   - **adr.md との照合はここで行う。** レビュアーは既決の設計判断を知らないまま指摘してくるので、adr.md で決着済みの判断を蒸し返した指摘は `wont-fix`（台帳の理由欄に該当 ADR 番号を書く）。判断を覆すべき新事実が出ているときだけ `fix` に上げ、Step 6 で ADR を更新する
   - **spec / docs の既存の誤り**（本 PR が触れても依拠してもいない記述の、もともとの誤り）は `fix` にしない — Phase 5 の基準で `defer`（既存 Issue への追記を優先）。この PR で直すのは、本 PR が触れた・依拠した記述の誤りだけ
   - **lint で機械的に防げる類の指摘**（変数のシャドウイング、未クォートのシェル引数、検出力ゼロのアサーション等）が同一 Issue 内で繰り返し出たら、個別修正とは別に lint ルール・CI ガード追加の Issue を `defer` で起票する
   - **wont-fix** — 誤った指摘、過度に防御的な提案、場当たり的に直すより設計を見直すべき指摘。一行理由を台帳に書く。設計の見直しが必要なものは Phase 5 の基準で別Issueも起票する
   - **defer** の前に `../SKILL.md` Phase 5 のスコープ基準を確認する。同じファイル・機能の中で完結する指摘や軽微な指摘は、ほぼ確実にこのPRで直す（軽微なほど修正コストが低い）。それでもこのPRで対応できないものだけ `gh issue create` で別Issueを起票し、Issue番号を台帳に記録する
   - 「要確認」で上がったものはメインが決めるか、ユーザーに判断を委ねる。設計判断を伴った決定は Step 6 で ADR に起こす
3. メインが方針を承認（承認でチェックする範囲は共通ガイド参照）して台帳に記録し、**実行計画の単位で**サブエージェント（**判断区分**）に委譲して修正させる。**Blocker・Warning とも残さず潰す**
   - 各サブエージェントには次を渡す:
     - 担当する指摘IDと、それが載っている担当別レビューファイル `.thread/{Issue番号}/review/review-NNN-{担当}.md`（複数担当にまたがるなら複数渡す）。指摘の詳細はサブエージェントがファイルから読む — メインが転記しない
     - 該当する台帳行の引用（Key・判定）。**`triage.md` のパスは渡さない**
     - 方針フェーズが決めた対応方針（採る側・採らない側の判断が絡む指摘のみ）
     - `.thread/{Issue番号}/plan.md`（受け入れ基準とスコープ）
     - 「方針に従って修正し、CLAUDE.md 記載の typecheck・lint を通すこと。修正対象外へスコープを広げないこと。テストを追加・変更した場合は `implementation-guide.md` Step 2 の変異スポットチェックを行い、結果を報告に含めること」
4. サブエージェント完了後、**メインが typecheck + lint を実行して整合性を確認する**。エラーが残っていればサブエージェントを再起動して修正させる
   - テストを追加・変更したのに報告に変異スポットチェックの結果が無ければ、そのチェックだけを再委譲する（Phase 2 の統合確認と同じ扱い）
   - 修正の委譲先が**中断**した場合、担当分の修正は入っていない。メインが代わりに直さず再委譲する（2回目は指摘単位まで分割）。修正は必須作業なので「成功した分だけで進める」は適用外 — 中断した指摘を未修正のまま再レビューに回すと、次ラウンドで同じ指摘が再指摘され、台帳の判定継承で握り潰されるおそれがある
   - 3回目も中断したら、その指摘を台帳に「中断・未修正」と記録し、レビューループを止めてユーザーに報告する
5. 台帳にラウンドブロック（**fix の担当別内訳を含む**。例: `fix内訳: backend 2 / frontend 0→休止 / general 1`）を追記し、`triage-keys.md` を更新する。修正をコミットしてから Step 1 に戻って再レビュー（ファイル一覧と差分ファイルを取り直し、次の連番ファイルを作る）。差分は `origin/{ベースブランチ}...HEAD` で引くため、未コミットの修正は差分ファイルに入らない。**コミット前に `git status` で `.thread/{Issue番号}/review/` がステージに混入していないことを確認する**

## Step 6: ADR への追記

レビュー中に**非自明な設計判断**を下した場合、`.thread/{Issue番号}/adr.md` に追記する。指摘への対応要否（wont-fix / defer）の記録には使わない — それは台帳の役割。仕分けが設計判断を伴う場合のみ ADR に起こし、台帳の理由欄からリンクする。adr.md は作業ログで、判断の経緯が残る唯一の場所。ここでは昇格の要否を判定しない — 気軽に記録してよい。spec / docs / CLAUDE.md に上げるべきものがあるかは Phase 7 の昇格ゲートでまとめて見る（`../../_shared/references/adr-guide.md`）。

Phase 1（計画時）で既に adr.md が存在する場合は、既存の連番の続きから追記する。なければ新規作成する。連番の調べ方は `../../_shared/references/adr-guide.md` の「作業ログへの追記」に従う（全文は読まない）。

各決定ごとに以下の形式で記載:

```markdown
## ADR-{NNN}: {タイトル}

### Context
{なぜこの判断が必要になったか}

### Decision
{何を決めたか}

### Consequences
{この判断の結果として何が起きるか}
```

作業ログなので書く時点では気軽に記録してよい。ただし些細な実装詳細（誰でも同じ結論に至る判断、コードの横の1〜2行のコメントで伝わるローカルな判断）はADRにしない。

## Step 7: 完了判定

完了条件は共通ガイドの通り「**そのラウンドで `fix` と仕分けた指摘がゼロ**」（台帳に記録済みの指摘は件数から除外）。

**再レビューを起こすのは `fix` だけ。** `fix` を修正した場合は Step 1 に戻って再レビュー（次の連番）。**`fix-editorial` はその場で適用して品質ゲートが通れば完了を妨げず、それだけでは次ラウンドを起こさない**（共通ガイドの完了条件どおり）。各ラウンドはゼロベースで行うが、**fix ゼロだった担当は次ラウンドから休止する**（休止・確認ラウンド・カバレッジの扱いは共通ガイドの「観点の休止」に従う — 同節の「観点」は本ガイドの担当）。次ラウンドの起動担当は台帳のラウンドブロックの fix 内訳から機械的に決める — 内訳が書けていないラウンドから次を起動しない。

**最大ラウンド数: 10回。** 10ラウンドに達しても収束しない場合は強制終了し、残っている指摘を最終ラウンドサマリーにまとめてユーザーに判断を委ねる。

## Step 8: 完了後の遷移

APPROVED になっても、この時点では PR を **Draft のまま**にする。Ready for review への切り替えは、Phase 4 の動作検証を通過した後に行う（`../SKILL.md` Phase 4 参照）。修正がすべてコミット・push 済みであることを確認して Phase 4 へ進む。

APPROVED に至らず強制終了した場合は Draft のまま残してユーザーに判断を委ね、Phase 4 の動作検証には進まない。

### Phase 4 からの戻り（スコープレビュー）

Phase 4 の動作検証で変更起因のバグが見つかり修正した場合は、増分に絞った**スコープラウンド**でこのレビューループに戻る:

- Step 1 のファイル一覧取得は行いつつ、レビュー対象は**修正で触れたファイル**に絞る。レビュアーは **`general` 1体**を起動し、修正差分と plan.md の受け入れ基準の観点で見させる
- レビューファイルの連番・台帳の判定継承・ラウンド上限（10回）の通算はフルレビューと同じ扱い。ラウンドサマリーに「スコープラウンド（Phase 4 戻り・対象: {ファイル一覧}）」と明記する
- スコープラウンドで fix が出たら修正して再びスコープラウンド。**fix ゼロで APPROVED** とし、再検証（Phase 4）へ進む。全担当の確認ラウンドは要求しない（フルの fix ゼロは Phase 4 前に観測済み）
- 修正が当初の変更範囲を超えて**新しい担当に広がった場合だけ**、Step 2 の担当判定からやり直してフルラウンドに戻す（初回に記録した担当セットを更新してよい唯一のケース。更新後のセットを台帳に追記する）

## 重要な注意点

共通原則（厳しくレビュー・確信あるものだけ修正・毎ラウンド新規作成）は `../../_shared/references/review-loop.md` に従う。固有の点:

- メインはオーケストレーションに徹する。レビュー（Step 3）も方針立案・修正（Step 5）も実作業はサブエージェント（いずれも判断区分）に委譲し、メインは方針の承認・台帳の記録・品質ゲート・ADR/起票の判断に集中する
- レビュー全文・差分本文・修正内容はメインのコンテキストに乗せない。サブエージェントがファイルに直接書き、メインはサマリー（件数と一行リスト）だけ扱う
- カバレッジはスキップ申告の突き合わせ（Step 4）で担保する — 担当でファイルを分割しない
- レビューの基準は plan.md の受け入れ基準とスコープ。レビュアーに配る `.thread/` ファイルは plan.md と triage-keys.md だけに絞る（Step 3 の「レビュアーに渡す `.thread/` ファイル」）— 同じファイルが担当数×ラウンド数だけコンテキストに乗るのを避ける
- 担当は Step 2 の固定語彙から差分の形で決める。上限5は上限であって目標ではない。観点は担当に紐づかない全レビュアー共通のレンズで、`security` / `test` / `docs` を担当として立てない
