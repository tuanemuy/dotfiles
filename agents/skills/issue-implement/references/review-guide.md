# Phase 3: レビュー・修正ガイド

Phase 2 で作成した PR を、全量レビュー 2 ラウンド（R1・R2）と Phase 4 後のスコープラウンドで品質担保する。レビューループの共通構造（コンテキストの原則・レビューの観点・出力フォーマット・指摘台帳・修正ループ）は `../../_shared/references/review-loop.md` を参照。ラウンドの遷移と完了条件は本ガイドの Step 7・Step 8 が定める。渡すのは変更ファイルの一覧と差分ファイルのパス。差分本文はラウンド頭に1回だけ `{scratchpad}` へ書き出し、各レビュアーはそこから担当分を読む（レビュアーに `git diff` を引かせない）。

## 出力先

すべての成果物は `.thread/{Issue番号}/` 配下に保存する。

- レビューファイル: `.thread/{Issue番号}/review/review-{NNN}-{担当}.md`（各レビュアーが直接書く）
- ラウンドサマリー: `.thread/{Issue番号}/review/review-NNN.md`（メインが件数・Verdict だけ書く）
- 指摘台帳: `.thread/{Issue番号}/review/triage.md`（メインが仕分け結果を記録する。フォーマットは `../../_shared/references/review-loop.md` の「指摘台帳」参照）
- 台帳の薄いビュー: `.thread/{Issue番号}/review/triage-keys.md`（`wont-fix` / `defer` の Key・判定・Issue番号だけ。台帳と同時にメインが書き出し、レビュアーにはこちらを渡す）
- ADR: `.thread/{Issue番号}/adr.md`（作業ログ。既存ファイルに追記。「あるべき」を変えた判断の spec 反映確認は Phase 5）

## Step 1: 変更ファイル一覧の取得

```bash
git branch --show-current   # Phase 2 で作成した issue/{Issue番号}/... にいることを確認する
gh pr view <PR番号> --json title,baseRefName
git fetch origin && git diff --no-renames --name-status origin/{ベースブランチ}...HEAD
mkdir -p {scratchpad}/diff
git diff --no-renames origin/{ベースブランチ}...HEAD > {scratchpad}/diff/{Issue番号}-round-{NNN}.diff
```

`--name-status` の出力から **`.thread/` 配下を除外したもの**がこのラウンドの**レビュー対象の全量**。担当の判定に使い、Step 3 でレビュアーにもそのまま渡す。差分の本文はリダイレクトで `{scratchpad}` のファイルに落とすだけで、メインは読まない（`{scratchpad}` の定義は `../../_shared/references/scratchpad.md`。`{NNN}` はこのラウンドのレビューファイルと同じ連番）。一覧・差分ファイルとも再レビューの各ラウンドで取り直す（修正でファイルが増えるため）。

- **`.thread/` 配下は一覧から除外する**（plan.md は判定基準としてレビュアーに渡るが、それ自体はレビュー対象ではない）。`testing.md` の正しさは Phase 4 の実行が判定する
- ブランチ確認は飛ばさない（`...HEAD` で引くので、HEAD が違うと対象ごと取り違える）
- `--stat`（パスを切り詰める）・`gh pr view --json files`（100 件で打ち切り）は使わない
- `--no-renames` を付ける（`R` の1行2パスはカバレッジ照合を壊す）
- 差分本文をレビュアーに引かせず、差分ファイルのパスを配る（Step 3）

## Step 2: 担当の判定

レビューの体制は**担当**（レビュアーの体をどう分けるか）と**観点**（各レビュアーが何を見るか）を分けて決める。担当は Step 1 の**変更ファイル一覧だけ**から決める。plan.md の規模は読まない。コードが1行もない段階の自己申告より、実際に何を変えたかのほうが正確。申告のブレがレビューの体数に化けることもない。

### 担当 — 固定語彙から選ぶ

担当は次の固定語彙だけを使う。**新しい担当名を発明しない** — 表記ゆれはラウンドをまたぐ台帳の照合を壊す:

- **`backend`** — ドメインモデル・ユースケース・アダプター・インフラを**1体で**見る。レイヤーで体を分けない — ポート契約の不一致（定義と実装、スキーマと spec の食い違い）は両側を同時に見ないと検出できない
- **`frontend`** — コンポーネント設計・ルーティング・状態管理・UX
- **`general`** — 差分が小さく1体で全体を見られる場合の単独レビュー、スコープラウンド、カバレッジ補完

**スケール規則:** backend の差分が複数のビジネスドメインにまたがり1体で注意深く読める量を超える場合（目安: 該当ファイル20超）、**`backend-{ドメイン名}`** の **2 体**に分割する（例: `backend-billing` / `backend-inventory`。ドメイン名はプロジェクトの構造 — `core/domain/` 直下等 — から取り、3 ドメイン以上は関連の近いものを束ねて 2 体に寄せる）。各体は担当ドメインの変更をエントリポイントから永続化までレイヤー横断で見る。frontend は分割しない。

- **担当数の上限は3。** 体を増やしても新規の指摘は増えず、同じ spec / docs を全員が読む分だけラウンドの費用が上がる。差分に該当ファイルがない担当は立てない。1担当に閉じるなら `general` 1体でよい
- **性質（セキュリティ・パフォーマンス）・テスト・ドキュメント整合を担当にしない。** これらは全レビュアーが担当範囲の中で見る観点（次項）。`security` / `test` / `docs` のような担当名が候補に挙がったら立てずに差し戻す
- **初回ラウンドで決めた担当セットを台帳（triage.md）の先頭に記録し、R2 も同じセットで起動する。** 修正で差分が伸びてスケール規則の目安を越えても分割し直さない（増えたファイルのカバレッジは Step 4 の確認申告で担保される）

### 観点 — 全レビュアーが共通で持つレンズ

観点は担当に紐づかない。各レビュアーは担当範囲の中で `../../_shared/references/review-loop.md` の「レビューの観点」をすべて見る（Step 3 のプロンプトに含まれている）。目的の充足と正しさを構造より先に見る。

担当はレビュアーの割り当ての単位であって、ファイルの分割ではない（`../../_shared/references/review-loop.md` のコンテキストの原則）。ファイルの割り振りはしない。

## Step 3: サブエージェントでレビュー

判定した担当ごとにサブエージェントを起動する。R1 は**審査区分**、R2 とスコープラウンドは**判断区分**（委譲方式とモデル選択は `../../_shared/references/subagent-policy.md` に従う）。critical な指摘は R1 で出る。R2 以降は R1 の修正増分と取りこぼしの確認で、メインと同じモデルで足りる。

- 担当が**1つの場合**（小規模 Issue 等）→ サブエージェント1つを単発実行する。
- 担当が**2つ以上の場合** → サブエージェントを並列に起動する。

### レビュアーに渡す `.thread/` ファイル

渡すのは **`plan.md`（契約）と `triage-keys.md`（既出判定の薄いビュー）だけ**。他の `.thread/` 成果物はプロンプトに列挙せず、「読め」とも指示しない。レビュアーが自分の判断で引くのは自由だが、メインが全員に配ると同じファイルが担当数×ラウンド数だけコンテキストに乗る。

- `triage.md` — 全文は方針フェーズの1体だけ。ラウンドを追うごとに肥大する

- `steps.md` — 手順どおりかではなく結果が正しいかで見るため（Step 1 の一覧と plan.md で足りる）
- `testing.md` — 実機確認の計画。Phase 4 の担当で、コードレビューの判断材料ではない
- `adr.md` — 作業ログで、ラウンドを追うごとに肥大する。**既決の設計判断への再指摘は、レビュアーに事前共有するのではなく Step 5 の方針フェーズで照合して潰す**（レビューはゼロベースで行う原則どおり）

各サブエージェントには以下を渡す:

```text
あなたは「{担当名}」を担当するPRレビューの専門家です。

## レビュー対象
- PR: {PR番号} / ベースブランチ: {ベースブランチ}
- リポジトリ: {リポジトリパス}
- 契約: .thread/{Issue番号}/plan.md
- 既出判定: .thread/{Issue番号}/review/triage-keys.md（2ラウンド目以降のみ。`wont-fix` / `defer` 済みの指摘を蒸し返さない）
- 差分本文: {scratchpad}/diff/{Issue番号}-round-{NNN}.diff（このラウンドの全差分を書き出し済み）
- 変更ファイル一覧（**この全量がレビュー対象**。`A`追加 / `M`変更 / `D`削除）:
{Step 1 で .thread/ を除外した後の一覧}

## やること
1. CLAUDE.md / README.md（あれば `spec/` の該当分も）を読み、規約とアーキテクチャを把握する。**「設計からの逸脱」はこれと plan.md を基準に判定する**
2. 一覧から自分の担当に関わるファイルを選び、担当分の差分を上記の差分本文ファイルから**1回にまとめて**読む（ファイルごとに読み直さない）。`git fetch` / `git diff` は実行しない（差分は上記ファイルに確定済み）。**スキップしたファイルは必ず記録する**
3. 判断に必要なら差分外の関連ファイルも読む。呼び出し側・呼び出し先が担当の外でも、判断に関わるなら引く。`.thread/` のファイル（`steps.md` / `adr.md`）は必読ではない — 上記だけで判断できないときに、必要な箇所を絞って引く。`testing.md` は引かない（Phase 4 の担当）
4. 担当分のテストを CLAUDE.md 記載のコマンドで実行し、件数と結果を「実行確認」に書く。UI の操作結果（フォーカス・遷移・表示）や外部ライブラリの挙動に関する指摘は、テスト実行かブラウザ観測で確かめたものだけを B / W にする。読解だけで導いた指摘には「未観測」と明記する（方針フェーズが再現してから fix にする）
5. 担当範囲を次の観点すべてで厳しくレビューする。目的の充足と正しさを構造より先に見る:
   - **目的の充足**: plan.md の「受け入れ基準」で自分の担当に関わる基準が漏れなく満たされているか。「スコープ / 含まれないもの」を越えた変更の混入、spec からの逸脱
   - **ロジックの正しさ**: 条件・境界値・エラー経路・null / 空 / 重複・順序・並行・冪等性。「この入力のときどうなるか」を具体値で追い、期待と違う経路を指摘する
   - **契約の整合**: ポート定義とアダプター実装、バリデーションスキーマと spec の記述、ドキュメンテーションコメントと実装。**必ず両側を突き合わせて**食い違いを見る
   - **性質**: 担当範囲のセキュリティ（認証・認可、入力バリデーション、機密情報）・パフォーマンス（N+1、不要な計算、リソースリーク）
   - **設計・モデリング**: 不正状態が型で排除されているか（直和型・判別ユニオン。内部の存在チェックや非nullアサーションはモデルが不正状態を許すシグナル。境界での検証は正当）、外部データが境界でデコードされてドメイン型になっているか、状態遷移が明示されているか、副作用が隔離されているか
   - **レイヤーと責務**: 依存の向きがアーキテクチャ（CLAUDE.md / spec）に従っているか、ビジネスロジックの置き場所がレイヤーの責務と一致するか、モジュール・関数が1つの責務に閉じているか。過剰な抽象化・早すぎる一般化も負債として指摘する
   - **既存資産との整合**: 既存の関数・型・パターンの再実装、規約からの逸脱、デッドコード、不要な依存追加がないか
   - **テストの必要十分性**: 受け入れ条件と確認した挙動ごとに、振る舞いを検証するテストが1本あるか。テストが実装詳細に結合していないか。検出力ゼロのアサーション（存在確認のみ・否定のみ）は検証と数えない（テストコードのスタイルには踏み込まない）
   - **ドキュメント整合**: 差分が触れた・依拠している**設計ドキュメント**（`spec/domains` · `usecases` · `pages` · `testcases` と `docs/`）の記述が本 PR の後も正しいか。**差分と無関係の既存の誤り**を見つけた場合も指摘してよいが、指摘に「既存の問題（本PRの変更起因ではない）」と明記する
   - **記述の衛生**: 指摘への弁明・修正の経緯など残す必要のない記述がコード・コメントに含まれていないか
6. **同種の欠陥を複数見つけたら、症状を個別に列挙せず、共通原因と集約先（1関数への集約等）を1件の指摘にまとめる**（例: 同じ正規化漏れが5箇所 → 5件ではなく「正規化を1関数に集約する」1件）
7. レビュー結果を `.thread/{Issue番号}/review/review-{NNN}-{担当名}.md` に**直接書き込む**

## レビューファイルのフォーマット
以下のフォーマットでファイルに書くこと:

### {担当名}

#### Blockers
- **[B-001]** 問題の説明
  - 場所: `ファイルパス:行番号`
  - 理由: なぜこれが問題か
  - 提案: どう直すべきか

#### Warnings
- **[W-001]** 問題の説明
  - 場所: `ファイルパス:行番号`
  - 理由: なぜ気になるか
  - 提案: 改善案

#### 実行確認
- `{コマンド}` — {件数・結果}
- ブラウザ観測: {観測した操作と結果 / なし}

#### テスト保証
- `挙動（ファイル:シンボル）` — 守っているテスト: `テストファイル:テスト名`
- `挙動（ファイル:シンボル）` — 守られていない → [B-xxx / W-xxx]

**確認した主要な挙動ごとに1行書く（必須）。** 守られていない挙動はこの表に書くだけで済ませず、必ず対応する指摘（B/W）を立てる。実行していないテストを「守っているテスト」に挙げない。

#### カバレッジ
- 確認: `パス`, `パス`
- スキップ: `パス` — {担当外と判断した理由を一行で}

**カバレッジは一覧と1対1で対応させること**（確認＋スキップの件数が一覧の件数と一致する）。一覧が大きい場合、スキップはディレクトリ単位でまとめてよい（確認は個別に列挙）。
BlockerがなければBlockersセクションに「なし」と書く。
厳しく見ること。妥協しない。でも的外れな指摘はしない。

このフォーマットは下限であって上限ではない。必須なのは ID 付きの指摘（B-/W-、場所・理由・提案、未観測なら「未観測」）と実行確認・テスト保証・カバレッジ。
分析の過程・前提・コード引用・代替案の比較など、伝えるべきことがあれば自由にセクションを足して深く書いてよい。

- 確認したファイル: `パス` の列挙
- スキップしたファイル: `パス` の列挙（なければ「なし」）

**この4項目だけ。** 分析の経緯・コード引用・提案の再掲は返さない（詳細はレビューファイルにある）。
```

**中断したレビュアーの扱い**: サマリーが返らなかった・レビューファイルが作られていない担当は「指摘なし」ではない（判定基準は `../../_shared/references/subagent-policy.md`）。その担当だけを再委譲する。2回目も中断するならレビュー対象を分割して振り直す。3回目も中断したら、その担当が未実施であることをラウンドサマリーに明記して先へ進む（担当は独立なので、他担当の結果は使ってよい）。**メインが代わりにレビューして埋めない** — レビュー全文をメインのコンテキストに乗せない原則と真っ向からぶつかる。

## Step 4: ラウンドサマリーの作成

すべてのサブエージェントが完了したら、返ってきたサマリーから連番のラウンドサマリーを作る。レビュー全文を読み直したり転記したりしない。

**カバレッジの確認（必須）**: Step 1 の一覧の各パスに**「確認」の申告が1体以上あるか**を突き合わせ、ゼロ件のパスがあれば `general` を1体追加起動してそのファイルだけ見させる。スキップ側で突き合わせると申告漏れがすり抜けるので、必ず「確認されたか」で判定する。

保存先: `.thread/{Issue番号}/review/review-NNN.md`（NNNは001から始まる3桁の連番。担当別ファイル `review-NNN-{担当}.md` と同じ連番を使う）

```markdown
# PR Review #NNN — {PRタイトル}

**PR:** #{PR番号}
**Date:** {日付}
**Round:** {N}回目

## Summary

- Blockers: {数}
- Warnings: {数}
- Verdict: **BLOCKED**（Blocker 1件以上）/ **APPROVED**（Blocker ゼロ。完了判定は台帳の fix ゼロ）

## 担当別ファイル

- {担当名}: review-NNN-{担当}.md（B: {数} / W: {数}）

## カバレッジ

- 確認申告ゼロのファイル: {なし / パス一覧 → `general` で追跡}

## 指摘一覧

- [B-001] {ファイル:シンボル/カテゴリ} — {タイトル}（{担当}）
- [W-001] {ファイル:シンボル/カテゴリ} — {タイトル}（{担当}）
```

## Step 5: 指摘の修正

方針: **Blocker・Warning 問わずすべて修正する。** 後回しは最終手段。ただし修正がゴールではない — 直すべきでない指摘は台帳に記録して対応しない。

メインエージェントはここでもオーケストレーションに徹する。**「どの指摘を直すか／後回しにするか」という判断はメインが担い、実際のコード編集はサブエージェントに委譲する**（委譲方式は `../../_shared/references/subagent-policy.md` に従う）。

ラウンドサマリーに指摘がある場合:

1. メインが**指摘一覧（一行リスト）**を指摘台帳 `.thread/{Issue番号}/review/triage.md` と突き合わせる。Key が一致する既出指摘は判定を継承して再指摘カウントを +1 し、再審議しない
2. 新規の指摘は**修正方針フェーズ**（共通ガイドの同名節に従う）にかける。サブエージェント（**審査区分**）を1体立て、そのラウンドの全担当別レビューファイルと `.thread/{Issue番号}/plan.md`、台帳、`.thread/{Issue番号}/adr.md`（あれば）を渡して横断で読ませ、各指摘の妥当性判定（fix / fix-editorial / wont-fix / defer）と修正の実行計画を返させる。メインはレビュー全文を読まない（省略条件も共通ガイドに従う）
   - **fix-editorial** — 修正がコメント・ドキュメンテーションコメント・spec / docs の文章・テスト名の記述に閉じ、コードの振る舞い・型・アサーションに触れない指摘。その場で適用して品質ゲートを通す。台帳のラウンドブロックで `fix` と分けて数え、Step 7 の遷移判定では `fix` に数えない
   - **「未観測」の指摘**（UI 挙動・外部ライブラリの挙動を読解で断定したもの）は、方針フェーズが再現してから `fix` にする。再現できないものは `wont-fix`
   - **adr.md との照合はここで行う。** レビュアーは既決の設計判断を知らないまま指摘してくるので、adr.md で決着済みの判断を蒸し返した指摘は `wont-fix`（台帳の理由欄に該当 ADR 番号を書く）。判断を覆すべき新事実が出ているときだけ `fix` に上げ、Step 6 で ADR を更新する
   - **spec / docs の既存の誤り**（本 PR が触れても依拠してもいない記述の、もともとの誤り）は `fix` にしない — Phase 5 の基準で `defer`（既存 Issue への追記を優先）。この PR で直すのは、本 PR が触れた・依拠した記述の誤りだけ
   - **lint で機械的に防げる類の指摘**（変数のシャドウイング、未クォートのシェル引数、検出力ゼロのアサーション等）が同一 Issue 内で繰り返し出たら、個別修正とは別に lint ルール・CI ガード追加の Issue を `defer` で起票する
   - **wont-fix** — 誤った指摘、過度に防御的な提案、場当たり的に直すより設計を見直すべき指摘。一行理由を台帳に書く。設計の見直しが必要なものは Phase 5 の基準で別Issueも起票する
   - **defer** の前に `../SKILL.md` Phase 5 のスコープ基準を確認する。同じファイル・機能の中で完結する指摘や軽微な指摘は、ほぼ確実にこのPRで直す（軽微なほど修正コストが低い）。それでもこのPRで対応できないものだけ `gh issue create` で別Issueを起票し、Issue番号を台帳に記録する
   - 「要確認」で上がったものはメインが決めるか、ユーザーに判断を委ねる。設計判断を伴った決定は Step 6 で ADR に起こす
3. メインが方針を承認（承認でチェックする範囲は共通ガイド参照）して台帳に記録し、**実行計画の単位で**サブエージェント（**判断区分**）に委譲して修正させる。**Blocker・Warning とも残さず潰す**
   - 各サブエージェントには次を渡す:
     - 担当する指摘IDと、それが載っている担当別レビューファイル `.thread/{Issue番号}/review/review-NNN-{担当}.md`（複数担当にまたがるなら複数渡す）。指摘の詳細はサブエージェントがファイルから読む — メインが転記しない
     - 該当する台帳行の引用（Key・判定）。**`triage.md` のパスは渡さない**
     - 方針フェーズが決めた対応方針（採る側・採らない側の判断が絡む指摘のみ）
     - `.thread/{Issue番号}/plan.md`（受け入れ基準とスコープ）
     - 「方針に従って修正し、CLAUDE.md 記載の typecheck・lint・build を通すこと。修正対象外へスコープを広げないこと。コード・コメント・spec・docs に指摘 ID（B-/W-）・ADR 番号・`.thread/` のパス・修正の経緯を書かないこと。理由が要る箇所は本文を一文で書くこと。コメントや記述を直すときは、書き換えた文が現在の実装と一致することを該当コードを読んで確かめ、根拠の行を報告に書くこと。テストを追加・変更した場合は `implementation-guide.md` Step 2 の変異スポットチェックを行い、結果を報告に含めること。挙動・UI・出力を変えた場合は `.thread/{Issue番号}/testing.md` の該当項目（手順・期待結果）も現在のツリーに合わせて更新すること」
4. サブエージェント完了後、**メインが typecheck + lint + build を実行して整合性を確認する**（build コマンドは CLAUDE.md / package.json から取る）。エラーが残っていればサブエージェントを再起動して修正させる
   - テストを追加・変更したのに報告に変異スポットチェックの結果が無ければ、そのチェックだけを再委譲する（Phase 2 の統合確認と同じ扱い）
   - 修正の委譲先が**中断**した場合、担当分の修正は入っていない。メインが代わりに直さず再委譲する（2回目は指摘単位まで分割）。修正は必須作業なので「成功した分だけで進める」は適用外 — 中断した指摘を未修正のまま再レビューに回すと、次ラウンドで同じ指摘が再指摘され、台帳の判定継承で握り潰されるおそれがある
   - 3回目も中断したら、その指摘を台帳に「中断・未修正」と記録し、レビューループを止めてユーザーに報告する
5. 台帳にラウンドブロック（`R{N}: 新規 {n} / fix {n} / fix-editorial {n} / wont-fix {n} / defer {n} / 継承 {n}`。担当別の内訳は書かない）を追記し、`triage-keys.md` を更新する。修正をコミットし、Step 7 の遷移に従って R2 か Phase 4 へ進む。差分は `origin/{ベースブランチ}...HEAD` で引くため、未コミットの修正は差分ファイルに入らない。**コミット前に `git status` で `.thread/{Issue番号}/review/` がステージに混入していないことを確認する**

## Step 6: ADR への追記

レビュー中に**非自明な設計判断**を下した場合、`.thread/{Issue番号}/adr.md` に追記する。指摘への対応要否（wont-fix / defer）の記録には使わない — それは台帳の役割。仕分けが設計判断を伴う場合のみ ADR に起こし、台帳の理由欄からリンクする。adr.md は作業ログで、判断の経緯が残る唯一の場所。ここでは昇格の要否を判定しない — 気軽に記録してよい。spec / docs / CLAUDE.md に上げるべきものがあるかは Phase 5 の昇格ゲートでまとめて見る（`../../_shared/references/adr-guide.md`）。

Phase 1（計画時）で既に adr.md が存在する場合は、既存の連番の続きから追記する。なければ新規作成する。連番の調べ方は `../../_shared/references/adr-guide.md` の「作業ログへの追記」に従う（全文は読まない）。

各決定ごとに以下の形式で記載:

```markdown
## ADR-{NNN}: {タイトル}

### Context
{なぜこの判断が必要になったか}

### Decision
{何を決めたか}

### Consequences
{この判断の結果として何が起きるか}
```

些細な実装詳細（誰でも同じ結論に至る判断、コードの横の1〜2行のコメントで伝わるローカルな判断）はADRにしない。

## Step 7: ラウンドの遷移

全量レビューは **R1 と R2 の 2 ラウンド**。R3 以降の全量ラウンドは行わない。R2 の修正の確認は Phase 4 の実行と、その後のスコープラウンド（Step 8）が担う。

- **R1 で `fix` がゼロ**（fix-editorial・wont-fix・defer のみ）→ fix-editorial を適用して品質ゲートを通し、APPROVED として Phase 4 へ
- **R1 で `fix` が 1 件以上** → 修正・品質ゲート・コミットの後、R1 と同じ担当セットで **R2** をゼロベースで行う（Step 1 から。次の連番）
- **R2 で `fix` がゼロ** → fix-editorial を適用して APPROVED として Phase 4 へ
- **R2 で `fix` が 1 件以上** → 修正・品質ゲート・コミットの後、再レビューせず Phase 4 へ。R2 の修正増分は Phase 4 後のスコープラウンドが見る

R1 の修正をコミットした時点の HEAD を台帳の先頭に `scope-base: {sha}` と記録する（R1 で fix がゼロなら R1 開始時の HEAD）。スコープラウンドはこの sha 以降の差分を対象にする。

**小規模**（`../SKILL.md` Phase 0）は R2 を行わない。R1 の fix を修正・コミットして Phase 4 へ進み、`scope-base` は R1 開始時の HEAD にする（R1 の修正増分をスコープラウンドが見る）。

全量ラウンドを 2 回で止めるのは、R3 以降の全量ラウンドが出す指摘のほぼ全部が前ラウンドの修正起因か文言であり、読解で届かない欠陥（ビルド不能・遷移・状態の巻き戻り）は Phase 4 の実行だけが拾うため。

## Step 8: 完了後の遷移

R1 / R2 を抜けた時点で PR は **Draft のまま**。Ready for review への切り替えは Phase 4 のスコープラウンドが fix ゼロで終わった後に行う（`../SKILL.md` Phase 4 参照）。修正がすべてコミット・push 済みであることを確認して Phase 4 へ進む。

### スコープラウンド（Phase 4 後）

Phase 4 の観測が全 PASS（または変更と無関係の FAIL のみ）になったら、`general` 1 体で**スコープラウンド**を行う。

- 対象は `git diff --no-renames --name-status {scope-base}...HEAD` から `.thread/` を除いた一覧。R2 の修正と Phase 4 の変更起因修正がここに入る。一覧が空ならスコープラウンドは行わず完了とする
- 差分本文は Step 1 と同じ手順で `{scratchpad}/diff/{Issue番号}-round-{NNN}.diff` に書き出す。レビュアーには増分の一覧・差分ファイル・`plan.md`・`triage-keys.md` を渡し、Step 3 のプロンプトで見させる。連番は R2 の続き
- レビュアーは**判断区分**
- fix が出たら Step 5 で修正・品質ゲート・コミットし、挙動・UI・出力を変えた修正は `testing.md` の該当項目を再実行する。次のスコープラウンドの対象は、前回のスコープラウンド開始時の HEAD 以降の差分。**fix ゼロで APPROVED**
- スコープラウンドの上限は 3 回。3 回目でも fix が残る場合は PR を Draft のまま残し、残った指摘を最終ラウンドサマリーにまとめてユーザーに判断を委ねる
- 台帳のラウンドブロックに `（スコープ・対象 {ファイル数}）` を付ける。ラウンドサマリーはラウンドごとに書く

`testing.md` の修正はレビューしない。手順書の正しさは Phase 4 の実行が判定する。

## 重要な注意点

共通原則（厳しくレビュー・確信あるものだけ修正・毎ラウンド新規作成）は `../../_shared/references/review-loop.md` に従う。固有の点:

- 全量ラウンドは 2 回まで。収束の確認はレビューの反復ではなく、Phase 4 の実行とスコープラウンドで行う
- メインはオーケストレーションに徹する。レビュー（Step 3）も方針立案・修正（Step 5）も実作業はサブエージェント（R1 のレビューと方針立案は審査区分、R2 以降のレビューと修正は判断区分）に委譲し、メインは方針の承認・台帳の記録・品質ゲート・ADR/起票の判断に集中する
- レビュー全文・差分本文・修正内容はメインのコンテキストに乗せない。サブエージェントがファイルに直接書き、メインはサマリー（件数と一行リスト）だけ扱う
- カバレッジはスキップ申告の突き合わせ（Step 4）で担保する — 担当でファイルを分割しない
- レビューの基準は plan.md の受け入れ基準とスコープ。レビュアーに配る `.thread/` ファイルは plan.md と triage-keys.md だけに絞る（Step 3 の「レビュアーに渡す `.thread/` ファイル」）— 同じファイルが担当数×ラウンド数だけコンテキストに乗るのを避ける
- 担当は Step 2 の固定語彙から差分の形で決める。上限3は上限であって目標ではない。観点は担当に紐づかない全レビュアー共通のレンズで、`security` / `test` / `docs` を担当として立てない
- 指摘の根拠は実行かブラウザ観測で取る。読解だけの指摘は「未観測」と明記し、方針フェーズが再現してから fix にする
