# Issue Investigate

指定 Issue の未確認事項を、実装に着手できる情報または具体的な確認待ちに変える。成果物は根拠・対応方針・完了条件が揃った Issue。修正コードや PR は成果物に含めない。

## 調査の契約

本文・最新コメント・関連 PR・過去の調査結果を読み、今回解消する問い、確かめる方法、終了条件を短く定める。トリアージから渡された問いがあれば引き継ぐ。既存の担当者や進行中の修正・調査と重なる場合は、引き継ぎの指定がなければ着手せず、その作業先を報告する。

過去に行った調査を同じ条件で繰り返さない。対象コミット、実行環境、入力、権限、手順のどこが変わったかを示せる場合か、新しい仮説を区別できる場合に再試行する。明示的な再試行依頼では目的を記録して実行する。

## 調べ方と境界

- spec・コード・テスト・履歴から経路と候補を絞り、必要に応じて実ブラウザや最小の再現コードで確かめる。使うブラウザ等の手順は対象環境のスキル・規約に従う。
- 観測した事実、コードからの推論、まだ確かめていない仮説を分ける。コード読解だけで実機での再現や外部サービスの挙動を断定しない。
- 再現確認ではコミット、環境、入力、権限、手順、期待と実際を残す。断続的な問題は試行数と発生数を記録する。「再現なし」は「修正済み」ではない。
- 必要なら隔離した作業場所で一時的な計測・再現テストを作る。利用者の作業ツリーを変更せず、自分が起動したプロセスを終了する。修正の実装・本番データ補正・外部サービスの設定変更へ進まない。
- 業務上どちらを正とするかは調査で捏造しない。既に合意された UX 方針を未決定に戻さず、その方針で検証できるかを調べる。

次のいずれかで調査を終える。

- 問いへの答えと根拠が得られ、方針・完了条件を定められた。
- 必要な権限・環境・入力・他者の回答が不足しており、具体的な取得先と再開条件が分かった。
- 区別可能な仮説を試し終え、新しい証拠を得られる次の手段がない。

未解決でも得られた事実と試したことを保存する。不足が同じまま自分を呼び直さない。新しい証拠を得る手段が残るなら、次の問いと方法を明記する。

## Issue への反映と引き渡し

調査の実行依頼では Issue の更新まで行う。相談・評価だけの依頼では結果を返す。本文には現状、対応方針、未確認事項、検証可能な完了条件を反映し、長い再現ログはコメントや証跡へのリンクにする。認証情報・個人情報・本番レコードの全文を転載しない。更新前に最新状態を取り直し、他者の更新を保つ。

以下を残す。

- 調べた問いと答え、根拠となるコード・仕様・観測結果。
- 採用する対応方針と範囲。候補が残るなら、その違いを確かめる方法。
- 未解決の問い、必要な回答者・権限・環境と再開条件。
- 過去と今回の調査条件、次回の再調査を有効にする新情報。

[issue-triage](../issue-triage/SKILL.md) を読み、この Issue だけを再判定して本文と判定ラベルを更新する。キュー作成は行わない。Ready なら次のトリアージで既存キューとの競合を確認してから実装へ渡す。追加調査の具体的な手段が残るなら調査必要、環境・回答待ちや新情報が必要なら確認待ちとする。

最終報告は Issue リンク、判定、解消した問い、残る問いと次の行動を示す。原因を特定しただけで修正完了と報告しない。
