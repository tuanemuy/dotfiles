コードのコメントから寿命の短い情報を取り除き、長く価値を保つコメントだけを残す。

## 前提となる考え方

コードは「何を」しているかを語る。だからコメントが「何を」を繰り返すと、コードと二重管理になり、片方だけ古くなって嘘をつき始める。残す価値があるのは、コードを読んでも分からない情報だけ。

残すコメントは次の2種類に集約される：

1. **ドキュメンテーションコメント** — 関数・型・クラス・モジュール・公開APIの「契約」を書く。JSDoc / TSDoc / docstring / rustdoc / GoDoc など言語ごとの形式は違っても、役割は同じ：**利用者が実装を読まずに使うための普遍的な情報**。引数・戻り値・例外・副作用・前提条件・使用例など、時間が経っても変わらない仕様を書く場所。

2. **why / why not コメント** — それ以外のすべてのコメント。コードだけでは伝わらない**判断の理由**を書く。「なぜこの実装にしたか」「なぜ自明に見える別の選択肢を避けたか」。読み手が「これ、こうすればよくない？」と思いそうな箇所の先回りの答えになっているのが理想。

この2つに当てはまらないコメントは、原則として削除する。

## 削除対象

以下は寿命が短い、あるいはコードと重複していてノイズになる。見つけたら消す：

- **修正の経緯**: 「○○のバグを修正」「△△から変更」「以前は〜だった」「リファクタリングで追加」など、変更の歴史。これは git が記録している。
- **メタデータ**: 作者名、日付、変更ログ、レビューのやりとりの残骸、`@author` / `@since` のような出自情報。
- **コード外の記録への参照**: チケット・Issue・設計文書などを指す ID やパス（`JIRA-123`、`SPEC-42`、`ADR-003`、`.thread/412/adr.md`）はメタデータなので消す。理由そのものはコメントに書き、参照だけ落とす（例: `// 並び順は表示仕様に合わせる（SPEC-42）` → `// 並び順は表示仕様に合わせる`）。
- **自明な言い換え**: コードをそのまま日本語/英語に直しただけ。`// ユーザーを取得` の下に `getUser()`、`// i をインクリメント` の上に `i++` など。
- **規約の言い直し**: アーキテクチャやプロジェクト規約で既に決まっていることをその場で繰り返すだけのコメント（「ドメイン層なので外部ライブラリに依存しない」「リポジトリはポート経由で呼び出す」）。規約の一次的な置き場所は CLAUDE.md / spec であり、コメントに複製すると規約変更時に全コピーが古くなる。残すのは規約から**逸脱**する理由（why not）と、規約をその場に適用した結果が非自明な場合の説明だけ。
- **コメントアウトされた古いコード**: 「念のため残した」死んだコード。復活させたいなら git から戻せる。
- **冗長な生成コメント**: 1行ずつ動作を説明する過剰な注釈や、内容の薄い定型コメント。

## 残す・書き換える判断

迷ったら「このコメントは半年後も正しいか？コードを読めば分かることか？」で考える。

- ドキュメンテーションコメントは**残す**。ただし上記の削除対象（経緯・メタデータ・自明な羅列）が混ざっていれば、その部分だけ削いで契約情報に絞る。
- why / why not を含むコメントは**残す**。説明が冗長なら要点に圧縮する。
- **whyのフリをしたノイズに注意する**。「〜ため」「〜ので」という形ではなく、その「理由」が何を参照しているかで判定する。本物の why が参照するのは**現在の制約**（外部事実・ドメイン知識・避けた代替案・落とし穴）。擬態が参照するのは**過去の変更やプロセス**（レビュー指摘・バグ修正・以前の実装）か、**コード自身の動作**の言い直し。
  - 過去やプロセスを参照する「理由」は経緯なので消す。現在形で成立する外部事実が混ざっていれば、その事実だけに書き換える。逆に、変更に触れず現在の制約を警告するコメントは経緯ではないので残す。
  - コード内の情報だけで完結する「理由」は自明な言い換えなので消す。
  - プロジェクト規約の繰り返しも擬態になる。規約は「現在の制約」なので why の形に見えるが、一次的な置き場所（CLAUDE.md / spec / ADR）が既にある情報の複製はノイズ。規約を**参照して非自明な判断を説明する**のが why、規約を**暗唱する**のは言い直し。
  - 判定テスト: 「コードにも規約ドキュメントにも書かれていない情報を足しているか？今日ゼロから書いても同じコメントになるか？」— 両方 yes のときだけ why として残す。このテストは「確信が持てなければ残す」より先に適用する。擬態を素通しすると保守バイアスが誤残しを固定化する。
- 「何を」しか言っていないコメントは、その下のコードが自己説明的なら**消す**。コードが複雑で読み解きにくいなら、コメントを足すのではなく**コードを分かりやすくする方を優先**し、それでも残る非自明さを why として書く。
- **TODO / FIXME / HACK / XXX などのマーカーは、理由・文脈を伴うなら残す**。これらは「ここに既知の問題があり、まだ直っていない」という、コードからは決して読み取れない未完了の状態を表す。`FIXME` という語そのものや、問題の内容（O(n²) で遅い等）・保留理由（仕様確定待ち等）はメタデータではなく価値ある情報なので、マーカーごと保持する。消すのは中身のない裸のマーカー（`// TODO: 後で直す`）だけ。これは経緯コメントとは別物で、まだ閉じていない約束だからこそ残す。
- 判断に確信が持てないコメント（暗黙の前提や落とし穴を示唆していそうなもの）は、**消さずに残す**。情報の喪失は誤った削除の方が痛い。

## 進め方

コメントを目視で拾わない。見落としの大半は列挙の漏れから生まれるため、列挙は Grep で作る台帳に任せ、分類・編集・検証は台帳の行単位で行う。

1. **対象ファイルを決める**: `target` 引数があればそのファイル/ディレクトリ。なければ `git diff`（および `git diff --staged`）で変更されたファイル。diff はファイルの特定にだけ使い、コメントの列挙は必ずファイル全文に対して行う（hunk の外のコメントも対象）。
2. **コメント台帳を作る**: 言語ごとのコメント記法（`//`、`/* */`、`#`、docstring、`<!-- -->`、`--` など）を Grep して、対象ファイルの全コメントを `file:line` で機械的に列挙する。複数行コメントや docstring はブロック単位で1エントリにまとめてよい。台帳が大きい場合（目安: 50エントリ超）はスクラッチファイルに書き出し、処理済みに印を付けながら進める。
3. **台帳の全行を分類する**: 各エントリを「ドキュメンテーション」「why / why not」「削除対象（経緯/メタデータ/自明/死にコード）」に振り分ける。台帳のエントリ数と分類した数が一致することを確認する — 一致しなければ飛ばした行がある。残すエントリには分類と理由を一言添える。理由が書けないなら「迷ったから残す」を無自覚にやっているサインなので、分類し直す。
4. **直接編集する**: 分類に従って削除・圧縮する。コードの挙動は一切変えない。コメント（と必要ならコメントに付随する空行）だけを編集する。
5. **再スキャンで残骸を確認する**: 編集後、パターン化できる削除対象を Grep で再スキャンする — 日付（`20[0-9]{2}[/.-]`）、出自メタデータ（`@author` `@since` `Created` `Changelog`）、コード外の記録への参照（`[A-Z]{2,}-[0-9]+`、`\.?[a-z]+/[a-z0-9-]+\.md`）、中身のない TODO/FIXME、コメントアウトされたコード片（`// const`、`# return` などコードで始まるコメント行）。ヒットは即削除ではなく1件ずつ判断し、削除対象なら手順4に戻る。このスキャンが検出できるのは機械的な残骸だけで、自明な言い換えは拾えない。手順3の全行分類の代わりにはならない。
6. **報告する**: 台帳のエントリ数、消した件数と残した件数をカテゴリ（経緯/メタデータ/自明/死にコード）付きで簡潔に伝える。

## 例

**修正の経緯 → 削除**
```
// 2024-03 にタイムアウトを5sから30sに変更（API遅延対応, by tanaka）
const TIMEOUT = 30_000;
```
↓
```
// 外部APIのp99が約20sあるため余裕を持たせる
const TIMEOUT = 30_000;
```
経緯・日付・作者は git に任せ、残った「なぜ30sなのか」という why だけ残す。

**自明な言い換え → 削除**
```
// ユーザーIDで検索する
const user = await repo.findById(id);
```
↓
```
const user = await repo.findById(id);
```
コードが既に同じことを言っている。

**ドキュメンテーションコメント → メタデータを削いで契約に絞る**
```
/**
 * 金額をフォーマットする。
 * 2024/01 作成。最初は円のみ対応、後でドル追加。
 * @param amount 金額
 * @param currency 通貨コード（ISO 4217）
 * @returns ロケールに応じた表示文字列
 */
```
↓
```
/**
 * 金額をロケールに応じた表示文字列にフォーマットする。
 * @param amount 金額（最小単位ではなく主単位）
 * @param currency 通貨コード（ISO 4217）
 * @returns 表示用にフォーマットされた文字列
 */
```
作成日や経緯を削り、普遍的な契約（引数の意味・単位・戻り値）に集中させる。

**why not → 残す**
```
// Set ではなく配列で持つ。要素数は常に数件で、順序を保持する必要があるため。
const handlers = [];
```
読み手が抱く「Set でよくない？」への先回りの答え。こういうコメントこそ価値がある。

**whyのフリをした経緯・言い換え → 丸ごと削除**
```
// レビュー指摘を受けて null チェックを追加
if (!user) return null;

// ループ境界が off-by-one だったのを修正
for (let i = 0; i < items.length; i++) {

// 結果を返すために map で変換する
return rows.map(toDto);
```
↓
```
if (!user) return null;

for (let i = 0; i < items.length; i++) {

return rows.map(toDto);
```
最初の2つは「追加」「修正」という変更の物語で、今のコードだけを読む人に何の情報も足さない（レビューのやりとりは PR に、前の間違いは git にある）。3つ目は「ため」の形をしたコードの言い直し。3つとも書き換える余地なく丸ごと消す。外部事実が混ざる経緯（冒頭の TIMEOUT の例）だけが、現在形の why への書き換え対象になる。

**規約の言い直し → 削除 / 規約からの逸脱 → 残す**
```
// ドメイン層なので外部ライブラリに依存しない
import { Result } from "./result";

// 営業日計算のみ date-fns を使う（依存規約の例外）。自前実装は祝日対応でバグ源になるため。
import { addBusinessDays } from "date-fns";
```
前者は規約ドキュメントの繰り返しで、規約が変わった瞬間に嘘になるコピーなので消す。後者は「この場所だけ規約と違う」という、ここにしか書けない why not なので残す。

**裸の TODO → 削除 / 理由付き FIXME → マーカーごと残す**
```
// TODO: 後で直す
const result = build(rows);

// FIXME: 入力が10万件を超えると O(n²) で遅い。仕様確定まで保留。
const sorted = rows.sort(cmp);
```
↓
```
const result = build(rows);

// FIXME: 入力が10万件を超えると O(n²) で遅い。仕様確定まで保留。
const sorted = rows.sort(cmp);
```
中身のない `TODO: 後で直す` は消す。一方 `FIXME` は「既知の未解決問題」という状態を表すので、マーカーごと残す。
