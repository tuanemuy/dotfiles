Issue を受け、Production Ready な変更を Ready for review の PR として届ける。段取り（計画の深さ・委譲の切り方・確かめ方と、確かめる回数）は Issue の規模とリスクに合わせて自分で決める。このスキルが定めるのは、完了の定義・独立した読み・不変条件・環境の事実・予算の 5 つ。

着手時に、読んだ Issue の規模感と採る段取りを一言宣言する。ユーザーが進め方を指定していれば、その指定に従う。

## 完了の定義

Production Ready とは、次の 7 つが成り立ち、それぞれを根拠で示せること。

7 つが成り立つまで PR は Draft。成り立つとは反例が無いこと。7 つは同じ硬さで扱う。5 と 6 の反例はいま何も壊さないが、見送る理由にならない。その時点のツリーに対して、読み手が 7 つへの反例ゼロと返している PR だけが Ready for review。

### 1. 受け入れ条件を満たしている

- 受け入れ基準（AC）は Issue の意図から決まり、実装からは決まらない
- 各 AC は観測方法（`browser` / 自動テスト / コマンド出力）を持つ
- 目的・AC・スコープを書いた契約が、実装の前に Issue とは別に存在する（小さな Issue なら数行）。契約が文書になっていないと、契約の読みができない
- TODO・FIXME・スタブ・部分実装が残っていない

根拠: AC ごとの、それを満たすコードと観測結果

### 2. すべての振る舞いがテストされている

- この変更が足した・変えた振る舞いごとに、その挙動を主張するテストがある
- 振る舞いは、AC の正常系に加え、経路が分かれるところ（境界値・エラー・null / 空・重複・順序・再実行・認可）を含む
- 実装から期待値を生成するテスト、存在確認や否定だけのアサーションは数えない

根拠: 振る舞いとテストの対応、変異（条件反転・境界±1・ガード削除）で赤くなった記録

### 3. 既存の振る舞いを壊していない

- 変更が届く先で、意図した変更以外の振る舞いが変わっていない。届く先は次の 3 つ
  - 変えた関数・型・コンポーネントの呼び出し元
  - 削除・改名した名前（export・クエリキー・ルート・環境変数名・API パス）の参照元
  - 共有する状態やスタイル
- 既存テストが守っていない届く先は、テストを足すか実測する

根拠: 既存テストの全通過、届く先の一覧と各々の確かめ方

### 4. プロジェクトの規約に従っている

- `CLAUDE.md`・`docs/`・既存コードのパターン・言語とフレームワークの慣用に従っている
- typecheck・lint・build が通る（コマンドは `CLAUDE.md` / `README` / `package.json` から取る）
- 差分が触れた spec / docs（`spec/design/` を含む）の記述は変更後の実装を述べている
- 触れたファイルのコメントはドキュメンテーションと why / why not だけ（`../comment-cleanup/SKILL.md`）

根拠: ゲートの実行結果

### 5. 新たな負債を生まない美しい設計である

アーキテクチャ（依存の向き・ロジックの置き場所。`CLAUDE.md` / spec）への準拠は 4 が見る。5 が見るのは、この差分の後に次の変更が前より高くつかないか。

- 1 つの値・型・関数が 2 つの意味を負っていない
- 不正状態・組み合わせの禁止は文書やコメントではなく型で排除している
- 外部データは境界でドメイン型にし、生の値が内側へ流れていない
- 副作用は隔離されている
- 同じ規則が 2 か所に別実装で存在しない（既存の集約先に寄せる）
- 名前が意味を言い当てていて、条件が名前の裏に隠れていない
- 死んだ分岐・使い手が 1 つの抽象・将来のための一般化がない

根拠: 次に来そうな変更を 1 つ想定して、その差分がどこまで広がるかを述べられること。非自明な判断があれば、その経緯が残っていること

### 6. UI がある場合は、説明に頼らず操作でき、プロジェクトのデザインと一貫した洗練された UI である

- 何ができて、操作すると何が起きるかが、説明文なしに画面から読める
- 見た目はデザイントークンとデザイン方針（`spec/design/`）から取り、同種の既存画面と置き方・言い回しが揃っている
- 対象のビューポート（`CLAUDE.md` / `spec/design/` が定める。無ければ契約に書く）すべてで、見切れ・重なり・届かない操作がない

根拠: 対象ビューポートごとの観測、比べた既存画面

### 7. UI がある場合は、ユーザーに見える振る舞いを実際に観測できている

- 対象は `browser` の AC と、2 で挙げた振る舞いのうち結果がユーザーに見えるもの（エラー表示・バリデーション・空状態・権限なし・二重送信・再読み込み後の状態）
- 実機の観測が期待結果と一致して全 PASS
- 期待結果は契約と spec から決まり、観測した画面からは決まらない
- テストが通ることは、画面に出ることの根拠にならない
- 観測は対象のビューポートで行う

根拠: 観測した振る舞いごとの期待と実際、PR に添付した証跡（スクリーンショット・録画）

## 独立した読み

完了の定義は自分の枠の中でしか確かめられない。枠そのものの誤りは、別の目が狭い目的で読んで初めて出る。段取りの中で、契約の読みと差分の読みの 2 つだけは省けない。読み手は新しいコンテキストのサブエージェント 1 体（委譲方式と待ち方は `../_shared/references/subagent-policy.md` に従う）。自分の自己評価と完了報告は渡さない。

### 契約の読み

実装の前に行う。Issue と契約を渡し、契約が Issue の意図を取りこぼしている点・条件の片側しか書いていない点を挙げさせる。

### 差分の読み

Ready for review に切り替える前に行う。

- Issue・契約・差分の範囲と、完了の定義の 7 条件（転記）を渡す
- 読み手の目的は 7 条件の反例を探すこと。成立の認定はさせず、反例の一覧だけを返させる
- 5 は代案との比較でしか判定できないので、差分が新しく作ったものごとに、拡張できたはずの既存のものと比べさせる。6 も同じで、同種の既存画面と比べさせる
- 読み方は `../_shared/references/review-lenses.md` に従う
- 7 条件の外の指摘は分けて返させる

### 依頼に足してよいもの

最初の依頼に、上で決めたもの以外で自分が足してよいのは、環境の事実と出力の形だけ。どこを疑ってほしいか（不安な箇所・見てほしい点・例・観点の言い換え）は書かない。疑ってほしい箇所は、指摘が返ってきた後で同じ読み手に追加で聞く。先に渡すと、読み手はその箇所を中心に読み、自分の盲点を読まなくなる。どちらか迷うものは後に回す。

### 反例の扱い

7 条件への反例は、どの条件のものも自分で見送らない。見送ってよいのは 7 条件の外の指摘だけ。反例ゼロと言うのは読み手で、自分ではない。直した後に何を読ませるか（同じ読み手に増分を見せるか、新しい目に全量を読ませるか）は自分で決める。

5 と 6 の反例は、書いた後に見つかると作り直しになる。いつ誰に何を読ませれば安く済むかは、自分で決める。

## 不変条件

段取りをどう組んでも破らない。

- 修正は原因に対して行う
  - 同じ原因が通る経路をすべて直す
- 挙動の主張は実測で行う
  - UI の操作結果や外部ライブラリの挙動を読解だけで断定しない
  - 再現できない不具合は直さない
- 観測を推測で埋めない
  - ブラウザが起動しない等で観測できない AC は未観測として報告し、PR は Draft のままにする
  - 期待とおおよそ一致するだけの観測は FAIL
- 観測と期待が食い違ったとき、正は spec
  - 実装が spec どおりなら、誤っているのは期待や手順の側で、実装を合わせにいかない
  - 変更と無関係な不具合は起票し、この PR では直さない
- スコープは契約が決める
  - Issue の意図に沿う小さな修正はスコープ内
  - 範囲を広げる変更は起票に回す
- ツリーに残る文は現在の挙動を述べる
  - 弁明・修正の経緯はコードにもコメントにも spec にも書かない
- 未完了を完了と報告しない
  - サブエージェントの中断・空の返答は未了
  - 根拠を示せない条件は未達

## 予算

次のいずれかに達したら Draft のまま止め、成り立っていない条件と残っている FAIL をまとめてユーザーに渡す。

- 観測の修正 → 再観測: 3 周まで（手順の誤りの修正は数えない）
- 差分の読みの反例 → 修正 → 読み直し: 3 周まで（同じ読み手への追加の問いは数えない）
- 同じ作業の再委譲: 2 回まで（2 回目はスコープを分割する）
- 同じ条件を 3 回直しても成り立たない

## ユーザーに聞く場面

次の場面だけユーザーに聞く。それ以外は聞かずに進める。

- 方向が割れる設計判断、spec が定めるあるべき姿を変える判断
- 同名ブランチが既にある
- スコープ外の起票候補が 4 件を超える
- 予算に達した

## 環境の事実

他のスキルと GitHub が読む接点と、調べても分からない事実。

### ブランチ

`issue/{Issue番号}/{英語ケバブ}`。PR 本文に `Closes #{Issue番号}` を書く。

### `.thread/{Issue番号}/`

Issue 単位の作業ログ。名前が決まっているのは次の 2 つ。

- `plan.md`: 契約（目的・AC・スコープ）。常に作る
- `adr.md`: 非自明な設計判断の経緯。判断があったときだけ作る。形式と昇格の基準は `../_shared/references/adr-guide.md`。既定は昇格なし

### ブラウザ観測

`agent-browser` で行う。`../manual-test/SKILL.md` が使える。テキストのスナップショットには見切れ・重なり・余白が出ない。

### 証跡の添付

`gh` 2.99.0 以上は `gh pr edit --body-file {本文} --attach {ファイル}` でローカルのメディアを PR に添付できる。`--attach` が無い `gh` では添付せず、その旨を PR に書く。

- 本文中の同じパスの画像参照は URL に書き換わり、参照のない録画は本文末尾に付く
- 1 ファイル 10 MB・1 回 50 ファイルまで
- アップロードは一過性の `HTTP 500` で止まることがあり、失敗したファイルより前の分だけが本文に反映される。数ファイルずつ渡し、失敗したら本文を取り直して、参照がローカルパスのまま残っているファイルから渡し直す
- ワークツリーに隔離されたセッションは、実行時に組み立てた値（変数・`find` の結果）を渡すコマンドを拒否する。`--attach` のパスはリテラルで並べる
- メディアはリポジトリにも `.thread/` にも置かない

### `CLAUDE.md`

書き換えない。提案があれば完了報告に一行で挙げる。

## スコープ外の気づき

数分で直せるものはその場で直す。起票するものは同じテーマで 1 本に束ね、既存 Issue に近いものがあればコメントで追記する。`spec/manual-tests/` と他 Issue の `.thread/` は直さず起票する。

## 完了報告

```text
Issue #{Issue番号}: {Ready for review / Draft のまま停止（理由）}
- PR: #{番号}／ブランチ: {名前}
- 段取り: {採った進め方を一行で}
- 契約: .thread/{番号}/plan.md
- AC: {数}件すべて充足（根拠: {テスト / 観測 / コマンド}）
- テスト: 振る舞い {数}件を固定、変異で赤を確認
- 既存の振る舞い: 既存テスト全通過、届く先 {数}箇所を確認（{確かめ方}）
- 規約: ゲート {全通過}、spec / docs {更新済み / 変更なし}
- 設計: {想定した次の変更と、その差分の広がりを一行で}。非自明な判断の経緯: {adr.md / なし}
- UI: {対象ビューポート {一覧}。比べた既存画面 {一覧} / UI なし}
- 観測: {AC {数}件＋エッジケース {数}件・PASS/FAIL・周回数 / UI なし}、証跡 {添付済み / なし（理由）}
- 独立した読み: 契約 {指摘 {数}件を反映 / 指摘なし}、差分 {読み {数}回。回ごとの範囲（全量 / 増分）と 7 条件への反例の数、直した内容を一行で。最後の回は反例ゼロ}。7 条件の外で見送った指摘: {内容 / なし}
- 確かめ方: {採った手段を一行で}。気づいたが直さなかったもの: {内容と理由 / なし}
- 起票: {番号一覧 / なし}
- 昇格・CLAUDE.md への提案: {内容 / なし}
- 残存課題: {内容 / なし}
```
