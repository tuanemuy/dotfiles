Issue を受け、Production Ready な変更を Ready for review の PR として届ける。段取り（計画の深さ・委譲の切り方・確かめ方と、確かめる回数）は Issue の規模とリスクに合わせて自分で決める。このスキルが定めるのは、完了の定義・独立した読み・不変条件・環境の事実・予算の 5 つ。

着手時に、読んだ Issue の規模感と採る段取りを一言宣言する。ユーザーが進め方を指定していれば、その指定に従う。

## 完了の定義

Production Ready とは、次の 2 つが成り立ち、それぞれを根拠で示せること。2 つが成り立つまで PR は Draft。

- 変更が `../_shared/references/quality.md` の性質を満たしている
- UI がある場合は、ユーザーに見える振る舞いを実機で観測し、期待どおりである

### 反例

成り立つとは反例が無いこと。反例は、条件を破る箇所の引用と、その箇所で条件を破る具体的な入力・状態の組で示す。2 つの箇所の食い違いでは、もう一方の箇所の引用が具体的な状態にあたる。構造と UI では、拡張できたはずの既存のものや同種の既存画面の引用がそれにあたる。

実装には良くする方向の指摘がいくらでも出せる。形を取らない指摘（一般的な強化策、裏づけのない規模の想定）まで数えると、反例ゼロは磨き尽くした状態でしか成り立たない。形を取らない指摘は、完了の定義の外の指摘として扱う。

問うのは変更と AC。変更の前のツリーでも同じ入力・状態で起きる破れを、既存の破れと呼ぶ。既存の破れは反例にせず、スコープ外の気づきとして扱う。既存の破れのせいで要求の項目が満たせないときは、満たせない項目が反例になる。その破れを直すことが Issue の求めることから外れるなら、直す前にユーザーに聞く。

反例はどれも同じ硬さで扱う。構造と UI の反例は、いま何も壊していなくても見送る理由にならない。その時点のツリーに対して、読み手が反例ゼロと返している PR だけが Ready for review。

### 読み替え

`quality.md` の言葉は、このスキルでは次のものにあたる。

- 要求は Issue とユーザーの答え、要件は契約の AC
- 画面の文言の利用者は、契約がその文言に書いた読み手

### 契約

契約（`plan.md`）は、要求を確かめられる AC にしたもの。

- 要求の項目ごとに、覆う AC を指す。要求の項目は要求の文ごとに立てる。文が並べるもの（判断の対象・画面・経路など）は 1 つずつ、「各」「すべて」の範囲は入るものをコードから数えて項目にする
- 各 AC は観測方法（`browser` / 自動テスト / コマンド出力）を持つ
- 変更が画面に出す文言ごとに、読み手（画面と役割）と、当てはまる語彙の決まりとその出どころを書く
- 対象の画面幅をプロジェクトが定めていなければ、対象の画面幅を書く
- ユーザーの答えと、それで決まったことを書く

### 観測

- 対象は `browser` の AC と、変更が足した・変えた振る舞いのうち結果がユーザーに見えるもの（エラー表示・バリデーション・空状態・権限なし・二重送信・再読み込み後の状態）
- 対象の画面幅で観測し、期待結果と一致して全 PASS
- 期待結果は契約と spec から決まり、観測した画面からは決まらない
- テストが通ることは、画面に出ることの根拠にならない

### 根拠

- AC ごとの、満たすコードと観測結果
- 足した・変えた振る舞いとテストの対応、変異（条件反転・境界±1・ガード削除）で赤くなった記録
- 変更が届く箇所ごとの確かめ方。届く箇所は、変更した箇所が返す値・投げる失敗・書く状態を受け取る箇所と、変えた・消した型・名前・スタイルを使う箇所。受け取ったものを別の失敗や値に変えて渡す箇所では、渡した先までたどる。既存テストが守る箇所はそのテストの通過で、守っていない箇所はテストを足すか実測して確かめる
- 自動検証の実行結果。コマンドは `CLAUDE.md` / `README` / `package.json` から取る。テストなど時間のかかる検証は、変更した箇所と届く箇所を守る部分だけを実行する
- 非自明な設計判断があれば、その経緯を書いた `adr.md`
- 対象の画面幅ごとの観測と、比べた既存画面
- 観測した振る舞いごとの期待と実際、PR に添付した証跡（スクリーンショット、FAIL があればその録画）

## 独立した読み

完了の定義は自分の枠の中でしか確かめられない。枠そのものの誤りは、別の目が狭い目的で読んで初めて出る。段取りの中で、契約の読みと差分の読みは省けない。読み手は新しいコンテキストのサブエージェント 1 体（委譲方式と待ち方は `../_shared/references/subagent-policy.md` に従う）。自分の自己評価と完了報告は渡さない。

### 契約の読み

契約の誤りは、早く見つかるほど安く直せる。契約を書いたらすぐ読ませ、返答を待たずに実装を進める。Issue と契約を渡し、契約が Issue の意図を取りこぼしている点・条件の片側しか書いていない点・Issue と契約が前提にしている事実や指定のうちコードと規約で成り立たない点を挙げさせる。要求の項目は読み手に自分で立てさせ、項目ごとに覆う AC を対応表で返させる。

### 差分の読み

Ready for review に切り替える前に行う。

- Issue・契約・差分の範囲と、「完了の定義」の節の全文（転記）、`quality.md` の絶対パスを渡す。`.thread/` の根拠の記録・PR 本文・起票の下書きも、差分と同じく反例を探す対象として渡す
- 読み手の目的は完了の定義への反例を探すこと。成立の認定はさせず、反例の一覧と、読んだ届く箇所の一覧を返させる。一覧に無い届く箇所は、読まれていない
- 反例には破る条件（`quality.md` なら性質）を添えて返させる。形を取らない指摘は、完了の定義の外として理由を添えて分けて返させる

### 依頼に足してよいもの

最初の依頼に、上で決めたもの以外で自分が足してよいのは、環境の事実と出力の形だけ。どこを疑ってほしいか（不安な箇所・見てほしい点・例・観点の言い換え）は書かない。疑ってほしい箇所は、指摘が返ってきた後で同じ読み手に追加で聞く。先に渡すと、読み手はその箇所を中心に読み、自分の盲点を読まなくなる。どちらか迷うものは後に回す。

### 反例の扱い

完了の定義への反例は、どの条件のものも自分で見送らない。見送ってよいのは完了の定義の外の指摘だけ。反例ゼロと言うのは読み手で、自分ではない。直した後の読みは、その回の修正と、それに合わせた根拠の記録・PR 本文・起票の下書きの更新を終えてから頼む。何を読ませるか（同じ読み手に増分を見せるか、新しい目に全量を読ませるか）は自分で決める。

読み手が完了の定義の外に置いた指摘も「反例」の節に照らし、あたるものは反例として扱う。形を取るか迷う指摘は、同じ読み手に返して判定させる。

構造と UI の反例は、書いた後に見つかると作り直しになる。いつ誰に何を読ませれば安く済むかは、自分で決める。

構造と UI の反例を受けて設計を変えたら、変える前の案・変えた後の案・変えた理由を `adr.md` に書く。読み手は過去の判断を知らないので、書いた判断と逆を向く反例も返す。その反例には、該当する `adr.md` のエントリを同じ読み手に追加で渡し、判断の前提がいまも成り立つかを読み手に判定させる。前提が成り立てば読み手は反例を取り下げ、崩れていれば直す。同じ判断を 2 度覆すことになるときは、直す前にユーザーに聞く。

## 不変条件

段取りをどう組んでも破らない。

- 修正は原因に対して行う
  - 同じ原因が通る経路をすべて直す
- 挙動の主張は実測で行う
  - UI の操作結果や外部ライブラリの挙動を読解だけで断定しない
  - 再現できない不具合は直さない
- 観測を推測で埋めない
  - ブラウザが起動しない等で観測できない AC は未観測として報告し、PR は Draft のままにする
  - 期待とおおよそ一致するだけの観測は FAIL
- 観測と期待が食い違ったとき、正は spec
  - 実装が spec どおりなら、誤っているのは期待や手順の側で、実装を合わせにいかない
- スコープは要求が決める
  - Issue の意図に沿う小さな修正はスコープ内
  - 範囲を広げる変更は起票に回す
- 未完了を完了と報告しない
  - サブエージェントの中断・空の返答は未了
  - 根拠を示せない条件は未達

## 予算

次のいずれかに達したら Draft のまま止め、成り立っていない条件と残っている FAIL をまとめてユーザーに渡す。

- 差分の読み: 10 回まで（最初の読みを含む。同じ読み手への追加の問いは数えない）
- 同じ作業の再委譲: 2 回まで（2 回目はスコープを分割する）
- 同じ条件を 5 回直しても成り立たない

## ユーザーに聞く場面

次の場面だけユーザーに聞く。それ以外は聞かずに進める。

- 方向が割れる設計判断、Issue の求めることから外れる判断、spec が定めるあるべき姿を変える判断
- 同じ設計判断を 2 度覆す
- 同名ブランチが既にある
- スコープ外の起票候補が 4 件を超える
- 予算に達した

## 環境の事実

他のスキルと GitHub が読む接点と、調べても分からない事実。

### ブランチ

`issue/{Issue番号}/{英語ケバブ}`。PR 本文に `Closes #{Issue番号}` を書く。Issue の求めることを一部残す PR では、代わりに `Refs #{Issue番号}` を書く。

### `.thread/{Issue番号}/`

Issue 単位の作業ログ。名前が決まっているのは次の 2 つ。

- `plan.md`: 契約（目的・要求の項目と AC・画面の文言・スコープ・ユーザーの答え）。常に作る。小さな Issue なら数行
- `adr.md`: 非自明な設計判断と、構造・UI の反例で変えた設計の経緯。どちらかがあったときだけ作る。形式と昇格の基準は `../_shared/references/adr-guide.md`。既定は昇格なし

### ブラウザ観測

`agent-browser` で行う。`../manual-test/SKILL.md` が使える。テキストのスナップショットには見切れ・重なり・余白が出ない。

コマンドは `../_shared/references/agent-browser.md` に従う。manual-test を通さずに観測するときも同じ。

- namespace は着手時に `agent-browser session id --scope worktree --prefix issue-ship` で 1 回だけ決め、自分とサブエージェントの全コマンドに付ける
- `agent-browser --namespace {ns} close --all` を、最初の観測の前と、完了報告の前（Draft で止めるときも）に実行する
- セッション名は用途ごとに使い回し、観測の周ごとに増やさない

### 証跡の添付

`gh` 2.99.0 以上は `gh pr edit --body-file {本文} --attach {ファイル}` でローカルのメディアを PR に添付できる。`--attach` が無い `gh` では添付せず、その旨を PR に書く。

- 本文中の同じパスの画像参照は URL に書き換わり、参照のない録画は本文末尾に付く
- 1 ファイル 10 MB・1 回 50 ファイルまで
- アップロードは一過性の `HTTP 500` で止まることがあり、失敗したファイルより前の分だけが本文に反映される。数ファイルずつ渡し、失敗したら本文を取り直して、参照がローカルパスのまま残っているファイルから渡し直す
- ワークツリーに隔離されたセッションは、実行時に組み立てた値（変数・`find` の結果）を渡すコマンドを拒否する。`--attach` のパスはリテラルで並べる
- メディアはリポジトリにも `.thread/` にも置かない

### `CLAUDE.md`

書き換えない。提案があれば完了報告に一行で挙げる。

## スコープ外の気づき

変更が触れたファイル・機能の中で、振る舞いを変えずに数分で直せるものは、その場で直す。起票するものは同じテーマで 1 本に束ね、既存 Issue に近いものがあればコメントで追記する。`spec/manual-tests/` と他 Issue の `.thread/` は直さず起票する。

## 完了報告

```text
Issue #{Issue番号}: {Ready for review / Draft のまま停止（理由）}
- PR: #{番号}／ブランチ: {名前}
- 段取り: {採った進め方を一行で}
- 契約: .thread/{番号}/plan.md（要求の項目 {数}件中 {数}件を AC が覆う）。設計判断の経緯: {.thread/{番号}/adr.md / なし}
- AC: {数}件すべて充足（根拠: {テスト / 観測 / コマンド}）
- テスト: 振る舞い {数}件を固定、変異で赤を確認
- 既存の振る舞い: 変更が届く箇所 {数}箇所を確認（{確かめ方}）
- 規約: 自動検証 {結果}、spec / docs {更新済み / 変更なし}
- UI: {対象の画面幅 {一覧}。比べた既存画面 {一覧}。画面の文言 {数}件 / UI なし}
- 観測: {AC {数}件＋エッジケース {数}件・PASS/FAIL・観測 {数}回 / UI なし}、証跡 {添付済み / なし（理由）}
- 独立した読み: 契約 {指摘 {数}件を反映 / 指摘なし}、差分 {読み {数}回。回ごとの範囲（全量 / 増分）と反例の数、直した内容を一行で。最後の回は反例ゼロ}。完了の定義の外で見送った指摘: {内容 / なし}
- 確かめ方: {採った手段を一行で}。気づいたが直さなかったもの: {内容と理由 / なし}
- 起票: {番号一覧 / なし}
- 昇格・CLAUDE.md への提案: {内容 / なし}
- 残存課題: {内容 / なし}
```
