# Spec Implement

`spec/` の設計を、検証できるフェーズに分割して実装する。メインエージェントを Manager、別のエージェントを Implementer として動かす。Manager が全体を保持し、Implementer は現在の一フェーズに集中する。

## 実装を前進させる原則

- Manager は全体の完成までの道筋を持ち、Implementer に一度に一フェーズを渡す。
- Implementer に成果と完了条件を伝え、実装方法・作業順序・検証方法の具体化を任せる。
- `extremely well` を目標にし、完了条件と検証根拠が揃ったら次へ進む。
- 完了件数と経過時間を使い、細部への固執や同じ試行の反復を見つけて進め方を変える。
- フェーズの粒度と並列度は、依存関係・不確実性・実際の進捗に応じて調整する。

## 役割と実行環境

| 担当 | 責務 |
| --- | --- |
| Manager | 設計と既存実装の把握、チェックリストの作成、フェーズ分割、依存関係の管理、進捗監視、成果の受け入れ |
| Implementer | 現在のフェーズの詳細化、コードとテストの実装、検証、完了候補・停滞の報告 |

Manager は実装コードを変更せず、コード・差分・検証結果を読んで判断する。Implementer は Manager が指定した範囲を実装し、次フェーズの開始は Manager に返す。通常の実装判断は Implementer が自律して進め、全体計画に影響する判断を Manager に上げる。

開始時に、エージェントの起動・メッセージ送信・継続実行・goal 管理の機能と制約を確認する。

- 別エージェントは、その環境の起動機能で作成する。同じ作業場所を共有しない場合は、ブランチやパッチで成果を受け渡し、統合後の状態を検証する。
- ユーザーが goal モードでの実行を指示し、対応機能がある場合は、Manager に全体の目標、Implementer に現在のフェーズだけの目標を設定する。既存の目標がある場合は内容と状態を確認し、その API の規則に従う。予算はユーザーが指定した場合だけ設定する。
- メッセージに `/goal` と書くだけでモードが切り替わるとは扱わない。goal 機能がない場合は、通常の起動・継続依頼とファイルによる進捗管理でループを実行する。
- 別エージェントを起動できない場合は制約を報告し、同一エージェント内で計画・実装・受け入れを順に実行する。別スレッドを起動したとは報告しない。
- Implementer は、独立した作業をサブエージェントへ並列に委譲する。統合の負担より並列化の利益が大きい作業を選び、書き込み先と成果の受け渡しを明確にする。モデルと同時実行数はユーザーの指定と実行環境に従う。

## 1. 入力と再開地点を確認する

プロジェクトの指示、既存実装、実行・検証方法を確認する。`spec/index.md` を入口に、依頼範囲に対応する要件・設計と検証手順を読む。

Manager は [進捗管理と委譲プロトコル](references/manager-loop.md) を読み、今回の依頼に対応する作業ディレクトリを確定する。以降、`{run-directory}` は確定した作業ディレクトリを表す。

同じ依頼の実行記録、`spec/progress.md`、関連 Issue があれば実装状態と照合し、完了済みの作業を取り込む。進捗の記載だけで完了と判断せず、コードと検証根拠を確認する。

プロジェクトのアーキテクチャと設計規約に従い、詳細設計は `spec/` と既存構造に基づいて Implementer が行う。詳細が未記載であることだけを理由に停止しない。結果を大きく変える判断が既存の指示から決まらない場合だけユーザーに確認する。対象外の機能の設計文書は要求しない。

## 2. 全体チェックリストとフェーズを作る

Manager が `{run-directory}/plan.md` に全体計画を作成する。

1. 依頼範囲の要件・設計に対応する実装・検証項目を洗い出す。既存の台帳があれば利用する。
2. 各項目に固定 ID、設計の参照先、完了条件、検証方法、依存先を付ける。機能の完了条件は利用者から観測できる結果で書く。適用するアーキテクチャ・設計規約への適合も、参照元と検証方法を付けて完了条件に含める。
3. 依存関係と不確実性から実装順序を決める。初期のフェーズで主要シナリオを端から端まで動かす。成立が不明な前提は、それに依存する実装より先に検証する。
4. 各フェーズに目的、対象 ID、前提、変更範囲、完了条件を定義する。一度の委譲で実装と検証を見通せないフェーズは分割する。
5. 最後に全体の統合検証と設計照合のフェーズを置く。設計要素に対応する項目がない場合は、項目を追加するか、依頼範囲外である根拠を記録する。

チェックリストは依頼範囲を網羅し、各項目は作業中の前進を観測できる大きさにする。最初に全体の広がりを洗い出し、直近フェーズを詳しくする。後続フェーズの実装手順は、依存先の成果を得てから具体化する。計画を簡潔にユーザーへ共有し、実装が依頼されていればフェーズごとの承認を挟まず開始する。

## 3. Implementer を起動する

Manager は別のエージェントを一つ起動し、計画の場所と現在のフェーズの実行に必要な情報を渡す。委譲文と報告形式は [進捗管理と委譲プロトコル](references/manager-loop.md) に従う。

Implementer には、全体の目的と現在のフェーズに必要な文脈を渡す。全体計画は参照できる状態に置き、過去の議論や後続フェーズの詳細を毎回プロンプトに詰め込まない。Manager も報告の要点を保持し、詳細なログは必要なときに読む。

Manager が `plan.md` で項目の状態と受け入れを管理する。Implementer はフェーズ報告に検証根拠を残す。再開・交代時は既存の項目 ID、受け入れ結果、検証根拠を引き継ぐ。

## 4. フェーズごとの Manager Loop

1. Manager が、依存フェーズを受け入れ済みのフェーズを一つ選び、Implementer に渡す。
2. Implementer が対象の設計とコードを読み、実装・接続・検証を行う。項目が完了条件を満たしたら、検証対象を識別できる根拠と時刻を記録して完了候補を報告する。
3. Manager はメッセージと進捗ファイルで状況を確認する。長時間の実行中も、ユーザーに進捗と未解決事項を伝える。
4. Manager は完了候補を `review` にし、差分、対象項目、検証結果、設計との対応を確認する。根拠が不足する場合は追加検証を行う。
5. 不足があれば Manager が項目を `in_progress` に戻し、項目 ID と満たしていない条件を示して差し戻す。受け入れた項目だけを `done` にし、フェーズ全体を受け入れたら次フェーズを継続依頼する。

受け入れでは、要求を満たさない振る舞い、再現できる不具合、検証不足を優先する。好みの書き換えや将来の仮説で新しい課題を増やさない。新しい変更や失敗がなければ同じ検証を繰り返さず、次の未完了フェーズを開始する。全フェーズの受け入れまでこのループを続ける。

Implementer が終了しただけではフェーズを完了にしない。途中終了なら未完了項目から継続させる。同じ Implementer を継続利用し、文脈の混乱や停滞が続く場合は、書き込みの停止を確認してから新しい Implementer に引き継ぐ。

### 共有設計を変更する場合

Implementer は設計の不整合や共有契約の変更が必要な箇所を見つけたら、根拠、影響する項目 ID、変更案を Manager に報告する。判断待ちの間は、その変更に依存しない作業を進める。

Manager は元の要件と照合して採用する変更を決め、`spec/` の該当設計・契約を更新する。`plan.md` の設計参照、依存関係、検証計画を揃え、影響する項目を `pending` に戻してフェーズの受け入れを取り消す。Implementer に変更を通知する。更新した設計に基づいて実装・再検証し、Manager が再度受け入れる。ユーザーの完成条件を達成しやすい条件に書き換えない。

### 停滞時の進め方

完了項目が増えない時間の目安を計画に設定する。指定がなければ15分を出発点に、項目の粒度と処理時間に合わせて調整する。既知の長時間処理は予定所要時間を記録する。経過時間は実時刻から判断する。

- 閾値を超えたら、Implementer は試したこと、得られた根拠、障害、次の一手を Manager に報告する。
- Manager は長時間処理の進行状況を確認し、問題の分割、別の実装方法、現在のフェーズ内の独立項目への切り替えを指示する。
- 別フェーズに移る場合は、Manager が依存関係を確認して計画を組み替える。残項目は未完了として保持する。
- 同じ試行を根拠なく繰り返さない。実行可能な代替策がなく、回答・権限・外部環境の変更が必要なら、障害と再開条件を記録してユーザーに報告する。

時間切れや停滞を理由に `done` にしたり、完了条件を緩めたりしない。

## 5. 受け入れと全体完了

各フェーズの検証は、その成果とリスクに合わせて選び、完了条件を直接確かめる。

全体完了には次の条件を満たす。

- 依頼範囲の全項目に実装と検証の根拠があり、Manager が全フェーズを受け入れている。
- 統合後の成果で、プロジェクトで定められた検証手順が成功している。
- 対象のシナリオが実際の実行環境で端から端まで動く。検証できない項目は未検証として残す。
- 対象範囲に仮実装や未接続の処理などの実装漏れがない。

未検証・ブロック中の必須項目があれば全体完了にしない。変更した範囲から外れる既存の失敗は区別して報告し、全体検証の成功とは記録しない。goal 機能を利用した場合も、その目標の完了条件を満たしてから完了として扱う。

最終報告には実装範囲、検証結果、残課題、再開条件がある場合はその内容、`plan.md` の場所を記載する。進捗ファイルは再開と確認のために残す。
