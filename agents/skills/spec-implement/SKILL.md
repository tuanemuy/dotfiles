# Spec Implement

`spec/` の設計を観測できる完成条件に変換し、実装・検証を一つのループで進める。要件と設計の正本は `spec/` とし、実装で確定した共有契約は Manager が `spec/` に反映する。

本ワークフローでは `spec`・`spec-revise`・`goal-implement` を呼び出さず、この制約をすべてのサブエージェントへの委譲に引き継ぐ。設計の変更は Manager が `spec/` を直接更新する。

完成条件を先に固定し、やり方は担当に任せる。手順を細かく指示するより、完了とは何かを明確にする。

## 役割と目標

| 担当 | 責務 |
| --- | --- |
| Manager | 依頼範囲と完成条件の管理、設計判断、フェーズの委譲、進捗管理、報告に基づく受け入れ判断 |
| Implementer | 既存実装の調査、設計の具体化、現在のフェーズの詳細設計・実装・テスト、修正 |
| Verifier | 実装から独立したコードレビューと動作検証、項目ごとの合否と根拠の報告 |

Manager はメインエージェント、Implementer と Verifier は別エージェントとする。Manager は `spec/`・計画・設計判断と報告の要約を扱い、調査・詳細設計・実装・検証は担当エージェントへ委譲する。根拠の不足や報告の矛盾は、担当へ追加確認を依頼する。

Verifier は担当フェーズの実装に参加していないエージェントを使い、Manager が直接委譲する。検証中は Implementer と補助エージェントによる対象コードの変更を止める。実装の並列数は検証用の枠を確保して決め、共有する検証環境の操作担当を一人に定める。Verifier は不具合を報告し、修正は Implementer が行う。

品質目標は `extremely well` とする。設計を満たす振る舞いと検証根拠があり、対象範囲に既知の欠陥がない状態を指す。この水準に達した項目は次へ進める。受け入れ済みの成果を好みで磨き続けない。

開始時に、実行環境が提供する goal 管理、エージェントの起動・継続・メッセージ送信、通知待機、検証手段を確認する。機能の名称と API は実行環境ごとに異なる。Claude Code で実行する場合は [Claude Code での実行](references/claude-code.md) に従い、対応表の読み替えと Stop hook の確認を行う。

- ユーザーが goal の利用を明示し、対応機能があれば、既存の goal を確認する。全体の完成条件を整理してから、Manager に依頼範囲全体の goal を設定する。Implementer の goal は現在のフェーズの完成とする。
- goal の作成・状態変更は提供された API の条件に従う。無関係な未完了 goal を上書きしない。親子で goal を分離できない場合は、全体 goal を Manager だけが管理し、フェーズ目標を委譲文で渡す。
- 予算はユーザーが指定した場合だけ設定する。全体予算を各エージェントへ重複設定しない。予算切れを達成として記録しない。
- goal の利用指定がない場合や機能がない場合は、`plan.md` の台帳と継続依頼で同じループを動かす。実行環境がセッション終了時の hook や外側のループを提供する場合は、`status.json` の終端状態を終了判定に使う。goal 機能がない場合はその制約を報告する。プロンプト中の `/goal` を機能の実行と扱わない。
- 別エージェントを使えない場合は制約を報告し、同一エージェントで計画・実装・検証を順に行う。この場合は独立検証なしと記録する。

goal の実行指示の例:

```text
$spec-implement spec/ の設計を、goal を設定して実装から動作検証まで完了させてください。
```

## 1. 入力と作業場所を把握する

Manager はプロジェクトの指示と `spec/index.md` を入口に、依頼範囲に対応する要件・設計と検証手順を確認する。既存実装と実行・検証方法の調査は Implementer に委譲し、設計に対して再利用できる範囲と不足を報告させる。

Manager は [進捗管理と委譲](references/manager-loop.md) を読み、今回の依頼に対応する作業ディレクトリを確定する。同じ依頼の記録、`spec/progress.md`、関連 Issue があれば実装状態と照合し、コードと検証根拠の照合を Verifier に委譲して再開する。別依頼の記録は分離する。以降、`{run-directory}` は確定した作業ディレクトリを表す。

進捗の記載だけで完了と判断しない。ユーザーの変更を保持し、完了済みの作業は関連する変更や失敗がない限り繰り返さない。

## 2. 依頼範囲と完成条件を固定する

Manager が `{run-directory}/brief.md` に依頼範囲をまとめる。`spec/` の本文は複製せず、該当箇所を参照する。

- 対象とする要件・シナリオと、その `spec/` の参照先
- 必須機能、対象外、優先度、譲れない業務ルール
- プロジェクトの制約、完成を確かめる実行環境
- 外部依存と、それぞれの検証段階
- 元の指示の参照先、採用する仮定、未決事項

`spec/` に書かれた要求とエージェントが補った仮定を区別する。可逆的な設計・実装判断は、`spec/` の方針と目的に合わせて決め、仮定を共有して進める。結果を大きく変える判断が `spec/` と既存の指示から決まらない場合だけ質問する。回答待ちの間は、その判断に依存しない作業を進める。回答がなく作業を止められない判断は、可逆で安全な側を採用し、仮定として `brief.md` に記録する。詳細が未記載であることだけを理由に停止しない。対象外の機能の設計文書は要求しない。

### 外部依存

資格情報・アカウント・外部環境がないと実接続できない依存 (認証プロバイダ、メール送信、LLM、外部ストレージなど) を `brief.md` に列挙する。依存ごとに検証段階を決め、完了条件に書く。

- 実接続: 実際のサービスで検証する。
- 契約検証: ポートに対する代替アダプターでシナリオを通す。実アダプターには、資格情報があるときだけ実行する契約テストを置く。
- 対象外: 依存する要件ごと対象外にする。

段階の決定に利用者の入力が要る依存は、この時点で一度にまとめて質問する。回答がない依存は契約検証で進める。契約検証で受け入れた項目は、実接続の検証手順と必要な設定を `plan.md` に残す。

### 完成条件

Manager は `plan.md` に要件 ID と完了条件を記録する。機能の完了条件は利用者から観測できる結果で書く。

完了条件の出どころは次の三つに限る。

- `spec/` の要件・シナリオ・テストケースの ID
- `brief.md` / `design.md` に記録したリスク
- プロジェクトに書かれたアーキテクチャ・設計規約 (参照元と検証方法を付ける)

出どころのない観察は「追加観察」として報告に残す。追加観察は受け入れ条件にも差し戻し理由にもならない。

`spec/` に存在しない機能を完成条件に追加しない。実装上必要な基盤作業は、それが支える要件に結び付ける。

全体 goal には利用者が達成する結果、対象範囲、統合検証まで含む完成条件と `brief.md` の場所を含める。「設計書を作る」「計画を立てる」だけを全体 goal にしない。

## 3. 設計を確定し、直近のフェーズを具体化する

Implementer が調査結果から、`spec/` の設計と既存実装の差分、`spec/` に記載のない実装レベルの判断事項を報告する。Manager は `spec/` との整合性を判断し、採用する決定を `{run-directory}/design.md` に記録する。複数のフェーズに影響する設計判断と共有契約を確定し、既存実装からの変更範囲を明らかにする。要件が `spec/` のどのドメイン・どのポートで実現されるかを記録し、フェーズごとに構造を発明させない。

プロジェクトのアーキテクチャと設計規約に従う。`spec/` が方針を定めていない範囲は、要件と既存構造に合わせて決める。設計の量は対象の複雑さに合わせ、詳細設計は Implementer が行う。共有設計の正本は `spec/` とし、`design.md` で確定した共有契約は Manager が `spec/` に反映する。

`{run-directory}/plan.md` に全体のフェーズと依存関係を置き、直近フェーズだけを実装・検証できる粒度にする。初期のフェーズで主要シナリオを端から端まで動かす。成立が不明な前提は、それに依存する実装より先に検証する。設計要素に対応する項目がない場合は、項目を追加するか、依頼範囲外である根拠を記録する。

計画と主な仮定を簡潔に共有し、実装を開始する。既に任された範囲でフェーズごとの承認を挟まない。

## 4. Manager Loop を回す

1. Manager が依存条件を満たすフェーズを選び、Implementer に対象の要件 ID、設計、変更範囲、完了条件を渡す。受け入れ条件はこの委譲時に確定する。
2. Implementer が詳細設計・実装・接続・検証を行い、検証対象を識別できる根拠を添えて完了候補を報告する。独立した作業は、利用可能な枠と統合負担を見てサブエージェントへ委譲する。書き込み先を分け、全体の進捗ファイルは変更させない。
3. Manager が Implementer の報告から進捗と未解決事項を確認する。ユーザーには完成した機能と次に確かめる点を伝える。
4. Manager が完了候補を `review` にし、`spec/` の該当設計、完了条件、実装報告、検証対象を Verifier に渡す。Verifier はコードと動作を確認し、項目 ID ごとに合否・未検証事項・根拠を報告する。
5. Manager は検証報告と完了条件を照合する。不合格項目は Implementer に差し戻し、根拠不足は Verifier に追加確認を依頼する。受け入れ条件の追加は Verifier が対応する要件を添えて提案し、Manager が採否を決める。修正後は Verifier が影響範囲を再検証する。
6. Manager は合格と根拠が揃った項目を受け入れて `done` にし、依存する次フェーズを継続依頼する。全フェーズの受け入れまで続ける。

待機中の担当に次フェーズ・修正・追加検証を依頼するときは、実行を開始する継続依頼を使う。通知だけで再開したと扱わない。

エージェントの終了や「完了」という自己申告だけでは受け入れない。途中終了なら残項目から継続させる。現在の Manager から操作できる間は同じ Implementer を継続利用する。文脈の混乱や停滞が続く場合は、書き込みの停止を確認して交代する。

共有契約、レイヤー境界、ポートの形に触れる修正は、Implementer が Manager に報告してから行う。実装で設計の不整合が判明した場合は、Manager が `spec/` の該当設計と照合して設計・契約・依存計画を更新し、採用した変更を `spec/` に反映する。受け入れ済み項目は、その完了条件に影響する変更があった場合だけ未完了に戻す。隣接する変更の影響は Verifier が根拠付きで報告する。ユーザーの完成条件を達成しやすい条件に書き換えない。

### 待機と進捗確認

Manager は独立して進める管理・判断がなければ、通知待機ツールで担当エージェントの報告を待つ。待機時間は、実行環境の上限、ユーザーへの報告間隔、停滞確認の期限に収まる範囲で長く取る。通知待機ツールがない場合は、同じ間隔で sleep と状態確認を行う。

Manager は完了・障害・判断依頼の通知、または停滞確認の期限で報告と進捗ファイルを読む。待機のタイムアウトだけでは読み直さない。新しい通知も期限の到来もなければ再び待機する。定期的なユーザー報告のために状態照会やレビューを追加しない。

### 停滞と外部依存

完了項目が増えない時間の目安を計画に記録する。指定がなければ15分を出発点にし、既知の長時間処理は予定所要時間を記録する。経過時間は実時刻で判断する。

閾値を超えたら、担当エージェントは試した方法、得た根拠、障害、次の一手を報告する。Manager は次の項目へ進めることを既定にし、満たしていない条件は項目に残す。同じ項目に留まるのは、後続の依存先で代替がない場合に限る。同じ試行を根拠なく繰り返さない。

資格情報、利用者の判断、外部環境の変更が必要になったら、依存しない実装と検証を完了させる。代替手段がなくなった時点で障害、未完了項目、再開条件を報告する。goal の `blocked` などの状態変更は API の条件を満たした時点で行う。

自走の指示は公開・本番デプロイ・外部への送信の許可を増やさない。必要な権限が不足する場合は、具体的に実行できる状態まで準備してから判断を求める。

## 5. 統合検証して完了する

最終フェーズで、Manager は統合後の成果の検証を Verifier に委譲する。Verifier は `spec/` の該当設計と完了条件から次を確認し、全項目の合否と未検証事項を報告する。

- 対象範囲の全要件に実装と検証の根拠があり、未検証の必須項目がない。
- 依頼範囲の設計要素に対応する項目があり、対応しないものは範囲外である根拠が記録されている。
- プロジェクトで定められた検証手順が成功している。プロジェクトにアーキテクチャの監査手順があればそれも実行する。
- 主要シナリオが実際の実行環境で端から端まで動く。Web アプリではブラウザで操作と結果を確認する。
- `spec/` のテストケースとリスクに応じた正常系・異常系を検証している。
- 必須機能に仮実装や未接続の処理が残っていない。
- 利用と検証の再実行に必要な手順をプロジェクトに残している。

未検証・ブロック中の必須項目があれば全体完了にしない。必要な検証環境を利用できない場合は、代替検証で分かった範囲と未検証部分を記録する。既存の無関係な失敗は今回の変更と区別して報告し、全体検証の成功と扱わない。

残る未検証項目が実接続待ちだけの状態を「完了 (実接続待ち)」とし、ループの終端にする。再検証に必要な設定と手順を `plan.md` に残し、goal は完了にせず API の条件に従って `blocked` などへ更新する。

Manager は統合検証報告と全体の完成条件を照合し、全項目を受け入れたら goal を完了にする。予算付き goal の完了報告に使用量が返る場合は、ユーザーへその値を伝える。

最終報告には、完成した機能、主な設計判断と `spec/` へ反映した変更、検証結果、利用手順、残課題、進捗ファイルの場所を記載する。契約検証で受け入れた項目と実接続待ちの項目は別枠で示す。未完了なら再開条件を含める。
