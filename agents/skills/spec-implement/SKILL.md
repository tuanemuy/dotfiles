# Spec Implement

`spec/` の設計を、検証できるフェーズに分割して実装する。メインエージェントを Manager、別のエージェントを Implementer として動かす。Manager が全体を保持し、Implementer は現在の一フェーズに集中する。

## 実装を前進させる原則

- Manager は全体の完成までの道筋を持ち、Implementer に一度に一フェーズを渡す。
- Implementer に成果と完了条件を伝え、実装方法・作業順序・検証方法の具体化を任せる。
- `extremely well` を目標にする。`perfectly` を要求せず、求められた品質を満たしたら次へ進む。
- 完了件数と経過時間を使い、細部への固執や同じ試行の反復を見つけて進め方を変える。
- フェーズの粒度と並列度は、依存関係・不確実性・実際の進捗に応じて調整する。

## 役割と実行環境

| 担当 | 責務 |
| --- | --- |
| Manager | 設計と既存実装の把握、チェックリストの作成、フェーズ分割、依存関係の管理、進捗監視、成果の受け入れ |
| Implementer | 現在のフェーズの詳細化、コードとテストの実装、検証、チェックリストと HTML の更新、完了・停滞の報告 |

Manager は実装コードを変更せず、コード・差分・検証結果を読んで判断する。Implementer は Manager が指定した範囲を実装し、次フェーズの開始は Manager に返す。通常の実装判断は Implementer が自律して進め、全体計画に影響する判断を Manager に上げる。

開始時に、エージェントの起動・メッセージ送信・継続実行・goal 管理の機能と制約を確認する。

- 別エージェントは、その環境の起動機能で作成する。同じ作業場所を共有しない場合は、ブランチやパッチで成果を受け渡し、統合後の状態を検証する。
- ユーザーが goal モードでの実行を指示し、対応機能がある場合は、Manager に全体の目標、Implementer に現在のフェーズだけの目標を設定する。既存の目標がある場合は内容と状態を確認し、その API の規則に従う。予算はユーザーが指定した場合だけ設定する。
- メッセージに `/goal` と書くだけでモードが切り替わるとは扱わない。goal 機能がない場合は、通常の起動・継続依頼とファイルによる進捗管理でループを実行する。
- 別エージェントを起動できない場合は制約を報告し、同一エージェント内で計画・実装・受け入れを順に実行する。別スレッドを起動したとは報告しない。
- Implementer は、探索・実装・検証の独立した作業をサブエージェントへ並列に委譲する。統合の負担より並列化の利益が大きい作業を選び、書き込み先と成果の受け渡しを明確にする。モデルと同時実行数はユーザーの指定と実行環境に従い、96並列などの固定値や設定変更を前提にしない。

## 1. 入力と再開地点を確認する

プロジェクトの `AGENTS.md`、`CLAUDE.md`、`README.md`、既存コードと検証コマンドを確認する。`spec/index.md` を入口に、依頼範囲に対応する設計を読む。

| 入力 | 実装で確認すること |
| --- | --- |
| `spec/idea.md`、`spec/scenario/` | プロダクトの範囲、利用者が達成する操作と結果 |
| `spec/pages/`、`spec/design/` | 画面構成、状態、操作、デザイン成果物がある場合の見た目 |
| `spec/domains/` | 用語、境界、不変条件、ポート契約 |
| `spec/usecases/`、`spec/flows/` | 操作の連携、トランザクション境界、時間をまたぐ状態遷移 |
| `spec/testcases/`、`spec/manual-tests/` | 自動テスト、ポート適合テスト、シナリオの動作確認 |

既存の `.spec-implement/`、`spec/progress.md`、関連 Issue があれば実装状態と照合し、完了済みの作業を取り込む。進捗の記載だけで完了と判断せず、コードと検証根拠を確認する。

`spec` は、複数の機能にまたがる設計判断を持つ。局所的な入出力、エラー処理、物理スキーマ、処理手順は、設計と既存コードから Implementer が具体化する。詳細が未記載であることだけを理由に停止しない。プロダクトの範囲や共有契約を左右し、既存の指示から決められない不明点だけをユーザーに確認する。対象外の機能の設計文書は要求しない。

## 2. 全体チェックリストとフェーズを作る

Manager が [進捗管理と委譲プロトコル](references/manager-loop.md) を読み、`.spec-implement/plan.md` に全体計画を作成する。

1. 対象となるシナリオ、画面の操作と状態、ビジネスルール、ポート契約、動的フロー、テストを列挙する。既存の台帳があれば利用する。
2. 各項目に固定 ID、設計の参照先、観測できる完了条件、検証方法、依存先を付ける。単なるファイル作成や「実装する」だけの項目にしない。
3. 依存関係と不確実性から実装順序を決める。主要シナリオの開通、難所の検証、共通基盤の構築など、後続の作業を進めやすくする成果を早期に置く。
4. 各フェーズに目的、対象 ID、前提、変更範囲、完了条件を定義する。一度の委譲で実装と検証を見通せないフェーズは分割する。
5. 最後に全体の統合検証と設計照合のフェーズを置く。設計要素に対応する項目がない場合は、項目を追加するか、依頼範囲外である根拠を記録する。

チェックリストは依頼範囲を網羅し、各項目は作業中の前進を観測できる大きさにする。最初に全体の広がりを洗い出し、直近フェーズを詳しくする。後続フェーズの実装手順は、依存先の成果を得てから具体化する。計画を簡潔にユーザーへ共有し、実装が依頼されていればフェーズごとの承認を挟まず開始する。

## 3. Implementer を起動する

Manager は別のエージェントを一つ起動し、計画の場所、現在のフェーズ、対象の設計、作業場所、規約、検証コマンドを渡す。委譲文と報告形式は [進捗管理と委譲プロトコル](references/manager-loop.md) に従う。

Implementer には、全体の目的と現在のフェーズに必要な文脈を渡す。全体計画は参照できる状態に置き、過去の議論や後続フェーズの詳細を毎回プロンプトに詰め込まない。Manager も報告の要点を保持し、詳細なログは必要なときに読む。

Implementer の最初の作業は、全体チェックリストを `.spec-implement/checklist.json` に移し、`.spec-implement/progress.html` を作ること。HTML は全フェーズのチェック項目、完了数、時系列グラフを表示する。以後、Implementer が項目の状態変更時にデータと表示を更新する。

委譲時の目標は `Complete phase {id} completely, extremely well.` とする。品質は完了条件と検証結果で判断し、完了条件を満たした後の追加の磨き込みを続けない。

## 4. フェーズごとの Manager Loop

1. Manager が、依存フェーズを受け入れ済みのフェーズを一つ選び、Implementer に渡す。
2. Implementer が対象の設計とコードを読み、実装・テスト・接続・動作確認を行う。項目が完了条件を満たしたら、根拠と時刻を記録してチェックを付ける。
3. Manager はメッセージと進捗ファイルで状況を確認する。長時間の実行中も、ユーザーに進捗と未解決事項を伝える。
4. Implementer がフェーズの完了候補を報告する。Manager は差分、対象項目、検証結果、設計との対応を確認する。必要なら該当コマンドを再実行する。
5. 不足があれば項目 ID と満たしていない条件を示して差し戻す。Implementer は該当項目を未完了に戻して修正する。受け入れたら Manager が `plan.md` を更新し、次フェーズを継続依頼する。

受け入れでは、要求を満たさない振る舞い、再現できる不具合、検証不足を優先する。好みの書き換えや将来の仮説で新しい課題を増やさない。新しい変更や失敗がなければ同じ検証を繰り返さず、次の未完了フェーズを開始する。全フェーズの受け入れまでこのループを続ける。

Implementer が終了しただけではフェーズを完了にしない。途中終了なら未完了項目から継続させる。同じ Implementer を継続利用し、文脈の混乱や停滞が続く場合は、書き込みの停止を確認してから新しい Implementer に引き継ぐ。

### 停滞時の進め方

完了項目が増えない時間の目安を計画に設定する。指定がなければ15分を出発点に、項目の粒度と処理時間に合わせて調整する。既知の長時間ビルドやテストは予定所要時間を記録する。経過時間は実時刻から判断する。

- 閾値を超えたら、Implementer は試したこと、得られた根拠、障害、次の一手を Manager に報告する。
- Manager は長時間処理の進行状況を確認し、問題の分割、別の実装方法、現在のフェーズ内の独立項目への切り替えを指示する。
- 別フェーズに移る場合は、Manager が依存関係を確認して計画を組み替える。残項目は未完了として保持する。
- 同じ試行を根拠なく繰り返さない。実行可能な代替策がなく、回答・権限・外部環境の変更が必要なら、障害と再開条件を記録してユーザーに報告する。

時間切れや停滞を理由にチェックを付けたり、完了条件を緩めたりしない。

## 5. 受け入れと全体完了

各フェーズの検証は、その成果とリスクに合わせて選ぶ。テスト、ビルド、ブラウザ操作、CLI 実行などで完了条件を直接確かめる。ファイルの存在や型チェックの成功だけで、利用者が求めた振る舞いの完成とは扱わない。

全体完了には次の条件を満たす。

- 依頼範囲の全項目に実装と検証の根拠があり、Manager が全フェーズを受け入れている。
- 統合後のコードで、プロジェクトが要求する build・typecheck・lint・test の該当コマンドが成功している。
- 対象のシナリオと動的フローが端から端まで動く。`spec/manual-tests/` があれば該当手順を実行する。ブラウザを利用できないなど検証できない項目は、未検証として残す。
- 対象範囲に仮実装、ダミーデータへの置換、未接続の操作、未消費イベントなどの実装漏れがない。

未検証・ブロック中の必須項目があれば全体完了にしない。変更した範囲から外れる既存の失敗は区別して報告し、全体検証の成功とは記録しない。goal 機能を利用した場合も、その目標の完了条件を満たしてから完了として扱う。

最終報告には実装範囲、検証結果、残課題、再開条件がある場合はその内容、`plan.md` と `progress.html` の場所を記載する。進捗ファイルは再開と確認のために残す。
