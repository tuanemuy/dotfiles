# 進捗管理と委譲プロトコル

## 永続化と書き込み担当

Manager は `.spec-implement/` 直下と各実行ディレクトリの `plan.md` を読み、元の依頼の参照先、対象範囲、完成条件を今回の指示と照合する。同じ依頼の継続・修正なら、そのディレクトリを再利用する。記録がなければ `.spec-implement/`、別依頼の記録だけがあれば未使用の `.spec-implement/{run-id}/` を使う。別依頼の記録は保持する。

確定した場所を `{run-directory}` とし、元の依頼の参照先とともに `plan.md` に記録する。以下の作業ファイルはすべてその配下に置く。委譲文、goal、最終報告には確定したパスを渡す。

| ファイル | 書き込み担当 | 内容 |
| --- | --- | --- |
| `plan.md` | Manager | 依頼範囲、設計との対応、項目の状態と受け入れ根拠、フェーズの依存関係、現在の指示、停滞の閾値、エージェント識別子 |
| `phases/{phase-id}.md` | Implementer | 変更内容、検証コマンドと結果、残項目、障害、次に必要な作業 |

Manager が `plan.md` を更新し、Implementer はフェーズ報告を更新する。追加のサブエージェントは結果を Implementer に返し、全体の管理ファイルを直接更新しない。

共有設計の正本は `spec/` とし、Manager が採用した変更を反映する。設計変更時の受け入れ取り消しも `plan.md` に記録し、影響する項目 ID と更新した設計の参照先を Implementer に渡す。

## 完了台帳

`plan.md` を計画・項目状態・受け入れの正本にする。初回委譲前に、各項目を短い表かリストで記録する。

- 固定 ID、要件・設計の参照先。
- 担当フェーズ、依存する項目 ID、観測できる完了条件、検証方法と期待値。
- 現在の状態、フェーズ報告の根拠へのリンク、障害と解消条件。

Manager だけが項目状態を更新する。通常の遷移は `pending → in_progress → review → done` とする。Implementer の完了候補を受け取ったら `review`、Manager が受け入れたら `done` にする。差し戻しは `in_progress`、前提が崩れた項目は `pending` に戻す。`blocked` からは障害の解消後に再開する。項目の `blocked` は goal API の状態とは別に管理する。

受け入れ・差し戻し・再オープン・範囲変更には、実時刻、対象 ID、理由を短く残す。元の検証根拠は保持する。ユーザーが範囲を変更した場合は、変更元と対象外になった ID を記録する。未完了項目を進捗率のために削除しない。

進捗は `plan.md` に現在のフェーズ、`done` 数 / 対象数、`review` 数、障害、次の一手、更新日時を短く記す。受け入れ前の項目は完了数に含めない。進捗専用の JSON・HTML・グラフは生成しない。

## 検証根拠

Implementer はフェーズ報告に、項目 ID、変更ファイル、検証コマンドや操作、期待値と結果、実行日時を記録する。成功・失敗・未実行を区別する。日時はタイムゾーン付き ISO 8601 形式にする。

根拠には検証対象のコミット ID を付ける。未コミット変更がある場合は、追跡外を含む対象ファイルのハッシュ一覧など、検証時の内容を識別できる記録も残す。Git や初回コミットがない場合は対象ファイルのハッシュなどで識別する。同じ状態の検証は一つの記録を参照し、長いログは必要な箇所へのリンクで示す。

Manager は検証対象と受け入れ対象のコード・設定・実行環境を照合する。根拠が現在の状態に適用できない項目は、依存関係を通じた影響も確認して再オープンし、再検証する。

## フェーズの委譲文

プレースホルダーを実際の値で置き換えて渡す。goal モードを使う場合は、対応する機能でこのフェーズを目標として設定する。

```text
あなたは Implementer。Manager が全体計画とフェーズの受け入れを担当する。
Complete phase {phase-id} completely, extremely well.

作業場所: {path}
計画と進捗: {run-directory}
対象フェーズと項目 ID: {phase / ids}
目的と完了条件: {observable outcomes}
設計の参照先: {paths and sections}
依存フェーズの成果: {accepted outputs}
変更範囲と規約: {scope / project instructions}
検証コマンド: {commands}
停滞の閾値と長時間処理の見込み: {durations}
goal 機能の利用条件: {available mechanism and authorization, or normal execution}

対象項目を実装・接続・検証し、完了根拠を記録する。
設計と完了条件の範囲で、実装方法と作業順序は自分で決める。
独立した作業は利用可能な上限内で並列に委譲し、成果を統合する。
現在のフェーズを完了するまで進め、完了条件を満たしたら報告する。
再開・交代時は既存の項目 ID、受け入れ結果、検証根拠を引き継ぐ。
検証根拠には実行日時と、コミット ID・未コミット変更を含む検証対象の識別情報を付ける。
全体の管理ファイルと項目状態は Manager が更新する。
停滞時は、試行・根拠・障害・次の一手を Manager に報告する。
共有設計・契約、スコープ、完了条件の変更が必要なら、根拠・影響する項目 ID・変更案を Manager に返す。
完了候補を {run-directory}/phases/{phase-id}.md に記録し、Manager に通知する。
次フェーズは Manager の指示を受けて開始する。
```

## 完了・停滞の報告

メッセージにはフェーズ ID、`完了候補 / 継続中 / ブロック中`、対象項目 ID、報告ファイルの場所を含める。報告ファイルには次を記録する。

- 実装した振る舞いと変更ファイル。
- 項目 ID ごとの検証根拠。記録方法は「検証根拠」に従う。
- 未完了項目と障害。停滞時は試した方法とその結果。
- Manager の判断が必要な点と、次に実行できる具体的な作業。

## 再開と引き継ぎ

Manager は `plan.md`、現在のフェーズ報告、作業ツリーを照合する。記録された検証が現在のコードに適用できるかを判断し、影響を受ける項目とフェーズの受け入れを取り消す。エージェントの稼働状況を確認し、同じファイルを変更する Implementer を重複起動しない。

新しい Implementer には、現在のフェーズ、未完了 ID、受け入れ済みの依存成果、既存の変更、検証済みの範囲、失敗した試行、次の一手を渡す。チャット履歴を読まなくても再開できる内容を進捗ファイルに残す。

既存の `checklist.json` がある場合は、Manager が受け入れ結果と検証根拠を照合し、固定 ID と必要な履歴を `plan.md` に取り込む。受け入れが確認できない完了候補は `review` とする。元の記録は保持し、以後の状態更新は `plan.md` に集約する。
