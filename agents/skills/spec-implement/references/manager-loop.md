# 進捗管理と委譲プロトコル

## 永続化と書き込み担当

実装対象のプロジェクトに `.spec-implement/` を作る。既存の実行記録が別の依頼を扱っている場合は、`.spec-implement/{run-id}/` を使う。

| ファイル | 書き込み担当 | 内容 |
| --- | --- | --- |
| `plan.md` | Manager | 依頼範囲、設計との対応、初期チェックリスト、フェーズの依存関係、受け入れ結果、現在の指示、停滞の閾値、エージェント識別子 |
| `checklist.json` | Implementer | 固定 ID 付きの全項目、現在の状態、検証根拠、状態変更履歴 |
| `progress.html` | Implementer | `checklist.json` から生成する進捗表示 |
| `phases/{phase-id}.md` | Implementer | 変更内容、検証コマンドと結果、残項目、障害、次に必要な作業 |

計画の変更と受け入れの正本は `plan.md`、項目の実行状態と履歴の正本は `checklist.json` とする。Manager は項目の追加・移動・差し戻しを計画に記録して Implementer に通知し、Implementer が JSON に反映する。追加のサブエージェントは結果を Implementer に返し、共有の進捗ファイルを直接更新しない。

## チェックリストのデータ

次の形を基に、実際の設計と検証コマンドで項目を作る。日時はタイムゾーン付き ISO 8601 形式にする。

```json
{
  "updated_at": "2026-09-05T10:00:00+09:00",
  "items": [
    {
      "id": "I-001",
      "phase": "P1",
      "title": "登録したデータを再読み込み後も表示できる",
      "spec_refs": ["spec/scenario/registration.md#登録"],
      "depends_on": [],
      "acceptance": "登録操作の結果が保存され、再読み込み後に表示される",
      "verification": "登録から再読み込みまでの統合テスト",
      "status": "pending",
      "evidence": [],
      "completed_at": null,
      "blocker": null
    }
  ],
  "events": [
    {
      "at": "2026-09-05T10:00:00+09:00",
      "item_id": "I-001",
      "from": null,
      "to": "pending",
      "reason": "計画 P1 の項目を登録",
      "done": 0,
      "total": 1
    }
  ]
}
```

状態は `pending`、`in_progress`、`done`、`blocked` とする。`done` には実装ファイルと、実行日時・コマンド・結果を含む検証根拠を付ける。対象項目に応じて操作結果やスクリーンショットも根拠にできる。

各変更を `events` に追記し、変更後の完了数と総数を保存する。項目を再開するときは `done` を解除し、完了日時を空にして理由を記録する。検証履歴は残す。修正によって以前の検証が無効になった依存項目も再確認する。

項目の分割・追加・除外は Manager の計画更新と対応させる。除外した項目は理由付きの別記録に残し、完了として数えない。総数を変更した履歴も残す。件数の増減だけで実装の品質や作業量を判断しない。

## HTML の進捗表示

Implementer は初回に、外部通信なしで開ける単一 HTML を作る。JSON のスナップショットを埋め込み、ブラウザから隣の JSON を `fetch` する構成は避ける。文字列は HTML として実行されない形で埋め込み、項目名や根拠はテキストとして表示する。

表示する内容:

- 全項目をフェーズごとにまとめた読み取り専用チェックリスト。チェックは `done` に対応する。
- 完了数 / 総数、進行中・ブロック中の数、最終更新日時。
- 各項目の設計参照、完了条件、検証根拠、障害。
- 横軸を実時刻、縦軸をその時点の完了数とする SVG または Canvas のグラフ。総数の変化も表示する。差し戻しによる完了数の減少を保持する。
- 最後に項目が完了してからの経過時間。履歴がない場合は作業開始からの時間。

状態を変えるたびに JSON を保存し、HTML を再生成する。ページの再読み込みで最新状態を確認できるようにする。HTML のチェックを手で切り替えても進捗は更新できない構成にする。

HTML の装飾は、一覧・件数・履歴が読めるところで終える。進捗ページの作り込みを実装フェーズの目的にしない。

## フェーズの委譲文

プレースホルダーを実際の値で置き換えて渡す。goal モードを使う場合は、対応する機能でこのフェーズを目標として設定する。

```text
あなたは Implementer。Manager が全体計画とフェーズの受け入れを担当する。
Complete phase {phase-id} completely, extremely well.

作業場所: {path}
計画と進捗: {run-directory}
対象フェーズと項目 ID: {phase / ids}
目的と完了条件: {observable outcomes}
設計の参照先: {paths and sections}
依存フェーズの成果: {accepted outputs}
変更範囲と規約: {scope / project instructions}
検証コマンド: {commands}
停滞の閾値と長時間処理の見込み: {durations}
goal 機能の利用条件: {available mechanism and authorization, or normal execution}

対象項目を実装・接続・検証し、完了根拠を記録する。
設計と完了条件の範囲で、実装方法と作業順序は自分で決める。
独立した作業は利用可能な上限内で並列に委譲し、成果を統合する。
現在のフェーズを完了するまで進め、完了条件を満たしたら報告する。
初回は全体チェックリストと HTML を作成する。
項目の状態変更時に checklist.json と progress.html を更新する。
停滞時は、試行・根拠・障害・次の一手を Manager に報告する。
スコープや完了条件の変更が必要なら Manager に返す。
完了候補を phases/{phase-id}.md に記録し、Manager に通知する。
次フェーズは Manager の指示を受けて開始する。
```

## 完了・停滞の報告

メッセージにはフェーズ ID、`完了候補 / 継続中 / ブロック中`、更新した項目 ID、報告ファイルの場所を含める。報告ファイルには次を記録する。

- 実装した振る舞いと変更ファイル。
- 実行した検証コマンド、実行日時、成功・失敗・未実行の区別。
- 完了条件と根拠の対応。
- 未完了項目と障害。停滞時は試した方法とその結果。
- Manager の判断が必要な点と、次に実行できる具体的な作業。

## 再開と引き継ぎ

Manager は `plan.md`、`checklist.json`、現在のフェーズ報告、作業ツリーを照合する。エージェントの稼働状況を確認し、同じファイルを変更する Implementer を重複起動しない。HTML が古ければ JSON から再生成させる。

新しい Implementer には、現在のフェーズ、未完了 ID、受け入れ済みの依存成果、既存の変更、検証済みの範囲、失敗した試行、次の一手を渡す。チャット履歴を読まなくても再開できる内容を進捗ファイルに残す。
