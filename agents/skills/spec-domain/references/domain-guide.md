# ドメイン設計ガイド

DDDにおけるドメイン区分を検討し、各ドメインの詳細設計を行う。
設計のゴールは「実装者がこのドキュメントだけ見てコードを書ける」こと。
フィールド名だけ並べて振る舞いが空の設計は不完全。

## Step 1: ドメイン一覧

出力先: `spec/domains/index.md`

上流の成果物（シナリオ、ページ設計、要件定義、ユーザーストーリー、フロー等）から、ビジネス上の関心事の境界を特定し、ドメインを切り出す。
各ドメインの責務を一文で定義し、ドメイン間の依存方向も明記する。

ドメイン境界の切り方は非自明な判断になりやすい。spec には採用した境界と依存方向だけを書き、検討した代替案とトレードオフは完了サマリーで報告する。

## Step 2: ドメイン詳細

出力先: `spec/domains/${domain}.md`（ドメインごとにファイルを分ける。ファイル名は小文字始まり）

各ドメインについて以下を設計する:

### ドメイン名（単数形・大文字始まり）

### ユビキタス言語

ドメイン内で使う用語の定義。曖昧さを排除するために、英語名・日本語名・定義を明記する。

### エンティティ

各エンティティについて以下をすべて定義する:

- **名前**
- **フィールド**: 名前、型、制約（required/optional、デフォルト値、値の範囲）
- **振る舞い**: メソッド名、引数の型、戻り値の型、処理内容
- **不変条件**: このエンティティが常に満たすべきビジネスルール
- **ライフサイクル**: 生成条件、状態遷移（あれば）。状態は直和型（判別可能なユニオン）として定義し、boolean フラグや optional の羅列であり得ない組み合わせを表現可能にしない

振る舞いが空のエンティティはただのデータ構造であり、ビジネスロジックの配置が不適切であることを示す。上流の成果物に記載されたビジネスルール（バリデーション、状態遷移、計算）をエンティティの振る舞いとして定義すること。

### 値オブジェクト

各値オブジェクトについて:

- **名前**
- **フィールド**: 名前、型
- **バリデーションルール**: 生成時の制約（例: メールアドレスの形式、金額の範囲）
- **等価性**: 何をもって同一とみなすか

### ドメインサービス

複数のエンティティにまたがるビジネスロジック、またはエンティティに持たせると不自然なロジックを配置する。

各ドメインサービスについて:

- **名前**
- **責務**: 何をするか（一文で）
- **メソッド**: 名前、引数の型、戻り値の型、処理の概要
- **依存するポート**: 利用する外部インターフェース

### ポート

外部依存（DB、外部API、ファイルストレージ等）のインターフェース定義。

アダプターは差し替え可能でなければならない（in-memory / SQLite / PostgreSQL / 外部サービスのモック）。**差し替えても振る舞いが変わらないことを保証するのはポートの契約だけ**なので、シグネチャに加えて振る舞いまで定義する。ここが曖昧だと、in-memory では通るのに永続実装で壊れる（またはその逆）という状態になり、差し替え可能性が失われる。

各ポートについて:

- **名前**
- **目的**
- **メソッド**: 名前、引数の型、戻り値の型
- **エラーケース**: 発生しうるエラーとその意味

各メソッドについて、さらに振る舞いの契約を定義する:

- **一意性・整合性の担保**: 一意制約・参照整合性をポートが担保するのか、呼び出し側が事前確認してから呼ぶのか。ポートが担保する場合は違反時に返すエラー（例: `ConflictError`）を明記する。「事前に検索して無ければ保存」で済ませると in-memory では通るが、永続実装では競合で壊れる
- **クエリ要件**: 絞り込み条件・並び順・ページング・件数上限。**ドメインの語彙で**書く（テーブル名・カラム名・`WHERE`・`JOIN` などの永続化技術の語彙を漏らさない）。ここに列挙された条件が、後の永続実装でインデックス設計の入力になる
- **並行性**: 楽観ロックの要否。必要なら version 相当のフィールドの扱いと、競合時に返すエラー
- **可視性**: 書き込み後の読み取りに即座に反映されるか（read-your-writes）、遅延を許容するか

メソッドシグネチャのないポートは定義として不完全。実装者がアダプターを書ける粒度で記述する。ポートはドメイン型を受け渡す。外部データのデコード（検証・変換）はアダプター境界の責務とする。

### トランザクション境界

複数の集約にまたがる書き込みを原子的に行う必要がある場合、`UnitOfWork` ポートで境界を明示する。

- 単一の集約に閉じた操作には使わない（1 メソッド = 1 トランザクションで足りる）
- ユースケースが UnitOfWork のスコープを開き、その中で各リポジトリを呼ぶ形にする
- ここで定義するのは UnitOfWork ポート自体のインターフェース（スコープの開始・コミット・ロールバック、スコープ内でリポジトリを得る方法、ネストの可否）。**どのユースケースが UnitOfWork を必要とするかは Phase 2（ユースケース設計）で確定する**

UnitOfWork の実現方法はアダプターに委ねる（RDB のトランザクション、in-memory のスナップショット等）。ポートの契約として約束するのは「スコープ内の全書き込みが、全部成功するか全部反映されないかのどちらかになる」ことだけ。

### ユースケース（概要）

このドメインに属するユースケースを列挙する（詳細は Phase 2 で定義）。

実装例が `docs/backend_implementation_example.md` にあれば参照する。

## Step 3: レビュー

出力先: `spec/domains/review/${連番}.md`

### 実装可能性チェック

各エンティティ・値オブジェクト・ドメインサービス・ポートについて:

- フィールド、型、メソッドシグネチャがすべて揃っているか
- 振る舞いが定義されず、フィールドだけのエンティティがないか
- あり得ない状態の組み合わせが型上表現可能になっていないか（排他的な状態は直和型か）
- ポートのメソッドが未定義のまま残っていないか
- ポートの各メソッドに振る舞いの契約（一意性・クエリ要件・並行性・可視性）が定義されているか
- 値オブジェクトにバリデーションルールが定義されているか

### アーキテクチャ適合性チェック

- ドメインモデルがインフラ層の関心事（DB、HTTP等）に依存していないか
- ビジネスロジックがドメインモデルまたはドメインサービスに配置されているか
- 集約の境界が適切か — 他の集約のエンティティを直接参照していないか（IDで参照すべき）
- ドメイン間に循環依存がないか

### 差し替え可能性チェック

アダプターを in-memory / SQLite / PostgreSQL のどれで実装しても契約が成立するかを確認する。

- ポートが特定の永続化技術に依存する語彙・型を露出していないか（テーブル名・カラム名・SQL 片・ORM の型など）
- 一意性・参照整合性の担保をどちらが持つかが、すべてのメソッドで決まっているか
- 複数集約にまたがる原子的更新を要する箇所に UnitOfWork が定義されているか
- クエリ要件がドメインの語彙で列挙されているか（永続実装がインデックスを設計できる情報になっているか）

### ビジネスロジック網羅チェック

- 上流の成果物に記載された全パス（正常系・異常系）がドメインモデルの振る舞いでカバーされているか
- 不変条件がビジネス要件を正しく反映しているか
- エラーケースが網羅されているか

問題があれば SKILL.md「レビューの共通原則」に従って仕分け・修正し、再レビュー。再レビュー時は前回のレビューファイルを参照せず、チェックリストに沿って一から評価する。`fix` と仕分けた指摘が0件のラウンドで完了（最大5ラウンド）。
