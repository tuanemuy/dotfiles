# テストケース定義ガイド

2 種類のテストケースを定義する。

| 種類 | 出力先 | 対象 |
|------|-------|------|
| ユースケーステスト | `spec/testcases/${domain}/${usecase}.md` | ユースケースごとの振る舞い |
| ポート適合テスト | `spec/testcases/ports/${port}.md` | ポート契約。全アダプター実装が共通で通す |

## ユースケーステスト

すべてのユースケースについて、Markdownテーブル形式でテストケースを定義する。

出力先: `spec/testcases/${domain}/${usecase}.md`

テーブル構成:

```markdown
| 前提条件 | 操作 | 期待結果 | 実装ステータス |
|---|---|---|---|
| テストの前提状態 | 実行する操作 | 期待される振る舞い | （空欄 — 実装時に埋める） |
```

以下を網羅する:
- **正常系**: ユースケースの基本フロー
- **異常系**: バリデーションエラー、ビジネスルール違反、外部サービスエラー
- **境界値**: エンティティの不変条件の境界
- **エッジケース**: シナリオの異常系フロー

ユースケース設計で定義したエラーケースがテストケースでカバーされていることを確認する。

## ポート適合テスト

出力先: `spec/testcases/ports/${port}.md`（ポートごとに 1 ファイル）

アダプターは差し替え可能でなければならない（in-memory / SQLite / PostgreSQL 等）。それを保証するのは「**すべてのアダプター実装が共通で通すテストスイート**」だけであり、ドキュメント上の宣言では保証されない。ポート適合テストはそのスイートの仕様にあたる。

`spec/domains/${domain}.md` のポート定義（メソッドと振る舞いの契約）を入力に、契約の各項目を検証可能なケースへ落とす。ユースケーステストと同じテーブル形式を使う。

各ポートについて、少なくとも以下を網羅する:

- **メソッドの基本動作**: 各メソッドの正常系と、契約に書かれたエラーケース
- **一意性・整合性**: 契約でポート側が担保するとした制約が、実際に違反時のエラーを返すか。担保しないとした制約は対象外
- **クエリ要件**: 絞り込み・並び順・ページング・件数上限が契約どおりか。境界（0 件、1 件、上限ちょうど、上限超過）を含める
- **並行性**: 楽観ロックを要求するメソッドについて、競合時に契約どおりのエラーを返すか
- **可視性**: read-your-writes を約束したメソッドで、書き込み直後の読み取りが反映されるか
- **UnitOfWork**: スコープ内の全書き込みがコミットで反映され、ロールバックで 1 件も残らないか。ネストの可否を定義した場合はその挙動も

### 書き方の制約

- **永続化技術に依存する記述を書かない。** テーブル名・SQL・ORM の API を前提にしたケースは、そのバックエンドでしか実行できないため適合テストとして機能しない
- 前提条件はポートのメソッド呼び出しだけで組み立てる（テストデータの投入も対象ポート経由で行う）
- 「このバックエンドでは検証不能」なケースが出たら、それは契約が曖昧である兆候。ポート定義に戻って契約を明確化する
