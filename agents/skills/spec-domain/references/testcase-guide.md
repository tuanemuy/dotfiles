# テストケースの形式

2 種類のテストケースを定義する。上流・下限・上限は `../../_shared/references/spec-ready.md` の層の表が定める。

| 種類 | 出力先 | 対象 |
|------|-------|------|
| ユースケーステスト | `spec/testcases/${domain}/${usecase}.md` | ユースケースごとの振る舞い |
| ポート適合テスト | `spec/testcases/ports/${port}.md` | ポート契約。全アダプター実装が共通で通す |

テストケースは振る舞いの仕様を持つ。規則はドメイン（不変条件・判定・ポートの契約）が一文で定め、テストケースはその規則が成り立つ例を、前提・操作・観測できる結果で示す。ユースケースは配線だけを持ち、振る舞いの結果を書かない（`usecase-guide.md`）。各行は、実装でテスト 1 本になる。

2つは網羅の要求が違う。ユースケーステストは**規則と決定ごとに代表 1 行**に絞り、残りは実装時に補完する。ポート適合テストは**契約の全項目を網羅する** — 複数のアダプター実装が同じ振る舞いをすることを保証できるのはこのスイートだけで、Issue 単位では書けないため。

## 表の形式

どちらの種類も、Markdown の表で書く。

```markdown
| ID | 前提条件 | 操作 | 期待結果 |
|---|---|---|---|
| TC-{ディレクトリ名}-{ファイル名}-01 | テストの前提状態 | 実行する操作 | 観測できる結果 |
```

- **ID**: `TC-{ディレクトリ名}-{ファイル名}-{2 桁の連番}`（例: `TC-form-applyRetentionToSubmissions-01`、`TC-ports-submissionRepository-01`）。ディレクトリ名はドメイン名か `ports` なので、別のドメインに同じ名前のユースケースがあっても ID は spec 全体で一意になる。行を消しても番号を詰め直さない。実装したテストは、名前に ID を含める。spec と実装の対応は ID で辿る
- **期待結果**: 戻り値、エラーの種類、ポート経由で読める状態で書く。内部の手順や呼び出しの順序は書かない
- 規則の本文を書き写さない。前提と期待結果を具体的な値で書き、どの規則の例かは規則の名前で指す

## ユースケーステスト

すべてのユースケースについて、ユースケースごとに 1 ファイルを書く。

出力先: `spec/testcases/${domain}/${usecase}.md`

ユースケースの振る舞いの結果は、ここだけが定める。次を行として持つ。

- **正常系**: ユースケースの基本フローと、結果の種類ごとの代表ケース
- **要件由来の異常系**: 要件・シナリオが振る舞いを定めているエラーと、シナリオの代替フロー。ユーザーに見せる内容が決まっている、代替フローがある、といったものが該当する
- **不変条件**: ドメインの不変条件が破られる操作を拒否すること
- **途中で止まったとき**: 書き込みを複数の UnitOfWork に分けるユースケースで、途中で止まったときに残る状態と、その後の扱い（やり直し・後続の主体）。要件・シナリオ・動的フローが扱いを定めているものだけ

**書かないもの:**

- 境界値・技術的なエッジケース・入力バリデーションの組み合わせ。実装時にコードを読んで補完するため、ここで先取りすると二重管理になる
- 技術的に起こりうるだけのエラー（DB 接続断、想定外の入力、ライブラリの例外）。扱いは実装の共通方針で決まる
- 共通の規則（認可、共通の前提条件など）を展開した行。展開は規則の定義元のテストが持ち、各ユースケースは、そのユースケースが名指しで定める拒否と、必要な権限の代表 1 行だけを持つ
- 同じ規則の例を 2 行以上。条件の組み合わせを変えただけの行は、規則が 1 つなら 1 行にする

## ポート適合テスト

出力先: `spec/testcases/ports/${port}.md`（ポートごとに 1 ファイル）

アダプターは差し替え可能でなければならない（in-memory / SQLite / PostgreSQL 等）。それを保証するのは「**すべてのアダプター実装が共通で通すテストスイート**」だけであり、ドキュメント上の宣言では保証されない。ポート適合テストはそのスイートの仕様にあたる。

`spec/domains/${domain}.md` のポート定義（メソッドと振る舞いの契約）を入力に、契約の各項目を検証可能なケースへ落とす。契約の規則はポート定義が持ち、適合テストはその例を持つ。

各ポートについて、少なくとも以下を網羅する:

- **メソッドの基本動作**: 各メソッドの正常系と、契約に書かれたエラーケース
- **一意性・整合性**: 契約でポート側が担保するとした制約が、実際に違反時のエラーを返すか。担保しないとした制約は対象外
- **クエリ要件**: 絞り込み・並び順・ページング・件数上限が契約どおりか。境界（0 件、1 件、上限ちょうど、上限超過）を含める
- **並行性**: 楽観ロックを要求するメソッドについて、競合時に契約どおりのエラーを返すか
- **可視性**: read-your-writes を約束したメソッドで、書き込み直後の読み取りが反映されるか
- **UnitOfWork**: スコープ内の全書き込みがコミットで反映され、ロールバックで 1 件も残らないか。ネストの可否を定義した場合はその挙動も

### 書き方の制約

- **永続化技術に依存する記述を書かない。** テーブル名・SQL・ORM の API を前提にしたケースは、そのバックエンドでしか実行できないため適合テストとして機能しない
- 前提条件はポートのメソッド呼び出しだけで組み立てる（テストデータの投入も対象ポート経由で行う）
- 「このバックエンドでは検証不能」なケースが出たら、それは契約が曖昧である兆候。ポート定義に戻って契約を明確化する
