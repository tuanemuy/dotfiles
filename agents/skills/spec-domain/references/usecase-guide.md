# ユースケースと動的フローの形式

ドメインごとにユースケースを定義する。上流・下限・上限は `../../_shared/references/spec-ready.md` の層の表が定める。
ユースケースはドメインモデルの操作を組み合わせて要件を実現するオーケストレーター。
ビジネスロジック自体はドメイン層に置き、ユースケースには含めない。

出力先: `spec/usecases/${domain}.md`

## 命名と粒度

- ユースケースは画面ではなくドメインの言葉で命名する（〜Page 等の画面語彙を使わない）
- 複数の読み取りを1つに合成してよいのは、合成をまたぐ規則があるときだけ。その合成にはドメインの名詞が付くはず — 名詞が「〜ページ」しかないなら分割し、束ねるのは画面の責務
- 1画面のデータ一式 ≠ 1ユースケース

## ユースケースの構成

各ユースケースについて以下を記載する:

### ユースケース名

### 概要

このユースケースが実現する操作の概要。

### 入出力

- **入力**: 何を受け取るか。要件が定めているバリデーションルールがあれば添える
- **出力**: 何を返すか

**全フィールドの列挙はしない。** DTO の具体的なフィールドと型は実装時にコードの型定義が正になるため、ここで先取りしても二重管理になる。書くのは「このユースケースが何を受け取り何を返すか」が伝わる粒度まで。

### 使用するドメインの振る舞い・ポート

このユースケースが呼び出すドメインモデルの振る舞いとポートメソッドを列挙する。**手順の番号付き記述はしない** — 呼び出しの順序は実装時に決まり、先に書くと実装との乖離が生まれる。ここで確認したいのは「必要な振る舞いとポートが設計済みか」だけ。

### トランザクション境界

このユースケースで原子的に確定する書き込みの範囲と、その保証方法を明示する。`UnitOfWork` を使う場合はスコープを記載する。

- **UnitOfWork の要否**: 必要 / 不要
- 必要な場合: スコープに含まれるステップの範囲、スコープ内で使うリポジトリ、ロールバックが起きる条件
- 不要な場合: 書き込みがない、リポジトリの契約で必要な原子性が保証される、または結果整合で許容される理由を一行で書く

UnitOfWork の要否は、必要な原子性とプロジェクトの方針に基づいて判断する。単一集約への使用も許容する。複数の書き込みを原子的に確定しない場合は、途中失敗時にどの状態が残るかを明記する。

### エラーケース

**要件・シナリオが振る舞いを定めているエラーだけ**を列挙する（条件と種類）。ユーザーに見せるメッセージが決まっている、代替フローがある、といったものが該当する。

技術的に起こりうるだけのエラー（DB 接続断、想定外の入力、ライブラリの例外）は書かない — 扱いは実装の共通方針で決まり、ユースケースごとに列挙しても増えるだけ。

## 動的フロー台帳

複数のユースケース・時間をまたいで生きる「動的フロー」を `spec/flows/index.md` に台帳としてまとめる。入力は全ドメインのユースケース定義。単一ユースケース内で完結する処理は対象外。

対象の例:
- 非同期ジョブ（生成 → 実行 → 完了 / 失敗 / リトライ）
- ドメインイベントとその消費者（投影の更新、通知、外部連携）
- ファイル・外部リソース（アップロード → 参照 → 削除）
- 有効期限つきのもの（トークン、招待、セッション、キャッシュ）

各フローについて以下を記載する:

- **フロー名**
- **対象**: ライフサイクルを追うエンティティ・リソース
- **トリガー**: フローを開始する操作・イベント・スケジュール
- **経路**: 状態遷移の列。各遷移について「遷移元 → 遷移先」と、遷移を実行する主体（ユースケース / ジョブ / トリガー）を明記する
- **終端**: 正常終端と異常終端（失敗、放棄、期限切れ）。すべての状態が終端であるか、脱出遷移を持つこと
- **失敗時の扱い**: リトライ、補償、孤児リソースの掃除

この台帳は、完了の定義の 3（動的フローが閉じている）を確かめる入力になる。フローは台帳の全量を 1 本ずつエンドツーエンドでトレースする。
