# ユースケース設計ガイド

ドメインごとにユースケースを詳細に定義する。
ユースケースはドメインモデルの操作を組み合わせて要件を実現するオーケストレーター。
ビジネスロジック自体はドメイン層に置き、ユースケースには含めない。

出力先: `spec/usecases/${domain}.md`

## 命名と粒度

- ユースケースは画面ではなくドメインの言葉で命名する（〜Page 等の画面語彙を使わない）
- 複数の読み取りを1つに合成してよいのは、合成をまたぐ規則があるときだけ。その合成にはドメインの名詞が付くはず — 名詞が「〜ページ」しかないなら分割し、束ねるのは画面の責務
- 1画面のデータ一式 ≠ 1ユースケース

## ユースケースの構成

各ユースケースについて以下を記載する:

### ユースケース名

### 概要

このユースケースが実現する操作の概要。

### 入出力

- **入力**: 何を受け取るか。要件が定めているバリデーションルールがあれば添える
- **出力**: 何を返すか

**全フィールドの列挙はしない。** DTO の具体的なフィールドと型は実装時にコードの型定義が正になるため、ここで先取りしても二重管理になる。書くのは「このユースケースが何を受け取り何を返すか」が伝わる粒度まで。

### 使用するドメインの振る舞い・ポート

このユースケースが呼び出すドメインモデルの振る舞いとポートメソッドを列挙する。**手順の番号付き記述はしない** — 呼び出しの順序は実装時に決まり、先に書くと実装との乖離が生まれる。ここで確認したいのは「必要な振る舞いとポートが設計済みか」だけ。

### トランザクション境界

このユースケースが複数の集約に書き込む場合、`UnitOfWork`（ドメイン設計で定義したポート）のスコープを明示する。

- **UnitOfWork の要否**: 必要 / 不要
- 必要な場合: スコープに含まれるステップの範囲、スコープ内で使うリポジトリ、ロールバックが起きる条件
- 不要な場合: 単一集約に閉じている、または複数の書き込みが結果整合で許容される理由を一行で書く

単一集約への書き込みしかないユースケースに UnitOfWork を付けない。逆に、複数集約へ書き込むのにスコープを張らない場合は、途中失敗時にどの状態が残るかを明記する。

### エラーケース

**要件・シナリオが振る舞いを定めているエラーだけ**を列挙する（条件と種類）。ユーザーに見せるメッセージが決まっている、代替フローがある、といったものが該当する。

技術的に起こりうるだけのエラー（DB 接続断、想定外の入力、ライブラリの例外）は書かない — 扱いは実装の共通方針で決まり、ユースケースごとに列挙しても増えるだけ。

## 動的フロー台帳

全ドメインのユースケース定義が完了したら、複数のユースケース・時間をまたいで生きる「動的フロー」を `spec/flows/index.md` に台帳としてまとめる。単一ユースケース内で完結する処理は対象外。

対象の例:
- 非同期ジョブ（生成 → 実行 → 完了 / 失敗 / リトライ）
- ドメインイベントとその消費者（投影の更新、通知、外部連携）
- ファイル・外部リソース（アップロード → 参照 → 削除）
- 有効期限つきのもの（トークン、招待、セッション、キャッシュ）

各フローについて以下を記載する:

- **フロー名**
- **対象**: ライフサイクルを追うエンティティ・リソース
- **トリガー**: フローを開始する操作・イベント・スケジュール
- **経路**: 状態遷移の列。各遷移について「遷移元 → 遷移先」と、遷移を実行する主体（ユースケース / ジョブ / トリガー）を明記する
- **終端**: 正常終端と異常終端（失敗、放棄、期限切れ）。すべての状態が終端であるか、脱出遷移を持つこと
- **失敗時の扱い**: リトライ、補償、孤児リソースの掃除

この台帳はクロスフェーズ検証（動的フロー検証）の入力になる。レビュー時に思い出せた分だけ確認するのではなく、台帳の全フローを潰すために使う。

## レビュー

出力先: `spec/usecases/review/${連番}.md`

レビュー観点:

- **トレーサビリティ**: 上流の成果物に記載された全操作がユースケースとしてカバーされているか
- **命名**: 名前・入出力に画面の語彙が混入していないか。名詞なき読み取り合成がないか
- **アーキテクチャ適合性**: ビジネスロジックがユースケース層に漏れていないか（ドメイン層の振る舞いを呼ぶだけになっているか）
- **トランザクション境界**: 全ユースケースに UnitOfWork の要否が記載されているか。複数集約に書き込むのにスコープがないユースケースで、途中失敗時の残存状態が明記されているか
- **依存の存在**: 使用すると書いたドメインの振る舞い・ポートメソッドが `spec/domains/` に定義済みか
- **単一責任**: 1つのユースケースが複数の独立した操作を含んでいないか
- **フロー台帳**: 非同期ジョブ・イベント・ファイル・期限つきリソースが `spec/flows/index.md` に載っているか。台帳の各遷移に実行主体（ユースケース / ジョブ / トリガー）が存在するか

指摘の受理は `../../_shared/references/spec-review.md` の受理基準に従う。「このエラーも起こりうる」「入力の型を明記すべき」は受理せず実装フェーズに委ねる。仕分け・修正・完了条件も同ガイドに従う。
