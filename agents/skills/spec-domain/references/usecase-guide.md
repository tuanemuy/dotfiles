# ユースケース設計ガイド

ドメインごとにユースケースを詳細に定義する。
ユースケースはドメインモデルの操作を組み合わせて要件を実現するオーケストレーター。
ビジネスロジック自体はドメイン層に置き、ユースケースには含めない。

出力先: `spec/usecases/${domain}.md`

## 命名と粒度

- ユースケースは画面ではなくドメインの言葉で命名する（〜Page 等の画面語彙を使わない）
- 複数の読み取りを1つに合成してよいのは、合成をまたぐ規則があるときだけ。その合成にはドメインの名詞が付くはず — 名詞が「〜ページ」しかないなら分割し、束ねるのは画面の責務
- 1画面のデータ一式 ≠ 1ユースケース

## ユースケースの構成

各ユースケースについて以下を記載する:

### ユースケース名

### 概要

このユースケースが実現する操作の概要。

### 入力DTO

フィールドごとに:
- フィールド名、型、必須/任意、バリデーションルール

### 出力DTO

フィールドごとに:
- フィールド名、型

### 処理フロー

主要なステップを番号付きで記述する。
各ステップで呼び出すドメインモデルの振る舞いやポートを明記する。

### エラーケース

発生しうるエラーを列挙する:
- エラーの条件
- エラーの種類（バリデーションエラー、ビジネスルール違反、外部サービスエラー等）

## 動的フロー台帳

全ドメインのユースケース定義が完了したら、複数のユースケース・時間をまたいで生きる「動的フロー」を `spec/flows/index.md` に台帳としてまとめる。単一ユースケース内で完結する処理は対象外。

対象の例:
- 非同期ジョブ（生成 → 実行 → 完了 / 失敗 / リトライ）
- ドメインイベントとその消費者（投影の更新、通知、外部連携）
- ファイル・外部リソース（アップロード → 参照 → 削除）
- 有効期限つきのもの（トークン、招待、セッション、キャッシュ）

各フローについて以下を記載する:

- **フロー名**
- **対象**: ライフサイクルを追うエンティティ・リソース
- **トリガー**: フローを開始する操作・イベント・スケジュール
- **経路**: 状態遷移の列。各遷移について「遷移元 → 遷移先」と、遷移を実行する主体（ユースケース / ジョブ / トリガー）を明記する
- **終端**: 正常終端と異常終端（失敗、放棄、期限切れ）。すべての状態が終端であるか、脱出遷移を持つこと
- **失敗時の扱い**: リトライ、補償、孤児リソースの掃除

この台帳はクロスフェーズ検証（動的フロー検証）の入力になる。レビュー時に思い出せた分だけ確認するのではなく、台帳の全フローを潰すために使う。

## レビュー

出力先: `spec/usecases/review/${連番}.md`

レビュー観点:

- **トレーサビリティ**: 上流の成果物に記載された全操作がユースケースとしてカバーされているか
- **命名**: 名前・DTOに画面の語彙が混入していないか。名詞なき読み取り合成がないか
- **DTO完全性**: 入力DTO・出力DTOのフィールドがすべて定義されているか
- **アーキテクチャ適合性**: ビジネスロジックがユースケース層に漏れていないか（ドメイン層の振る舞いを呼ぶだけになっているか）
- **エラー網羅性**: エラーケースが網羅されているか
- **単一責任**: 1つのユースケースが複数の独立した操作を含んでいないか
- **フロー台帳の網羅性**: 非同期ジョブ・イベント・ファイル・期限つきリソースがすべて `spec/flows/index.md` に載っているか。台帳の各遷移に実行主体（ユースケース / ジョブ / トリガー）が存在するか

問題があれば SKILL.md「レビューの共通原則」に従って仕分け・修正し、再レビュー。再レビュー時は前回のレビューファイルを参照せず、チェックリストに沿って一から評価する。`fix` と仕分けた指摘が0件のラウンドで完了（最大5ラウンド）。
