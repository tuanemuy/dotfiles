# Spec Domain

上流の成果物を受け、Implementation Ready な技術設計を `spec/` に作る。完了の定義・層・独立した読み・不変条件・予算は `../_shared/references/spec-ready.md` に従う。このスキルが定めるのは契約・範囲・アーキテクチャ制約。

## 契約

出典は `spec/` 配下の上流成果物。形式は問わない。シナリオ・ページ設計・要件定義・ユーザーストーリー・フロー・サイトマップのどれでも、何を作るかが読み取れれば出典になる。上流成果物が定める操作とルールを番号付きの台帳にし、`spec/review/contract.md` に置く。

上流成果物が見つからなければ、技術設計の入力になる成果物が必要だと伝え、進め方をユーザーに聞く。

## 範囲

既定は domains / usecases / flows / testcases。ユーザーが層を指定していれば、その層だけを範囲にする。

上流成果物は範囲の外にある。上流成果物の誤りや矛盾に気づいたら、直さずにユーザーに聞く。

## アーキテクチャ制約

完了の定義の 6 が基準にする。

- **ドメインモデルの独立性**: ドメイン層はインフラ層（DB, HTTP, 外部API）に依存しない
- **ビジネスロジックの配置**: ビジネスルールはエンティティまたはドメインサービスに置く。ユースケース層はオーケストレーションのみ
- **集約境界**: 他の集約のエンティティは ID で参照する。直接の参照を持たない
- **ポートによる抽象化**: 外部依存はすべてポート（インターフェース）経由。メソッドシグネチャと振る舞いの契約まで定義する
- **アダプターの差し替え可能性**: ポートは特定の永続化技術・外部サービスに依存する語彙や型を露出しない。同じポートを in-memory / SQLite / PostgreSQL のどれで実装しても契約が成立する。**設計の成果物はテーブル定義ではなくポートの契約であり、物理スキーマは実装時にバックエンドごとに決める**
- **トランザクション境界の明示**: 原子的に確定する書き込みの範囲を明示する。集約数にかかわらず、リポジトリ単体の契約で必要な原子性を保証できない場合は `UnitOfWork` ポートを使う。単一集約への使用も許容する
- **ドメイン間の非循環**: ドメイン間に循環依存を作らない

## 環境の事実

- ユースケーステストはドメイン単位、ポート適合テストはポート単位で独立している。並列に委譲できる
- `spec/flows/index.md` は、全ドメインのユースケースが揃ってから書ける
- `docs/backend_implementation_example.md` があれば、実装例として読む
