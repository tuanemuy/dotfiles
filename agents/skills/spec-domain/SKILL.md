# Spec Domain

上流の成果物（シナリオ、ページ設計、要件定義、ユーザーストーリー、フロー、サイトマップなど）をもとに、ドメイン設計以降の技術設計を行う。
上流の形式は問わない — 「何を作るか」が明確になっていれば、そこから技術設計に落とし込む。
各フェーズは前フェーズの成果に基づいて進む。レビューで見つかった問題を修正し、レビューが完了してから次へ進む（完了条件は「レビューの共通原則」参照）。

## 設計思想

### 実装可能な設計を出す

このスキルのゴールは「設計フェーズを完了すること」ではなく、「実装者が設計書だけを読んで、質問なしにコードを書ける状態を作ること」。エンティティに振る舞いが足りない、ポートのメソッドが未定義、ユースケースの異常系が未検討 — こうした穴が実装時に TODO になる。レビューフェーズはそれを潰すためにある。

### ユーザー体験の設計を前提にする

体験側の設計（要件定義、シナリオ、ユーザーストーリー、ページ構成、フロー等）は完了済みという前提で、技術設計に集中する。上流の成果物が既にあるので、それを忠実に技術で実現することに注力する。

### 決定を記録する

設計中に下した非自明な判断は ADR として記録する。「なぜそうしたか」が残っていれば、実装者が迷わず、将来の変更時にも意図を追える。

## アーキテクチャ制約

設計全体を通じて以下を守る。レビューではこれらへの違反がないかを必ず確認する。

- **ドメインモデルの独立性**: ドメイン層はインフラ層（DB, HTTP, 外部API）に依存しない
- **ビジネスロジックの配置**: ビジネスルールはエンティティまたはドメインサービスに置く。ユースケース層はオーケストレーションのみ
- **集約境界**: 他の集約のエンティティは ID で参照する。直接の参照を持たない
- **ポートによる抽象化**: 外部依存はすべてポート（インターフェース）経由。メソッドシグネチャと振る舞いの契約まで定義する
- **アダプターの差し替え可能性**: ポートは特定の永続化技術・外部サービスに依存する語彙や型を露出しない。同じポートを in-memory / SQLite / PostgreSQL のどれで実装しても契約が成立すること。**設計の成果物はテーブル定義ではなくポートの契約であり、物理スキーマは実装時にバックエンドごとに決める**
- **トランザクション境界の明示**: 複数の集約にまたがる原子的な書き込みは `UnitOfWork` ポートでスコープを明示する。単一集約に閉じた操作には使わない
- **ドメイン間の非循環**: ドメイン間に循環依存を作らない

## ADR（Architecture Decision Records）

設計中に非自明な判断を下したら、プロジェクトルートの `.adr/{YYYY-MM-DD}-{slug}.md` に記録する。記録基準・記載項目・supersede の扱いは `../_shared/references/adr-guide.md` を参照。

## Phase 0: 前提確認

`spec/` 配下を探索し、ドメイン設計の入力となる上流の成果物を特定する。
形式は問わない — シナリオ、ページ設計、要件定義書、ユーザーストーリー、フロー、サイトマップなど、「何を作るか」が分かる成果物があればよい。

- 上流成果物が見つかった場合: 内容を読み込み、設計の入力とする。`spec/index.md` があれば確認し、なければ作成する。
- 上流成果物が見つからない場合: ユーザーに「ドメイン設計の入力となる上流の成果物（要件定義、シナリオ、ページ構成など）が必要です」と案内し、どう進めるか確認する。

既存の `spec/domains/` 等が部分的に存在する場合は、内容を確認して続きから再開する。

確認が完了したら、以降は最後まで自走する（フェーズ間でユーザー承認を挟まない）。

## Workflow Overview

```
Phase 0: 前提確認
  spec/ 配下の上流成果物を探索・特定
  → 既存成果物の確認・再開判定

Phase 1: ドメイン設計
  シナリオ・ページ設計 → spec/domains/index.md → spec/domains/${domain}.md
  → レビュー・修正 → spec/index.md 更新

Phase 2: ユースケース設計
  ドメイン設計 → spec/usecases/${domain}.md → spec/flows/index.md（動的フロー台帳）
  → トランザクション境界（UnitOfWork の要否）を確定
  → レビュー・修正 → spec/index.md 更新

Phase 3: テストケース定義
  ユースケース → spec/testcases/${domain}/${usecase}.md
  ポート契約 → spec/testcases/ports/${port}.md（適合テスト）
  → レビュー・修正 → spec/index.md 更新

Phase 4: クロスフェーズ検証
  全成果物を横断的に検証
  → トレーサビリティ・動的フロー・アーキテクチャ適合性・実装可能性
  → spec/index.md 更新

※ ADR は全フェーズを通じて随時作成 → .adr/
```

途中のフェーズから再開する場合は、既存の成果物を確認して該当フェーズから開始する。

## Phase 1: ドメイン設計

`references/domain-guide.md` を読み、その手順に従ってドメイン設計を行う。

成果物:
- `spec/domains/index.md` — ドメイン一覧
- `spec/domains/${domain}.md` — ドメイン別の詳細設計

完了後、`spec/index.md` を更新する。

---

## Phase 2: ユースケース設計

`references/usecase-guide.md` を読み、その手順に従ってユースケース設計を行う。

成果物:
- `spec/usecases/${domain}.md` — ユースケース定義
- `spec/flows/index.md` — 動的フロー台帳（ユースケース・時間をまたぐライフサイクルの一覧）

完了後、`spec/index.md` を更新する。

---

## Phase 3: テストケース定義

`references/testcase-guide.md` を読み、その手順に従ってテストケースを定義する。

ユースケーステストはドメイン単位で、ポート適合テストはポート単位で独立しているため、`../_shared/references/subagent-policy.md` に従いサブエージェント（**判断区分** — テストケースの設計を伴う）へ並列に委譲する。

成果物:
- `spec/testcases/${domain}/${usecase}.md` — ユースケーステスト
- `spec/testcases/ports/${port}.md` — ポート適合テスト（全アダプター実装が共通で通すスイートの仕様）

`spec/index.md` の更新は競合を避けるため全サブエージェント完了後にまとめて行う。

---

## Phase 4: クロスフェーズ検証

すべてのフェーズが完了した後、成果物を横断的に検証する。
個々のフェーズレビューでは見落としやすいフェーズ間の不整合を検出する。

### トレーサビリティ検証

以下のチェーンをたどり、抜け漏れを特定する:
- **上流の成果物 → ユースケース**: 上流で定義された全操作がユースケースの組み合わせで実現されているか（1画面=1ユースケースの対応は求めない）
- **ユースケース → ドメインモデル**: ユースケースが呼び出すドメインの振る舞いがすべて定義されているか
- **ドメインエンティティ → ポート**: 永続化が必要なすべてのエンティティ・値オブジェクトに、それを読み書きするポートメソッドが存在するか
- **ポート → ユースケース**: 定義されたポートが少なくとも1つのユースケースから利用されているか
- **ポート → 適合テスト**: すべてのポートメソッドと契約項目が `spec/testcases/ports/` のケースでカバーされているか

### 動的フロー検証

トレーサビリティ検証は成果物間の静的な対応関係を見る。ここでは `spec/flows/index.md` の各フローを1本ずつエンドツーエンドでトレースし、フェーズをまたぐ時間軸の流れ（イベント → 投影、ジョブのライフサイクル、ファイルの生涯など）に穴がないかを検証する。台帳が成果物と食い違っている場合は、まず台帳を成果物に合わせて更新してから検証する。

各フローについて確認する:
- すべての状態に「入る遷移」があり、「出る遷移」または終端の明示があるか（到達不能な状態・行き止まりの状態がないか）
- 各遷移を実行する主体（ユースケース / ジョブ / トリガー）が定義されているか
- イベントに消費者がいるか。投影・通知の更新元が揃っているか。結果整合の遅延が上流の設計（画面の表示内容など）と矛盾しないか
- ファイル・外部リソースは生成・参照・削除が揃っているか（親レコード削除時の孤児化を含む）
- フローの各状態がエンティティのライフサイクルとポート契約で表現できるか
- テストケースにフローの異常系（途中失敗、二重実行、タイムアウト、期限切れ）があるか

### アーキテクチャ適合性の最終確認

「アーキテクチャ制約」セクションのすべてのルールについて、全成果物を横断的に確認する。

### 差し替え可能性の最終確認

全ポートについて、「このポートを in-memory で実装したときに通り、PostgreSQL で実装したときに落ちる（またはその逆の）ケースが存在しないか」を確認する。

- ポート定義に永続化技術の語彙・型が漏れていないか
- 一意性・参照整合性の担保がポート側か呼び出し側か、全メソッドで決まっているか
- 複数集約への書き込みを持つユースケースに UnitOfWork の要否が記載されているか
- 適合テストのケースが特定バックエンドを前提にしていないか

### 実装可能性の最終確認

各ドメインについて「このドメインの実装に必要な情報はすべて揃っているか」を確認する。
不足があれば該当フェーズに戻って補完する。

出力先: `spec/review/cross-phase/${連番}.md`

問題があれば該当フェーズの成果物を修正し、再検証する。仕分け・完了条件は「レビューの共通原則」に従う（台帳は `spec/review/cross-phase/triage.md`）。

完了後、`spec/review/cross-phase/` を削除し（収束しなかった場合は残す）、`spec/index.md` を更新する。

## レビューの共通原則

各フェーズのレビューでは以下を守る:

- 対象ディレクトリの `review/` 配下に連番ファイル（`001.md`, `002.md`, ...）で記録する
- 無駄な情報を省き、対応が必要な問題点のみ記載する
- ドキュメントの責任範囲をそのレビューの対象に限定する
- 指摘は Blocker（前フェーズとの矛盾・欠落など、設計として成立しない問題）と Warning（改善推奨）に分類する
- **問題が見当たらなければ「指摘ゼロ」と明示してよい** — 無理に粗探しをしない。厳しく見ることと、出す指摘がなくなるまで深掘りの粒度を下げ続けることは別。そのフェーズの責務範囲で設計が成立していれば、より細かい記述の余地があること自体は指摘にしない

### トリアージと完了条件

指摘の仕分けは `../_shared/references/review-loop.md` の指摘台帳方式に従う。台帳は対象ディレクトリの `review/triage.md` に置く。

- 各ラウンドの指摘はまず台帳と突き合わせ、Key が一致する既出指摘は判定を継承して再審議しない
- 新規の指摘は `fix` / `wont-fix`（一行理由を記録）に仕分け、`fix` を修正して再レビューする
- **`fix` と仕分けた指摘が0件のラウンドでレビュー完了**（台帳に記録済みの指摘は件数に含めない）。最大5ラウンド。収束しない場合は残った指摘をまとめてユーザーに報告し、判断を委ねる

### 後片付け

フェーズのレビューが完了条件を満たしたら、対象ディレクトリの `review/` を削除する（`../_shared/references/review-loop.md` の「後片付け」参照）。指摘は成果物に反映済みか台帳で決着しており、残すと後続セッションの検索に紛れ込んでコンテキストを浪費する。最大ラウンドに達して収束しなかったフェーズの `review/` は削除せず残し、完了報告に明記する。

### 各ラウンドの独立性

レビューの各ラウンドは独立した完全なレビューとして実施する。前回のレビューファイルを読まずに、成果物とチェックリストだけを見て一から評価する。前回の指摘への対応確認ではなく、毎回ゼロベースで見直す。再登場する既出指摘は台帳の判定継承で吸収して収束させる。

### レビューの3軸

すべてのフェーズで以下の3軸を確認する（各ガイドに詳細なチェック項目がある）:

1. **実装可能性**: 実装者がこの設計書だけ見てコードを書けるか。型、シグネチャ、制約が揃っているか
2. **アーキテクチャ適合性**: 「アーキテクチャ制約」セクションのルールに違反していないか
3. **トレーサビリティ**: 前フェーズの成果物と整合しているか。漏れているシナリオ・要件がないか

すべてのフェーズが完了したら、作成した設計ドキュメントのサマリーを出す。
spec スキルの Phase 3 として呼び出されている場合は、この単体の完了報告は出さず、spec 側の完了報告に統合する。

```

```

## 原則

- 各フェーズは前フェーズの成果に基づいて進める — 飛ばさない
- レビューで見つかった問題は即座に修正する — 先送りにしない
- スコープクリープを避け、既存のシナリオ・ページ設計の範囲に集中する
- 実装時に TODO を残さない粒度で設計する。型・シグネチャ・制約・エラーケースまで定義する
- 非自明な判断は ADR に記録する
- `spec/index.md` はフェーズ完了ごとに更新し、成果物と進捗を反映する
