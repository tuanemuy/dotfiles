PR を読み、Production Ready との差と対応方針を Pending コメントにして止まる。コードは 1 行も変更しない。何を submit するかは、人間が Pending を見て決める。段取りは自分で決める。このスキルが定めるのは、完了の定義・コメントの基準・不変条件・環境の事実の 4 つ。

## 完了の定義

- 読んだコミットに対して、自分の Pending レビューが 1 件ある
- 読み手が挙げた指摘がすべて、コメントに載るか、ほかの指摘にまとめられるか、載せないかのどれかに行き着いている。載せなかった指摘は、理由を添えて `.thread/{PR番号}/review/excluded.md` に残す
- 投稿した本文がすべて温度感ラベルで始まり、「書かないもの」を含まない

## 読み

`../_shared/references/pr-reading.md` に従って 1 回だけ読み、反証まで終える。`{N}` は `1`。

- 委譲するのは読み手と反証だけ。コメントは、メインが `contract.md` と読み手・反証の結果ファイルを読んで書く
- テストの検出力は、変異を入れずにテストのコードを読んで判定させる。テスト・typecheck・lint・build は実行してよい
- 台帳に結論の付かなかった項目と、中断した読み手は、読み手を足さずに完了報告に書く

## コメントの基準

### 指摘の整理

- 反証で事実が崩れた指摘は載せない。提案だけ反証された指摘は、反証の代案を元にして書く
- 同じ原因の指摘と、同じ直し方で解消する指摘は 1 件にまとめる。読み手が違えば原因に近い側を採り、採らなかった側の具体性を本文に取り込む。ある指摘を直すと不要になる指摘は、その指摘にまとめる
- 7 条件の外の指摘は、PR の作者にとって価値のあるものだけを載せる

### ラベル

コメントの先頭に温度感ラベルを付ける。ラベルは、この PR をそのままマージすると、いま何かが壊れるかで決める。7 条件への反例でも、いま何も壊さないものは `[imo]` にする。使うのは次の 4 つだけ。

| ラベル | PR の作者にとっての意味 | 付ける指摘 |
| --- | --- | --- |
| `[must]` | マージ前に対応してほしい | この PR が持ち込み、具体的な入力で、利用者に見える失敗・データの不整合・spec の MUST 違反・認可の不備（他者のデータに届く、権限のない操作ができる）・機密情報の露出が起きるもの。typecheck・lint・テストの失敗 |
| `[imo]` | レビュアーの意見。対応するかは任せる | テストの不足・設計の代案・次の変更を高くつかせる構造など、いま何も壊さないもの。この PR の範囲外の提案 |
| `[nits]` | 些細な指摘。流してもよい | 書き方・命名・文書の誤り |
| `[ask]` | 質問。判断を聞きたい | 契約への指摘、反証でも未観測のままの指摘（テストの不足を除く）、採る側を決められないもの |

### アンカー

- コメントを付けられるのは、`gh pr diff` のハンクの中の行だけ。読みの差分は改名を追わない（`--no-renames`）ので、改名したファイルではハンクが違う
- 範囲で示すときは、同じ side の同じハンクに収める
- ```` ```suggestion ```` は RIGHT にだけ使う。`start_line` から `line` までをそのまま置き換えるので、範囲と中身をそろえる
- 差分外のファイルを指す指摘は、差分内の最も近い原因箇所（呼び出し側など）に寄せる。寄せられない指摘・ハンクに収まらない行・PR 全体への指摘は、レビューの body にまとめる

### 本文

コメントは、submit されると PR の作者がそのまま読む。ラベルに続けて、その行について何が問題で、どう変えるとよいかだけを、次の 3 要素で素の文章にする。

1. 何が起きるか（具体的な条件・入力での結果。経路をまたぐなら「A で〜した値が B で〜になります」）
2. なぜ問題か（1 文。自明なら省く）
3. どうするか（具体案。コードで示せるなら ```` ```suggestion ```` ブロックを使う）

- どうするかは、指摘箇所への局所的な修正ではなく、原因に対する修正として書く。同じ原因が通る経路があれば挙げる
- 口調をラベルに合わせる。`[must]` は何が壊れるかを言い切り、`[imo]` と `[nits]` は提案として、`[ask]` は結論を書き切らずに判断を仰ぐ質問として書く
- PR の範囲を超える指摘は「この PR の範囲外なので別 Issue にしませんか」という提案として書く
- 敬体で書く。断定を避けるべきところは「〜かもしれません」「〜のほうがよさそうです」を使う
- 見出し・箇条書きで飾らない。1 コメント 3〜6 行を目安にし、長くなるなら論点を絞る
- 結果ファイルの文章をそのまま貼らない

書かないもの（レビューの body も同じ）:

- 指摘の ID（`acceptance:3` など）・読み手の名前・条件の番号・件数
- 反例・反証・条件の外・未観測・台帳・契約への指摘・Production Ready といった内部の語
- 進め方への言及（読み手を分けたこと、「レビューの結果」「本スキルでは」）

## 不変条件

- コードを変更しない。書いてよいのは `.thread/{PR番号}/review/` と `{scratchpad}`（`../_shared/references/scratchpad.md`）だけ。コミット・push・submit はしない
  - 読み手と反証も同じ。完了報告の前に `git status --porcelain` を確かめ、`.thread/` 以外に変更があれば、戻さずに報告する
- 既存の Pending レビューを、承認なしに削除しない
- 別 Issue の提案は起票しない。起票が必要になったら、ユーザーの承認後にプロジェクトの規約どおりに行う
- `.thread/{PR番号}/review/` は、ユーザーが Pending を裁くまで残す

## ユーザーに聞く場面

- 着手時に、この PR に自分の Pending レビューがある。件数を伝え、破棄して投稿し直すか中断するかを聞く
- 投稿の前に、PR の head が読んだコミットと違う（読んだ後に PR が更新された、またはローカルに push していないコミットがある）
- 契約を書き出せない、未コミットの変更で checkout できない（`pr-reading.md`）

## 環境の事実

### Pending レビュー

- Pending は投稿者本人にしか見えず、submit するまで通知されない。1 つの PR に 1 人 1 件まで
- `POST repos/{owner}/{repo}/pulls/{PR番号}/reviews` で、`event` を省いたときだけ Pending になる。`event` を付ける、または `gh pr review` を使うと即時投稿になる
- `commit_id` には読んだコミットを渡す。行番号はそのコミットで決めたので、ほかのコミットを渡すと行がずれる
- 行は `line` / `side` で指定する。`position` は使わない
- POST は全件アトミック。アンカーが 1 件でもハンクの外なら 422 で 1 件も投稿されない。`errors[]` から該当コメントを特定し、body に移して再送する
- レビューの一覧は、レビューが多い PR では Pending が後ろのページに来る。`--paginate` を付ける

### ブラウザ観測

UI がある変更では、読み手と反証が `agent-browser` で観測する。コマンドは `../_shared/references/agent-browser.md` に従う。

- namespace は着手時に `agent-browser session id --scope worktree --prefix pr-comment` で 1 回だけ決め、読み手と反証に渡す
- `agent-browser --namespace {ns} close --all` を、最初の読みの前と、完了報告の前に実行する

## 完了報告

```text
Pending コメントを投稿しました（修正は未実施）。

- PR: #{PR番号} {PRタイトル}
- 契約: 受け入れ条件 {数}件（.thread/{PR番号}/review/contract.md）
- ラベル: [must] {数} / [imo] {数} / [nits] {数} / [ask] {数}
- [must]: {なし / `ファイル:行 — 根拠の要約` の列挙}
- body に置いた指摘: {数}件（行に紐づけられなかった理由の要約）
- 載せなかった指摘: {数}件（.thread/{PR番号}/review/excluded.md）
- 読めていない箇所: {なし / `{読み手}: {台帳の項目 / 中断} — {理由}` の列挙}
- 確認: {PR の URL}/files

Pending は自分にしか見えません。内容を確かめ、必要なら編集・削除してから submit してください。載せなかった指摘を加えたいときは指示してください。修正まで進めるなら pr-review を使ってください。
```
