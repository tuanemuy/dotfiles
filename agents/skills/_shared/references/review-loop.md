# レビュー・修正ループ共通ガイド

レビューサイクルの共通構造とレビューの観点を定義する。各スキルのレビューガイドはこの共通構造に従い、担当の分け方とラウンドの遷移を定める。

issue-implement のレビューガイド、pr-review、spec 系のレビュー（`spec-review.md`）から参照される。ラウンドの遷移（何ラウンド回すか・誰を起動するか）は各スキルのガイドが定める。

## コンテキストの原則

**ペイロードではなくポインタを渡す。** レビュアーはツールを持つエージェントなので、対象をプロンプトに詰めず自分で引かせる。

- **対象の全量だけは決定的に渡す** — 差分レビューなら `git diff --no-renames --name-status origin/{ベース}...HEAD` の出力、レイヤー実装のレビューなら台帳（`spec-inventory.md`）。LLM の判断で対象範囲を先に絞らない
  - 差分レビューは**先に対象ブランチへ切り替える**（`...HEAD` で引くので HEAD が違えば全量ごと狂う）。`--stat` はパスを `.../foo.ts` と切り詰めるので使わない
  - `--no-renames` を付ける — `R 旧 新` の1行2パスはカバレッジの1対1照合を壊す
- **同一ラウンドの複数レビュアーが読む共通ペイロードは、親が1回ファイルへ落としてパスで配る** — 差分レビューなら、ラウンド頭に `git diff --no-renames origin/{ベース}...HEAD > {scratchpad}/diff/{番号}-round-{NNN}.diff` で差分本文を書き出し（リダイレクトなので親のコンテキストに乗らない）、レビュアーにはこのパスを渡して `git fetch` / `git diff` の実行を禁じる。各自に引かせると同じ差分が観点の数だけ重複して実行・滞留する。`{scratchpad}` の定義は `scratchpad.md`（同ディレクトリ）
- **判定の基準も渡す** — 「逸脱」の根拠（CLAUDE.md・`spec/`・plan.md・PR 本文）を明示する。基準がないと指摘が主観に流れる
- **何を読むかはレビュアーが決める** — 観点でファイルを割り振らない。レイヤーは**観点**であって分割単位ではなく、呼び出し側・呼び出し先が別レイヤーでも必要なら引く。差分は配られた差分ファイルから担当分をまとめて1回で読ませる（ファイルごとに読み直さない）
- **確認とスキップを両方申告させる** — 親は一覧の各対象に「**確認申告が1体以上あるか**」を突き合わせ、ゼロなら追加レビュアーを1体立てる。スキップ側で突き合わせると申告漏れがすり抜ける
- **本文はメインに往復させない** — レビュアーはレビュー全文をファイルに直接書き、メインには件数と一行リストだけ返す。一行リストの書式は `[B-001] {ファイル:シンボル/カテゴリ} — {タイトル}` — 先頭は指摘台帳の Key そのもの（行番号・タイトルは毎ラウンド変わるため照合に使わない）

## レビューの観点

レビューの目的は、変更が受け入れ条件を満たし、バグも負債も生まないこと。観点はこの目的から引き、全レビュアーが担当範囲の中で全観点を見る。担当（レビュアーの体の分け方）は各スキルのガイドが定め、観点は担当に紐づかない。順序は重要度順で、目的の充足と正しさを構造より先に見る。

### 受け入れ条件

- **目的の充足** — 変更の目的（PR 本文・Issue・plan.md の受け入れ基準）が漏れなく実現されているか。部分実装、目的外の変更の混入、spec からの逸脱

### バグ

- **ロジックの正しさ** — 条件・境界値・エラー経路・null / 空 / 重複・順序・並行・冪等性。「この入力のときどうなるか」を具体値で追い、期待と違う経路を指摘する
- **契約の整合** — ポート定義とアダプター実装、バリデーションスキーマと spec、ドキュメンテーションコメントと実装。必ず両側を突き合わせる
- **性質** — 担当範囲のセキュリティ（認証・認可、入力バリデーション、機密情報）とパフォーマンス（N+1、不要な計算、リソースリーク）

### 負債

- **設計・モデリング** — 不正状態が型で排除されているか（直和型・判別ユニオン。内部の存在チェックや非nullアサーションはモデルが不正状態を許すシグナル。境界での検証は正当）、外部データが境界でデコードされてドメイン型になっているか、状態遷移が明示されているか、副作用が隔離されているか
- **レイヤーと責務** — 依存の向きがアーキテクチャ（CLAUDE.md / spec）に従っているか、ビジネスロジックの置き場所がレイヤーの責務と一致するか、モジュール・関数が1つの責務に閉じているか。過剰な抽象化・早すぎる一般化も負債として指摘する
- **既存資産との整合** — 既存の関数・型・パターンの再実装、規約からの逸脱、デッドコード、不要な依存追加がないか
- **テストの必要十分性** — 受け入れ条件と確認した挙動ごとに、振る舞いを検証するテストが1本あるか。テストが実装詳細に結合していないか。検出力ゼロのアサーション（存在確認のみ・否定のみ）は検証と数えない。テストコードのスタイルには踏み込まない
- **ドキュメント整合** — 差分が触れた・依拠している spec / docs の記述が変更後も正しいか

## 出力フォーマット

レビューの指摘は以下のカテゴリに分類する:

### Blockers（マージ不可の問題）

```text
- **[B-001]** 問題の説明
  - 場所: `ファイルパス:行番号`
  - 理由: なぜ問題か
  - 提案: どう直すべきか
```

### Warnings（改善推奨）

```text
- **[W-001]** 問題の説明
  - 場所: `ファイルパス:行番号`
  - 理由: なぜ気になるか
  - 提案: 改善案
```

### カバレッジ（対象範囲の申告）

```text
- 確認: `パス`, `パス`
- スキップ: `パス` — {観点外と判断した理由を一行で}
```

渡された一覧と**1対1で対応させる**。確認＋スキップの件数が一覧の件数と一致すること。一覧が大きい場合（目安50件超）、スキップはディレクトリ単位でまとめて申告してよい（例: `src/legacy/**` — 観点外）。確認は必ず個別に列挙する — 親は確認側で突き合わせる。

Blocker がなければ「なし」と書く。

### 共通の Blocker 基準

以下は常に Blocker として報告する:

- 設計からの逸脱（spec/ や plan.md の受け入れ基準・スコープとの不整合）
- TODO・FIXME・仮実装が残っている
- テストケース定義のカバレッジ不足（テストレビューの場合）

## レビューファイルのテンプレート

```markdown
# {Layer} Review #{連番}

**Date:** {日付}
**Round:** {N}回目

---

## Summary

- Blockers: {数}
- Warnings: {数}
- Verdict: **BLOCKED**（Blocker 1件以上）/ **APPROVED**（Blocker ゼロ。完了判定は Verdict ではなく台帳の fix ゼロ）

---

{レビュー結果}
```

## 指摘台帳（triage.md）

指摘の仕分け結果は、レビューディレクトリ直下の `triage.md` に一元記録する。指摘 ID（B-001 等）はラウンドごとに振り直されるため、照合キーは **Key（ファイル＋シンボル＋問題カテゴリ）** で正規化する。Key はレビュアーが一行リストの先頭に付けて返す（コンテキストの原則）。

```markdown
| Key | 初出 | 判定 | 理由（一行） | 再指摘 |
|---|---|---|---|---|
| `src/foo.ts:parseUser/エラー処理` | R2 | wont-fix | 境界で検証済み、二重防御は過剰 | 1 |
```

- 判定は `fix`（コード・テスト・挙動に触る修正）/ `fix-editorial`（コメント・ドキュメントの文言のみ。修正 diff がドキュメント行に閉じることが条件）/ `wont-fix`（直さない）/ `defer`（別 Issue #番号 で対応）
- 新ラウンドの指摘はまず台帳と突き合わせる。**Key が完全一致する既出指摘は、文面が違っても判定を継承して再指摘カウントを +1 する。再審議しない**
- 継承できるのは Key の**完全一致だけ**。「同系統」「同じファミリー」「同一箇所への別角度」は新規として審議する
- **台帳の全文を配らない。** 台帳を更新したら、同時に `wont-fix` / `defer` 行の Key・判定・（あれば）Issue番号だけを写した薄いビュー `triage-keys.md` を同じディレクトリに書き出す。レビュアーに渡すのはこちら。全文を渡すのは方針フェーズの1体だけ（台帳はラウンドを追うごとに肥大し、観点数×ラウンド数だけコンテキストに乗る）
- 再指摘カウントが**3に達したら必ずエスカレーションする** — 別 Issue 起票・設計判断としての決着（`adr-guide.md` の置き場所に従って記録）・ユーザー判断のいずれかを行い、リンクを台帳行に記入する。以降の再指摘はリンク先を根拠に継承する
- 毎ラウンド、台帳末尾にラウンドブロックを1行追記する: `R{N}: 新規 {n} / fix {n} / fix-editorial {n} / wont-fix {n} / defer {n} / 継承 {n}（方針フェーズ: 実施 or 省略理由）`
- **ラウンドブロックを書き終えるまで次ラウンドを起動しない**

## 修正ループ

Blocker・Warning がある場合:

1. 指摘を台帳と突き合わせる（既出は判定継承）
2. 新規の指摘は**修正方針フェーズ**で方針を立てる（後述）
3. 方針に沿って修正する。**`fix` は Blocker から優先的に、Warning も残さず修正する** — 修正はサブエージェント（**判断区分**）に委譲する。委譲プロンプトには、対応する台帳の Key・判定行の引用と「CLAUDE.md を最初に読んで規約に従う」指示を必ず含める（ラウンドが進んでも省略しない）。**台帳ファイルのパスは渡さない** — 該当行の引用で足りる
   - 委譲プロンプトには記述の原則も含める: 「ツリーに残るものはすべて現在の挙動を述べる。経緯と証跡は返り値と台帳に置く。理由が要る箇所は本文を一文で書き、その文を真にするコードの行を報告に書く」。ツリーに残った経緯や実装と食い違う文は、次ラウンドの指摘になる
   - 委譲プロンプトには「修正の受け取り条件」（後述）の 3 項目を返り値として要求し、修正設計が成り立たないと判断したら修正せず異議を返してよいことも伝える
4. 返り値を「修正の受け取り条件」に照らし、満たすまで受け取らない
5. 修正後、品質ゲートを実行する（typecheck + lint + build。build コマンドは CLAUDE.md / package.json から取る。テストレビューの場合は + test run）
6. 再レビュー（次の連番ファイルを作る）

### 修正の受け取り条件

修正担当の返り値に次の 3 つが揃っていない修正は**未修正として扱う**。台帳のラウンドブロックを書かず、欠けた項目だけを同じ担当に再委譲する。再委譲は 2 回まで。3 回目も揃わなければ中断と同じ扱い（その指摘を台帳に「未受け取り」と記録し、ループを止めてユーザーに報告する）。証跡の無い修正は、次ラウンドで修正そのものへの指摘（新しいテストの検出力・書いた文の真偽・直し残した経路）になる。

1. **変異の証跡** — 追加・変更したテストごとに、赤くしたテスト名と入れた変異（条件反転・境界±1・ガード削除のいずれか）。修正設計の「守る挙動」を主張するテストは必ず含める。変異で赤くならないテストは検出力が無いので、直してから返す。テストに触れていなければ「テスト変更なし」と書く
2. **同根の経路** — 修正設計の「及ぶ経路」の各項目について「直した」か「該当しない（理由を一言）」。設計に無い経路を見つけたら追加して同じように書く
3. **記述の根拠** — 書いた・書き換えたコメント・spec・docs の文ごとに、その文を真にするコードの行。根拠を示せない文は書かない

方針フェーズを省略したラウンド（fix-editorial のみ）では 3 だけを求める。

**修正設計への異議**は 3 項目の代わりになる。「守る挙動」が成り立たない、「形」が CLAUDE.md や既存の型と衝突する、「及ぶ経路」の前提がコードと違う — 修正担当がそう判断したら、修正せずに食い違いの内容と根拠の行を返す。メインは異議を要確認として扱い、自分で決めるかユーザーに委ねる。異議を出さずに設計どおり書けば偽の修正になり、異議を出さずに設計から逸れれば次ラウンドの指摘になる。

### 修正方針フェーズ

指摘を個別にサブエージェントへ投げる前に、そのラウンドの指摘**全体**を1体（**審査区分**）に横断で読ませて方針を立てさせる。メインは一行リストしか持たず、レビュアーは互いの指摘を知らないため、全文を俯瞰する視点はここにしか作れない。

**メイン単独で下せる判定は `fix` / `fix-editorial` と Key 完全一致の継承だけ。** 新規指摘を直さない判定（wont-fix / defer）は、このフェーズかユーザーの承認を必ず通す — 収束が近いことは省略の理由にならない。

**省略条件**: 新規指摘のすべてが `fix-editorial`（文言のみ）か、変異証跡の規則で `wont-fix` になるものなら、メインが直接仕分けてよい。**挙動・型・契約・テストに触る `fix` が 1 件でもあればフェーズを立てる。** 設計なしの修正は次ラウンドの指摘になり、方針体 1 体より高くつく。省略しても台帳の更新は省略しない。

渡すもの: そのラウンドの全レビューファイル、台帳、設計の契約（`plan.md` / `spec/` など）。

返させるもの:

- 各指摘の妥当性判定（`fix` / `fix-editorial` / `wont-fix` / `defer`）と一行理由。的外れな指摘・過度に防御的な提案はここで落とす。修正がコメント・ドキュメンテーションコメント・spec / docs の文章・テスト名の記述に閉じ、コードの振る舞い・型・アサーションに触れないものは `fix-editorial`
- 前ラウンドの修正担当が変異の証跡を付けたテストへの検出力の指摘（アサーションの形・否定形・重複）は、証跡を覆す実測（レビュアー自身が変異を入れて緑のままだった）が無ければ `wont-fix`。読解の指摘は実測の証跡に勝たない。テストが主張する挙動が修正設計の「守る挙動」と一致しないという指摘は**主張の中身の指摘**で、この規則の対象外。変異で赤くなることは、正しい挙動を主張している証明にならない
- UI の操作結果（フォーカス・遷移・表示）や外部ライブラリの挙動を読解だけで断定した指摘（レビューファイルに「未観測」とあるもの）は、`fix` にする前に再現する。再現できないものは `wont-fix`
- 指摘どうしの関係を踏まえた**修正の実行計画** — 同じ箇所や同じ原因に紐づく指摘はまとめ、依存があれば順序をつける。逆方向を要求する指摘が並んでいればどちらを採るかも決める
- `fix` にした Key ごとの**修正設計**（後述）
- 判断が割れるもの・トレードオフや spec の変更を伴うものは「要確認」として上げる

#### 修正設計

指摘を 1 件ずつ直すと、次の 3 つが次ラウンドの指摘になる: 直し残した同根の経路、既存の設計と噛み合わない修正、修正が持ち込んだコードを守らないテスト。修正設計は、そのラウンドの指摘全体と設計の契約（`plan.md` / `spec/` / CLAUDE.md）を俯瞰して、修正が既存の構造にどう収まるかを先に決める。妥当性判定が指摘を受け入れるかを決め、修正設計がどう直すかを決める。

方針フェーズは `fix` の Key ごとに次の 3 点に答える。メインは修正担当への委譲プロンプトに転記し、「修正の受け取り条件」の照合先にする。

1. **守る挙動** — 修正後に成り立つ挙動を一文で（「閉じる経路はすべて `closePresetForm` を通る」「検証スキーマは空文字を先に弾く」）。修正担当はこの挙動を主張するテストを置く。実装から期待値を生成するテストは主張にならない
2. **及ぶ経路** — 同じ原因が通る経路を grep で列挙する（同じハンドラ・同じ状態遷移・同じ写し・同じスキーマのコピー）。修正担当はこの全部を直すか「該当しない」と返す
3. **形** — 型・契約・集約先に触るなら、既存の設計に収まる形（判別ユニオンか任意 props か、集約先のモジュール、検証の順序）。CLAUDE.md・`docs/` の規約に反する形は通さない

方向（採る側・採らない側、spec を変えるか）が割れる Key は修正設計を書かず、要確認に上げる。

メインは方針を承認して台帳に記録し、実行計画の単位で委譲する。**要確認はメインが決めるか、ユーザーに判断を委ねる** — 方向の判断を方針体に決めさせない。設計判断を伴った決定は記録する（「設計判断の記録」参照）。

「承認」は再審議ではない（メインは全文を読まないため材料がない）。チェックするのは4点だけ: 要確認の裁定 / `wont-fix` の理由が台帳の基準を満たすか / 委譲単位が重なっていないか（同じファイルを2体に触らせない）/ `fix` の全 Key に修正設計が付いているか（無い Key は委譲しない）。

委譲の単位は実行計画に従う。レビューのレイヤー分割を修正の分割に流用しない — レビューは観点が重なってよいが、修正が重なると上書き・二重実装が起きる。修正どうしの矛盾は次ラウンドのゼロベースレビュー（累積差分の全量が対象）で検出する。

### 対応しない場合（wont-fix）

誤った指摘・過度に防御的な提案・場当たり的に直すより設計を見直すべき指摘は修正せず、台帳に一行理由を記録する。設計の見直しが必要なものは別 Issue も起票する。

### 後回しにする場合（defer、最終手段）

どうしてもスコープ外でしか対応できない場合のみ、`gh issue create` で別 Issue を起票し、台帳に Issue 番号を記録する。

### 設計判断の記録

指摘への対応要否の記録は台帳の役割で、設計判断の記録とは分ける。仕分けの過程で設計判断を下した場合は、経緯を作業ログ（`.thread/{番号}/adr.md`）に追記して台帳の理由欄からリンクする。作業ログが既定の置き場所で、spec / docs / CLAUDE.md への昇格はここでは判定しない（`adr-guide.md`（同ディレクトリ）の昇格ゲート）。

指摘が既決の判断（spec の記述や作業ログのエントリ）と矛盾する場合、記録の存在を理由に自動で `wont-fix` にしない — 前提が今も真かを確認し、崩れていれば再検討を要確認に上げる（`adr-guide.md`）。

## 完了条件

**そのラウンドで `fix` と仕分けた指摘がゼロ**になったらレビュー完了。`fix-editorial` はその場で適用して品質ゲートが通れば完了を妨げない（同じ記述の正本と写しは両方直す — 片方だけ直すと次ラウンドの指摘になる）。台帳に `wont-fix` / `defer` を記録済みの指摘は件数に含めない（Blocker・Warning とも）。フレッシュなレビュアーが毎回新しく出す既出の再指摘は、台帳の判定継承で吸収して収束させる。

**`fix` を修正したラウンドは最終ラウンドにできない** — 修正の後は、各スキルのガイドが定めるラウンド（全量ラウンドか、修正増分だけを見るスコープラウンド）で fix ゼロを観測してから完了する。完了宣言には台帳の最終ラウンドブロックをそのまま引用する（台帳が書けていなければ完了は宣言できない）。

各スキルが定めるラウンド上限に達しても fix ゼロのラウンドを観測できなかった場合、**収束扱いにしない** — 「傾向として収束している」は完了の根拠にならない。残っている指摘をまとめてユーザーに報告し、判断を委ねる。

## 後片付け

完了条件を満たしたら、レビューディレクトリ（レビューファイル＋台帳）は役目を終える。指摘はすべてコードに反映済みか、台帳の判定（wont-fix / defer）として決着している。残したままにすると、後続セッションの検索に紛れ込んでコンテキストを浪費するため削除する。

- 呼び出し元スキルが片付けフェーズを定義している場合（issue-implement / implement 等のオーケストレーター）はそれに従う — 再実装ループで台帳の判定を引き継ぐため、レイヤー・ラウンド単位では削除しない
- スキル単体で呼ばれた場合は、完了報告の前にレビューディレクトリを削除する
- **ラウンド上限に達して収束しなかった場合は削除しない** — ユーザーが残指摘を確認するために残す
- 削除前に、defer で起票した Issue 番号が完了報告に載っていることを確認する（台帳が消えても追跡先が残るように）
- 削除前に台帳の `wont-fix` 行を確認する。「指摘が誤りだった」ものはそのまま消してよいが、「指摘は正しいが意図的に逸脱している」ものは、台帳ごと消すと後続の監査・レビューで同じ箇所が永遠に再指摘される。恒久的な逸脱は削除前に、現場の why not コメントに転記する（今回の変更を越えて効く逸脱だけ、`adr-guide.md` の昇格ゲートに照らして spec / docs に上げる）
- 作業ログ（`.thread/{番号}/adr.md`）は設計判断の経緯なので削除しない

## サブエージェントの運用原則

委譲方式（サブエージェント / OSプロセス / 親内シミュレート）の判定・並列化・モデル選択の原則は `subagent-policy.md` に従う。

レビュー固有の原則:

- **レビューと方針立案は審査区分、修正は判断区分**。見落としがそのままマージされるため、軽量モデルに落とさない
- **中断した委譲先の作業をメインが引き取らない**（`subagent-policy.md` の「中断時の再委譲」）。レビュアーが中断したらその観点だけ再委譲し、3回目で諦める場合は「その観点は未実施」とラウンドサマリーに明記する（指摘ゼロと混同しない）。修正の委譲先が中断した場合は必ず再委譲する — 修正は必須作業なので、欠けたまま再レビューに進むと同じ指摘が既出扱いで継承され、直っていないのに収束したように見える
- **中断は完了条件を満たさない**。中断で fix が適用されなかったラウンドを「fix ゼロ」と数えない

- レビューは**厳しく**行う。「まあいいか」は禁止。ただし的外れな指摘はしない
- **全観点の共通チェック** — テスト観点は常設しない。各レビュアーが自分の観点で確認した挙動について、振る舞いを検証する実効的なテストで守られているか（アサーションが形骸化していないか）を見る。あわせて、指摘への弁明・修正の経緯など残す必要のない記述がコード・コメントに含まれていないかも見る。テストコードのスタイル・構造の磨き込みは指摘しない
- 修正するのは確信を持てるものだけ。判断に迷うものはユーザーに聞く
- **各ラウンドのレビューは独立して行う** — 前回の指摘を前提にせず、ゼロからレビューする
- レビューファイルは追記ではなく、毎ラウンド新規作成する（履歴が残る）
