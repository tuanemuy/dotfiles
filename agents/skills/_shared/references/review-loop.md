# レビュー・修正ループ共通ガイド

レビューサイクルの共通構造を定義する。各スキルのレビューガイドはこの共通構造に従いつつ、レイヤー固有のレビュー観点を追加する。

issue-implement のレビューガイドや implement-* サブスキルのレビューガイドから参照される。

## コンテキストの原則

**ペイロードではなくポインタを渡す。** レビュアーはツールを持つエージェントなので、対象をプロンプトに詰めず自分で引かせる。

- **対象の全量だけは決定的に渡す** — 差分レビューなら `git diff --no-renames --name-status origin/{ベース}...HEAD` の出力、レイヤー実装のレビューなら台帳（`spec-inventory.md`）。LLM の判断で対象範囲を先に絞らない
  - 差分レビューは**先に対象ブランチへ切り替える**（`...HEAD` で引くので HEAD が違えば全量ごと狂う）。`--stat` はパスを `.../foo.ts` と切り詰めるので使わない
  - `--no-renames` を付ける — `R 旧 新` の1行2パスはカバレッジの1対1照合を壊す
- **判定の基準も渡す** — 「逸脱」の根拠（CLAUDE.md・`spec/`・plan.md・PR 本文）を明示する。基準がないと指摘が主観に流れる
- **何を読むかはレビュアーが決める** — 観点でファイルを割り振らない。レイヤーは**観点**であって分割単位ではなく、呼び出し側・呼び出し先が別レイヤーでも必要なら引く
- **確認とスキップを両方申告させる** — 親は一覧の各対象に「**確認申告が1体以上あるか**」を突き合わせ、ゼロなら追加レビュアーを1体立てる。スキップ側で突き合わせると申告漏れがすり抜ける
- **本文はメインに往復させない** — レビュアーはレビュー全文をファイルに直接書き、メインには件数と一行リストだけ返す。一行リストの書式は `[B-001] {ファイル:シンボル/カテゴリ} — {タイトル}` — 先頭は指摘台帳の Key そのもの（行番号・タイトルは毎ラウンド変わるため照合に使わない）

## 出力フォーマット

レビューの指摘は以下のカテゴリに分類する:

### Blockers（マージ不可の問題）

```text
- **[B-001]** 問題の説明
  - 場所: `ファイルパス:行番号`
  - 理由: なぜ問題か
  - 提案: どう直すべきか
```

### Warnings（改善推奨）

```text
- **[W-001]** 問題の説明
  - 場所: `ファイルパス:行番号`
  - 理由: なぜ気になるか
  - 提案: 改善案
```

### カバレッジ（対象範囲の申告）

```text
- 確認: `パス`, `パス`
- スキップ: `パス` — {観点外と判断した理由を一行で}
```

渡された一覧と**1対1で対応させる**。確認＋スキップの件数が一覧の件数と一致すること。一覧が大きい場合（目安50件超）、スキップはディレクトリ単位でまとめて申告してよい（例: `src/legacy/**` — 観点外）。確認は必ず個別に列挙する — 親は確認側で突き合わせる。

Blocker がなければ「なし」と書く。

### 共通の Blocker 基準

以下は常に Blocker として報告する:

- 設計からの逸脱（spec/ や plan.md の受け入れ基準・スコープとの不整合）
- TODO・FIXME・仮実装が残っている
- テストケース定義のカバレッジ不足（テストレビューの場合）

## レビューファイルのテンプレート

```markdown
# {Layer} Review #{連番}

**Date:** {日付}
**Round:** {N}回目

---

## Summary

- Blockers: {数}
- Warnings: {数}
- Verdict: **BLOCKED**（Blocker 1件以上）/ **APPROVED**（Blocker ゼロ。完了判定は Verdict ではなく台帳の fix ゼロ）

---

{レビュー結果}
```

## 指摘台帳（triage.md）

指摘の仕分け結果は、レビューディレクトリ直下の `triage.md` に一元記録する。指摘 ID（B-001 等）はラウンドごとに振り直されるため、照合キーは **Key（ファイル＋シンボル＋問題カテゴリ）** で正規化する。Key はレビュアーが一行リストの先頭に付けて返す（コンテキストの原則）。

```markdown
| Key | 初出 | 判定 | 理由（一行） | 再指摘 |
|---|---|---|---|---|
| `src/foo.ts:parseUser/エラー処理` | R2 | wont-fix | 境界で検証済み、二重防御は過剰 | 1 |
```

- 判定は `fix`（このスコープで直す）/ `wont-fix`（直さない）/ `defer`（別 Issue #番号 で対応）
- 新ラウンドの指摘はまず台帳と突き合わせる。**Key が一致する既出指摘は、文面が違っても判定を継承して再指摘カウントを +1 する。再審議しない**
- `fix` 済みの箇所が別角度から**3回以上**再指摘されたら、個別修正で追いかけず設計の問題として扱う — 別 Issue を起票するかユーザーに判断を委ねる

## 修正ループ

Blocker・Warning がある場合:

1. 指摘を台帳と突き合わせる（既出は判定継承）
2. 新規の指摘は**修正方針フェーズ**で方針を立てる（後述）
3. 方針に沿って修正する。**`fix` は Blocker から優先的に、Warning も残さず修正する** — 修正はサブエージェント（**判断区分**）に委譲する
4. 修正後、品質ゲートを実行する（typecheck + lint、テストレビューの場合は + test run）
5. 再レビュー（次の連番ファイルを作る）

### 修正方針フェーズ

指摘を個別にサブエージェントへ投げる前に、そのラウンドの指摘**全体**を1体（**判断区分**）に横断で読ませて方針を立てさせる。メインは一行リストしか持たず、レビュアーは互いの指摘を知らないため、全文を俯瞰する視点はここにしか作れない。

**省略条件**: 新規指摘が**2件以下**で、互いに独立（別ファイル・別原因）かつ判定が自明なら、メインが直接仕分けてよい。関係が疑わしければ（同じ箇所・逆方向の提案・設計判断を含む）フェーズを立てる。

渡すもの: そのラウンドの全レビューファイル、台帳、設計の契約（`plan.md` / `spec/` など）。

返させるもの:

- 各指摘の妥当性判定（`fix` / `wont-fix` / `defer`）と一行理由。的外れな指摘・過度に防御的な提案はここで落とす
- 指摘どうしの関係を踏まえた**修正の実行計画** — 同じ箇所や同じ原因に紐づく指摘はまとめ、依存があれば順序をつける。逆方向を要求する指摘が並んでいればどちらを採るかも決める
- 判断が割れるもの・設計判断を伴うものは「要確認」として上げる

メインは方針を承認して台帳に記録し、実行計画の単位で委譲する。**要確認はメインが決めるか、ユーザーに判断を委ねる** — 方針を立てた側に設計まで決めさせない。設計判断を伴った決定は ADR に起こす。

「承認」は再審議ではない（メインは全文を読まないため材料がない）。チェックするのは3点だけ: 要確認の裁定 / `wont-fix` の理由が台帳の基準を満たすか / 委譲単位が重なっていないか（同じファイルを2体に触らせない）。

委譲の単位は実行計画に従う。レビューのレイヤー分割を修正の分割に流用しない — レビューは観点が重なってよいが、修正が重なると上書き・二重実装が起きる。修正どうしの矛盾は次ラウンドのゼロベースレビュー（累積差分の全量が対象）で検出する。

### 対応しない場合（wont-fix）

誤った指摘・過度に防御的な提案・場当たり的に直すより設計を見直すべき指摘は修正せず、台帳に一行理由を記録する。設計の見直しが必要なものは別 Issue も起票する。

### 後回しにする場合（defer、最終手段）

どうしてもスコープ外でしか対応できない場合のみ、`gh issue create` で別 Issue を起票し、台帳に Issue 番号を記録する。

### ADR との使い分け

ADR に書くのは**プロダクトとしての設計判断だけ**。指摘への対応要否の記録には使わない（それは台帳の役割）。仕分けの過程で設計判断を下した場合のみ ADR に起こし、台帳の理由欄からリンクする。

指摘が既存 ADR と矛盾する場合、ADR の存在を理由に自動で `wont-fix` にしない — 前提が今も真かを確認し、崩れていれば supersede 提案として要確認に上げる（`adr-guide.md`）。

書き先は作業スコープに従う: Issue / PR 単位の作業では作業ログ（`.thread/{番号}/adr.md`）に追記し、プロジェクトスコープの作業では `.adr/` に直接書く。記録基準と昇格の流れは `adr-guide.md`（同ディレクトリ）を参照。

## 完了条件

**そのラウンドで `fix` と仕分けた指摘がゼロ**になったらレビュー完了。台帳に `wont-fix` / `defer` を記録済みの指摘は件数に含めない（Blocker・Warning とも）。「0件」を文字通り待つのではなく、フレッシュなレビュアーが毎回新しく出す主観的な指摘や既出の再指摘は、台帳の判定継承で吸収して収束させる。

修正した指摘が1件でもあれば再レビューする。最大ラウンド数に達しても収束しない場合は、残っている指摘をまとめてユーザーに報告し、判断を委ねる。

## 後片付け

完了条件を満たしたら、レビューディレクトリ（レビューファイル＋台帳）は役目を終える。指摘はすべてコードに反映済みか、台帳の判定（wont-fix / defer）として決着している。残したままにすると、後続セッションの検索に紛れ込んでコンテキストを浪費するため削除する。

- 呼び出し元スキルが片付けフェーズを定義している場合（issue-implement / implement 等のオーケストレーター）はそれに従う — 再実装ループで台帳の判定を引き継ぐため、レイヤー・ラウンド単位では削除しない
- スキル単体で呼ばれた場合は、完了報告の前にレビューディレクトリを削除する
- **最大ラウンド数に達して収束しなかった場合は削除しない** — ユーザーが残指摘を確認するために残す
- 削除前に、defer で起票した Issue 番号が完了報告に載っていることを確認する（台帳が消えても追跡先が残るように）
- 削除前に台帳の `wont-fix` 行を確認する。「指摘が誤りだった」ものはそのまま消してよいが、「指摘は正しいが意図的に逸脱している」ものは、台帳ごと消すと後続の監査・レビューで同じ箇所が永遠に再指摘される。恒久的な逸脱は削除前に、現場の why not コメントか ADR（`adr-guide.md` の記録基準で判定）に転記する
- ADR（`.adr/` や adr.md）は設計判断の記録なので削除しない

## サブエージェントの運用原則

委譲方式（サブエージェント / OSプロセス / 親内シミュレート）の判定・並列化・モデル選択の原則は `subagent-policy.md` に従う。

レビュー固有の原則:

- **レビューと修正はいずれも判断区分**。見落としがそのままマージされるため、軽量モデルに落とさない

- レビューは**厳しく**行う。「まあいいか」は禁止。ただし的外れな指摘はしない
- 修正するのは確信を持てるものだけ。判断に迷うものはユーザーに聞く
- **各ラウンドのレビューは独立して行う** — 前回の指摘を前提にせず、ゼロからレビューする
- レビューファイルは追記ではなく、毎ラウンド新規作成する（履歴が残る）
