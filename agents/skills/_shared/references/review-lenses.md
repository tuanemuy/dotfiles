# レビューの観点

レビューの目的は、変更が受け入れ条件どおりに振る舞い、負債を生まないこと。観点は**振る舞い**と**構造**の 2 軸と、その外にある**規約**に分かれる。3 つとも原則を一文で置き、その原則から導いたルールを並べる。ルールにない事象でも原則に当たれば指摘する。振る舞いを構造より先に見る。

## 振る舞い

原則: 変更は受け入れ条件どおりに動き、その動きはテストで固定されている。

基準（PR 本文・Issue・plan.md の受け入れ基準・spec）、実装、テストの 3 つを一本の線で突き合わせる。

- 経路を具体値で追う
  - 経路が分かれるところ（境界値・エラー・null / 空・重複・順序・並行・再実行）ごとに、具体値を入れて結果まで辿り、基準と違う経路を指摘する
  - 認可は、誰が何をしてよいかを定める業務ルールとして同じ方法で追う
- 契約は両側を読む
  - ポート定義とアダプター実装、バリデーションスキーマと spec、ドキュメンテーションコメントと実装のように両側があるものは、片側だけ読んで整合を判定しない
- 挙動ごとに固定するテストがある
  - 受け入れ条件と確認した挙動それぞれに、その振る舞いを主張するテストが 1 本ある
  - 検出力は変異（条件反転・境界±1・ガード削除）で赤くなるかで判定する
  - 実装から期待値を生成するテストと、実装詳細に結合したテストは固定と数えない
  - テストコードのスタイルには踏み込まない
- 基準の誤りは契約への指摘として分ける
  - 受け入れ基準が条件の片側しか書いていない、前提が設定やビルド定義と食い違う、といった誤りが当たる
  - 基準の誤りはコードを基準に照らしても出ないので、コードへの指摘と混ぜない

## 構造

原則: 負債とは次の変更のコストを上げる構造であり、変更は負債を持ち込まない。

判定の基準は CLAUDE.md / spec のアーキテクチャと既存コードのパターン。

- 不正状態は型で排除する
  - 直和型・判別ユニオンで表現できる状態を、任意プロパティの組み合わせで許していないか
  - 内部の存在チェックや非 null アサーションは、モデルが不正状態を許しているシグナル
  - 境界での検証は正当
- 外部データは境界でデコードしてドメイン型にする
  - 境界を越えた後に生の文字列や unknown が流れていないか
- 状態遷移は明示し、副作用は隔離する
  - 遷移がどこで起きるか追えるか
  - 純粋な計算と I/O が分かれているか
- 依存の向きはアーキテクチャに従う
  - 内側のレイヤーが外側を知らないか
  - ビジネスロジックがレイヤーの責務どおりの場所にあるか
- モジュール・関数は 1 つの責務に閉じる
  - 変更理由が複数あるものは分ける
- 同種のロジックは 1 か所に集約する
  - 既存の関数・型・パターンの再実装や、同じ処理の散らばりは集約先を示して指摘する
- 抽象化は必要になった時点で入れる
  - 使い手が 1 つしかない抽象、将来のための一般化は負債

## 規約

原則: 判定の根拠が変更の外にある既知のルールにあり、挙動を理解しなくても照らせば判定できる。

- 言語・フレームワークの慣用に従っているか
- CLAUDE.md のプロジェクト規約に従っているか
- 既知のアンチパターン（入力の未検証、機密情報の露出、N+1、リソースリーク）がないか
- アサーションが存在確認や否定だけになっていないか
- デッドコード・不要な依存がないか
- 差分が触れた・依拠している spec / docs の記述が変更後の実装を述べているか
- 指摘への弁明や修正の経緯がコード・コメントに残っていないか
