# Production Ready

変更をマージしてよい状態の定義。

Production Ready とは、次の 7 つが成り立ち、それぞれを根拠で示せること。成り立つとは反例が無いこと。7 つは同じ硬さで扱う。5 と 6 の反例はいま何も壊さないが、見送る理由にならない。

6 と 7 は、変更が UI を持つときだけ問う。

## 契約と反例

契約は、変更の目的・受け入れ条件・スコープを書いたもの。置き場所と書き方は、使う側が定める。

反例は、場所（`ファイル:行`）と、そこで条件が破れていることを示す事実を伴い、条件ごとに決まった形を取る。形を取れない指摘は 7 条件の外の指摘として扱う。

事実は、実環境で起こる状態についてのもの。応答の差し替えやデータの直接投入など、実環境と違う状態を作って観測したものは、その状態が実環境で起こりうるとコードで示すまで事実にならない。

7 条件が問うのは、この変更が持ち込んだものだけ。変更の前からある問題は 7 条件の反例ではない。

## 1. 受け入れ条件を満たしている

- 受け入れ条件は変更の意図から決まり、実装からは決まらない
- 各受け入れ条件は観測方法（`browser` / 自動テスト / コマンド出力）を持つ
- TODO・FIXME・スタブ・部分実装が残っていない

根拠: 受け入れ条件ごとの、それを満たすコードと観測結果

反例の形: 受け入れ条件の引用と、それを満たさない具体的な入力と結果。残っている TODO・スタブはその箇所

## 2. すべての振る舞いがテストされている

- この変更が足した・変えた振る舞いごとに、その挙動を主張するテストがある
- 振る舞いは、受け入れ条件の正常系に加え、経路が分かれるところ（境界値・エラー・null / 空・重複・順序・再実行・認可）を含む
- 実装から期待値を生成するテスト、実装の詳細に結合したテスト、存在確認や否定だけのアサーションは数えない

根拠: 振る舞いとテストの対応、変異（条件反転・境界±1・ガード削除）で赤くなった記録

反例の形: 足した・変えた振る舞いと、それを主張するテストが無いこと、または変異を入れても赤くならないこと

## 3. 既存の振る舞いを壊していない

- 変更が届く先で、意図した変更以外の振る舞いが変わっていない。届く先は次の 3 つ
  - 変えた関数・型・コンポーネントの呼び出し元
  - 削除・改名した名前（export・クエリキー・ルート・環境変数名・API パス）の参照元
  - 共有する状態やスタイル
- 既存テストが守っていない届く先は、テストを足すか実測する

根拠: 既存テストの全通過、届く先の一覧と各々の確かめ方

反例の形: 届く先と、意図しない振る舞いの変化を示す具体的な入力と結果

## 4. プロジェクトの規約に従っている

- `CLAUDE.md`・`docs/`・既存コードのパターン・言語とフレームワークの慣用に従っている
- typecheck・lint・build が通る（コマンドは `CLAUDE.md` / `README` / `package.json` から取る）
- 既知のアンチパターン（入力の未検証・機密情報の露出・N+1・リソースリーク）がない
- デッドコード・不要な依存がない
- 差分が触れた・依拠した spec / docs（`spec/design/` を含む）の記述は変更後の実装を述べている
- 触れたファイルのコメントはドキュメンテーションと why / why not だけ（`../../comment-cleanup/SKILL.md`）。弁明や修正の経緯を残さない

根拠: ゲートの実行結果

反例の形: 照らした規約の引用（`CLAUDE.md`・`docs/` の記述、または既存コードの同じ種類の書き方とその件数）と、そこから外れている箇所。ゲートの失敗は、その出力

## 5. 新たな負債を生まない美しい設計である

問うのは、この差分の後に次の変更が前より高くつかないか。判定の原則は `design-principles.md` に従う。プロジェクトが書いたルール（層の置き場所・依存の向きなど）への準拠は 4 が見る。

根拠: 次に来そうな変更を 1 つ想定して、その差分がどこまで広がるかを述べられること。非自明な判断があれば、その経緯が残っていること

反例の形: 想定した次の変更と、その変更の差分がこの差分の前より広がること。既存の書き方をそのまま使うものは、前より広がらない

## 6. 説明に頼らず操作でき、プロジェクトのデザインと一貫した洗練された UI である

- 何ができて、操作すると何が起きるかが、説明文なしに画面から読める
- 見た目はデザイントークンとデザイン方針（`spec/design/`）から取り、同種の既存画面と置き方・言い回しが揃っている
- 対象のビューポート（`CLAUDE.md` / `spec/design/` が定める。無ければ契約に書く）すべてで、見切れ・重なり・届かない操作がない

根拠: 対象ビューポートごとの観測、比べた既存画面

反例の形: ビューポートと操作、そこで観測した見切れ・重なり・届かない操作。または比べた既存画面と、揃っていない置き方・言い回し

## 7. ユーザーに見える振る舞いを実際に観測できている

- 対象は `browser` の受け入れ条件と、2 で挙げた振る舞いのうち結果がユーザーに見えるもの（エラー表示・バリデーション・空状態・権限なし・二重送信・再読み込み後の状態）
- 実機の観測が期待結果と一致して全 PASS
- 期待結果は契約と spec から決まり、観測した画面からは決まらない
- テストが通ることは、画面に出ることの根拠にならない
- 観測は対象のビューポートで行う

根拠: 観測した振る舞いごとの期待と実際、証跡（スクリーンショット、FAIL があればその録画）

反例の形: 観測した振る舞いの期待と実際の食い違い、または観測していない対象
