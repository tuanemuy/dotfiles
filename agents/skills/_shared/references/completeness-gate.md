# 完全性ゲート（レイヤー単位）

実装フェーズの直後・レビューサイクルの前に、実装したレイヤーに省略がないことを検証するゲート。各 implement-* スキルの「実装」と「レビューサイクル」の間で実行する。

## なぜこのゲートが必要か

typecheck + lint は型・構文しか見ない。スタブ（`return []`/固定値）・ダミーデータ・部分実装・spec 機能のまるごと未実装は型が通るため素通りする。だから完全性は別の手段で担保する必要がある。

- **レイヤー単位で前倒しする:** 省略をレイヤーごとに潰せば、後続が未完成の基盤の上に積み上がらない。最終段の implement-audit まで持ち越すと、実装当時のコンテキストが失われて再実装が高コストになる。
- **独立した検証者に任せる:** 実装者自身は自分の省略を「仕様の範囲外」「ダミーで十分」と正当化しがち。ゼロベースの独立したサブエージェントに「何が欠けているか」を探させて捉える（find → adversarially verify）。
- **列挙は台帳に任せる:** 検証者にその場で spec 要素を列挙させると、列挙自体が漏れたときにどの裏取りでも検出できない。列挙は永続化された台帳（`spec-inventory.md`）が担い、検証者は台帳の各行の裏取りだけを行う。

## 入力

- 対象レイヤー（domain / adapter / usecase / test / frontend）
- そのレイヤーの spec（`spec/domains/`、`spec/usecases/`、`spec/pages/`、`spec/testcases/` 等。adapter レイヤーは `spec/domains/` のポート定義が spec にあたる）
- そのレイヤーの台帳 `spec/inventory/{layer}.md`（`spec-inventory.md` 参照。なければ手順 2 の冒頭で生成する）
- 実装したファイル群
- 実装サブエージェントが出力した**カバレッジ表**（spec 要素 → 実装箇所 → 状態）

## 手順

### 1. パターンスキャン（機械的・安価）

`../../implement-audit/references/detection-patterns.md` に定義されたパターンで、**対象レイヤーのファイルだけ**を Grep する（**探索区分**）。TODO/FIXME、`not implemented` 系、`return []`/`return {}` の固定返し、「省略」「ここに〜を追加」等のコメントを検出する。偽陽性フィルタ（テストファイル内の mock/stub、生成ファイル等）は同ドキュメントに従う。

### 2. spec 照合（網羅性）— 最重要

**台帳の確認。** `spec/inventory/{layer}.md` が存在するか確認する。なければ、または spec が台帳の最終同期より後に変更されていれば、`spec-inventory.md` の生成手順（クロスチェック含む）に従って先に台帳を用意する。

**裏取り。** 独立したサブエージェント（**判断区分** — 意図的な設計と省略の区別を伴うため軽量モデルに落とさない）を起動し、台帳の各行が実装に存在し、かつスタブでないことを裏取りさせる。検証者に要素を列挙させてはいけない — 列挙は台帳が担い、検証者は行単位の判定に専念する。行数が多い場合は行を分割して複数サブエージェントに並列で振ってよい（1 体あたり 20〜30 行が目安。全行がどれかの検証者に割り当てられていることを親が機械的に確認する）。実装者のカバレッジ表は参考情報として渡すが、判定は必ず実コードで行わせる。

```markdown
あなたは実装の完全性を検証する独立した監査エンジニアです。実装した本人ではないため、忖度せず「何が欠けているか」を探してください。

## 前提
- まずプロジェクトルートの CLAUDE.md を読み、構成・規約を把握する

## 対象
- レイヤー: {domain/adapter/usecase/test/frontend}
- 検証対象の台帳行（この全行を 1 行も飛ばさず判定する）: {台帳から担当行を貼る（ID・要素・定義場所・要点）}
- 実装ファイル: {実装したファイル群}
- 実装者が申告したカバレッジ表（参考。鵜呑みにしない）: {カバレッジ表を貼る}

## やること
台帳の各行について、定義場所の spec を読んで期待される振る舞いを把握し、実装コードを Read で開いて判定する:
- 要素が実装に存在するか（存在しない = まるごと未実装）
- 設計で要求された振る舞いが実装されているか、それともスタブか
  （`return []`/固定値、ダミーデータ、空ボディ、`not implemented` 系はスタブ）
- CRUD・分岐・エラー処理・バリデーション等が一部だけで残りが省略されていないか

## 重要
- 構文が通ること（typecheck/lint がパスすること）は完全性の証明にならない。中身を見て判定する
- 意図的な設計（抽象メソッド、空実装が正しいケース）と省略を区別する。判断に迷うものは「要確認」とする
- **定義場所を開いても対応する記述が spec に見つからない行は「実体なし疑い」とする。**「未実装」と判定してはいけない（spec にない実装を要求することになる）
- 担当行以外の要素を探しに行かない。ただし判定の過程で台帳にない spec 要素に気づいたら「台帳漏れ疑い」として別枠で報告する

## 出力
台帳の**全行**について 1 行ずつ判定を返す（担当行数と判定数が一致すること）:
- ID / 判定（PASS / まるごと未実装 / スタブ / 部分実装 / TODO残り / 要確認 / 実体なし疑い）
- PASS の場合: 実装箇所（ファイル:行）
- 実体なし疑いの場合: 定義場所として読んだファイル・セクションと、そこに何が書かれていたか
- それ以外の場合: 実装側の該当ファイル:行（存在する場合）と、何を実装すべきか（埋めるべき振る舞いの具体）
```

親エージェントは、返ってきた判定の行数が担当行数と一致するかを検証者ごとに確認する。不一致（未判定の行がある）なら、その行だけを再度判定させる。「台帳漏れ疑い」が報告されたら、spec を確認して正しければ台帳に行を追記し、その行も判定対象に加える。「実体なし疑い」が報告されたら、spec を確認して実体がなければ台帳から行を削除する（欠落に数えない）。実体があれば定義場所を正しい参照に直して再判定させる。

### 3. 判定とループ

- パターンスキャンと spec 照合で欠落・スタブ・部分実装が**1件でも**見つかったら、ゲート不通過。
- 修正は新しい実装サブエージェント（**判断区分**）に委譲する。**欠落リストを台帳 ID 付きで具体的に明示**して渡す（「全体を見直して」ではなく「DOM-user-002 のこの振る舞いが未実装、埋めよ」）。実装者本人の正当化バイアスを避けるため、可能なら別のサブエージェントに埋めさせる。
- 修正後、typecheck + lint を実行し、ゲート（手順 1〜2）を再実行する。再実行の spec 照合は、前ラウンドで PASS 以外だった行と修正の影響範囲に絞ってよい。
- **全行 PASS**（欠落 0 件）になったらゲート通過 → レビューサイクルへ進む。
- 3 ラウンドで収束しない場合は、残っている欠落をまとめてユーザーに報告し、判断を委ねる。「要確認」だけが残っている場合もユーザーに確認する。

## 出力

- ゲート結果を `.review/{layer}/completeness-{連番}.md` に記録する。台帳の**全行**について ID と判定（PASS / 欠落の種類）を残し、どの行が何ラウンド目で埋まったかを追えるようにする
- ゲート通過後、レビューサイクル（各スキルの Phase 3）に進む

## 委譲方式

委譲方式（サブエージェント / OS プロセス / 親内シミュレート）の判定・並列化・モデル選択の原則は `subagent-policy.md` に従う。spec 照合は台帳の行単位で分割して並列実行する（手順 2 参照）。
