# Spec インベントリ（実装要素台帳）

spec/ で定義された「実装されるべき要素」に決定的な ID を振って列挙した台帳。`spec/inventory/{layer}.md` に保存する。

完全性検証を「サブエージェントがその場で spec から要素を列挙する」方式に頼ると、列挙自体の漏れは以降のどの裏取りでも検出できない。台帳を一度だけ丁寧に作って永続化し、以降の検証は「台帳の各行を実コードで裏取りする」だけにすることで、列挙漏れを構造的に防ぐ。

台帳は次の場面で共通の基準として使う:

- 完全性ゲート（`completeness-gate.md`）— 各行を実コードと照合して PASS/FAIL を付ける
- implement-audit の spec 照合 — 照合対象の列挙を台帳から取る
- spec-to-issues — 縦スライス Issue のチェックリストを台帳行から組み立てる

## 台帳の性質

- **spec の純粋な列挙である。** 実装状態（済み/未実装）は持たない。状態は完全性ゲートの結果ファイルや Issue のチェックリストが持つ。
- **決定的である。** 誰が生成しても同じ行が出るよう、下記の粒度規則に機械的に従う。判断で行を増減しない。
- **spec と同期する。** spec を変更したら（spec-revise・spec-sync・実装中の spec 更新を含む）、該当レイヤーの台帳を必ず更新する。台帳が古いままだと、以降のすべての検証が古い基準で走る。

## ファイル構成

```text
spec/inventory/
  domain.md
  adapter.md
  usecase.md
  frontend.md
  test.md
```

対応する spec ディレクトリが存在しないレイヤー（例: フロントエンドのないプロジェクトの frontend.md）は作らない。

## フォーマット

各ファイルは次のテーブル形式とする。

```markdown
# Inventory — {layer}

生成元: spec/{対象ディレクトリ}/（最終同期: {YYYY-MM-DD}）

| ID | 要素 | 定義場所 | 実装されるべき振る舞いの要点 |
|----|------|---------|------------------------------|
| DOM-user-001 | User エンティティ | spec/domains/user.md#エンティティ | id/name/email を持つ。email は Email 値オブジェクト |
| DOM-user-002 | UserRepository.findById | spec/domains/user.md#ポート | ID 指定で取得。見つからなければ NotFoundError |
```

- **ID** — `{プレフィックス}-{グループ}-{連番3桁}`。プレフィックスはレイヤーごとに `DOM` / `ADP` / `UC` / `PAGE` / `TC`。グループはドメイン名・ページ名などの slug。連番は spec 内の出現順。ID は一度振ったら変えない（spec 変更で要素が消えたら行を削除し、欠番はそのまま残す。並び直しをすると過去の検証記録・Issue チェックリストとの対応が壊れる）
- **定義場所** — `{specファイルパス}#{セクション}` 形式。検証者が Read で直接開ける粒度にする
- **要点** — その行だけ読んで「何が実装されていれば PASS か」が判断できる 1 文。spec の丸写しではなく判定基準を書く

## 粒度規則（レイヤー別）

省略が紛れ込む単位で行を切る。粗すぎると行内のスタブが素通りし、細かすぎると台帳が管理不能になる。

| レイヤー | 1 行にする単位 |
|---------|----------------|
| domain | エンティティ・値オブジェクトごとに 1 行、ドメイン関数・ドメインサービスごとに 1 行、ポートは**メソッドごと**に 1 行 |
| adapter | 実装すべきポートの**メソッドごと**に 1 行、マイグレーション・スキーマ定義はテーブルごとに 1 行 |
| usecase | ユースケースごとに 1 行。spec で明示された主要分岐・エラーケースは要点欄に列挙する（行は分けない） |
| frontend | ページごとに 1 行、加えてページ内の**ユーザー操作起点のアクション**（フォーム送信・API 呼び出し・遷移）ごとに 1 行 |
| test | spec/testcases/ のテストケースごとに 1 行（testcases 側に ID があればそれを流用する） |

ポートメソッド・フロントエンドのアクションを独立行にするのは、実装漏れ・スタブ化が最も起きやすい単位だから。

## 生成手順

1. レイヤーごとにサブエージェントを並列起動する（委譲方式は `subagent-policy.md`）。各サブエージェントに、対象 spec ディレクトリと上記の粒度規則・フォーマットを渡し、spec の全ファイルを Read させて台帳を生成させる。
2. **クロスチェック（必須）。** 生成とは別のサブエージェントに、spec と生成済み台帳を渡し「spec に定義があるのに台帳に行がない要素」だけを探させる。台帳は以降のすべての検証の基準になるため、この一度のクロスチェックに投資する。漏れが見つかったら行を追記して再チェックする。
3. `spec/inventory/{layer}.md` に保存し、最終同期日を記録する。

既に台帳が存在する場合は再生成せず、spec の最終変更が台帳の最終同期より新しいときだけ差分を反映する（変更された spec ファイルに対応する行の追加・修正・削除）。
