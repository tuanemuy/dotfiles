# 設計ドキュメントのレビュー共通原則

spec / spec-domain / spec-revise の各フェーズレビューが従う共通構造。レビューサイクルの土台（出力フォーマット・指摘台帳・修正ループ・サブエージェント運用）は `review-loop.md` に従い、本ガイドは設計ドキュメント固有の受理基準と完了条件を定める。

## 記録

- 対象ディレクトリの `review/` 配下に連番ファイル（`001.md`, `002.md`, ...）で記録する
- 対応が必要な問題点のみ記載する。責任範囲はそのレビューの対象に限定する
- 指摘は Blocker（設計として成立しない問題）と Warning（改善推奨）に分類する
- 問題が見当たらなければ「指摘ゼロ」と明示してよい。無理に粗探しをしない

## 指摘の受理基準

設計ドキュメントのレビューは、放置すると「記述を増やす提案」だけが無限に湧く。フレッシュなレビュアーは毎ラウンド新しいエッジケースを思いつけるため、`fix` ゼロが「書き尽くした状態」でしか成立しなくなる。それを防ぐため、**受理する指摘を次の2種類に限定する**。

1. **要件からの欠落** — 上流の成果物（`spec/idea.md`・`spec/scenario/`・`spec/pages/`・直前フェーズの成果物）に書かれている事柄が、この成果物に落ちていない。**根拠となる上流の記述を引用する**
2. **成果物内の矛盾・違反** — 定義どうしの食い違い、アーキテクチャ制約への違反、トレーサビリティの断絶、旧仕様の残骸

引用元を示せない指摘は受理しない。典型例:

- 「こういうケースも考えられる」「この入力の境界も定義すべき」
- 「エラーの種類をもっと細かく分けるべき」
- 「実装者が迷いそうなので手順を書き足すべき」

これらは `wont-fix` に仕分け、一行理由（例: 「要件に対応なし。実装時に決定」）を台帳に記録する。要件にない分岐を spec で先回りしても、実装時にコードを見て決め直すことになり、記述量だけが残る。**spec に書いていない詳細は、issue-planner が Issue 単位で決める**（`../../issue-planner/SKILL.md`）。

受理基準に反する指摘が続くレビュアーには、次ラウンドの委譲プロンプトで本セクションを明示的に引用する。

## レビューの2軸

1. **トレーサビリティ**: 上流の成果物と整合しているか。漏れているシナリオ・要件がないか
2. **アーキテクチャ適合性**: 設計制約に違反していないか

「実装可能性」は軸に立てない — 立てると受理基準1・2に当たらない指摘の入口になる。必要な粒度は各ガイドが定義済みで、それを満たしているかは軸1で見る。

## トリアージと完了条件

指摘の仕分けは `review-loop.md` の指摘台帳方式に従う。台帳は対象ディレクトリの `review/triage.md` に置く。

- 各ラウンドの指摘はまず台帳と突き合わせ、Key が一致する既出指摘は判定を継承して再審議しない
- 新規の指摘は受理基準に照らし、`fix` / `wont-fix`（一行理由）に仕分ける
- **`fix` と仕分けた指摘が0件のラウンドで完了**（台帳に記録済みの指摘は件数に含めない）。最大5ラウンド
- 収束しない場合は残った指摘をまとめてユーザーに報告し、判断を委ねる

## 各ラウンドの独立性

各ラウンドは独立した完全なレビューとして実施する。前回のレビューファイルを読まず、成果物とチェックリストだけを見て一から評価する。再登場する既出指摘は台帳の判定継承で吸収する。

## 後片付け

完了条件を満たしたら対象ディレクトリの `review/` を削除する（`review-loop.md` の「後片付け」）。指摘は成果物に反映済みか台帳で決着しており、残すと後続セッションの検索に紛れ込む。最大ラウンドに達して収束しなかった場合は削除せず、完了報告に明記する。
