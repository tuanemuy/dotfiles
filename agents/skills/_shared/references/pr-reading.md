# PR の読み

PR の差分を、目的ごとに分けた読み手で読み、反証させる段取り（読み手の立て方・契約・渡すもの・結果の形・反証）を定める。読み手の読み方は `diff-reading.md` に従う。読みを何回重ねるかと、読んだ後の指摘の扱いは、呼び出し側が定める。

委譲方式と待ち方は `subagent-policy.md` に従う。読み手と反証は結果をファイルに書き、メインには要約だけを返す。

## 読み手

`diff-reading.md` の目的ごとに読み手を分け、読み手ごとに台帳を持たせる。台帳は、読み手が 1 つずつ結論を付ける項目の一覧で、結論の付かなかった項目が読めていない箇所になる。

| 読み手 | 台帳 |
| --- | --- |
| `acceptance` | 契約の受け入れ条件と、変更が届く先 |
| `design` | 差分が新しく作ったものと、変えたインターフェース |
| `conventions` | 変更ファイル一覧 |

届く先と、新しく作ったものの台帳は、読み手が差分から作る。

- 差分が小さくても、1 体に複数の目的を持たせない。目的を狭くして読ませることが、それぞれの盲点を減らす
- 台帳が 1 体で注意深く読める量を超えたら、台帳を分けて体を増やす。名前は `acceptance-2` のように連番を付ける
- 差分がバックエンドとフロントエンドの両方に及ぶとき、`design` を `design-backend` と `design-frontend` に分ける。`design-principles.md` の節が違うため
- これ以外の読み手を立てない

## 対象の確定

最初の読みでは、対象のブランチに切り替える。

```bash
gh pr checkout {PR番号}
gh pr view {PR番号} --json title,body,baseRefName,headRefName,closingIssuesReferences
git fetch origin
```

変更ファイル一覧と差分ファイルを作る。`{N}` は読みの回で、1 から振る。

```bash
mkdir -p .thread/{PR番号}/review {scratchpad}/diff
git diff --no-renames --name-status origin/{ベースブランチ}...HEAD -- . ':(exclude).thread' > .thread/{PR番号}/review/{N}-files.txt
git diff --no-renames origin/{ベースブランチ}...HEAD -- . ':(exclude).thread' > {scratchpad}/diff/{PR番号}-{N}.diff
cut -f2 .thread/{PR番号}/review/{N}-files.txt | cut -d/ -f1-2 | sort | uniq -c
```

- `checkout` は省略しない。差分を `...HEAD` で引くので、HEAD が違うと対象ごと取り違える。未コミットの変更で切り替えられなければ、stash せずユーザーに聞く
- `.thread/` は作業ログで、レビューの対象ではないので除く
- `--stat` はパスを切り詰め、`gh pr view --json files` は 100 件で打ち切るので使わない
- `--no-renames` を付ける。`R` の行は 1 行に 2 パスを持ち、一覧との照合を壊す
- 一覧と差分本文はファイルに落とし、読み手にはパスを配る。メインには領域ごとの件数だけを出し、読み手の構成を決める材料にする。`{scratchpad}` は `scratchpad.md` に従う

## 契約

読み手を起こす前に、メインが `.thread/{PR番号}/review/contract.md` に書き出す。出典は PR 本文・紐づく Issue・spec（プロジェクトの仕様の置き場所は `CLAUDE.md` に従う）。受け入れ条件ごとに、番号・出典・観測方法（`browser` / 自動テスト / コマンド出力）を付ける。UI がある変更では、対象のビューポートも書く。

- spec・design が理由を添えて明示した設計判断（「X でなく Y にする。なぜなら」）も、出典付きで書く。ファイルパス・関数名・処理の手順のような実装の記述は、設計判断に含めない
- spec・design が定めていない点は「未定」として書く
- 意図そのものが読み取れず、契約を書き出せないときだけユーザーに聞く

## 読み手に渡すもの

- PR 番号・ベースブランチ・リポジトリのパス
- PR の title と body
- `diff-reading.md`・`production-ready.md`・`design-principles.md` のパスと、その読み手の目的
- `contract.md`・`{N}-files.txt`・差分ファイルのパス
- 書き込み先のパスと、結果の形
- UI がある変更では、ブラウザの namespace とセッション名、証跡の置き場所（`{scratchpad}/evidence/`）

メインの自己評価と完了報告は渡さない。どこを疑ってほしいか（不安な箇所・見てほしい点・例・観点の言い換え）も渡さない。先に渡すと、読み手はそこを中心に読み、自分の盲点を読まなくなる。疑ってほしい箇所は、結果が返った後で同じ読み手に追加で聞く。

## 読み方

読み手は `diff-reading.md` の共通の節と、自分の目的の節に従って読み、台帳の項目ごとに結論を付ける。

`conventions` は、変更ファイル一覧の各ファイルを「確認」か「スキップ（理由）」で申告する。スキップしてよいのは、生成物や lockfile のように、照らす規約が無いファイルだけ。一覧が大きい場合、スキップはディレクトリ単位でまとめてよい。確認は個別に列挙する。

## 結果の形

読み手は結果を `.thread/{PR番号}/review/{N}-{読み手}.md` に直接書く。指摘の ID は `{読み手}:{連番}`（`acceptance:3`、`design-frontend:1`）。

````markdown
## {読み手}

### 台帳

- {項目} — {成立 / 反例 {ID} / 追えなかった（理由）}

### 反例

- **[{ID}]** 条件 {番号}: {何が起きるか}（読解だけなら先頭に「未観測」）
  - 場所: `ファイル:行`
  - 事実: {その条件の反例の形に沿って}
  - 観測の条件: {実環境 / 差し替えあり（何を差し替えたか、実環境で起こりうるか） / 読解のみ}
  - 提案: {どう直すか。置き場所の層・モジュールと、そこに置く理由}

### 契約への指摘

- **[{ID}]** {契約の項目と、実物との食い違い}

### 7 条件の外の指摘

- **[{ID}]** {内容}（場所・提案は反例と同じ形）

### 実行確認

- `{コマンド}` — {件数・結果}
- ブラウザ観測: {観測した操作・ビューポート・結果・証跡のパス / なし}
````

- 該当がない節には「なし」と書く
- `conventions` の台帳は、各ファイルの「確認」か「スキップ（理由）」
- この形は下限で、上限ではない。経路の分析・前提・代替案の比較など、伝えるべきことがあれば節を足してよい

返答は次の項目だけにする。全文・コード引用・分析の経緯は返さない。

- 件数: 反例 {数}（条件ごとの内訳、うち未観測 {数}）/ 契約への指摘 {数} / 7 条件の外 {数}
- 指摘の一行リスト: `[{ID}] 条件 {番号} {ファイル:シンボル} — {タイトル}`
- 台帳: 項目数と、結論が「追えなかった」の項目

## 反証

読み手は反例を探すことを目的にしているので、指摘の事実と提案の両方が過大になりやすい。読み手が全員返したら、反例と 7 条件の外の指摘を、読み手とは別の委譲先 1 体（`refute`）に反証させる。指摘を確かめるのは反証だけで、1 体がすべての指摘を見ることで、判定がそろい、提案どうしの矛盾にも気づける。

- 指摘が 1 体で注意深く確かめられる量を超えたら、指摘を分けて体を増やす。名前は `refute-2` のように連番を付ける
- 渡すもの: 反例か 7 条件の外の指摘がある読み手の結果ファイルすべて、`contract.md`、`diff-reading.md`・`production-ready.md`・`design-principles.md` のパス、差分ファイルのパス。UI がある変更では、ブラウザの namespace とセッション名
- メインの評価や、どこを疑ってほしいかは渡さない

反証する委譲先は、指摘ごとに次の 2 つを確かめる。

- 事実: `diff-reading.md` の共通の節に従い、コードと実行で導き直す。読み手どうしで結論が食い違う項目は決着させる。未観測の指摘は再現を試みる。前提が崩れたら反証
- 提案: 置き場所の層と概念が `design-principles.md` とプロジェクトのルールに合うか、既存の書き方に沿うか、契約の設計判断やほかの指摘の提案と矛盾しないか、過度に防御的でないか。合わなければ代案を書く

結果は `.thread/{PR番号}/review/{N}-refute.md`（分けたときは `{N}-refute-2.md` など）に、指摘の ID ごとに書く。

```markdown
- **[{ID}]** {成立 / 反証（理由） / 提案だけ反証（理由と代案） / 未観測のまま（試したこと）}
```

返答は件数だけにする: 成立 {数} / 反証 {数} / 提案だけ反証 {数} / 未観測のまま {数}。
