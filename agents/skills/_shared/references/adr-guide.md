# ADR（Architecture Decision Records）ガイド

プロダクトの方向性に関わる設計判断は、プロジェクトルートの `.adr/` に記録する。「なぜそうしたか」が残っていれば、実装者が迷わず、将来の変更時にも意図を追える。architecture-audit や spec-sync などの読み手は `.adr/` だけを参照する — 永続的な判断の置き場所はここ一箇所に集約する。

## 記録の2層構造

- **`.adr/`（永続台帳）**: プロジェクト全体に効く判断。下の記録基準を満たすものだけを置く。ディレクトリがなければ新設してよい
- **作業ログ（`.thread/{番号}/adr.md`）**: Issue / PR の作業中に下した判断の一時的な記録（GitHub の Issue と PR は採番を共有するため、番号だけで一意に特定できる）。書く時点では基準を気にせず気軽に書いてよい。作業の片付けフェーズで各エントリを記録基準にかけ、満たすものだけを `.adr/` に転記（昇格）する。残りは作業履歴としてそのまま残す

spec 系スキル（spec / spec-domain / spec-revise）や spec-sync のようにプロジェクトスコープで作業する場合は、作業ログを介さず、記録基準を満たす判断を直接 `.adr/` に書く。

### 作業ログへの追記

作業ログは追記のたびに肥大し、作業の後半ほど読み込みが高くつく。**追記に必要なのは次の連番だけなので、全文は読まない。**

```bash
grep '^## ADR-' .thread/{番号}/adr.md | tail -1   # 無ければファイルごと新規作成
```

既存エントリの内容が要るのは、判断そのものを見直すとき（既決の判断に反する指摘の仕分け、片付けフェーズの昇格判定）だけ。

## ファイル名

**`.adr/` に通し連番は使わない。** 並行するブランチが同時に `ls` して同じ番号を取っても、slug が違えばファイル名が別になり、git は衝突なくマージしてしまう — 重複した番号がサイレントに残る。番号は自分で採らず、作業スコープごとに**外部から一意に与えられるもの**を使う。

| 作業スコープ | ファイル名 | 例 |
| --- | --- | --- |
| Issue / PR 単位（issue-implement / pr-review からの昇格） | `.adr/{Issue または PR 番号}-{slug}.md` | `.adr/412-optimistic-locking.md` |
| プロジェクトスコープ（spec / spec-domain / spec-revise / spec-sync / implement 系） | `.adr/{YYYY-MM-DD}-{slug}.md` | `.adr/2026-08-13-aggregate-boundaries.md` |

- GitHub の Issue と PR は採番を共有するため番号だけで一意になる。`.thread/{番号}/` と同じ番号を使うので、判断の出所を辿れる
- 1つの Issue / PR から複数の ADR を昇格する場合は slug で分ける（`412-optimistic-locking.md` / `412-id-format.md`）
- 日付は推測せず `date +%F` の実行結果を使う。基準は**決定した日**（マージ日ではない）
- slug は英小文字・ハイフン区切りで、タイトルではなく**判断そのもの**を表す（`locking` ではなく `optimistic-locking`）
- **ファイル名は後から変えない。** supersede がファイル名で参照するため、リネームはリンク切れを生む

見出しは `# ADR: {判断の概要}` とし、本文に識別番号を書かない — 識別子はファイル名。

## 記録基準（昇格判定）

次の2つのテストで判定する。

- **寿命テスト**: この理由は、マージ後にこの PR / Issue を見ていない人にとってもまだ意味を持つか
- **波及テスト**: この判断を覆すと、複数のモジュール・レイヤー・データに波及するか

両方 Yes なら `.adr/` に記録する。次のものは記録しない。

- 有能な開発者なら誰でも同じ結論に至る判断 → 記録不要
- 理由がコードのすぐ横の1〜2行で伝わるローカルな判断 → ADR ではなく why / why not コメント
- レビュー指摘への対応要否（fix / wont-fix / defer） → ADR ではなく指摘台帳（triage.md）の役割

「プロダクトの方向性」という言葉が企画寄りに聞こえても、長寿命で横断的な技術判断（ロック戦略、ID 形式、ライブラリ選定など）は基準を満たすなら記録する。

## 情報の置き場所の階段

- ローカルな why / why not → コードコメント
- 横断的な why（判断の経緯・代替案・トレードオフ） → `.adr/`
- 現在のルール・規約 → CLAUDE.md / spec/

ADR は「なぜそうなったか」の履歴であり、「今どうなっているか」は spec / CLAUDE.md が担う。判断の結果としてルールが変わるなら、ADR とは別に spec / CLAUDE.md 側も更新する。

## 記載項目

- **ステータス**: 承認済み / superseded by `{置き換えた ADR のファイル名}`
- **コンテキスト**: なぜこの決定が必要になったか
- **前提**: この決定が依存する条件。崩れたら再検討の対象になる
- **決定**: 何を決めたか
- **検討した代替案**: 各案と不採用の理由
- **影響**: この決定がもたらす結果・トレードオフ

## 拘束力と supersede

ADR は履歴であって法律ではない。拘束力を持つのは前提が生きている間だけ。既存 ADR と矛盾したときに問うのは「ADR があるか」ではなく「その前提が今も真か」— 崩れていればどのスキルからでも supersede を提案してよい（裁定はメインかユーザー）。

既存の ADR と矛盾する判断を下す場合は、新しい ADR を作成し、旧 ADR のステータスを「superseded by `{新しい ADR のファイル名}`」に更新する。旧 ADR の本文は書き換えない — 履歴として残す。ステータス行以外は触らない（ファイル名も変えない）。

## ADR を書くべき判断の例

- ドメイン境界の切り方
- 集約の設計（何をひとつの集約にまとめるか）
- 複数のモデリング手法のうちどれを採用したか
- パフォーマンスや一貫性のトレードオフ
- ページ構成・ナビゲーション方針など、体験設計上の非自明な選択
- 意図的な規約からの逸脱（アーキテクチャ監査が例外として扱うべきもの）
