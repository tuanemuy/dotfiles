# 設計判断の記録ガイド

作業中に下した判断は、既定では作業ログ（`.thread/{番号}/adr.md`）に置く。そこから CLAUDE.md / docs/ / spec/ に上げるのは**昇格**であって、手順の一部ではない。**昇格ゼロで終わる作業のほうが普通。**

## 置き場所

| 置き場所 | 持つもの | 書き手 |
| --- | --- | --- |
| `CLAUDE.md` | 作業を始めるときに**必ず知っておくべきこと** — 開発運用・設計・実装の原則 | ユーザー。スキルからは書き換えない |
| `docs/` | 具体的な規約 | 昇格したときだけ |
| `spec/` | 設計。あるべき姿を現在形で | 設計スキル、または昇格したときだけ |
| `.thread/{番号}/adr.md` | その作業で下した判断の経緯・代替案・トレードオフ。**既定の置き場所** | 判断を下したその場で |
| コードコメント | ローカルな why / why not。理由がコードのすぐ横1〜2行で伝わるもの | 実装時 |

プロジェクト横断の ADR 台帳（ルートの `.adr/` 等）は置かない。GitHub の Issue と PR は採番を共有するため、作業ログは番号だけで一意に特定できる。Issue / PR 番号を持たない作業は作業ログを持たない — 判断はコミットメッセージと完了サマリーで報告する。

## 昇格の判断

判断を `.thread` の外に出すのは、次を**両方**満たすときだけ:

1. その判断を知らずに別の作業を始めると、同じ判断を誤るか、同じ議論を繰り返す
2. 判断の効き目が今回の変更の外に及ぶ（他の機能・今後の実装がそれに従うことになる）

片方でも欠けたら `.thread` に置いたままにする。次のものは昇格しない:

- 今回のコード内で完結する理由 → why / why not コメント
- 一度きりの選択（このバージョンの既知バグを回避した等）
- すでに CLAUDE.md / docs / spec に書かれていることの言い直し
- 「今後こうしたほうがいい」という願望 — そうすると決めていないものは判断ではない

## 昇格先

両方を満たしたときだけ、内容で行き先を決める:

- **あるべき姿・仕様が変わった** → `spec/` の該当ドキュメントを現在形で更新する
- **具体的な書き方のルールが増えた・変わった** → `docs/` の該当ドキュメントを更新する（該当ファイルが無ければ勝手に新設せず、ユーザーに提案する）
- **上のどちらでもなく、知らずに着手すると事故る前提** → CLAUDE.md 相当。**スキルからは書き換えない** — 該当箇所と提案内容を完了報告に一行で挙げ、判断はユーザーに委ねる

spec / docs に書くのは結果だけ。「以前は X だったが」「〜という経緯で」といった履歴の文は書かない — 旧仕様は git 履歴と作業ログが持つ。昇格させた逸脱は注記ではなく現在形のルールとして書く（例: 「一覧の読み取りは性能要件のため非正規化ビューを参照する」）。今回の変更に閉じた逸脱は昇格させず、現場の why not コメントで足りる。

## 作業ログへの追記

作業ログは追記のたびに肥大し、作業の後半ほど読み込みが高くつく。**追記に必要なのは次の連番だけなので、全文は読まない。**

```bash
grep '^## ADR-' .thread/{番号}/adr.md | tail -1   # 無ければファイルごと新規作成
```

既存エントリの内容が要るのは、判断そのものを見直すとき（既決の判断に反する指摘の仕分けなど）だけ。

各エントリは「## ADR-{NNN}: {タイトル}」の見出しに Context / Decision / Consequences を書く。**ここは気軽に書いてよい場所** — 昇格の要否を書く時点で判定する必要はない。ただし次のものは書かない:

- 指摘への対応要否（fix / wont-fix / defer）→ 指摘台帳（triage.md）の役割
- 理由がコードのすぐ横の1〜2行で伝わるローカルな判断 → why / why not コメント

## 既決の判断との照合

作業ログは法律ではない。既存エントリと矛盾する指摘・判断が出たときに問うのは「記録があるか」ではなく「その前提が今も真か」。前提が生きていれば蒸し返さず、崩れていれば判断し直して新しいエントリを追記する（旧エントリは書き換えない — 経緯として残す）。
