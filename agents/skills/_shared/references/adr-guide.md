# 設計判断の記録ガイド

判断の記録は2つに分かれる。「今どうあるべきか」は spec/ が持ち、「作業中に何をなぜ決めたか」は Issue / PR 単位の作業ログ（`.thread/{番号}/adr.md`）が持つ。プロジェクト横断の ADR 台帳（ルートの `.adr/` 等）は置かない — 監査・レビュー・実装が従うのは spec/ と CLAUDE.md だけで、判断の結果はすべてそこに現在形で反映する。

## 置き場所

- **spec/**: 判断の結果（採用した設計・規約・意図的な例外）。常に現在形で書く。経緯・代替案・変更履歴は書かない — 旧仕様は git 履歴が持つ
- **コードコメント**: ローカルな why / why not。理由がコードのすぐ横の1〜2行で伝わるもの
- **作業ログ（`.thread/{番号}/adr.md`）**: 作業中に下した判断の経緯・代替案・トレードオフ。経緯が残る唯一の場所として恒久に残す。GitHub の Issue と PR は採番を共有するため、番号だけで一意に特定できる
- **CLAUDE.md**: ユーザーが管理する規約。スキルからは書き換えない。判断が CLAUDE.md と衝突する、または規約の変更を要する場合は、書き換えずにユーザーに提案する

Issue / PR 番号を持たない作業は作業ログを持たない。判断の結果を spec に反映し、経緯はコミットメッセージと完了サマリーで報告する。

## spec への反映

「あるべき」を変えた判断は、下したその場で spec の該当ドキュメントを更新する。反映するのは結果だけ — 「以前は X だったが」「〜という経緯で」といった履歴の文は spec に書かない。意図的な規約からの逸脱も、逸脱の注記としてではなく現在形のルールとして書く（例: 「一覧の読み取りは性能要件のため非正規化ビューを参照する」）。監査・レビューは spec / CLAUDE.md に書かれていない逸脱を違反として扱う。

## 作業ログへの追記

作業ログは追記のたびに肥大し、作業の後半ほど読み込みが高くつく。**追記に必要なのは次の連番だけなので、全文は読まない。**

```bash
grep '^## ADR-' .thread/{番号}/adr.md | tail -1   # 無ければファイルごと新規作成
```

既存エントリの内容が要るのは、判断そのものを見直すとき（既決の判断に反する指摘の仕分けなど）だけ。

各エントリは「## ADR-{NNN}: {タイトル}」の見出しに Context / Decision / Consequences を書く。書く時点では気軽に記録してよい。ただし次のものは書かない:

- 指摘への対応要否（fix / wont-fix / defer）→ 指摘台帳（triage.md）の役割
- 理由がコードのすぐ横の1〜2行で伝わるローカルな判断 → why / why not コメント

作業ログに書いた判断が「あるべき」を変えるものなら、記録とは別にその場で spec を更新する。作業ログは経緯の履歴であって、spec 反映の代わりにはならない。

## 既決の判断との照合

作業ログは法律ではない。既存エントリと矛盾する指摘・判断が出たときに問うのは「記録があるか」ではなく「その前提が今も真か」。前提が生きていれば蒸し返さず、崩れていれば判断し直して新しいエントリを追記する（旧エントリは書き換えない — 経緯として残す）。
