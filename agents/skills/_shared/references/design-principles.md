# 設計の原則

負債を生まない設計の原則。負債とは、次の変更のコストを上げる構造のこと。

バックエンドとフロントエンドは同じ 3 つの考えに立つ。

- 不正な状態は型で表現できなくする
- 外部のデータは境界でデコードする
- 副作用は端に寄せる

バックエンドはこの考えをドメインモデルに当てる。フロントエンドは「UI は状態の関数」として画面の状態に当てる。

プロジェクトが書いたルール（`CLAUDE.md` / spec のアーキテクチャ・規約）が定めていることは、そのルールで判定する。この原則は書かれたルールの外で使い、既存コードのパターンと比べて当てる。

## 共通

- 1 つの値・型・関数に 2 つの意味を負わせない
  - 変更理由が複数あるモジュール・関数は分ける
- 名前が意味を言い当て、条件を名前の裏に隠さない
- 同じ規則を 2 か所に別々に実装しない
  - 既存の関数・型・パターンを再実装せず、集約先に寄せる
  - 同じ規則かどうかは意味で判定する。語・リテラル・形が同じでも、指す概念や変わる理由が違えば別のものとして扱い、型で結ばない
- 抽象化は必要になった時点で入れる
  - 使い手が 1 つしかない抽象、将来のための一般化、死んだ分岐は負債

## バックエンド

- 不正な状態は型で排除する
  - 直和型・判別ユニオンで表現できる状態を、任意プロパティや boolean フラグの組み合わせで許さない
  - 値の制約は値オブジェクトの生成時に検証し、生成された値は常に正しい
  - 内部の存在チェックや非 null アサーションは、モデルが不正状態を許しているシグナル。境界での検証は正当
- 外部データは境界でデコードしてドメイン型にする
  - リクエスト・永続化のアイテム・外部 API の応答はアダプターでドメイン型に変換し、生の文字列や unknown を内側へ流さない
  - リクエストの語彙（API の列挙値・フラグ）は、アダプターとユースケースの入力の型として置き、ドメインの型にしない。ドメインに渡す前に、ドメインの言葉に写す
- 状態遷移は明示する
  - 遷移はドメインモデルの振る舞いとして起き、どこで起きるかを追える
- 副作用は隔離する
  - ドメインは I/O を持たない計算にし、I/O はポートの向こうに置く
  - ユースケースはドメインの振る舞いとポートを組み合わせる
- 規則は、成り立つ範囲で置き場所を決める
  - どのユースケースでも成り立つ業務ルールと不変条件はドメインに置く
  - そのユースケースだけの方針（入力の優先順位、どの判定を使うか、保存前の値の扱い）はユースケースに置き、ドメインのメソッドに引数やフラグで持ち込まない
- 依存は内側に向ける
  - 内側のレイヤーが外側を知らない
- 業務上の失敗は、呼び出し側が種類を判別できる形で返す

## フロントエンド

- 状態の持ち主を種類ごとに決める
  - サーバーから取得したデータのキャッシュ・URL の状態（検索条件・タブ・ページ）・フォームの入力・画面ローカルの UI 状態・アプリ全体の状態（認証・テナント）を区別する
  - 取得したデータを画面ローカルの状態に写さない
  - リロードや共有で残すべき状態は URL に置く
- 導出できる値は状態として持たない
  - 入力や他の状態から計算できる値は、描画のたびに計算する
- ありえない状態を表現できなくする
  - 非同期の状態・画面のモード・フォームの段階は判別ユニオンで持つ
  - `isLoading` と `error` の組み合わせや、`variant` と連動する任意のプロパティで表さない
- 描画に伴う副作用は、外部のシステムとの同期だけに使う
  - ユーザー操作で起きることはイベントハンドラに書く
  - 状態から状態を作るのに副作用を使わない
- API の応答は境界でデコードする
  - 生成型を画面の奥まで流さず、画面が使う形への変換を 1 か所にまとめる
  - API に送る列挙値・フラグは API の型の側に置き、画面やドメインの型に格上げしない
  - バックエンドの内部（テーブル構造・内部処理）を知らない
- 振る舞いを描画から切り離す
  - 表示可否・計算・遷移の判定は、DOM なしで試せる関数に置く
  - コンポーネントは描画とイベントの受け渡しを持つ
- すべての状態に画面を用意する
  - 読み込み中・空・エラー・権限なし・部分的な失敗・送信中を描き、それぞれでユーザーが次にできることを示す
- 意味のある要素で組み立てる
  - ボタンは `button` にし、入力にはラベルを付け、キーボードで操作できるようにする
  - 操作の後、フォーカスに行き先がある
  - 要素を役割と名前で特定してテストを書けるかが目安になる
