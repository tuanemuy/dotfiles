# サブエージェント委譲ポリシー

スキル群で「サブエージェント」と呼ぶ委譲先は、以下の優先順位で実行する。

## 実行方式の優先順位

1. **実行環境がサブエージェントをサポートする場合**（例: Claude Code の Task 系、Anthropic Agent SDK のマルチエージェント機能など）
   → 各作業を**別々のサブエージェント**として起動する。
2. **実行環境がプロセスレベルのエージェント実行をサポートする場合**（OSプロセス単位でエージェントを起動できる場合）
   → 各作業を**独立したOSプロセス**として起動する。
3. **上記いずれも利用できない場合のみ**
   → 親エージェント内で各作業を順に実行する（シミュレート）。

サブエージェントもプロセスランナーも利用できる環境で、親エージェント内に全作業を閉じ込めて逐次シミュレートしてはいけない。

「サブエージェントが許可されている場合は」のような条件分岐は不要。サブエージェントまたはプロセスが使えるなら必ずそちらを使う。

## 完了の待ち方

**委譲はブロッキングで待つ。バックグラウンド起動して完了をポーリングしない。**

禁止するのは次の形。`sleep` を挟んで成果物ファイルやステータスの有無を繰り返し確認し、揃うまでターンを回すもの:

```bash
sleep 550; ls .thread/123/review/ 2>/dev/null || echo "pending"
```

- 委譲先の完了は**呼び出しの戻り値で受け取る**（Claude Code の Task 系、Agent SDK など、戻り値まで待つ呼び出し方をする）
- 環境が完了通知を提供する場合はそれを使う。自前のスリープループで代替しない
- 並列で起動した複数体も、まとめて戻りを待つ。1体ずつ存在確認して回らない
- OSプロセスとして起動する場合は `wait` 等でプロセスの終了を待つ。生成物の有無で判定しない

## モデル選択

委譲先には作業の性質に応じたモデルを割り当てる。全委譲先を同じモデルで起動しない。

区分は2つ。

**探索区分** — 事実の収集に徹する作業。ファイル探査、grep での列挙、インベントリ作成、既存資料の読み取りと要約、機械的な整形など。判断を伴わず、出力が「見つかったものの一覧」に収まるもの。軽量モデルを割り当てる。

**判断区分** — 判断・生成を伴う作業。設計、実装、レビュー、違反の認定、分類、優先度づけ、ドキュメントの更新など。誤りが成果物に残るもの。メインエージェントと同じモデルを使う。

迷ったら判断区分にする。探索区分の誤りは見落としで済むが、判断区分の誤りは下流に伝播する。

**例外 — 定型実行。** 手順と期待結果が事前に確定していて、委譲先は観測した事実を記録するだけの作業（テスト手順書のブラウザ実行など）は探索区分に落としてよい。条件は次の2つを満たすこと:

- 委譲先に**合否の確定と原因分析をさせない**。期待結果と実際に観測した内容を並べて返させ、判定は呼び出し元が付ける
- 観測は要約・言い換えせず、画面の文言・URL などをそのまま転記させる

この条件を満たさない（委譲先が PASS/FAIL を確定する）なら判断区分のまま扱う。

実行環境ごとの割り当て:

| 実行環境 | 探索区分 | 判断区分 |
| --- | --- | --- |
| Claude Code | サブエージェント起動時に `model: sonnet` を指定 | モデルを指定しない（メインを継承） |
| OpenCode | `-m opencode-go/deepseek-v4-flash` を指定 | モデルを指定しない（メインを継承） |
| Agent SDK | 軽量モデル（Sonnet 系）を指定 | メインと同じモデル |
| その他 | 環境で利用できる軽量モデル | 既定モデル |

OpenCode で `opencode/...-free`（OpenCode Zen 無料枠）を委譲先に指定してはいけない。context が 200K に制限され、サブスク契約中でもサブエージェントが無料枠のレート制限で弾かれる既知の不具合がある。

軽量モデルを選べない環境では、区分ラベルを無視して既定モデルで起動してよい。区分ラベルは委譲の要否を変えない。

各スキルは委譲先に **（探索区分）** または **（判断区分）** のラベルだけを付ける。モデル名は書かない。

## 画像を扱う委譲

スクリーンショットやデザインカンプの判定を伴う委譲は、区分に関わらず **vision 対応モデルを明示的に指定する**。メインが text-only モデルで動いている環境では、継承すると画像を読めないまま「問題なし」と返ってくる。

| 実行環境 | 指定するモデル |
| --- | --- |
| Claude Code | 指定しない（メインを継承。Opus / Sonnet はいずれも vision 対応） |
| OpenCode | `-m opencode-go/kimi-k3` を指定 |

委譲先には「画像を読めなかった場合は判定せず、その旨を報告して止まる」ことを明示する。読めていないことに気づかないまま進むのが最悪の失敗。

## 並列実行の原則

- 独立した作業は**必ず並列で**起動する。直列だと遅すぎる。
- 依存関係がある場合のみ順序を守る（依存先を先に完了させる）。

## 委譲時のコンテキスト

- 各委譲先には**独立したコンテキスト**を渡す。前の結果を前提にしない（ゼロベースで実行させる）。
- 委譲先には必ず**プロジェクトルートの CLAUDE.md を最初に読むよう指示する** — コマンド・規約・構成の情報源として。
- 複数の委譲先に同じプロンプトを渡すと似た結論に収束しやすい。視点を分ける場合は視点ごとに明確に指示を変える。

## 中断と完了の区別

委譲先の止まり方は2つあり、扱いが正反対になる。

**中断** — 作業が終わっていないのに委譲先が消えた状態。context / token の上限、レート制限、タイムアウト、API エラー、ユーザーによるスキップ、空の返答。**その作業はまだ誰もやっていない。**

**完了** — 委譲先が作業結果を報告して終わった状態。報告に不足があっても完了は完了で、不足分は追加の委譲で埋める。

判定は「返答があったか」ではなく**中身**で行う。次のいずれかに当てはまれば中断として扱う:

- エラー・空文字・null で返った
- 「context の上限に達した」「これ以上続けられない」旨の申告がある
- 指示した成果物ファイル（レビューファイル・計画ファイル等）が存在しない、または途中で切れている
- 報告自体が作業の途中で切れている（「次に〜する」で終わっている）

迷ったら中断として扱う。完了と誤認して先へ進むほうが被害が大きい。

## 中断時の再委譲

**中断した作業を親エージェントが引き取ってはいけない。** 同じ作業を**委譲し直す**。「1回試したから今度は自分で」「残りは少ないから自分で」は禁止 — 親がオーケストレーションを降りた時点で、以降のフェーズの委譲も一緒に崩れる。

1. **1回目の再委譲** — 同じスコープでもう一度起動する。中断は一過性のことも多い
2. **2回目の再委譲** — **スコープを分割**し、複数の委譲先に分ける。context / token 上限による中断は、スコープが1体に対して大きすぎることが原因なので、同じスコープで投げ直しても同じところで止まる。ステップ単位・ファイル単位・レイヤー単位など、作業が自然に切れるところで割る
3. **3回目も中断したら** — 親は作業せず、そこで止めてユーザーに報告する。「どこまで終わっていて / 何が残っていて / なぜ止まったか」を書き、判断を委ねる

同じ作業を4回以上投げない（無限ループの防止）。再委譲の回数は数えておき、完了報告に残す。

### 再委譲時に渡すもの

再委譲先にとって作業はゼロベースだが、**ワークツリーはゼロベースではない** — 中断した委譲先が途中まで変更を書き込んでいる可能性がある。「委譲時のコンテキスト」のゼロベース原則はここだけ緩め、次を明示する:

- 「前の実行が途中で中断している。まず `git status` / `git diff` で現在の変更を確認し、適用済みの変更はやり直さず残りを進めること」
- スコープを分割した場合は、その委譲先が**担当する範囲だけ**を明示し、範囲外のファイルには触れないよう指示する
- 分割した委譲先を並列で走らせるのは担当ファイルが重ならない場合だけ。重なるなら直列にする

## 一部だけ中断したとき（並列委譲）

独立した観点で複数体を並列起動している場合（レビュー観点・探索の切り口など）、一部が中断しても成功した結果だけで先に進んでよい。ただし**中断した観点は「指摘なし」ではない** — 中断した旨を記録に残し、その観点が担保されていないことを完了報告に明記する。

これは観点が独立に価値を持つ場合の話。**単一の必須作業を分担して並列化した場合（実装ステップの分担・修正の分担）には適用しない** — 一部が欠けると成果物が壊れるので、中断した分は必ず再委譲する。
