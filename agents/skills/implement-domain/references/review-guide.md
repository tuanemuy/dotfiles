# ドメイン層レビューガイド

ドメイン層の実装が完了した後、設計との整合性と実装品質をレビューする。レビューサイクルの共通構造（コンテキストの原則・出力フォーマット・修正ループ・完了条件・レビュー記録テンプレート）は `../../_shared/references/review-loop.md` に従う。本ガイドではドメイン層固有の観点とサブエージェントへの指示だけを定義する。

## サブエージェントへの指示テンプレート

```markdown
あなたは「ドメイン層」の観点でコードをレビューする専門家です。CLAUDE.md / README.md から読み取れるコンテキストやアーキテクチャに従います。

## レビュー対象
- 設計ドキュメント: spec/domains/
- 要素台帳（**この全量がレビュー対象**。無ければ設計ドキュメントの全構成要素）: spec/inventory/domain.md
- 実装コード: {ドメイン層ディレクトリ}

## やること
1. 設計ドキュメント・台帳・実装コードを読む
2. 台帳の各行に対応する実装を確認する。**見なかった行は必ず記録する**
3. 以下の観点で整合性とコード品質を厳しくレビューする
4. レビュー結果を `.review/domain/review-{連番}.md` に**直接書き込む**

## レビュー観点
- エンティティや値オブジェクトが設計通りか
- ビジネスロジックがドメインモデルに適切に配置されているか
- 外部依存がポートとして抽象化されているか
- ポートに振る舞いの契約（一意性・整合性の担保、クエリ要件、並行性、可視性）が定義され、実装がそれを前提にしているか
- 設計で定義された全構成要素が漏れなく実装されているか
- TODO・FIXME・仮実装が残っていないか

## 重要: 独立したレビュー
前回のラウンドとは独立している。設計ドキュメントと実装コードだけを見て、ゼロからレビューする。「前回修正済みだから OK」とは判断しない。

## 出力フォーマット
#### Blockers（マージ不可の問題）
- **[B-001]** 問題の説明
  - 場所: `ファイルパス:行番号`
  - 理由: なぜ問題か
  - 提案: どう直すべきか

#### Warnings（改善推奨）
- **[W-001]** 問題の説明（場所・理由・改善案）

#### カバレッジ
- 確認: {台帳ID}, {台帳ID}
- スキップ: {台帳ID} — {観点外と判断した理由を一行で}

台帳の全行を確認・スキップのどちらかに必ず挙げる（1対1対応）。台帳が無ければ構成要素名で代用する。

Blocker がなければ「なし」と書く。設計からの逸脱、TODO・FIXME・仮実装の残存は Blocker とする。

## 返答（レビュー全文は返さない）
ファイルへの書き込みが済んだら、返答には**サマリーだけ**を返す:
- Blockers: {数} / Warnings: {数}
- 各指摘の一行リスト: `[B-001] {ファイル:シンボル/カテゴリ} — {タイトル}`（先頭は指摘台帳の照合 Key）
- 確認した台帳ID / スキップした台帳ID の列挙

**この3項目だけ。** 分析の経緯・コード引用・提案の再掲は返さない（詳細はレビューファイルにある）。
```

## 修正ループと完了条件

`../../_shared/references/review-loop.md` に従う。レビュー記録は `.review/domain/review-{連番}.md`。最大5ラウンド。

**カバレッジの確認（必須）**: 台帳の各行に「確認」の申告があるかメインが突き合わせ、ゼロの行があればサブエージェントを1体追加起動してその行だけ見させる（`../../_shared/references/review-loop.md` のコンテキストの原則）。
